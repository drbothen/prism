# Technical Architecture And Security Deep-Dive On The Query Security Data Mesh Platform

The Query security data mesh platform, delivered by Query.AI, is positioned as a cloud-native federated search and data access layer for security telemetry that allows analysts to query disparate sources without centralizing or ingesting the underlying data.[1][7][11] Public documentation describes a multi-tenant SaaS model organized around organizations, tenants, and teams, with a web console that provides federated search, schema normalization to an OCSF-based data model, and connector-driven integration to a wide range of security-relevant systems such as SIEMs, data lakes, endpoint detection tools, identity providers, and cloud observability platforms.[1][3][10][11] At the same time, Query’s materials are deliberately high-level on internal implementation details such as credential storage, cryptographic key hierarchy, and deployment topology, so any deep technical analysis must clearly separate what is explicitly documented from what is inferred from general industry practice. This report therefore proceeds in two parallel tracks: first, synthesizing everything that can be reliably learned from Query’s product pages, documentation, and blog posts about their deployment topology, architecture, UI, configuration model, and organization-level authorization; and second, outlining best-practice patterns for secure credential management and multi-tenant web application security in federated query platforms that a security architect should expect from a system like Query, even where the vendor has not publicly confirmed implementation choices.[1][3][6][7][10][11][15]  

## Overview Of Query’s Security Data Mesh Platform

### Federated Search And The Security Data Mesh Concept

Query describes itself as a “security data mesh platform” that allows organizations to put their existing security data “to work” without moving or ingesting it into a central repository.[1][10][11] The core value proposition is the ability to perform federated search and investigations across multiple security data sources—endpoint detection and response (EDR), identity platforms, email security solutions, threat intelligence feeds, SIEMs, data lakes, and other telemetry systems—through a single console and API.[1][3][10][11] Instead of building and maintaining pipelines to transport logs and events into a monolithic SIEM or data lake, Query emphasizes “no ingestion” and “no pipelines,” stating that data remains in its source systems and is accessed on demand via connectors and a platform-agnostic query layer.[1][10][11] This architecture is presented as a way to avoid the “centralization tax” often associated with security data platforms, namely the engineering overhead of ETL, schema mapping, and pipeline maintenance, while continuing to leverage existing tooling investments.[10]  

To make federated search operational, Query functions as what it calls an “API bridge” between analysts and their distributed data sources.[11] From the analyst’s perspective, the system exposes a unified search experience—either using a proprietary Federated Search Query Language (FSQL) or natural language—which is translated by the platform into native queries for each underlying source, executed in parallel, and then normalized back into a common data model.[1][11] This design provides a level of abstraction where security staff no longer need detailed knowledge of each source’s query language or schema; instead, they interact with a unified interface and rely on Query’s connectors and normalization layer to handle the heterogeneity of the environment.[1][3][11]  

The “security data mesh” framing situates Query in a broader architectural trend in which data is treated as a distributed resource governed by local ownership but made globally accessible via standardized interfaces and semantics. In such meshes, each domain (for example, endpoint telemetry or identity data) retains control of its data store, while mesh services provide discovery, normalization, and query capabilities that span domains.[1][10][11] Query emphasizes that its mesh adapts to the customer’s stack rather than forcing customers to adapt their data to a centralized schema, highlighting features such as dynamic connector mappings and in-flight schema normalization as key elements of that mesh architecture.[1][3][6][11]  

### Query Data Model And OCSF-Based Normalization

A central pillar of Query’s architecture is the Query Data Model, which is explicitly described as being built on the Open Cybersecurity Schema Framework (OCSF).[1][6] OCSF is an industry-standard schema initiative that defines common event classes and attributes for security telemetry, making it easier to integrate and analyze data from multiple vendors and tools. Query states that all connected sources are mapped to this model, providing “one set of field names across every connected source” such that a detection rule or investigation query can be written once and executed everywhere.[1]  

The Query Data Model therefore serves as the semantic foundation for the federated search functionality. When the platform receives a query, it maps that query onto OCSF-aligned fields such as principal identifiers, resource identifiers, event classifications, and time attributes, regardless of how those concepts are represented in the underlying source systems.[1][6] For static-schema tools—those with fixed APIs and event structures—Query maintains pre-defined mappings from the vendor’s schema to OCSF, which allows the platform to return normalized results without requiring per-customer configuration in most cases.[1][3] For dynamic-schema sources such as SIEMs, data lakes, or log management platforms, Query uses a schema introspection and mapping process, aided by its Configure Schema and CoPilot features, to align arbitrary datasets to the Query Data Model.[3][6][11]  

Once results are normalized, the platform is able to support cross-source analytics and detections written at the OCSF level. Documentation explicitly highlights the ability to “write a detection once, run it everywhere” as a key outcome of using the common data model.[1] This approach has important implications for multi-tenant deployments: it suggests that Query maintains per-tenant mappings from each data source to the OCSF-based model, but the detection logic itself may be reusable across tenants as long as field names and semantics are preserved. It also implies that any storage of query results or saved searches will reference OCSF schema elements rather than vendor-specific fields, which can simplify governance and reduce the risk of schema drift in longer-lived detection rules.[1][6][11]  

### FSQL And Natural-Language Query Interface

On the query-language side, Query introduces FSQL, the Federated Search Query Language, as a platform-agnostic syntax that is translated into each source’s native language at query time.[1] FSQL appears to be a domain-specific language tailored to security investigations, with semantics designed to run across multiple normalized sources while still allowing the platform’s mesh to emit valid queries for systems such as SIEMs, databases, and cloud log providers.[1][11] Documentation notes that the mesh translates FSQL into native syntax for each source, executes those queries in parallel, and returns OCSF-normalized results, implying that FSQL is anchored in the Query Data Model fields.[1]  

In addition to FSQL, Query’s federated search pages mention natural-language input, stating that users can “start typing using natural language to instantly search across all of your connected integrations.”[11] This suggests that the browser-based console includes an AI-assisted query entry component that can translate free-form investigative questions into FSQL or directly into native source queries, similar to patterns described in broader AI deployment literature where large language models are used to convert natural language into structured queries.[2][8][11] The platform’s emphasis on being “the data foundation AI requires” further reinforces the idea that FSQL and OCSF normalization are designed not only for human-written detections, but also to support AI-driven copilots and agents that need consistent, machine-readable semantics.[1]  

It is also noteworthy that Query provides guidance for AI agents via an index of documentation and OpenAPI endpoints specifically formatted for large language models, accessible at a dedicated path indicated in the docs portal.[9] This indicates that their API and data model are exposed in machine-consumable ways for agentic systems, and reinforces the importance of a consistent query language and schema for both human and AI consumers.[1][9][11]  

### Connectors As Integration Control Plane

Connectors are described as the integration control plane between Query and the distributed sources that house security-relevant data.[3][11] They are characterized as a critical component enabling a security data mesh architecture, and are divided into static connectors for tools with fixed schemas and dynamic connectors for platforms with custom or evolving schemas.[3][11] Static connectors provide “instant access to key data pre-mapped to the Query Data Model,” which means that once a user configures credentials and connectivity, events from those tools can be queried using FSQL and OCSF fields without additional schema work.[1][3]  

Dynamic connectors, by contrast, are designed to work with SIEM indices, data lakes, cloud buckets, and analytics platforms whose schemas differ per customer, such as Splunk, Snowflake, Google BigQuery, Amazon S3, Databricks, and similar systems.[1][3][11] For these sources, Query performs schema introspection and allows customers to configure their own mappings through the Configure Schema feature, now enhanced with the Query CoPilot AI assistant.[3][6] This process automatically discovers partitions and schema elements, then suggests event classes and attribute mappings to OCSF, reducing manual effort and requiring less detailed knowledge of each data source’s internal structure.[6]  

Connectors are also described as being “pre-built API integrations” that deliver normalized, ready-to-use data from SIEMs, data lakes, endpoint, network, and identity tools without engineering overhead.[3][11] This characterization supports the view that Query primarily interacts with these systems via their published APIs rather than via agents that ingest logs or replicate data. From an architecture standpoint, connectors likely encapsulate connection parameters, credential secrets, mapping definitions, and any required polling or query logic, and they execute queries “in-flight” when investigations are run, returning normalized results to the console.[1][3][11]  

## Deployment Topology And Product Architecture

### Cloud-Native, Multi-Tenant SaaS Orientation

Query’s product architecture documentation describes the platform as a “modern, cloud-native web application” that searches across disparate security data sources without incurring the cost of moving that data into a centralized store.[7] The overall user journey reinforces a SaaS orientation: a prospective user is instructed to create an account and an organization, connect integrations using access credentials such as URLs, API keys, or auth tokens, and then perform their first federated query—all within roughly thirty minutes.[11] The presence of concepts like “Organization,” “tenant,” and “team” in the Team Management documentation further indicates a multi-tenant SaaS model in which each customer’s environment is represented as a logical tenant with associated teams and user roles.[11][15]  

When a team administrator signs up, Query generates a tenant and a team name, which can later be renamed through the console.[15] Users are managed at the organizational level, with roles of Team Admin and Team Member determining what operations they can perform in the system.[15] Team Admins can invite team members, establish new connection sources, and perform edit and delete actions on connection sources and team members, while Team Members can perform searches and save searches.[15] This organizational and role structure is characteristic of a SaaS platform that hosts multiple independent customer environments within a shared infrastructure, using tenant identifiers and access control policies to ensure isolation of configuration and data for each organization.[8][11][15]  

From the statements about the platform being “one console” for “every source” and about eliminating centralization tax through schema normalization at query time, it is reasonable to infer that Query operates primarily as a centralized cloud service where the core web application, query translation engine, normalization logic, and connector orchestration run in Query-managed cloud infrastructure.[1][7][10][11] Each customer’s tenant configuration includes registered integrations, their credentials and schemas, and saved searches or detections, but the underlying application runtime is shared across tenants with appropriate isolation controls. Such a topology aligns with broader SaaS practices for AI and ML workloads, where model hosting, inference scaling, and tenant-specific tuning are handled centrally, while tenant context and authorization information flows into the system via JWTs or similar tokens.[2][8][11]  

### On-Premises Edge And Connector Runtime Considerations

Public Query documentation, as represented in the search results, does not explicitly describe an on-premises “edge” component or connector runtime that must be installed inside the customer’s network.[1][3][7][10][11] Instead, connectors are portrayed as pre-built API integrations that integrate with tools and platforms such as SIEMs, data lakes, and cloud log services, and Query’s messaging emphasizes the lack of any data ingestion, ETL, or pipeline construction within customer environments.[1][3][10][11] This suggests that many supported sources are cloud-hosted services or APIs reachable from Query’s cloud environment via secure network connections, rather than on-premises systems behind strong network controls that would require a local agent to bridge connectivity.  

In cases where Query integrates with on-premises systems—such as self-hosted Splunk instances, private data lakes, or log platforms within a corporate network—the documentation focuses on schema introspection and connector configuration, but does not detail transport-level arrangements such as VPNs, private links, or reverse proxies.[1][3][11] Given the lack of explicit guidance, security architects should assume that Query requires network routes from its SaaS environment to the relevant APIs, which may be implemented via customer-managed exposure of APIs (for example, through reverse proxies with IP allowlists) or through private networking arrangements negotiated with Query’s operations team. Any on-premises runtime, if offered, would need to be explicitly documented with installation and “phone home” behavior; no such component appears in the materials provided.[1][3][7][10][11]  

It is important to distinguish between the concept of a “connector” in Query’s terminology and the traditional notion of an on-premises agent. Query’s connectors are described as integration control-plane objects in the SaaS platform, with static connectors for fixed-schema tools and dynamic connectors for custom schemas.[3][11] The documentation does not mention customers installing binaries or containers in their own environment to act as connectors; instead, connectors seem to be logical objects configured with API credentials and mapping definitions, and executed by Query’s infrastructure when queries are run.[1][3][6][11] Without vendor documentation to the contrary, one should treat Query as an API-driven SaaS platform that connects directly to reachable endpoints rather than using a persistent edge runtime in the customer’s network.  

### Tenant Context And Isolation Across Shared Infrastructure

In multi-tenant SaaS architectures, a central challenge is ensuring strict isolation of tenant data and configurations while leveraging shared application infrastructure for scalability and efficiency.[8] While Query’s documentation does not delve into the internal mechanics of tenant isolation—for example, whether it uses separate databases per tenant or row-level access control within a shared database—the presence of tenant and team constructs suggests that tenant context is carried through the application and used to scope all operations.[11][15] For instance, when a Team Admin invites users, those users are added to the team associated with that tenant, and the connectors, saved searches, and permissions they can access are bounded by that organizational scope.[11][15]  

AWS’s guidance on SaaS environments for generative AI underscores the importance of propagating tenant context via JWTs or similar tokens, and using that context both to route requests to appropriate resources and to enforce isolation at the data layer.[8] In Query’s case, tenant context would likely be associated with a unique tenant identifier and used to partition the configuration data for connectors, schema mappings, and saved searches; it may also be used in the query engine to select which connectors are eligible to run for a given request and to restrict which results are returned to users.[1][3][11][15] Multi-tenant generative AI scenarios also highlight challenges when tenant data is co-mingled in shared resources, such as indices or knowledge bases, and recommend careful design of isolation controls—often via IAM policies or application-level filters—to avoid cross-tenant leakage.[8] Query’s heavy reliance on connector definitions and OCSF mappings provides a natural boundary: connectors, mappings, and resulting normalized data can be kept tenant-specific even if the code and infrastructure are shared.  

### Relationship To AI Model Deployment Patterns

Although Query’s primary focus is federated security data access, it explicitly positions itself as “the data foundation AI requires” and introduces AI-powered features such as Query CoPilot for schema mapping.[1][6] In broader AI model deployment literature, such as the TrueFoundry overview, there is a distinction between training and serving phases, with deployed models exposed via APIs for real-world use.[2] Query’s AI integration appears to be oriented around the serving and augmentation context: AI models are used to propose schema mappings, support natural-language search, and assist investigative workflows, leveraging the normalized OCSF data as input.[1][2][6][11]

If Query extends its CoPilot concept beyond schema mapping—for example, into investigative assistants—it will need to adopt identity and authorization patterns similar to those recommended by FusionAuth and Curity, such as propagating user identity through agent workflows and ensuring that AI agents only access documents and data chunks that pass deterministic authorization checks.[5][12]  

## Connector Architecture, Schema Mapping, And Credential Handling

### Static Versus Dynamic Connectors

Query divides connectors into static and dynamic types, based on the nature of the underlying data source’s schema.[3][11] Static connectors are used for tools with fixed schemas, such as commercial EDR platforms, identity providers, email security solutions, and threat intelligence services. For these integrations, Query maintains pre-mapped relationships between the source’s fields and the Query Data Model, enabling nearly “instant access” to key data once connectivity and credentials are configured.[1][3] Static connectors therefore minimize per-customer schema work, and allow for quick onboarding of common security tools such as CrowdStrike, Okta, Microsoft Entra ID, Defender, SentinelOne, Auth0, VirusTotal, Jamf, ServiceNow, and others listed in the product materials.[1][3]  

Dynamic connectors, by contrast, are designed for platforms and services with custom schemas, where each customer’s data layout may differ substantially.[3][11] These include SIEMs, cloud buckets, and analytics platforms such as Amazon S3, Splunk, Snowflake, BigQuery, Google SecOps, Azure Sentinel, Databricks, ClickHouse, and Amazon CloudWatch.[1][3][11] For dynamic connectors, Query uses schema introspection to discover field structures and partitions, then allows customers to configure mappings via the Configure Schema feature.[3][6] This process can be interactive, using a no-code wizard for mapping dynamic schema sources to the Query Data Model, and is now augmented by Query CoPilot, which analyzes data and recommends event classes and attribute mappings based on identified patterns and security context.[6]  

The existence of static and dynamic connectors implies that the connector abstraction in Query carries several responsibilities beyond mere connectivity. For static connectors, it encapsulates vendor-specific query logic, field mappings, and any necessary pagination or rate limiting; for dynamic connectors, it supports schema exploration, mapping configuration, and potentially transformation logic to align custom datasets with OCSF.[1][3][6][11] In both cases, connectors also need to manage credentials and connection parameters, and must be associated with a specific tenant and team for authorization and isolation purposes.[3][11][15]  

### Configure Schema And Query CoPilot For Mapping Dynamic Data

Configure Schema is a feature within Query that provides a no-code wizard for mapping data from dynamic schema sources—data lakes, warehouses, SIEMs, and log management platforms—to the Query Data Model.[6][11] It allows engineers and architects to iteratively map tables, indices, or log streams to OCSF event classes and attributes, without requiring them to write code or deeply understand the internal schemas of each source.[6] The recent introduction of Query CoPilot for Configure Schema enhances this process by using AI to automatically analyze sample data and recommend event classes and field mappings.[6]  

CoPilot’s recommendations are based on patterns identified within the data and its security context, such as recognizing common fields for user identities, IP addresses, timestamps, and event categories that match OCSF definitions.[6] This AI-driven capability is intended to reduce complexity and the time required to integrate new data sources, while improving the accuracy and consistency of mappings across all data sources.[6] The user interface for CoPilot is described as intuitive and step-by-step, guiding engineers and architects through iterative mapping while lowering the need for intimate knowledge of individual data sources.[6]  

From a configuration management perspective, Configure Schema and CoPilot suggest that Query maintains structured mapping configurations per dynamic connector, which are stored and applied at query time to transform native source data into OCSF-normalized results.[3][6][11] These mappings likely include declarations of event classes, attribute-to-field relationships, and any transformations or type conversions required, and they are associated with specific connectors and tenants. The existence of a wizard and AI assistant implies that Query stores mapping versions and may support updates over time as schemas evolve, though the documentation does not explicitly describe versioning mechanisms.[6][11]  

### Credential Provisioning For Connectors

While Query’s documentation is detailed about the functional behavior of connectors, it provides only limited explicit information on how connector credentials and secrets are handled. In the “Get started” flow for federated search, Query instructs users to connect integrations by providing access credentials such as URLs, API keys, or authentication tokens.[11] These credentials are necessary for the platform to call SIEM APIs, data lake endpoints, EDR platform APIs, and other services when running federated queries.[1][3][11] Connectors are described as integration control-plane objects that manage these relationships, and the Team Management documentation notes that Team Admins can “add new connection sources” and perform edit and delete actions on connection sources.[3][11][15]  

However, the documentation does not specify whether connector credentials are stored client-side (for example, in a customer-managed secrets manager with Query only holding references) or server-side within Query’s cloud infrastructure.[1][3][7][10][11] Nor does it state which secret storage technology is used, such as AWS Secrets Manager, HashiCorp Vault, or a custom encrypted store, or whether Query employs key management systems (KMS) for envelope encryption and per-tenant data encryption keys. Given that connectors are configured via the SaaS console and must be available for Query’s cloud infrastructure to execute queries, it is reasonable to infer that credentials are stored server-side in Query’s platform, with appropriate encryption at rest and access controls; but this remains an inference, not an explicitly documented fact.[1][3][11][15]  

From a security architecture perspective, connectors must hold enough information to authenticate to each source on behalf of the tenant, which may include long-lived API keys, OAuth client credentials, or service accounts. Best practice in multi-tenant SaaS systems is to minimize the storage and scope of such secrets—for example, by using short-lived access tokens derived from refresh tokens or client credentials, and by limiting the privileges of these credentials to read-only querying of specific datasets.[5][8] Query’s emphasis on “no ingestion” and “no pipelines” suggests that connectors are primarily used to execute read-oriented queries on demand rather than to perform continuous ingestion or write operations, which reduces the risk surface associated with stored credentials; however, the platform will still need to implement secure secret storage mechanisms to protect these keys from compromise.[1][3][10][11]  

### Data Residency And Minimization Of Data Movement

A recurring theme in Query’s messaging is that data “stays at its source,” with no ingestion into a central platform and no DDL risk.[1][10][11] This design has direct implications for both deployment topology and credential management. By avoiding data movement, Query reduces the need to store large volumes of customer data in its infrastructure, instead acting as a transient query and normalization layer that retrieves data from sources, normalizes it to OCSF, and presents it to analysts for investigations.[1][7][10][11]  

From a residency perspective, this means that the bulk of customer security telemetry remains in systems such as SIEMs, data lakes, and EDR platforms, which may have their own residency guarantees and compliance certifications.[1][3][11] Query’s role is to access these systems via APIs using configured credentials, perform federated queries, and expose results via its web console and APIs, potentially caching or storing limited subsets of data such as query results or saved searches. The reduction in data movement decreases the compliance burden on Query with respect to long-term storage and retention of sensitive logs, but it heightens the importance of secure credential handling and transport security, because compromise of connector credentials could allow an attacker to query and access sensitive data residing in customer systems.[1][3][10][11]  

The data mesh approach also means that Query’s architecture must accommodate heterogeneous residency and network topologies: some sources may be cloud-native services in the same region as Query’s infrastructure, while others may be on-premises systems accessible only via specific network routes. In all cases, secure connector credential management and robust authorization controls are essential to ensuring that federated queries do not inadvertently breach data residency policies or access controls enforced by the underlying systems.[1][3][7][10][11]

## Authentication, Authorization, And Tenant Isolation

### Team Management, Roles, And Permissions

Query’s Team Management documentation provides the clearest window into its authentication and authorization model at the user and team level.[15] User management is organized at the organizational level, with each organization corresponding to a tenant and containing one or more teams. When a team administrator signs up, Query generates a tenant and a team name, both of which can later be renamed via the console.[15] Users are assigned either a Team Admin or Team Member role to access Query, with these roles determining the operations they can perform.[15]  

Team Admins can invite team members to join their team, add new connection sources, and perform edit and delete actions on connection sources and team members.[15] Team Members, by contrast, are limited to performing searches and saving searches.[15] This simple role model aligns with the principle of least privilege, ensuring that only designated administrators can configure integrations and manage user access, while standard analysts can use the platform for federated search without the ability to alter sensitive configuration settings. The distinction also reflects a separation between operational duties (investigation and analysis) and administrative duties (connector management and user provisioning).  

The process for inviting users involves navigating to a user profile menu, selecting settings and organization, and then using an “Invite” action to add team members.[15] When users are invited, they are associated with the team in that tenant, and their assigned role controls their capabilities. Although the documentation does not explicitly describe password policies or authentication methods, the presence of an invitation flow indicates that Query maintains a user directory per organization, with accounts linked to email identities and roles.[11][15]  

### Authentication Mechanisms And SSO/SAML/OIDC Considerations

The search results provided do not include explicit documentation on Query’s supported authentication mechanisms, such as whether it supports Single Sign-On (SSO) via SAML, OpenID Connect (OIDC), or OAuth-based integrations with corporate identity providers.[1][7][10][11][15] However, in the broader ecosystem of AI-powered SaaS platforms and agentic systems, identity management patterns are increasingly standardized around OIDC flows and token exchange mechanisms.[5][12]  

Curity’s guidance on SSO for AI agents, for example, highlights two aspects: SSO when the user logs in to an AI agent, and SSO when the AI agent performs tasks on behalf of the user on downstream systems.[12] The core asset in OIDC-based SSO is the ID token, which conveys user data and is used in token exchange flows to obtain new credentials that preserve user identity across trust domains.[12] In a platform like Query, which might integrate with corporate identity providers and downstream systems via AI or automation, similar patterns would be necessary to ensure that user identity is consistently propagated and that actions taken by agents or automated workflows can be traced back to the originating human.[5][12]  

FusionAuth’s discussion of AI authentication and authorization emphasizes that authorization must be deterministic even when AI systems are probabilistic, particularly in retrieval-augmented generation (RAG) scenarios where documents must be filtered based on user permissions before being passed to an LLM.[5] While Query’s core functionality is federated search rather than RAG, its AI-powered features and potential use in agentic workflows mean that any integration with AI services should adopt a similarly strict identity and authorization layer, using JWTs or other tokens to represent user identity, and applying fine-grained authorization (FGA) checks before granting access to data.[5]  

Given the lack of explicit Query documentation in this area, security architects should assume that the platform uses a standard username/password or email-based login by default, and should inquire about SSO capabilities and OIDC support when deploying Query in enterprise environments. Integration with corporate identity providers via SAML or OIDC would be expected for large organizations and is consistent with best practices for multi-tenant SaaS platforms that handle sensitive security data.  

### Role-Based And Fine-Grained Authorization

Beyond the basic Team Admin and Team Member roles described in Query’s documentation, modern AI and security platforms often require more granular role-based access control (RBAC) and fine-grained authorization to properly govern access to agents, datastores, and administrative features.[13] Contextual AI’s RBAC documentation, for instance, describes a system where permissions can be scoped to specific agents or datastores, enabling finer-grained governance so each team member has the right level of access for their role.[13] Administrators can define custom roles with tailored permission bundles across key objects, and permissions can be scoped to agents, datastores, or admin tools, with user membership in roles and groups determining their effective permissions.[13]  

Query’s current public documentation describes only two roles and focuses on organizational-level administration and connector management.[15] It does not mention agent-level permissions, datastore-specific access controls, or custom roles. However, as Query increasingly supports AI agents and integrates with a variety of sensitive data sources, it may evolve toward more sophisticated RBAC models similar to those used by other AI platforms, allowing administrators to restrict which connectors, datasets, or detections each user can access.[9][13] Such capabilities would be important in large organizations where different teams handle different subsets of data and where certain connectors may expose highly sensitive logs that should be available only to specific roles.  

Fine-grained authorization systems, such as FusionAuth FGA by Permify, enable deterministic authorization decisions that can be deployed on-site for data safety and scale with needs.[5] In AI contexts, FGA can be used to enforce access policies before documents or data chunks are retrieved for RAG systems, ensuring that models never see documents the user should not access.[5] While Query’s documentation does not mention FGA explicitly, similar principles should be applied to federated search: connectors and datasets should be tagged with access control attributes, and user roles should be mapped to those attributes so that only authorized users can query sensitive sources.  

### Chain Of Identity For AI Agents And Automated Workflows

The concept of a “chain of identity” is critical in agentic AI systems, where agents perform tasks on behalf of users and may interact with multiple downstream services.[5] FusionAuth’s guidance stresses that when a human kicks off an agent workflow, the human’s identity must travel with the agent through every step.[5] If an agent reads a file, schedules a meeting, or accesses an API, the system must record on whose behalf those actions were taken, and maintain an audit trail back to the originator.[5]  

In a platform like Query, which may use AI agents to perform federated searches, propose detections, or retrieve data from multiple sources, preserving the chain of identity means associating user identity (for example, via a JWT) with each connector invocation and recording these associations in audit logs.[5][9] When the agent queries a SIEM or data lake via a connector, the audit log should note that the query was initiated by a particular user or role, and any downstream actions—such as saving a search or exporting results—should also carry that identity context. Curity’s description of token exchange flows for AI agents, using Identity Assertion JWT Authorization Grants (ID-JAG), provides one mechanism for maintaining user identity across different trust domains, allowing an AI agent to act on behalf of a user at services in another trust domain while preserving the user’s identity.[12]  

Although Query’s documentation does not explicitly discuss agent workflows or chain-of-identity concepts, its emphasis on being a data foundation for AI and its provision of AI-specific documentation endpoints suggest that as the platform evolves, it will need to adopt similar patterns for identity propagation and auditability.[1][6][9] Security architects evaluating Query should inquire whether its audit logs capture user identity for connector invocations and whether AI-driven features preserve identity relationships throughout their operations.

## Best-Practice Patterns For Server-Side Credential Storage In Multi-Tenant Federated Query Platforms

### Threat Model For Connector Credentials

In a federated query platform like Query, connectors and associated credentials represent a critical attack surface. If an attacker compromises the platform’s credential store or gains unauthorized access to connector configuration, they may be able to query sensitive security data residing in SIEMs, data lakes, EDR systems, identity providers, and other telemetry sources. The threat model therefore includes both external attackers who target the SaaS platform and insiders who may misuse their privileges, as well as supply-chain risks if the credential storage subsystem or its dependencies are exploited.  

Because Query emphasizes that it does not ingest data and instead accesses data where it lives, the compromise of connector credentials can have far-reaching consequences. These credentials may allow queries across extensive log histories and sensitive events, including authentication logs, endpoint activity, cloud access logs, and identity information. Consequently, secure credential storage, strict access control, and robust auditing are essential to protecting customer data in such a platform.  

### Envelope Encryption And KMS-Based Key Hierarchies

A widely recommended best practice for server-side credential storage in multi-tenant SaaS environments is the use of envelope encryption with a cloud-based Key Management Service (KMS). In envelope encryption, each secret or group of secrets is encrypted with a data encryption key (DEK), and the DEK itself is encrypted with a master key managed by KMS. This approach limits the exposure of root keys, allows central management of key rotation policies, and enables fine-grained control over who can decrypt specific DEKs.  

In a federated query platform, each connector’s credentials should ideally be stored as encrypted blobs in a secure database, with DEKs derived from or associated with tenant-specific key material. Per-tenant DEKs ensure that even if an attacker compromises one tenant’s DEK, they cannot decrypt credentials associated with other tenants. KMS master keys can be configured with usage policies that restrict decryption operations to specific services and contexts, such as the connector runtime executing within the platform’s secure environment.  

Envelope encryption also supports key rotation without requiring re-encryption of all secrets with new master keys. DEKs can remain constant while master keys are rotated, or DEKs can be periodically re-encrypted with new master keys, depending on the organization’s security policies. In a platform like Query, where connectors may be long-lived and used by many queries over time, KMS-backed envelope encryption provides a scalable and secure foundation for managing connector credentials.  

### Per-Tenant Data Encryption Keys And Secret Segregation

Per-tenant data encryption keys are an important technique for segregating secrets and configuration data between tenants in a multi-tenant platform. Instead of using a single DEK for all stored secrets, the platform generates and manages separate DEKs for each tenant (or even for each connector), which are themselves encrypted under KMS master keys. This ensures that compromise of one tenant’s DEK does not expose other tenants’ secrets, and reinforces the isolation model at the cryptographic level.  

In Query’s context, per-tenant DEKs would mean that connector credentials and other sensitive configuration items belonging to a specific organization are encrypted with keys tied to that organization’s identity. Combined with application-level authorization checks, this ensures that even if a bug or misconfiguration allows cross-tenant access to credential records, the cryptographic barrier prevents decryption unless the correct tenant keys are used.  

Segregation can also extend to storage-level partitioning, where credential records for different tenants are stored in separate tables, schemas, or even databases. While not strictly required if cryptographic and application-level controls are strong, such partitioning can provide additional defense-in-depth and simplify migration or backup operations.  

### Secret Broker And Short-Lived Credential Vending

Another best practice is to minimize the lifetime and scope of stored secrets by using a secret broker or credential vending mechanism. Instead of storing long-lived API keys or passwords, the platform can store higher-level credentials such as OAuth client credentials or refresh tokens, and use them to obtain short-lived access tokens from downstream systems. These access tokens are then used for query execution and can be configured with limited scope, such as read-only privileges or access to specific datasets.  

This pattern is analogous to the flows described by FusionAuth for AI systems, where the chain of identity is preserved by associating user identity with tokens used to access documents.[5] In a federated query platform, the secret broker can use stored client credentials to obtain short-lived access tokens for connectors, associating those tokens with tenant and user identity for audit purposes. Downstream systems should be configured to accept only these short-lived tokens and to enforce scopes that restrict what operations can be performed.  

Short-lived tokens drastically reduce the window of opportunity for attackers: even if a token is compromised, its validity period is limited, and it may be bound to specific IP ranges or device identifiers. By contrast, long-lived API keys or passwords, if compromised, can be used indefinitely until rotated. A platform like Query should prefer OAuth-based integrations where possible, using token refresh mechanisms and secret brokers to manage access tokens on behalf of tenants.  

### Credential Rotation, Monitoring, And Incident Response

Secure credential management also requires robust rotation, monitoring, and incident response practices. Tenants should be able to rotate connector credentials periodically or on demand—such as when an employee leaves the organization or when an incident suggests possible credential compromise. The platform should support updating credentials for connectors via both the console and APIs, and should enforce policies that encourage regular rotation.  

Monitoring is essential to detect anomalies in credential usage. The platform should log all connector invocations, including which credentials were used, which tenant and user initiated the operation, and which downstream systems were accessed. These logs should be analyzed for unusual patterns, such as access from unexpected IP ranges, unusual query volumes, or attempts to access datasets outside the expected scope.  

Incident response procedures should include mechanisms for revoking or disabling specific connectors, invalidating tokens, and temporarily suspending access for affected tenants while investigations are conducted. In multi-tenant environments, it is crucial to ensure that incident containment actions are scoped appropriately, avoiding unnecessary disruption to unaffected tenants while providing rapid mitigation for the affected environment.  

### Storage And Access Controls For Secrets

Beyond cryptography and rotation, effective secret management requires strict access control and operational hygiene. Access to the secret store should be limited to specific services and processes that need to decrypt credentials for connector operations; other services, such as front-end components or logging subsystems, should not have access to decrypted secrets. Role-based access control within the platform’s infrastructure should ensure that only a minimal number of operational staff can access secret management systems, and that such access is governed by strong authentication and approval workflows.  

Secrets should never be exposed in logs, error messages, or diagnostic outputs. The platform should scrub any sensitive fields from logs and ensure that debugging tools do not inadvertently capture secrets. Backup and disaster recovery processes should encrypt secrets at rest and in transit, and test procedures should avoid using production credentials.  

In multi-tenant SaaS platforms, secret access patterns should also be carefully monitored and audited. Any attempts to access secrets outside the expected context—for example, attempts by one tenant’s processes to access another tenant’s secrets—should be logged and flagged. Internal security reviews and penetration testing should include tests for secret handling, verifying that there are no paths by which secrets can be exfiltrated or misused.  

## Best-Practice Patterns For Multi-Tenant Web-UI Security In Federated Query Platforms

### Tenant Context Propagation And Isolation

As AWS’s guidance on SaaS and generative AI emphasizes, proper handling of tenant context is fundamental to multi-tenant web applications.[8] Tenant context, often encoded in JWTs or similar tokens, must flow from the front-end to the back-end and through all downstream services, ensuring that each request is associated with the correct tenant and that data access is scoped appropriately.[8] In Query’s case, tenant context would be represented by organizational and team identifiers, with connectors and schema mappings associated with specific tenants.[11][15]  

The web UI should use secure token storage mechanisms, such as HTTP-only cookies or browser storage with appropriate safeguards, to store authentication tokens that carry tenant and user claims. These tokens should be validated on each API call, and authorization checks should enforce that users can only access connectors, mappings, detections, and results that belong to their tenant and that align with their role. For example, a Team Member should not be allowed to modify connectors or view configuration details, while a Team Admin should have such permissions within their tenant but not across other tenants.[15]  

Isolation also extends to UI state and rendering. The front-end should never display data from multiple tenants in the same context, and should avoid any client-side logic that could infer cross-tenant information. For example, UI elements that list connectors or teams should be populated only with data scoped to the current tenant, and client-side caching should be designed to prevent leakage if users switch between accounts or roles.  

### Authentication, Session Management, And SSO Integration

Secure authentication is the foundation of multi-tenant web UI security. The platform should implement robust authentication mechanisms, including support for SSO via SAML or OIDC, and enforce strong password policies for local accounts. OIDC-based SSO flows enable integration with corporate identity providers, allowing users to authenticate once and access both the Query console and other systems via a common identity.[12]  

Curity’s approach to SSO for AI agents involves obtaining an ID token during login via OIDC, then using that token in an Identity Assertion JWT Authorization Grant (ID-JAG) flow to obtain new tokens that preserve user identity across trust domains.[12] While Query’s documentation does not detail such flows, similar mechanisms could be used to allow the Query console to authenticate users via corporate identity providers and to propagate identity to downstream services or AI agents.  

Session management should include safeguards such as session expiration, idle timeout, and device recognition. Tokens should be short-lived and regularly refreshed, with refresh tokens protected in secure storage. The platform should detect and prevent session fixation, implement CSRF protections (for example, using anti-CSRF tokens and SameSite cookie attributes), and enforce secure cookie flags to mitigate attacks. Logs should capture login attempts, successful logins, and session terminations, enabling detection of anomalous authentication behavior.  

### Defense-In-Depth Against Common Web Vulnerabilities

Multi-tenant web UIs must guard against common vulnerabilities such as cross-site scripting (XSS), cross-site request forgery (CSRF), clickjacking, and injection attacks. Given the sensitivity of data accessible via Query’s console, even minor vulnerabilities can have serious consequences.  

XSS protection requires careful handling of user-generated content and dynamic content injection. The platform should encode all output and avoid directly inserting user-supplied HTML into the DOM. Content Security Policies (CSPs) can restrict the sources of scripts and resources, reducing the risk of malicious code execution.  

CSRF protections ensure that state-changing actions, such as adding connectors or inviting users, cannot be triggered by unauthorized third-party sites. Anti-CSRF tokens tied to user sessions and validated on each state-changing request, combined with SameSite cookies, provide effective protection.  

Clickjacking defenses, such as X-Frame-Options or equivalent CSP directives, prevent the UI from being embedded in frames on malicious sites. Input validation and parameterization help mitigate injection attacks, ensuring that user-supplied data does not lead to query manipulation or back-end compromise.  

### Secure Integration With Downstream APIs And AI Models

The Query console acts as a front-end to downstream APIs and, increasingly, to AI models. This requires careful design of API interactions and AI integrations. When the UI triggers federated searches, it calls back-end endpoints that orchestrate connector invocations. These back-end calls must be authorized with tokens that carry tenant and user identity, and must enforce policies on which connectors and datasets can be accessed.  

In AI integrations, such as CoPilot and natural-language search, the platform may call external model services or internal model hosting APIs. AWS’s guidance on SaaS and generative AI describes patterns where tenant-specific training data and validation data are used to fine-tune models, and where knowledge bases are populated and managed per tenant.[8] The UI and back-end must ensure that prompts sent to models contain only data appropriate to the tenant and user, and that responses are interpreted within the correct context.  

FusionAuth’s and Curity’s discussions of AI authentication and SSO emphasize that identity enforcement must be deterministic, even when the AI systems themselves are probabilistic.[5][12] The UI’s integration with AI features should always go through an identity-aware back-end, where authorization checks are performed before data is retrieved and passed to models. Models should not be allowed direct access to raw connector credentials or data; instead, they should receive curated and filtered inputs.  

### Monitoring, Logging, And Security Analytics

Given Query’s role as a security investigation platform, it is natural for organizations to integrate its own logs into broader security analytics. The web UI should emit logs for user activities such as logins, searches, connector management, and configuration changes. These logs should be enriched with tenant and user identity, and captured in a format compatible with OCSF or other standardized schemas for security events.[1][6][11]  

Monitoring these logs can reveal patterns of misuse or attack, such as attempts to access unauthorized connectors, unusual query volumes, or modifications to schema mappings. Integrating these logs with SIEMs via connectors allows organizations to apply detection rules to Query’s own activity, creating a meta-layer of security analytics over the platform itself.  

In multi-tenant SaaS environments, monitoring must also respect tenant isolation. Logs should be partitioned or tagged by tenant, and access to log data should be restricted to relevant administrators and security teams. Aggregated analytics across tenants may be used by Query’s internal teams to detect systemic threats, but such analytics must preserve privacy and avoid exposing individual tenant details.
