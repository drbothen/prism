# Technical Analysis of Query’s Federated Security Data Mesh and Query Language

Query (formerly branded as Query.AI) has evolved into a **security data mesh platform** that delivers federated search, detection, and investigation across highly heterogeneous security and business data sources, with a strong emphasis on “zero-ETL” access, a unified OCSF-based data model, and a mix of structured query and natural-language interaction.[1][2][11] At its core, the platform exposes a federated query layer that translates a single logical query—expressed via a proprietary Federated Search Query Language (FSQL), earlier Unified Query Language (UQL), or natural-language prompts—into native requests against dozens of tools and data stores, normalizes the responses into an OCSF-derived schema, and surfaces them through a browser-based investigations console and programmatic APIs.[11][13][17] The architecture is explicitly designed to centralize *insights* rather than *data*, using connectors as read-only API bridges into SIEMs, EDR tools, identity providers, cloud services, ticketing systems, and threat intel platforms, while avoiding bulk ingestion, pipelines, or long-lived indexes.[1][2][8][11] This analysis examines, in technical detail, (1) how Query’s query language and search interface work, (2) how its federated search and data mesh architecture operates, and (3) how its decoupled access model handles on‑prem versus cloud environments, credentials, and data residency, with particular focus on the role of the Open Cybersecurity Schema Framework (OCSF) in schema normalization and cross-source correlation.[3][9][11]  

## 1. Background: Query as a Security Investigations Control Plane and Data Mesh

### 1.1 Positioning and Core Objectives

Query positions itself simultaneously as a **security investigations control plane** and a **security data mesh platform**, two complementary roles that shape its architecture and query model.[2][11][13] As a control plane for security operations, Query offers a unified browser interface that “plugs into existing security technologies quickly and easily using APIs,” providing analysts a single console from which to investigate alerts and events across SIEMs, EDR tools, cloud security platforms, identity systems, and contextual data stores such as ticketing and HR systems.[2][13] This investigations console is not itself a SIEM or log store: instead, it overlays existing tools, aiming to simplify incident management by simultaneously normalizing, aggregating, enriching, visualizing, and analyzing alert data that already lives in those systems.[2]  

The platform’s data philosophy is explicitly anti-centralization: Query describes its offering as a “security data mesh platform” whose architecture is “platform‑agnostic” and designed to **centralize insights, not data**.[11] Rather than ingesting and storing logs and events into a monolithic data lake or SIEM, Query deploys API-based connectors as “bridges” into distributed data sources, executes federated searches directly against those systems, and returns OCSF-normalized results in real time.[1][8][11] This orientation is reinforced in marketing and technical materials that emphasize “no ingestion,” “no pipelines to build or maintain,” and an ability to reach security data “wherever it lives,” including cloud buckets, on‑prem SIEMs, SaaS platforms, endpoints, and identity providers.[1][8][11]  

The platform emerged in an industry context where organizations struggled to access and correlate security-relevant data that was fragmented across multiple vendors and environments, and where traditional SIEM architectures required expensive, complex ETL pipelines and centralization in order to perform cross-source investigations.[2][5][11] Query’s stated goal is to “unlock access to and value from cybersecurity data wherever it is stored—across cloud, third-party SaaS, and on‑prem environments—regardless of vendor or technology, without requiring centralization.”[2] By functioning as connective tissue that delivers federated search to conduct cybersecurity operations across data silos, Query aims both to reduce costs and to expand investigative scope beyond what a single SIEM or data lake can realistically ingest.[1][2][11]  

A secondary but important objective is **skill abstraction**: Query explicitly advertises that it permits analysts to query multiple systems “with the simplicity of a single query—via text, natural language, or Unified Query Language—so security analysts don’t need to be experts in individual systems.”[2][13] The platform’s query layer hides tool-specific query languages (for example, Splunk SPL or Azure KQL) behind a unified logical query model, and in some cases can even translate existing SPL, KQL, or Sigma detection rules into its own FSQL language, further decoupling detection engineering from particular vendors.[11][17] This abstraction is increasingly reinforced by AI-based features, including mission-specific agents and natural-language-to-FSQL generation, which are discussed later.[4][11][17]  

### 1.2 Data Mesh, Zero‑ETL, and Open Standards as Conceptual Foundations

Query’s platform design is rooted in several broader architectural trends in data and security engineering: **data mesh**, **zero‑ETL** integrations, and adoption of open schemas such as OCSF.[3][5][9][11][16] The data mesh concept emphasizes distributed ownership of data, domain-oriented data products, and a federated architecture where data remains in source systems but is discoverable and queryable through a common layer.[16] Query explicitly describes its connectors as “a critical component in enabling a security data mesh architecture,” suggesting that each connector constitutes a security data product that is made accessible to the mesh via standardized field names and an OCSF-based schema.[1][11]  

Zero‑ETL, as articulated by cloud providers such as AWS, refers to a model where point-to-point data integrations minimize or eliminate explicit ETL pipelines, enabling querying across data silos without bulk data movement or reprocessing.[5] Query’s technology aligns closely with this concept, repeatedly emphasizing that it operates “without pipelines,” “no ETL,” and “no ingestion,” instead providing “point-to-point” API bridges into each source tool or data store.[1][8][11] In a typical ETL-driven SIEM, security telemetry is extracted, transformed, normalized, and loaded into a central index before queries can run; by contrast, Query’s federation model uses in‑flight normalization and schema mapping at query time, allowing analytics and detection logic to run directly against distributed sources.[1][11][17]  

The Open Cybersecurity Schema Framework (OCSF) is a vendor-neutral, open standard schema for security telemetry, backed by large ecosystem participants including Splunk, AWS, Broadcom, CrowdStrike, IBM Security, Okta, Palo Alto Networks, Trend Micro, and others.[3][9] Query’s internal **Query Data Model (QDM)** is explicitly based on OCSF: all search results in Query are represented as *events* conforming to OCSF-style event classes, grouped into categories, and decorated with attributes and enumerations.[9][11] The platform describes its data model as “normalized to OCSF,” with “one set of field names across every connected source” such that analysts can “write a detection once, run it everywhere,” reinforcing the use of OCSF as the semantic foundation of its query language.[9][11]  

Query has been an active contributor to OCSF, and its blogs discuss mapping between proprietary schemas and OCSF event classes and attributes, underlining the importance of schema normalization in its approach.[3][9] By adopting OCSF, Query can treat heterogeneous events—network flows, process activity, authentication events, alerts, detections, vulnerability findings—as instances of standardized event categories, while still preserving source-specific nuances in attributes and values.[9] This standardization is vital for federated correlation and for FSQL’s ability to express grouping and threshold logic across multiple platforms simultaneously.[9][11][17]  

### 1.3 Scope of Integrations and Security-Relevant Domains

An effective security data mesh requires broad connectivity, and Query emphasizes the breadth of its integration library as a core differentiator.[1][2][11] The platform currently provides centralized access to decentralized data across “more than 150 of the most widely used enterprise technologies” in domains such as cloud infrastructure and security, SaaS applications, SIEM and log management, endpoint security, email and communications, vulnerability management, threat intelligence, network security, identity and HR systems, MDR providers, ticketing and CRM, SOAR, and XDR.[2] On its product page, Query highlights “50+ connectors” and distinguishes between “static schema sources” and “dynamic schema sources,” indicating a nuanced approach to data-source heterogeneity.[11]  

Static schema sources correspond to tools whose schemas are reasonably stable and well-understood, such as EDR platforms, identity providers, and email security tools; Query pre-maps these systems to its Data Model, allowing customers to integrate them without additional schema engineering.[1][11] Examples cited include CrowdStrike, Okta, Microsoft Entra ID, Microsoft Defender, SentinelOne, Auth0, VirusTotal, Jamf, and ServiceNow, among others.[11] For dynamic schema sources—any SIEM, cloud bucket, or analytics platform—Query introspects the schema, auto-discovers partitioning, and then maps the data to OCSF via a no‑code Configure Schema workflow, which is particularly relevant for platforms like Splunk, Snowflake, Google BigQuery, Google Security Operations (Chronicle), Microsoft Sentinel, Databricks, and Amazon CloudWatch.[11][18]  

Beyond core security telemetry, Query also integrates with specialized systems such as the MISP Malware Information Sharing Project, leveraging MISP’s restSearch API to retrieve indicators of compromise (IOCs), CVEs, vulnerabilities, and weaknesses, and normalizing them into OCSF event classes like OSINT Inventory Info.[20] This breadth allows Query to incorporate threat intelligence, vulnerability data, and contextual business information alongside traditional logs and alerts, providing a richer substrate for federated search and AI-driven analysis.[2][4][20]  

## 2. Query Language and Search Interface

### 2.1 User-Facing Search Workflows in the Federated Console

From an analyst’s perspective, Query’s primary interaction surface is a **browser-based search and investigations console** that offers federated search across all connected integrations.[1][2][13][19] The interface centers around a search bar and time picker, a connectors selection pane, and controls for switching between different search modes such as *Entities* and *Events*.[19][20] Analysts can launch searches in natural language or structured query form, specifying which connectors should participate, constraining the time range, and choosing whether to search by observable entities (for example, an IP address or user identity) or by event classes and attributes within the OCSF-based data model.[1][9][19][20]  

The platform’s documentation and marketing materials describe a quick-start path where users “start typing using natural language to instantly search across all of your connected integrations,” indicating that the search bar accepts free-text questions that are subsequently translated into one or more underlying queries.[1] At the same time, Query emphasizes that analysts can query via “text, natural language, or Unified Query Language (UQL),” suggesting that the input channel supports both human-language queries and a structured domain-specific language.[2][13] More recent materials on the security data mesh product explicitly foreground **Federated Search Query Language (FSQL)** as the unified syntax across all sources, indicating that FSQL has superseded or incorporated the earlier UQL.[11][17]  

Within the search console, connectors are organized into categories such as SIEM and log management, endpoint security, threat intelligence and enrichment, identity, and others, and analysts can enable or disable particular connectors before running a search.[1][19][20] For example, the MISP connector appears under a “Threat Intelligence and Enrichment” section in the Selected Connectors dropdown, and is enabled by checking its checkbox before issuing a query.[20] This selection mechanism allows analysts to scope federated searches to specific domains or tools, which can be important for performance, governance, or investigative focus.  

The console also exposes an **Entities-based search mode**, where analysts select an entity type (for instance, IP Address, Domain, User, Email, CVE) and provide a value, and Query expands this entity into the appropriate attributes across the schema to search for corresponding occurrences in normalized events.[9][20] Entities are defined in the Query Data Model as aliases that point to multiple attributes across the schema, representing key facts or indicators of compromise such as IP addresses, hostnames, or user identities.[9] An Entity-based search therefore acts as a semantic pivot: searching for an IP Address observable automatically traverses all fields that may contain IP addresses across different event classes and data sources, saving analysts from writing multiple field-specific filters.[9][20]  

An **Events-based search mode** allows analysts to select event classes from OCSF categories and filter them by attributes and time.[9][20] For example, when exploring MISP data, analysts may select the OSINT Inventory Info event class in the Discovery category and then apply attribute filters reflecting the types of indicators (e.g., vulnerabilities, weaknesses) they are interested in.[20] The interaction between Entities and Events modes illustrates the way Query’s query model blends semantic shortcuts (entities) with schema-aware event selection, leveraging its OCSF-based normalization to make cross-source searches more intuitive than raw log queries.  

### 2.2 Structured Query Language: UQL and Federated Search Query Language (FSQL)

While the user interface supports natural-language input, Query’s core technical mechanism for expressing search and detection logic is a **domain-specific query language** designed explicitly for federated operations over OCSF-normalized data.[11][13][17] Earlier materials refer to a **Unified Query Language (UQL)** that allows users to query across cybersecurity systems and contextual information stores via a single text-based syntax, insulating them from the need to master tool-specific languages such as SPL or KQL.[2][13] In later product documentation, this role is taken up by **Federated Search Query Language (FSQL)**, described as “one query language across every source” and used both for ad hoc federated search and for scheduled detections.[11][17]  

FSQL is not documented publicly at the level of a full formal grammar in the available materials, but several sources outline its design goals and capabilities.[11][17] It is described as a platform-agnostic syntax that the data mesh “translates to each source’s native language at query time,” suggesting that FSQL is an intermediate representation rather than a direct executable on any particular backend.[11] The Federated Detections documentation states that detections are defined as scheduled queries written in FSQL with **explicit evaluation semantics**, supporting windowed aggregations and rates, grouping by users, identities, IPs, resources, or assets, and threshold-based match conditions.[17] This implies that FSQL includes constructs analogous to SQL’s aggregation, grouping, and filtering, but with semantics tailored to time-windowed detection logic and OCSF event categories.  

Moreover, Query advertises translation capabilities between FSQL and existing detection rule formats: detections can be authored natively in FSQL, or converted from Splunk’s Search Processing Language (SPL), Azure’s Kusto Query Language (KQL), or Sigma rules.[11][17] This indicates that FSQL is expressive enough to capture the key logical patterns used in those query languages—such as filters, aggregations, joins or correlations, and event-time windows—and that it can preserve detection semantics while decoupling them from specific SIEM vendors.[11][17] The platform also supports generating FSQL from natural-language prompts, using AI agents or LLM-based translation to assist non-expert users in authoring detection logic.[17]  

Conceptually, FSQL can be viewed as a **schema-aware query DSL** that operates over the Query Data Model, referencing OCSF event classes, attributes, entities, and enumerations rather than raw table names and column names.[9][11][17] For example, a detection rule in FSQL might specify a time window and event category (such as Authentication or Network Activity), filter events where a particular Entity (like a user or host) exhibits suspicious behavior, group by that Entity, compute rates or counts, and compare those aggregates against thresholds to decide whether to trigger a finding.[9][17] The fact that detections record their execution context—including time range evaluated, source coverage, and match counts—emphasizes FSQL’s role in encoding deterministic evaluation semantics across multiple sources.[17]  

While detailed syntax examples are not provided in the sources, the design echoes structured query languages in other domains, such as the Google Visualization API Query Language (which uses SQL-like clauses like `select`, `where`, `group by`, `order by`) and Lucene-based search syntaxes used by Azure AI Search, which support boolean expressions, grouping, and filters.[10][12] However, FSQL differs from these generic languages in its tight integration with the OCSF schema, its awareness of entities and event categories, and its federation semantics, where a single FSQL query is compiled into multiple native queries in parallel.[11][17]  

### 2.3 Data Model and Field Name Normalization via OCSF

The effective operation of FSQL and the search interface depends on **consistent field naming and schema normalization** across heterogeneous sources, a problem Query addresses through its OCSF-based Query Data Model.[9][11] In this model, all search results are represented as **events**, which may include observability data (such as network or process activity), alerts, detections, findings, remediation actions, and even queries to systems of record.[9] Events are grouped into categories corresponding to OCSF event classes, such as Authentication, Network Activity, Discovery, OSINT Inventory Info, and others, providing a semantic classification backbone.[9][20]  

Each event has **attributes**, representing primitive data types such as strings, numbers, booleans, and more complex structures; attributes are addressed as paths through the schema in dot notation, for example `<event>.<attribute>.<nested_attribute>`, and are associated with both machine-friendly internal names (all lowercase with underscores) and human-friendly captions.[9] Enumerations are coded attributes whose values must be selected from predefined lists, which are useful for normalizing status codes or categorical fields across data sources; for instance, different tools may represent authentication outcome statuses differently, but OCSF enumerations allow Query to expose a unified field for “Outcome” with standardized values.[9] Entities, also referred to as observables, act as aliases that span multiple attributes across the schema, typically representing indicators of compromise or key identity constructs such as IP addresses, domains, users, and hosts.[9]  

When Query federates a search, it constructs a logical query in terms of these **unified event and attribute names**, rather than the original field names used by each source system.[9][11] Static connectors encapsulate the mapping from each tool’s native schema to OCSF attributes in advance: for example, a CrowdStrike EDR connector would map its process activity fields onto OCSF’s Process or Endpoint event classes, while an Okta connector would map its logs onto Authentication or Identity-related event classes.[11] The Query team pre-defines these mappings, sparing customers from schema engineering for popular tools.[1][11]  

Dynamic connectors, by contrast, introspect schemas at onboarding time and rely on a **no‑code Configure Schema workflow** to map fields from arbitrary SIEMs or data lakes to the Query Data Model.[11][18] In the case of Google Security Operations (Chronicle), Query retrieves the UDM (Unified Data Model) schema for each feed, fetches sample data, and guides customers in mapping UDM fields into OCSF attributes via a visual interface.[18] Once the mappings are defined, Query Federated Search handles query translation and optimization into UDM, transforms UDM data into OCSF data per the mappings, and parallelizes searches across feeds to expedite answers.[18] A similar pattern applies to other dynamic connectors such as Splunk, Snowflake, and BigQuery, where Query first discovers the partitioning and tables, then associates them with OCSF categories and attributes.  

Importantly, Query does not strictly enforce all OCSF field requirements or constraints for every profile; instead, it “attempts to maximize the amount of data” it can provide, even when some sources lack sufficient fields to form a fully valid OCSF record.[9] This pragmatic approach acknowledges that real-world data sources may be incomplete or idiosyncratic, while still allowing Query to present a reasonably consistent schema to analysts. All events in OCSF have three time attributes—`time`, `start_time`, and `end_time`—and Query ensures that the `time` field is always populated, using the source’s event timestamp; `start_time` and `end_time` may be left empty if the source does not support time intervals, but the UI’s time picker always filters on the `time` field.[9]  

The result is that, once connectors are configured, analysts and detection engineers can treat the entire security estate as if it were one large OCSF-compliant event store, using standardized field names and entity abstractions to write queries and detections that apply across SIEMs, EDR, cloud logs, identity providers, and threat intel sources.[9][11][17] This normalization dramatically reduces the cognitive overhead of cross-source investigation and is essential to FSQL’s claim of “one set of field names across every connected source,” enabling detections to be written once and run everywhere.[11][17]  

### 2.4 Natural-Language and AI-Assisted Querying

Although the underlying query layer is structured, Query invests significantly in **natural-language and AI-assisted interfaces** to make its capabilities usable by a broader set of security practitioners.[1][2][4][11][17] The platform’s security investigations descriptions emphasize that analysts can “simply ask questions” using text or natural language and receive the answers they need quickly, without needing to understand each tool’s query language.[2] This is reinforced by the multi-modal query input options—text, natural language, or UQL/FSQL—and by the ability to generate FSQL detections from natural-language prompts.[13][17]  

A key component of this interface is the use of **large language models (LLMs)** and mission-specific AI agents. In its blog introducing the Vulnerability Intelligence Agent, Query describes a framework where an LLM (such as Google’s Gemini) serves as the reasoning engine, integrated with specialized tools and a curated knowledge base.[4] The agent is described as an AI-powered analyst dedicated to extracting, enriching, and contextualizing vulnerability data to determine its real-world impact on a specific environment, using tools for CVE and vulnerability retrieval, as well as federated search integration.[4] The agent leverages Query Federated Search to ask questions of data where it lives, correlating a newly announced CVE with live asset data from EDR platforms, vulnerability scan results, and network telemetry from SIEMs within a single workflow.[4]  

This architecture implies that natural-language queries—such as “Which of our internet-exposed assets are vulnerable to CVE‑2023‑XXXX and have active exploitation attempts detected in the last 24 hours?”—are parsed by an LLM, decomposed into sub-queries expressed in FSQL or source-specific query languages, and then executed via Query’s federated search layer.[4][11][17] The LLM interprets user intent and domain concepts, maps them onto the OCSF-based data model (for example, assets, vulnerabilities, exploits, network connections), and orchestrates calls to connectors to retrieve relevant data.[4] Because the data mesh centralizes access and schema normalization, the AI agent can reason over normalized events rather than tool-specific logs, simplifying prompt-to-query translation.  

More broadly, Query advertises “mission-specific agents” for workflows like triage, investigation, threat hunting, and identity threat detection and response (ITDR), each engineered to perform verifiable work and to earn analysts’ trust.[11] These agents rely on the data mesh as the “data foundation AI requires,” highlighting the symbiotic relationship between the federated query layer and AI capabilities.[11] Natural-language queries thus become a higher-level interface over FSQL and the OCSF schema, with the platform translating human questions into structured queries and then aggregating the results back into human-readable reports and recommendations.  

Compared to generic natural-language query tools that federate access to multiple data sources through a conversational layer and convert user questions into database queries or API calls, Query’s approach is distinguished by its security-specific schema (OCSF), its tight integration with detection logic (FSQL-based rules), and its focus on real-time operations rather than offline analytics.[7][11][17] Nevertheless, it shares with such tools the goal of hiding query-language complexity and returning actionable results, including basic statistical insights, without forcing users to learn multiple syntaxes.[7][2][11]  

### 2.5 Comparison with Other Query Paradigms

To contextualize Query’s query language and interface, it is useful to compare FSQL and its natural-language layer with more conventional query paradigms such as SQL, Lucene-based search, and other DSLs. The table below summarizes key aspects of FSQL relative to generic SQL and Lucene-like syntaxes, drawing on available documentation and standard characteristics.[10][11][12][17]  

| Aspect | Query FSQL | SQL (e.g., Google Visualization Query Language) | Lucene-based search (e.g., Azure AI Search Simple Syntax) |
|--------|------------|-----------------------------------------------|----------------------------------------------------------|
| Primary domain | Security telemetry and detections over OCSF-normalized events.[9][11][17] | Relational tables and structured data sources.[10] | Full-text search over indexed documents.[12] |
| Schema basis | OCSF event classes, attributes, entities, enumerations; Query Data Model.[9][11] | Database tables, columns, types; arbitrary schemas.[10] | Document fields; often schemaless or lightly typed.[12] |
| Semantics | Windowed aggregations, rates, grouping by identities/assets, threshold-based match conditions; federated across multiple sources.[17] | Select/project columns, aggregate, group, filter; single data source or join across tables.[10] | Keyword and phrase search, boolean operators, filters; ranking and relevance.[12] |
| Federation | Designed to translate a single logical query to multiple native backends (SPL, KQL, etc.) and aggregate normalized results.[11][17][18] | Federation requires external orchestration; query is typically sent to one data source at a time.[10] | Federation is possible but not intrinsic; each index is queried separately unless orchestrated.[12] |
| Query input modes | Textual FSQL, natural language, and AI-assisted prompt-to-FSQL generation; entity-based shortcuts.[1][2][17] | SQL-like query strings; rarely integrated with natural language directly.[10] | Lucene-like syntax; some UIs offer natural-language front ends, but language itself is keyword-based.[12] |
| Integration with detection logic | Directly used to define scheduled detections with explicit evaluation windows and thresholds.[17] | SQL used for analytics and reporting; detection systems may use SQL but lack standardized detection semantics.[10] | Search queries used for retrieval; detection rules sometimes encode search patterns but not typically standardized.[12] |

This comparison underscores that Query’s FSQL is less a generic data manipulation language and more a **security-specialized federated detection language** rooted in OCSF, designed to express time-windowed patterns across multiple tools and to be both human-authored and machine-translated from existing rules or natural-language prompts.[9][11][17] Its federation semantics and schema-awareness distinguish it from traditional SQL, which presumes centralized data, and from Lucene-based search, which focuses on full-text matching within a single index.[10][12]  

## 3. Federated Search Architecture and Data Mesh Implementation

### 3.1 High-Level Architecture: Centralizing Insights, Not Data

Query’s federated search architecture is explicitly framed as a **security data mesh** where data remains distributed but is made consistently accessible via a common platform-agnostic layer.[1][11][18] The core components of this architecture can be conceptualized as: a browser-based UI and control plane, a federated query engine implementing FSQL and natural-language translation, an OCSF-based schema and data model, and a network of connectors that act as read-only API bridges to source systems.[1][2][8][11][18][20]  

The **platform architecture** is described as a “platform-agnostic data layer” that translates FSQL to each source’s native syntax, executes parallel queries, and returns OCSF-normalized results.[11] This layer is responsible for parsing user queries or detection rules, resolving them against the Query Data Model (event classes, attributes, entities), and then decomposing the logical query into a set of backend-specific queries that target SIEM indices, EDR APIs, cloud logging services, threat intel platforms, or business applications.[11][18][20] The engine then dispatches these queries in parallel via connectors, collects responses, applies schema mappings to transform data into OCSF events, and aggregates results for presentation in the UI or for consumption by AI agents and downstream tools.[1][8][11][18][19]  

Critically, Query emphasizes that **no ingestion** or **pipe-based ETL** is required: the platform does not require customers to centralize their security data into a new data lake, nor does it store or process bulk event data itself.[1][2][11][13] The architecture is described as “read-only,” with “no DDL risk,” and “data stays at its source,” underscoring that connectors retrieve data on demand and do not modify or reindex source systems.[11] In its security investigations marketing, Query highlights that its architecture “doesn’t store, process, or require vendor access to the data,” alleviating privacy and governance concerns about enterprise data.[2] At the same time, the platform is described as “patented” and “browser-based,” suggesting that the federated query engine and UI run as a SaaS or appliance delivering real-time access to decentralized data.[13]  

This design contrasts sharply with traditional SIEM architectures, which typically ingest logs into a centralized store (ELK stacks, proprietary indexes, cloud data warehouses) and then apply queries and detection logic on that centralized corpus.[5][11] Query instead centralizes:

1. The **schema** (via OCSF-based QDM), ensuring that events from different sources share common field names.[9][11]  
2. The **query and detection logic** (via FSQL), decoupling detection rules from any single vendor’s ingest pipeline.[11][17]  
3. The **insight outputs** (via federated dashboards, AI agent reports, and findings), which can be delivered to existing ticketing or incident response tools.[2][11][17][19]  

By separating these from data storage, Query can expand coverage to sources that are impractical to ingest into a SIEM due to cost, volume, or data type, while still enabling cross-source correlation and detection.[1][11][17]  

### 3.2 Connectors and Source Integration

Connectors are fundamental to Query’s federated architecture, acting as the **integration control plane** between the Query platform and distributed data sources.[1][11] They encapsulate the details of authentication, schema mapping, query translation, rate limiting, and data retrieval for each source, and are categorized broadly into **static connectors** and **dynamic connectors**, reflecting differences in schema stability and mapping strategy.[1][11][18][20]  

Static connectors target tools with relatively stable and well-documented schemas (for example, CrowdStrike, Okta, Microsoft Defender, various EDR and identity platforms). Query develops and maintains pre-defined mappings for these connectors, aligning their native fields with OCSF event categories and attributes in the Query Data Model.[11] For such connectors, customers typically only need to provide access credentials—URLs, API keys, auth tokens—and basic configuration like connector aliases or tenant identifiers; normalization and query translation are handled entirely by Query.[1][11] The MISP connector is a good example: it is explicitly described as a static schema connector where all normalization and search translation are defined by Query’s engineering team.[20] Customers configure it by supplying the MISP external URL (or reverse proxy), an API key, and optional MISP types (such as `ip-dst` or `vulnerability`) that they want to retrieve; Query then uses the restSearch API to fetch attributes within events and surfaces them normalized to the OSINT Inventory Info event class.[20]  

Dynamic connectors are designed for **arbitrary or evolving schemas**, such as SIEMs with custom log types, cloud buckets with diverse data sets, or analytics platforms like Snowflake and BigQuery.[11][18] For these sources, Query introspects the schema and auto-discovers partitioning, then guides customers through a **no‑code Configure Schema workflow** to map native fields onto OCSF attributes.[11][18] In the Google Security Operations (Chronicle) connector, Query handles parsing the specific log type from each feed, retrieving the UDM schema, fetching sample data, and presenting a mapping interface where customers associate UDM fields with Query Data Model attributes.[18] Once these mappings are saved, Query Federated Search can describe searches in terms of QDM/OCSF entities, event classes, and attributes, while the federated engine handles query translation and optimization into UDM under the hood.[18]  

Connector configuration typically involves steps such as creating service accounts or API keys, retrieving project and tenant identifiers, specifying regional codes and feed names, and testing the connection to ensure credentials and dataset references are valid.[18][20] For instance, integrating Google SecOps requires a service account with Chronicle API admin role, a JSON key, the project ID or number, location name, customer ID, and feed names; these are entered into the connector configuration panel along with an alias and default login setting.[18] Similarly, MISP integration requires the external base URL, an API key, and optional type filters, followed by a “Test Connection” action to confirm that Query can successfully dispatch a search.[20]  

Some connectors operate not only from the Query console but also as **embedded bridges** into existing tools. The Query Federated Search App for Splunk demonstrates this pattern: it allows Splunk users to run searches that access data not ingested into Splunk, using Query as a bridge between Splunk and external data stores.[8] In this case, Query’s connector to Splunk and its connectors to other tools work together to enrich Splunk reports and rule sets with additional data, again without ingesting that data into Splunk itself.[8] This illustrates how connectors can support both the Query console and third-party UIs, embedding federation into familiar analyst workflows.  

### 3.3 Query Fan-Out, Translation, and Execution

When an analyst issues a federated search or when a scheduled detection runs, Query’s federated query engine must **fan out** the logical request into multiple backend-specific queries, execute them efficiently, and then normalize and aggregate the results.[1][11][17][18] The platform’s description of this process emphasizes parallelization and on‑the‑fly query translation.

The high-level flow can be described as follows, based on the documented behavior. First, the engine parses the user input—whether natural language, FSQL, or entity-based—and resolves it against the Query Data Model to determine the relevant event categories, attributes, and entities.[9][11][17] It then enumerates the connectors that are enabled for the search—either all connectors or a user-selected subset—and determines which ones can support the requested event classes or attributes based on their schema mappings.[1][11][19][20]  

For each connector, the engine compiles the logical query into that source’s native query dialect or API form. In the case of dynamic connectors, this may mean translating FSQL filters and aggregations into queries expressed in UDM’s dot-notation typed query language or in Splunk SPL or Azure KQL; Query explicitly supports translation from SPL and KQL to FSQL and vice versa, indicating that it maintains mappings between FSQL constructs and native constructs.[11][17][18] The Google SecOps connector documentation notes that Query Federated Search handles query translation and optimization into UDM, suggesting that the engine is aware of UDM’s query capabilities and constraints.[18]  

Once queries are prepared, the federated engine executes them **in parallel** across connectors, leveraging the platform-agnostic data layer’s ability to dispatch multiple API calls concurrently.[11][18] This parallelization is key to performance: it allows Query to return aggregated results quickly even when dozens of connectors are involved, and when some backends have higher latency than others.[1][11][18] Results are streamed back to the engine, which applies connector-specific schema mappings to transform native data structures into OCSF-style events, sets the `time` attribute based on source timestamps, and associates events with their originating connector and source.[9][18][20]  

For **Federated Detections**, FSQL queries have explicit evaluation windows and thresholds, and the engine applies detection logic as results arrive.[17] Detections run on a defined cadence and evaluate data within a specified time window; each execution records the time range evaluated, source coverage, and match counts, providing traceability into what data was checked and why a detection fired.[17] As events are processed, the engine computes aggregations and evaluates threshold-based match conditions; if conditions are met, the detection can terminate early, surfacing meaningful activity quickly without waiting for a full scan when speed is critical.[17]  

The engine then produces **findings**—normalized records representing detection matches—which can be delivered to chat systems, ticketing tools, or incident response platforms, and each finding includes a replay link that reruns the detection against the original time window.[17] Replay links enable analysts to re-execute the exact detection logic and examine normalized results across contributing sources, pivoting into related entities and events using federated search to continue the investigation.[17] This integration between detection and interactive search underscores the tight coupling between FSQL, the data mesh, and the UI.  

### 3.4 Normalization, Aggregation, and Cross-Source Correlation

One of the central challenges in federated security search is **correlating results across sources** that represent different views of the same underlying entities or activities. Query addresses this through its OCSF-based normalization, entity abstractions, and federated dashboard capabilities.[1][2][4][9][17][19][20]  

When events from multiple connectors are normalized into the Query Data Model, entities such as IP addresses, hostnames, user identities, email addresses, and CVEs become common pivots across sources.[9][20] An Entity-based search on an IP address, for instance, will retrieve events where that IP appears in network logs (as source or destination), in EDR telemetry (as connection endpoint), in firewall logs, or in threat intel feeds that list it as a known malicious indicator.[9][20] Because entities are aliases to multiple attributes across the schema, a single entity value can unify many different fields from disparate tools.[9]  

Federated dashboards, referred to as **Summary Insights**, provide aggregated views across connectors, allowing analysts to visualize counts, trends, and metrics derived from normalized events.[19] The platform’s documentation indicates that federated dashboards are built on top of the federated search capabilities, using normalized events and the time picker to present cross-source summaries.[19] This suggests that the aggregation and correlation logic is expressed either in FSQL or a related internal DSL, which computes statistics such as alert volumes, endpoint activity rates, or vulnerability coverage across multiple tools, leveraging the unified schema to avoid per-tool metric definitions.[9][11][19]  

In more advanced scenarios, AI agents use federated search to perform **multi-source correlation** for specific workflows. The Vulnerability Intelligence Agent, for example, uses Query Federated Search to correlate a newly announced CVE with live asset data from EDR, vulnerability scan results from scanners, and network telemetry from SIEM, providing a holistic view of the organization’s exposure and active exploitation attempts.[4] The agent’s integration with the data mesh allows it to reason about relationships between vulnerabilities, assets, and network activity in real time, without relying on a centralized vulnerability database.[4][11]  

Federated Detections also embody cross-source correlation: FSQL rules can group by users, identities, IPs, resources, or assets, and apply threshold conditions that span events from multiple connectors.[17] For example, a detection might look for a user whose identity is used across several cloud tenants and on‑prem systems in a suspicious pattern, aggregating authentication events from Okta, Microsoft Entra ID, and on‑prem AD logs normalized under the Authentication event class, and grouping by the unified user entity.[9][11][17] Because all events share common field names and enumerations, FSQL can express such correlations without per-tool logic, and the federated engine can apply them across sources.  

It is also noteworthy that Query’s platform advertises capabilities to **normalize, correlate, collate, deduplicate, and enrich** data across sources, suggesting that the federated engine performs additional processing beyond simple field mapping.[1][2] While detailed algorithms are not described, deduplication likely involves recognizing identical or overlapping events reported by multiple tools (for example, SIEM and EDR logs for the same alert) using identifiers or entity correlations, while enrichment may involve joining events with threat intel from MISP or OSINT sources normalized into OCSF event classes.[2][20] The unified data model and entity abstraction again play crucial roles in these operations.  

### 3.5 Operational Concerns: Partial Failures, Rate Limits, Pagination, and Performance

Public documentation does not fully specify how Query handles operational concerns such as partial connector failures, source-specific rate limits, or pagination, but certain design hints and standard patterns can be inferred from connector and detection behavior.[17][18][20]  

Since connectors rely on external APIs, they are subject to **authentication errors, network timeouts, API quota limits, and schema changes**. Query’s connector configuration interfaces include “Test Connection” actions that verify whether credentials, dataset identifiers, and API endpoints are valid and whether Query can successfully dispatch a search against them.[18][20] This suggests that Query validates connectivity before enabling connectors in production and provides feedback to administrators when connectors fail at configuration time. During query execution, partial failures would likely be surfaced either as warnings in the UI or as reduced source coverage metrics in detection logs; indeed, detections explicitly record **source coverage** for each execution, indicating whether all intended data sources were evaluated.[17] If a connector fails during a detection run, the recorded source coverage can inform analysts that some sources were missing, preserving transparency.  

Regarding **rate limits and pagination**, connectors such as those to Google SecOps or MISP must respect each platform’s API constraints.[18][20] For instance, the MISP restSearch API may require paging through results when retrieving large sets of attributes, and Google SecOps feeds may impose per-request limits on the number of events returned.[18][20] Query’s connectors likely implement pagination and backoff logic internally, fetching multiple pages of results as needed and aggregating them before normalization. Performance-focused features such as early termination in detections—where a detection can stop scanning once a threshold condition is met—help mitigate the cost of processing high-volume data across many pages.[17]  

Parallelization of queries across connectors is a key performance optimization, reducing the impact of slow or high-latency sources.[11][18] By executing queries concurrently and normalizing results as they arrive, Query can present partial results quickly and then update dashboards or AI agents as more data arrives. The platform’s emphasis on “real-time access” to decentralized data and “centralized insights” suggests that responsiveness is a priority.[2][11][13] Additionally, because Query avoids centralizing data, it sidesteps the performance overhead of building and maintaining large indexes, shifting the compute burden to the source systems and focusing its own compute on translation, normalization, and aggregation.[1][5][11]  

Caching strategies are not explicitly documented, but it is reasonable to infer that Query may cache **schema metadata** (such as field mappings and enumerations) and possibly **recent query results** for dashboards, while treating live security event data as ephemeral. Static connectors can rely on pre-defined mappings that rarely change, while dynamic connectors maintain mapping configurations in the platform’s metadata store (for example, the Configure Schema definitions), which are reused across queries.[11][18][20] Since Query eschews long-term data storage, any event caching is likely bounded and oriented towards UI responsiveness rather than archival.  

Overall, Query’s federated architecture must balance the variability of external systems with its promise of unified, real-time insights. Its use of connectors, schema mapping workflows, detection coverage metrics, and early-termination semantics all point to a design that anticipates heterogeneity and partial visibility, while striving to provide analysts with clear indications of what data was analyzed and what might be missing.[11][17][18][20]  

## 4. Decoupled Access Model, Deployment, and Data Residency

### 4.1 Decoupled Security Investigations Control Plane

Query’s platform is often described as a **security investigations control plane**, a term that captures its decoupled relationship to underlying logging and security systems.[2][13] Rather than replacing SIEMs, EDR tools, or cloud-native security services, the control plane sits above them, providing a unified browser interface and federated query layer that orchestrates investigations across data silos.[2][13]  

This control plane approach means that Query does not dictate where security data must reside; SIEMs can continue to ingest and store subsets of data, EDR platforms can maintain their telemetry, and cloud providers can host logs in native formats.[5][11] Query connects to these systems as needed, retrieves data for specific queries or detections, and presents normalized insights back to analysts.[1][11][18] For organizations that already have extensive investments in SIEM pipelines, Query can augment them by expanding coverage to sources that are not ingested into the SIEM, such as SaaS platforms, ticketing systems, or threat intel feeds; the Splunk federated search app exemplifies this augmentation, allowing Splunk users to incorporate external data into their analyses without ingesting it into Splunk.[8]  

In its Businesswire announcement, Query describes the platform as providing “real-time access and centralized insights across on-premises, multi-cloud, and SaaS applications, without duplicating data from its native locations.”[13] The platform’s enhancements—automated alert triage, one-click response actions, streamlined ticketing—reflect control-plane functionality: Query enriches and normalizes alerts, provides contextual information to prioritize and understand incidents, and initiates response actions via integrated tools and infrastructure.[13] Resetting passwords, locking or isolating users, IPs, or hosts, and creating or assigning tickets can be performed directly from the Query console, using underlying tools as actuators while Query orchestrates the logic and interface.[13]  

By decoupling investigations from ingestion and storage, Query can help organizations **avoid vendor lock-in**, accelerate SecOps-related migration and transformation projects, and plug data gaps during transitions by providing federated access to all relevant data stores.[1][11] This decoupling is particularly valuable when organizations are moving from one SIEM to another or consolidating cloud environments: Query’s control plane can persist across such changes, maintaining continuity in detection logic and investigative workflows, while connectors are updated to reflect new backends.  

### 4.2 Access, Credentials, and Authorization

Operating as a control plane over distributed systems requires careful management of **credentials and access control**. Query’s connectors are configured using access credentials such as URLs, API keys, service account JSON keys, auth tokens, and tenant identifiers, which grant the platform read-only or appropriately scoped access to each source.[1][18][20]  

For Google SecOps integration, Query requires a service account with the Chronicle API Admin role, a JSON key for that account, the project number or ID, location name (such as `us` or `eu`), the customer ID for the SecOps tenant, and feed names to onboard.[18] These details are entered into the connector configuration, and Query uses them to authenticate API calls to Google SecOps APIs, retrieve UDM schemas, and dispatch queries.[18] Similarly, the MISP connector requires the external base URL of the MISP instance (or reverse proxy) and an API key (Auth Key), along with optional MISP types; Query uses these to authenticate to the MISP restSearch API and fetch attributes.[20] Static connectors to EDR or identity platforms typically require API tokens or OAuth credentials, which are stored in the connector configuration.[1][11]  

Query emphasizes that its platform architecture does not store, process, or require vendor access to the data in the sense of bulk storage; however, it must store credentials and metadata to function.[2][11] Connectors are described as read-only, and the platform highlights “no DDL risk,” indicating that it does not issue schema-modifying commands to source systems.[11] When initiating response actions—such as resetting passwords or isolating hosts—Query relies on integrated tools’ APIs, and these actions are exposed as one-click operations in the console.[13] Appropriate authorization scopes for such actions must be configured carefully, ensuring that Query has the ability to call remediation APIs without overprivileging.  

From a security standpoint, credential storage in Query must be secure and auditable; while public documentation does not detail the implementation, standard practices would involve encrypted storage, role-based access control for connector management, and logging of API calls made on behalf of connectors. The “Test Connection” feature helps ensure that credentials are valid and that Query can perform read operations; for write operations (response actions), similar validations and least-privilege configurations are likely encouraged.[18][20][13]  

### 4.3 Data Residency, Privacy, and Governance

Query’s architectural mantra of **“data stays at its source”** is central to its privacy and governance story.[2][11][13] By avoiding bulk ingestion and centralization, Query reduces the need to replicate sensitive security data into new environments, which can simplify compliance with regional data protection laws and internal policies.[2][5][11] Organizations can keep logs and telemetry in their existing SIEMs, data lakes, or cloud-native log services—often co-located with applications in region-specific data centers—while Query accesses them over secure APIs for specific queries and detections.[1][11][18]  

In marketing materials, Query states that its architecture alleviates privacy and governance concerns because it “doesn’t store, process, or require vendor access to the data,” and allows companies to “enjoy privacy by design” while investigating in minutes.[2] Although the platform necessarily processes data in transit—retrieving events and normalizing them for display—it does not maintain long-term storage of those events, distinguishing itself from SIEMs and data lakes that hold years of logs.[2][11] This ephemeral processing model can reduce the risk surface for data breaches within Query’s environment, though it does shift reliance onto source systems’ security.  

Data residency considerations also apply to connector placement and network paths. For on‑prem systems behind firewalls or DMZs, Query may require reverse proxies or externally reachable endpoints to access data; the MISP connector documentation, for example, notes that if a MISP instance is behind a DMZ, customers must set up a reverse proxy and ensure that the external URL used by Query is internet reachable, or adjust SSL verification accordingly.[20] For cloud platforms like Google SecOps, Query must target appropriate regional endpoints (such as `us` or `eu`) as specified by location names, aligning API traffic with regional tenancy.[18]  

Query’s zero‑ETL, federated approach aligns well with trends toward **minimizing data movement** and respecting data sovereignty. AWS’s description of zero‑ETL emphasizes point-to-point data movement and querying across silos without the need to build ETL pipelines, which is analogous to Query’s use of connectors instead of ingest pipelines.[5][11] By not forcing customers to duplicate data into a new platform, Query reduces infrastructure costs and governance complexity; however, organizations must still consider cross-border query paths, the legal implications of accessing data across regions, and the role of Query as a data processor under regulatory frameworks.  

### 4.4 On-Prem and Hybrid Connectivity Patterns

Given the ubiquity of hybrid environments, Query’s connectors must support both **on‑prem and cloud** systems, often under challenging network constraints.[1][2][11][20] The platform documentation and connector guides provide some insight into how this is accomplished.

For on‑prem systems like MISP servers, Query requires that the relevant APIs be reachable from its execution environment. Similarly, for on‑prem SIEMs or custom log stores, Query’s dynamic connectors rely on endpoints that can be reached via APIs; once reachable, Query introspects schema and maps data to OCSF.[11][18] In hybrid setups where some systems are hosted in public cloud and others on‑prem, Query can connect to both, provided appropriate connectivity is in place. Organizations may choose to deploy Query in a manner that aligns with their connectivity model—either as a cloud-based service with secured inbound access from on‑prem proxies, or as an appliance within their network—but specific deployment modes are not detailed in the available sources.  

For cloud-native services, connectivity is more straightforward: Query uses standard APIs and identity models. Google SecOps integration uses service accounts and project IDs within Google Cloud Platform; Query connects to region-specific endpoints like `us` or `eu` and uses the customer ID to scope queries to the correct tenant.[18] Other cloud connectors, such as those to Amazon S3, Snowflake, BigQuery, or ClickHouse, rely on standard cloud authentication and authorization mechanisms, with Query mapping schemas and executing queries remotely.[11]  

In all cases, Query’s requirement that connectors be able to dispatch searches and retrieve data reinforces the importance of **network architecture** in deployments. Organizations must ensure that Query’s platform can reach source systems securely, that proxies are configured appropriately, and that API credentials are managed safely. This hybrid connectivity is intrinsic to the data mesh model, where data products may reside anywhere but must remain accessible through the mesh layer.[16][11][20]

### 5.2 Federated Detections: Scheduled FSQL Queries and Replay

Beyond AI agents, Query’s platform includes a robust **Federated Detections** capability, which uses FSQL to define detection logic that runs directly across federated security data, decoupled from ingestion.[11][17] Federated detections are expressed as scheduled queries in FSQL with explicit evaluation semantics, including windowed aggregations and rates, grouping, and threshold-based match conditions.[17]  

Detections run as scheduled queries across all connected security data, or a subset selected by the rule author, without centralizing or duplicating data.[11][17] Each detection evaluates data within a defined time window—such as the last five minutes, last hour, or last day—and records the time range evaluated, source coverage, and match counts for each execution.[17] This deterministic evaluation model ensures that detections have clear auditability: analysts can see which connectors were included, what data was analyzed, and how many matches were found.  

High-signal detections often rely on **windowed aggregations and grouping**; for example, a detection might compute the number of failed authentication attempts per user per ten-minute window across multiple identity providers, and trigger when the count exceeds a threshold.[9][11][17] Another detection might compute the rate of endpoint process creations spawning scripts or interpreters per asset and alert on unusual spikes.[9][11][17] FSQL provides constructs to express these aggregations and thresholds in a source-agnostic way, and the federated engine executes them across connectors.  

When a detection’s conditions are met, Query can **terminate evaluation early**, surfacing meaningful activity quickly without scanning an entire window, which is particularly important for high-volume data.[17] The platform generates a **finding** representing the detection match, which includes the execution context and a **replay link**. Replay links rerun the detection logic against the original time window, allowing analysts to explore normalized results across contributing sources and pivot into related entities and events using federated search.[17]  

Detections can be authored directly in FSQL or converted from existing logic in SPL, KQL, or Sigma rules.[11][17] Query supports translation from these formats, reducing the effort required to migrate detections into its federated model and enabling organizations to leverage existing detection libraries.[11][17] Additionally, Query can generate FSQL from natural-language prompts, using AI to assist in authoring detection logic.[17] This hybrid approach allows detection engineers to write rules in whichever format is most convenient while retaining the ability to run them across federated sources.  

By separating detections from ingestion decisions, Query’s Federated Detections architecture creates a more sustainable detection pipeline: rules no longer depend on which data has been ingested into a SIEM, and detection coverage can expand naturally as new data sources are connected.[11][17] This reduces long-term operational friction and helps prevent blind spots as environments evolve.

## 6. Comparative Technical Analysis and Limitations

### 6.1 Query vs Traditional SIEM and ETL Architectures

Traditional SIEM architectures typically revolve around **centralized ingestion and indexing**, where logs and events from multiple sources are collected, transformed via ETL pipelines, normalized, and stored in a central repository for query and detection.[5][11] This model requires extracting data from each tool, transforming it into a common schema, and loading it into the SIEM, often involving complex pipelines, data engineering overhead, and significant storage and compute costs.[5] Detection rules and investigations then run against the indexed data, and any sources not ingested are effectively invisible to the SIEM’s analytic layer.  

Query’s federated security data mesh offers a contrasting approach: it avoids ingestion, pipelines, and central storage, focusing instead on **on‑the‑fly access and normalization** via connectors.[1][11] Rather than building ETL jobs for each source, customers configure connectors with credentials and mappings, and Query federated search uses FSQL and OCSF to retrieve and normalize data as needed for queries and detections.[1][9][11][18] This zero‑ETL model simplifies data architecture and reduces data engineering efforts, while enabling inclusion of new data sources without reprocessing large historical datasets.[5][11]  

There are trade-offs. Centralized SIEMs excel at **historical queries** over long retention periods; they store months or years of logs, allowing analysts to run retrospective queries across large volumes of data. Query, by contrast, relies on the retention and query capabilities of each source system; if an EDR tool or cloud log service retains data for a limited period or imposes query restrictions, Query’s federated layer can only access data within those constraints.[5][11][18] However, Query can access archived and historical data where sources support it, such as data lakes or cold storage buckets, bridging them into investigations.[1][11]  

Another trade-off involves **index-based performance versus federated latency**. SIEM indices can provide fast search over centralized data once ingestion is complete, whereas federated queries must traverse potentially slower APIs and heterogeneous backends. Query mitigates this through parallelization and early termination for detections, but some operations may remain constrained by backend performance.[11][17][18] On the other hand, Query avoids the performance and operational burden of index maintenance and pipeline management, shifting those responsibilities back to source systems.  

From a detection-engineering perspective, Query’s FSQL and OCSF normalization offer significant advantages. Detections can be written once and applied across multiple sources, while translation from SPL, KQL, and Sigma protects investments in existing rules.[11][17] Centralized SIEMs often tie detection logic to their specific query language and ingestion pipelines, making migrations and multi-SIEM deployments difficult. Query’s federated approach decouples detection logic from ingestion choices, improving portability and sustainability.[11][17]  

### 6.2 Query vs Data Mesh and Zero‑ETL Patterns

Within the broader **data mesh** and **zero‑ETL** discourse, Query exemplifies a security-specific implementation of these patterns.[5][11][16] Data mesh principles emphasize domain ownership of data, self-service data infrastructure, and federated computational governance, with data products exposed via standardized interfaces.[16] Query’s connectors and OCSF-based data model align with this philosophy: each connector exposes a domain’s data—such as identity logs, endpoint telemetry, or vulnerability findings—as an OCSF-normalized data product accessible through FSQL.[9][11][18][20]  

Zero‑ETL integrations minimize the need to build ETL pipelines and enable querying across data silos without data movement.[5] Query’s no‑pipelines stance and use of connectors as point-to-point bridges are consistent with zero‑ETL ideology.[1][5][11] Where AWS describes zero‑ETL as facilitating point-to-point data movement without ETL jobs, Query’s design goes further by avoiding movement altogether, instead querying data in place and returning normalized results.[1][5][11]  

However, Query differs from generic data mesh or zero‑ETL platforms in its **deep security specialization** and its use of OCSF as a schema, FSQL as a detection language, and AI agents tuned to SOC workflows.[3][4][9][11][17] Many data mesh implementations focus on analytics and BI use cases; Query’s focus is real-time security operations, detection, and incident response. Its federation layer is optimized for investigation, alert triage, and automation of response actions, rather than for generic data exploration.[2][11][13][17]  

At the same time, Query shares common challenges with data mesh architectures: the need to manage complex connectivity, governance across domains, and heterogeneity in data quality. Its pragmatic approach to OCSF constraints—attempting to maximize data even when sources lack full fields—reflects the messy reality of domain data products.[9][16]  

### 6.3 Query vs Generic Natural-Language Data Access Platforms

Generic natural-language query solutions, such as those offered by Xebia, allow users to ask questions in plain language and have those questions converted into SQL queries or API calls across multiple databases and systems.[7] These tools often federate access to relational databases, NoSQL stores, and APIs through a single conversational layer, hiding query language complexity and returning actionable results, including statistical insights.[7]  

Query shares with these platforms the goal of **simplifying data access through natural language**. Analysts can pose questions in text or natural language, and Query’s AI agents and federated query engine translate these into structured queries over OCSF-normalized data.[1][2][4][11][17] However, Query’s specialization in security operations introduces significant differences.  

First, Query’s schema is dedicated to security telemetry and events, built on OCSF, whereas generic NL query platforms typically operate over arbitrary database schemas.[3][7][9] This allows Query’s LLMs and AI agents to reason using security-specific concepts such as alerts, detections, vulnerabilities, indicators, identities, and assets, supported by a domain-informed knowledge base.[4][9][11] Second, Query integrates detection logic (FSQL detections) and response actions into its query layer, enabling natural-language-driven workflows that not only retrieve data but also trigger detections or orchestrations.[11][13][17]  

Third, Query’s federation spans security tools (SIEM, EDR, identity, threat intel) and business systems relevant to SecOps (ticketing, HR, CRM), whereas generic platforms focus on business analytics. Integration with systems like MISP and Google SecOps further underscores Query’s focus on security telemetry, threat intelligence, and incident response.[18][20]  

Azure AI Search and similar Lucene-based engines provide powerful full-text search capabilities with support for filters, vector search, and query syntax, but they typically assume an indexed corpus managed by the search service.[12][15] Query’s federation avoids central indexing, instead normalizing results from disparate systems on demand.[1][11] While both support filters and search expressions, Query’s OCSF schema and detection semantics differentiate it from pure search platforms.  

### 6.4 Limitations and Open Questions

While Query’s public documentation and marketing materials describe a sophisticated federated architecture, several **technical details remain either abstracted or undisclosed** in available sources, and these gaps represent areas for further investigation or caution.

First, the **formal specification of FSQL**—its grammar, full operator set, and type system—is not fully documented in the accessible materials. Detection examples and capability descriptions suggest SQL-like constructs for aggregation, grouping, and thresholds, but the exact syntax, capabilities for joins, nested queries, or complex temporal patterns are not publicly detailed.[11][17] Organizations adopting FSQL will need to engage with Query’s documentation and possibly training to understand the language fully.  

Second, the **handling of partial connector failures, rate limits, and throttling** is only hinted at through concepts like source coverage metrics and Test Connection actions.[17][18][20] While these features indicate awareness of heterogeneity, the robustness of Query’s error handling, retry strategies, and fallback behaviors under heavy load is not explicitly described. In high-stakes SOC environments, understanding how federated detections behave when key sources are unavailable is crucial.  

Third, **performance characteristics** under large-scale, high-volume workloads, especially when many connectors are involved, are not quantitatively documented. Parallelization and early termination are promising designs, but organizations may need to benchmark Query in their environments to measure latency, throughput, and resource usage compared to SIEM queries or data-lake analytics.[11][17][18]  

Fourth, **security of credential storage and connector communication** is addressed at a high level through statements about read-only access and privacy by design, but implementation specifics—such as encryption schemes, RBAC models for connector management, and auditing of API calls—are not detailed in the sources.[2][11][18][20] Given Query’s role as a control plane with access to multiple sensitive systems, security architecture is paramount.  

Finally, the **interaction between AI agents and human oversight**, including mechanisms for validating and explaining agent decisions, is described conceptually but not deeply elaborated. Query emphasizes that agents are engineered to earn trust and perform verifiable work, but formal guarantees, governance controls, or bias mitigation strategies are not apparent in the public materials.[4][11]  

Despite these open questions, the available evidence supports a view of Query as a technically sophisticated federated security platform that leverages OCSF, a unified query language, and AI to provide a decoupled, zero‑ETL investigations control plane over heterogeneous security data.[1][2][3][4][9][11][17][18][20]  

## Conclusion

Query’s federated security data mesh platform represents a significant rethinking of how security operations can access, query, and correlate data across a fragmented ecosystem of tools and environments. Technically, the platform is built around four central pillars: an OCSF-based Query Data Model that normalizes events from diverse sources; a unified, security-specific query language (FSQL) that encodes detection logic and federated search semantics; a network of static and dynamic connectors that act as read-only API bridges into SIEMs, EDR platforms, identity providers, cloud services, and threat intel systems; and a browser-based investigations control plane that overlays existing security architectures without requiring data centralization or ETL pipelines.[1][2][3][9][11][17][18][20]  

Analysts interact with this ecosystem through a flexible search interface that supports natural language, structured FSQL, and entity-based shortcuts, allowing them to express queries and detections in terms of standardized event classes, attributes, and entities rather than tool-specific fields.[1][2][9][11][20] The federated query engine translates these logical queries into native dialects such as SPL, KQL, or UDM, executes them in parallel via connectors, and returns OCSF-normalized results, enabling cross-source correlation, aggregation, and visualization.[11][17][18][19] Federated detections extend this model to scheduled rules with explicit evaluation windows, thresholds, and replay capabilities, decoupling detection logic from ingestion decisions and providing deterministic, auditable findings.[11][17]  

AI integration, through mission-specific agents and LLM-based reasoning, leverages the data mesh as a unified substrate for advanced workflows like vulnerability intelligence, triage, and threat hunting. These agents translate natural-language questions into orchestrated federated queries, correlate results across EDR, vulnerability scanners, SIEM telemetry, and threat intel, and produce human-readable reports and recommendations.[4][11][17] The synergy between AI and the data mesh—where the mesh provides unified data access and AI agents provide specialized intelligence—illustrates the platform’s potential to address skill shortages and complexity in modern SOCs.[2][4][11]  

From an architectural standpoint, Query’s control-plane design and zero‑ETL philosophy differentiate it from traditional SIEMs and data lakes, centralizing insights rather than data and avoiding the cost and rigidity of ingestion pipelines.[1][5][11][13] Its alignment with data mesh principles and open standards like OCSF positions it well within emerging industry trends toward federated, schema-driven security analytics.[3][9][16] At the same time, organizations considering Query must evaluate practical aspects such as connector deployment, credential management, performance, and error handling, as well as governance around AI agents and federated detections, many of which are only partially documented publicly.[17][18][20]  

Overall, Query offers a technically nuanced and ambitious vision: a unified query and detection layer that can reach “every connected source” and translate a single logical query into actionable insights across a highly heterogeneous security landscape, without forcing data to move or be duplicated.[1][11][17] For security teams grappling with data fragmentation, tool proliferation, and skill constraints, this federated, OCSF-centered approach—with its combination of FSQL, AI agents, and a decoupled investigations control plane—constitutes a compelling alternative to traditional centralized SIEM architectures, and an example of how data mesh and zero‑ETL concepts can be concretely realized in cybersecurity operations.[1][2][5][9][11][16][17]
