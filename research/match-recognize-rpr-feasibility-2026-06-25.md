# SQL Row Pattern Recognition, MATCH_RECOGNIZE, and Apache DataFusion: A Technical Status and Feasibility Report

Row pattern recognition in SQL, embodied in the `MATCH_RECOGNIZE` clause introduced by SQL:2016, provides a declarative mechanism to detect complex sequences of events across ordered rows, closely analogous to applying regular expressions to strings but lifted to sequences of tuples.[1][11] It allows analysts to express patterns such as “A then B then C within a given logical window” using pattern variables, Boolean predicates, partitioning, ordering, and measures, thereby turning what used to require intricate self-joins and window‑function gymnastics into a single composable table operator.[17][13] This report verifies, with as much precision as the available evidence allows, the current standardization, vendor adoption, and implementation status of row pattern recognition, examines the present and likely future of support in Apache DataFusion, and analyzes alternative SQL idioms for expressing kill‑chain/sequence detection when `MATCH_RECOGNIZE` is unavailable.[7][16][19] It further dissects the technical challenges in implementing even a subset of SQL:2016 row pattern recognition semantics—covering grammar, non‑deterministic automata construction, matching semantics, and streaming time‑window constraints—and surveys the Rust ecosystem for potentially reusable components. Because verifiable sources available here and the model’s training cut‑off extend only to late 2024, any statements about the situation in 2025–2026 are clearly marked as inferences or projections rather than confirmed facts; the report distinguishes normative SQL standard behavior from vendor-specific extensions throughout.[11][1]

## 1. Row Pattern Recognition and MATCH_RECOGNIZE in the SQL Standard

### 1.1 Origins and Standardization in SQL:2016

The concept of row pattern recognition (RPR) was formally incorporated into the ISO SQL standard with ISO/IEC 9075:2016, commonly referenced as SQL:2016.[11] Row pattern recognition extends SQL in a way that parallels how regular expressions extend string processing: instead of searching for character patterns inside a single value, RPR searches for patterns in sequences of rows, according to a specified logical partitioning and ordering.[11][1] The standard organizes RPR into features, most notably feature R010, “Row pattern recognition: FROM clause”, and feature R020, “Row pattern recognition: WINDOW clause”, along with the auxiliary feature R030, “Row pattern recognition: full aggregate support”.[11][1] Feature R010 defines the `MATCH_RECOGNIZE` table operator that appears in the `FROM` clause, taking an input table or table expression and producing a virtual table whose rows correspond to matched patterns.[11][17] Feature R020 generalizes the idea to window definitions, allowing row patterns to be used for defining window frames in the `OVER` clause, although as of the information reflected in 2019 commentary, R020 had not been implemented in mainstream systems.[11] Feature R030 deals with the availability of aggregate functions within row patterns, controlling whether constructs like `DISTINCT` and filter clauses are permitted in aggregates used inside RPR expressions.[11][1]

Modern summaries of SQL:2016 confirm that row pattern matching was introduced with these three optional features and identify `MATCH_RECOGNIZE` as the central clause for expressing R010 semantics.[1] The `MATCH_RECOGNIZE` operator must support at least basic aggregates such as `MIN`, `MAX`, `SUM`, `COUNT`, and `AVG`, and with R030 may support the full range of aggregate functions including more advanced ones like `STDDEV_POP`.[1] The operator’s context is similar to that of other table operators defined by the standard, such as `JOIN`, `APPLY`, `PIVOT`, and `UNPIVOT`: it appears after a table reference in the `FROM` clause and yields a virtual table that can be further joined, filtered, or aggregated.[11][13] In Oracle’s SQL documentation, the pattern matching syntax is spelled out with an explicit `row_pattern_recognition_clause ::= MATCH_RECOGNIZE (...)` grammar attached to the `table_reference` production, reinforcing the view that `MATCH_RECOGNIZE` in the `FROM` clause is the canonical instantiation of feature R010.[17]

The standard itself is not directly accessible in the search results provided, but derivative texts and vendor documentation collectively support the claim that SQL:2016 is the first version of the SQL standard to formalize row pattern recognition and to define `MATCH_RECOGNIZE` as the normative way to express it.[11][1][17] These secondary sources consistently describe `MATCH_RECOGNIZE` as part of SQL:2016, sometimes noting that row pattern recognition has since been implemented by several leading relational systems using non‑deterministic finite automata (NFA) under the hood, further suggesting that vendors are adhering broadly to the standard’s semantics even if they layer additional capabilities on top.[2][17]

### 1.2 The Expressive Components of MATCH_RECOGNIZE

The key subclauses that make up `MATCH_RECOGNIZE` in SQL:2016 include `PARTITION BY`, `ORDER BY`, `PATTERN`, `DEFINE`, `MEASURES`, and various options for rows‑per‑match and post‑match skipping, such as `AFTER MATCH SKIP`, along with optional constructs for controlling pattern overlap.[11][17][13] Oracle’s SQL documentation for data warehousing provides a detailed breakdown of the clause and its tasks: it describes how one can logically partition and order the data involved in pattern matching using `PARTITION BY` and `ORDER BY`, define patterns of rows to search for in the `PATTERN` subclause, specify conditions that map rows to pattern variables via `DEFINE`, and define measures—expressions computed over matched patterns—in the `MEASURES` clause.[17] This description aligns closely with the standard‑oriented summary on modern-sql.com, which explains that row pattern matching applies regular expression syntax to pattern variables, and that the fundamental use cases include finding series of consecutive events, recognizing trend reversals or periodic events, and performing top‑N per group queries.[1]

In Trino’s documentation and blog material, the syntax of `MATCH_RECOGNIZE` is presented in a way that mirrors SQL:2016, emphasizing the centrality of `PATTERN` and `DEFINE` as the heart of row pattern recognition.[13][5] A typical Trino syntax sketch shows `MATCH_RECOGNIZE` following a table name in the `FROM` clause, optionally specifying `PARTITION BY` to segment data, `ORDER BY` to sort within each partition, `MEASURES` to define output expressions, rows‑per‑match options, `AFTER MATCH SKIP TO` to control resumption, a `PATTERN (row_pattern)` expression, optional `SUBSET` definitions, and `DEFINE` clauses to bind predicates to pattern variables.[13] Snowflake’s description similarly notes that `MATCH_RECOGNIZE` treats table data as a series of events, with each row representing an event, and then attempts to match sequences of rows against a regex‑like pattern defined in the `PATTERN` clause and interpreted via pattern variables whose conditions are given in `DEFINE`.[4] Flink SQL’s explanation echoes this: it states that `MATCH_RECOGNIZE` allows one to define patterns, match data against those patterns, extract parts of the data that match, and perform actions on matched data, accomplished through the interplay of pattern variables and regular expression syntax inside the `PATTERN` clause and associated conditions in `DEFINE`.[6]

The `MEASURES` subclause is described in Oracle SQL and Oracle CQL documentation as exporting attribute values and computed expressions for events that successfully match the pattern, making them available in the outer `SELECT` list.[3][17][9] Oracle’s CQL documentation notes that `MEASURES` exports attribute values of events that satisfy the `PATTERN` clause regular expression over `DEFINE` clause conditions, while the SQL data warehouse documentation explains that measures are expressions that can be used elsewhere in the query for analysis.[3][17] These measures can be defined in terms of pattern variables, aggregates over portions of the matched sequence, or navigation functions like FIRST, LAST, and similar constructs, and they play a central role in summarizing or annotating detected patterns.

Row pattern partitioning and ordering are treated as essential for correct semantics: both Oracle and SQLPerformance’s article stress that RPR supports partitioning and ordering analogous to window functions, making it natural to look for pattern matches within partitions (such as per customer, per account, or per device), according to defined ordering (such as by timestamp or sequence number).[11][17] This partitioning has two roles: it defines independent “pattern matching universes” and ensures that the regular expression semantics interpret the row sequence in a deterministic order. Without ordering, the notion of “A then B then C” would be ill-defined; `ORDER BY` inside `MATCH_RECOGNIZE` resolves this by establishing a well‑ordered row sequence per partition, much as `ORDER BY` within window functions defines row ordering for window frame evaluation.[11][17]

The `AFTER MATCH SKIP` clause, described explicitly in the Microsoft research paper as part of the `MATCH_RECOGNIZE` semantics, determines where pattern recognition resumes after a successful non‑empty match.[2] For example, options such as `AFTER MATCH SKIP PAST LAST ROW` or `AFTER MATCH SKIP TO NEXT ROW` control whether subsequent pattern searches begin after the last row of the previous match or after the first row of that match (enabling overlapping matches).[2][17] Flink SQL examples show similar semantics, using `AFTER MATCH SKIP PAST LAST ROW` to express that pattern recognition should continue from the row after the last event in a match, thereby avoiding overlapping detection in some scenarios.[6] Oracle CQL documentation complements this with an `ALL MATCHES` clause, allowing explicit control over whether overlapping patterns are detected or suppressed; omitting `ALL MATCHES` configures the system to detect only one pattern per relevant segment of the stream, while including it enables detection of multiple overlapping matches.[9]

The standard also interacts with aggregate functions via feature R030, which controls whether distinct aggregates and filter clauses are permitted within row patterns.[11][1] Modern-sql.com explains that SQL:2016 introduced row pattern matching with optional feature R030 to support all aggregate functions for row patterns, including advanced ones such as population standard deviation.[1] Without R030, only basic aggregates may be allowed in `MATCH_RECOGNIZE` contexts; with R030, the full range of aggregate semantics applies, thereby increasing the expressive power of `MEASURES` and pattern‑dependent calculations.

### 1.3 Time Windows, WITHIN, and Non-Event Detection

The question of whether a dedicated `WITHIN` clause exists in the SQL standard for time‑window constraints on patterns is subtle. The SQL:2016 feature descriptions and general references to `MATCH_RECOGNIZE` focus on partitions, ordering, pattern variables, and measures, and do not mention a specific `WITHIN` subclause by name in the context of R010 or R020.[11][1] Oracle’s SQL data warehouse documentation outlines the syntax of `row_pattern_recognition_clause` with `MATCH_RECOGNIZE` and lists `PARTITION BY`, `ORDER BY`, `MEASURES`, rows‑per‑match options, `AFTER MATCH SKIP`, and other elements, but again does not explicitly introduce a `WITHIN` keyword as part of the standard syntax for pattern timing.[17] Instead, temporal constraints are typically expressed inside the `DEFINE` clause as conditions over timestamp or sequence columns, such as requiring that the difference between two events’ timestamps be less than a given interval, or that no intervening events occur in a certain time frame.[17][3]

Oracle’s CQL (Continuous Query Language) documentation, which targets complex event processing over streams rather than static tables, introduces a `DURATION` clause that is explicitly described as an optional clause used when writing queries involving non‑event detection.[9] Non‑event detection is defined as the detection of a situation where a certain event that should have occurred in a particular time limit does not occur, and the `DURATION` clause ensures that a match is reported only when the regular expression in the `PATTERN` clause is matched completely and no other event or input arrives until the specified duration expires.[9] This behavior effectively implements a form of time window or timeout semantics, but it is clearly presented as part of Oracle CQL’s pattern recognition construct rather than as a core SQL:2016 `MATCH_RECOGNIZE` feature.[3][9] Thus, while time windows and “within X minutes” constraints can be expressed in SQL:2016 row pattern recognition using `DEFINE` predicates that compare timestamps or sequence numbers, the standardized syntax does not appear to define a dedicated `WITHIN` keyword akin to what some specialized CEP languages or vendor extensions provide; instead, vendor dialects such as Oracle CQL’s `DURATION` clause and streaming systems’ “WITHIN” or “INTERVAL” constructs fill this role.[9][6]

Flink SQL’s examples of `MATCH_RECOGNIZE` for streaming data show patterns like sequences of subscription events representing a downgrade, using partitioning by user and ordering by event time, combined with conditions in `DEFINE` that refer to event attributes and times.[6] While the snippet provided does not show a standalone `WITHIN` clause, it implies that time constraints would be handled by expressing conditions over event timestamps in the `DEFINE` predicates or by filtering the underlying stream via windowing before applying `MATCH_RECOGNIZE`.[6] Azure Stream Analytics’ documentation similarly introduces `MATCH_RECOGNIZE` as a means to define patterns and compute values from matched events in a streaming context, without explicitly mentioning `WITHIN` but suggesting that temporal constraints are managed through event‑time columns and stream windows in the overall query.[18] These examples collectively support the view that in standardized SQL and many vendor implementations, temporal constraints for CEP scenarios are expressed via predicates and windowing rather than a dedicated `WITHIN` subclause within `MATCH_RECOGNIZE` itself.

### 1.4 MATCH_RECOGNIZE as the Canonical SQL Mechanism for CEP

Given its formalization in SQL:2016 and its adoption by multiple vendors, `MATCH_RECOGNIZE` is widely regarded as the canonical way to express complex event processing and sequence detection directly in SQL.[11][1][17] The modern-sql.com description explicitly mentions that pattern matching over multiple rows, via `MATCH_RECOGNIZE`, is useful for finding series of consecutive events, patterns like trend reversal and periodicity, and top‑N per group queries, all of which map naturally onto CEP scenarios such as detecting stock price trends, user behavior sequences, or fraud patterns.[1] SQLPerformance’s discussion states that with row pattern recognition you use regular expressions to identify patterns in a sequence of rows, and for each pattern match you may return either a summary row or detailed rows with computed measures, echoing the typical CEP use cases of summarizing detected sequences or tagging individual events within them.[11] Oracle’s data warehousing documentation illustrates patterns such as stock price trend detection and various sequence patterns using `MATCH_RECOGNIZE`, emphasizing that starting with Oracle Database 12c, this capability is available in native SQL that executes efficiently, avoiding the need to export data to external programs for pattern recognition.[17]

The Microsoft research paper motivates the inclusion of `MATCH_RECOGNIZE` in the SQL standard specifically as a response to the increasing importance of row pattern recognition tasks in domains like fraud detection, user analytics, and operational monitoring.[2] It notes that `MATCH_RECOGNIZE` was added to the official SQL standard to handle such tasks declaratively, and that several leading relational systems—Oracle, Apache Flink, Azure Streaming Analytics, Snowflake, and Trino—have announced support for it.[2][4][6][13][18] This is consistent with the broad industry trend of moving CEP functionality into relational engines via `MATCH_RECOGNIZE`, rather than relying exclusively on external event processing systems.

It is, however, important to distinguish “canonical within SQL” from “exclusive in practice”. There are long‑standing idioms for expressing sequence detection using self‑joins, window functions, recursive common table expressions, and conditional aggregation, which remain common in engines that do not support `MATCH_RECOGNIZE`.[11][19] SQLPerformance’s article, for instance, contextualizes row pattern recognition as a profound new concept compared to traditional window functions, but it implicitly assumes that before RPR, analysts used such lower‑level constructs to approximate pattern detection.[11] Materialize’s documentation on “Idiomatic Materialize SQL” for lead values recommends self‑joins with equality conditions on order fields to access the next row’s value, effectively implementing a simple notion of pattern detection between adjacent rows without using `MATCH_RECOGNIZE`.[19] These alternatives mean that while `MATCH_RECOGNIZE` is the standardized, expressive, and declarative way to perform CEP in SQL, it is not the only way; in engines lacking RPR support, these idioms constitute the de facto mechanisms for expressing patterns, albeit with greater complexity and potential for subtle errors.

From a standards perspective, therefore, the verified claim is that `MATCH_RECOGNIZE` is indeed a standardized SQL feature introduced in SQL:2016 under the umbrella of row pattern recognition, with well‑defined components `PATTERN`, `DEFINE`, `PARTITION BY`, `ORDER BY`, `MEASURES`, and post‑match control via `AFTER MATCH SKIP`, and that it is designed specifically to support CEP‑style sequence detection.[11][1][17][2] The claim that it is the canonical SQL way to express patterns like “A then B then C within a time window” is supported by the standard’s focus and vendor documentation, although practical SQL usage still includes alternative idioms where RPR is unavailable.[11][19]

## 2. Apache DataFusion and the Status of Row Pattern Recognition

### 2.1 Overview of DataFusion’s Capabilities and Architecture

Apache DataFusion is a Rust‑based query engine that provides SQL and DataFrame APIs, focusing on high performance and extensibility.[16] Its documentation emphasizes that “out of the box” DataFusion offers SQL and DataFrame APIs, excellent performance, built‑in support for numerous data types and functions, and mechanisms for extension such as custom scalar functions, aggregate functions, and logical plan nodes.[16] The engine is used as a core for analytical systems and is designed to be embedded, making it suitable for implementing relational query processing in Rust applications or in higher‑level frameworks built on Rust.[16] The DataFusion SQL engine delegates parsing to an external crate, `datafusion-sqlparser-rs`, which implements an ANSI/ISO SQL lexer and parser and supports multiple dialects.[15] This architecture separates SQL parsing from logical and physical planning, which in principle facilitates adding new SQL constructs by extending the parser and then mapping them to new logical operators or rewrites within DataFusion’s planner.[16][15]

Because DataFusion is highly extensible, the idea of adding a `MATCH_RECOGNIZE` operator or a row pattern recognition feature fits naturally into its architecture at a conceptual level: one could imagine extending the parser to recognize the clause, adding a new logical plan node representing `MATCH_RECOGNIZE`, and implementing a physical operator that performs pattern matching across partitions and ordered rows.[16] However, as the DataFusion community discussion reveals, the practical complexity of implementing full SQL:2016 RPR semantics is considerable, and this has influenced the appetite for integrating such features into the engine’s core.[7]

### 2.2 Parser Support for MATCH_RECOGNIZE and DataFusion-SQLParser-RS

The `datafusion-sqlparser-rs` crate is described as a lexer and parser for SQL that conforms with the ANSI/ISO SQL standard and various dialects, serving as the foundation for SQL parsing in DataFusion and related ecosystems.[15] The crate’s capabilities include parsing complex SQL constructs, and according to the issue report in the DataFusion GitHub repository, it can parse SQL queries that contain `MATCH_RECOGNIZE` clauses.[7] The issue notes that `datafusion-sqlparser-rs` already supports parsing `MATCH_RECOGNIZE` syntax, suggesting that the grammar for this clause has been encoded in the parser, possibly by aligning with SQL:2016 or vendor dialects like Oracle and Trino.[7][15] This means that from a syntax perspective, DataFusion’s parsing layer is ahead of its execution layer: it can recognize and build parse trees for `MATCH_RECOGNIZE` queries, but the core query engine does not yet provide logical or physical operators to execute them.

The existence of parser support implies that implementing a subset of `MATCH_RECOGNIZE` in DataFusion would not require changes to the SQL grammar, at least for the basic constructs; instead, it would require mapping parsed constructs into sensible logical plans.[7][15] The parser can distinguish `PATTERN`, `DEFINE`, `PARTITION BY`, `ORDER BY`, `MEASURES`, and other subclauses, enabling the planner to inspect them and generate appropriate relational algebra plus pattern matching operators. However, without such planner and executor support, parsed `MATCH_RECOGNIZE` queries would either result in errors during planning or be ignored, depending on how DataFusion handles unsupported constructs at present.[16][7] The parser’s readiness thus reduces one barrier—syntax recognition—but leaves the semantics and execution challenges untouched.

## 3. Vendor Adoption of MATCH_RECOGNIZE and Row Pattern Recognition

### 3.1 Oracle Database and SQL Row Pattern Matching

Oracle Database is widely recognized as the earliest major relational engine to implement feature R010 of SQL:2016, providing `MATCH_RECOGNIZE` in the `FROM` clause for pattern matching in data warehouses.[11][17] The Oracle data warehouse documentation explains that beginning in Oracle Database 12c, users can perform pattern matching in SQL using the `MATCH_RECOGNIZE` clause, which enables tasks such as logically partitioning and ordering data for pattern matching, defining row patterns using regular expression syntax applied to pattern variables, specifying conditions for mapping rows to pattern variables via `DEFINE`, and defining measures using `MEASURES`.[17] It notes that `MATCH_RECOGNIZE` generates output either as one summary row per match (`ONE ROW PER MATCH`) or as detailed rows (`ALL ROWS PER MATCH`), and that the `AFTER MATCH SKIP` clause determines where pattern matching resumes within a partition after a non‑empty match is found.[17]

Oracle’s documentation also presents the syntax of pattern matching in SQL, showing how `MATCH_RECOGNIZE` fits into the `table_reference` grammar, and discussing options such as `PER MATCH` (summary rows) versus `ALL ROWS PER MATCH` (expanded output).[17] The semantics described align closely with SQL:2016 R010, suggesting that Oracle’s implementation largely conforms to the standard, albeit with some extensions. In particular, Oracle supports navigation functions within `MEASURES` and pattern definitions and may offer vendor‑specific features beyond the core standard; however, the fundamental constructs `PARTITION BY`, `ORDER BY`, `PATTERN`, `DEFINE`, `MEASURES`, and `AFTER MATCH SKIP` behave as described in the SQL standard and in derivative expositions like SQLPerformance’s article.[11][17]

Oracle CQL, a continuous query language for complex event processing, also includes a `MATCH_RECOGNIZE` construct with similar subclauses: it performs pattern recognition in CQL queries, exporting measures for events that satisfy patterns defined using `PATTERN` and `DEFINE`, and always producing an output stream.[3][9] The CQL documentation specifies the principal subclauses as `MEASURES`, `PATTERN`, and `DEFINE`, describes how correlation variables (pattern variables) identify events, and explains that a sequence of consecutive events satisfying the defined conditions constitutes a pattern.[3][9] The CQL implementation also introduces `ALL MATCHES` to control overlapping pattern detection and a `DURATION` clause for non‑event detection within time windows, which are vendor-specific extensions geared toward streaming CEP scenarios.[9] These extensions illustrate how Oracle builds on the standard’s `MATCH_RECOGNIZE` semantics to support streaming and temporal logic, reinforcing its position as a leading adopter of RPR.

SQLPerformance’s 2019 article corroborates Oracle’s pioneering role, stating that “so far, the only platform I know of that implemented feature R010 is Oracle” and noting that no platform had implemented feature R020 at that time.[11] While this statement predates adoption by other engines, it confirms that Oracle’s implementation was early and aligned with the standard’s R010 feature. Combined with Oracle’s documentation, this provides strong evidence that Oracle Database supports `MATCH_RECOGNIZE` in production, both for static tables and for complex event processing in CQL.[17][3][9][11]

### 3.2 Snowflake’s MATCH_RECOGNIZE Implementation

Snowflake’s documentation and blog posts explicitly state that `MATCH_RECOGNIZE` is available for pattern matching across rows within a table.[4] A guide entitled “Pattern in Snowflake: Comprehensive guide to Match Recognize” explains that `MATCH_RECOGNIZE` allows matching patterns across data rows in Snowflake, enabling identification of valuable insights and trends buried in large volumes of data.[4] It describes the clause as treating table data as a series of events, with each row representing an event, and attempting to match sequences of rows to a defined regex‑like pattern.[4] The guide lists the key components of `MATCH_RECOGNIZE` as `PARTITION BY` to split rows into partitions, `ORDER BY` to sort rows within each partition, `PATTERN` to define the regex‑like pattern using pattern variables, `DEFINE` to specify conditions for those pattern variables, and `MEASURES` to define expressions that return information about matches such as match number and row counts.[4]

This description corresponds closely to SQL:2016 semantics and to the general understanding of `MATCH_RECOGNIZE` as a row pattern recognition clause.[1][11] Snowflake’s implementation thus appears to be a vendor realization of feature R010, adapted to its cloud data warehouse environment. The guide also recommends tips for using `MATCH_RECOGNIZE`, such as choosing optimal partitioning, aligning sort order with pattern logic, using descriptive pattern variable names, crafting `DEFINE` carefully, and specifying `MEASURES` to output necessary match data, implying that the feature is sufficiently mature and widely used to warrant best‑practice guidance.[4] This strongly supports the claim that Snowflake has production support for `MATCH_RECOGNIZE` today.

### 3.3 Trino’s Row Pattern Recognition and MATCH_RECOGNIZE

Trino, a distributed SQL query engine descended from Presto, has announced support for row pattern recognition and `MATCH_RECOGNIZE` since version 356.[5][13] Trino’s blog and episode materials describe the feature as allowing users to define patterns using well‑known regular expression syntax and match them to sets of rows.[5][13] Upon finding a matching row sequence, `MATCH_RECOGNIZE` can retrieve detailed or summary information about the match, which can then be processed by subsequent parts of the query.[5][13] The documentation emphasizes that this capability represents a “new level of what a pure SQL statement can do”, highlighting its power for analyzing trends.[5][13]

Technically, Trino implements `MATCH_RECOGNIZE` as part of the `FROM` clause, consistent with SQL:2016 R010.[13] The syntax sketch shows the general structure:

```sql
SELECT ...
FROM some_table
MATCH_RECOGNIZE (
    PARTITION BY ...
    ORDER BY ...
    MEASURES ...
    ONE ROW PER MATCH | ALL ROWS PER MATCH
    AFTER MATCH SKIP TO ...
    PATTERN (row_pattern)
    SUBSET ...
    DEFINE ...
)
```

This code block paraphrases the documented syntax and illustrates how Trino aligns with the standard by supporting `PARTITION BY`, `ORDER BY`, `MEASURES`, rows‑per‑match options, `AFTER MATCH SKIP`, `PATTERN`, optional `SUBSET` definitions, and `DEFINE` clauses.[13] Trino’s blog notes that `PATTERN` and `DEFINE` are the heart of row pattern recognition, serving as the declarative mechanism for specifying patterns and their associated predicates.[13] Episode notes further mention that “running semantics” are the default in `DEFINE` and `MEASURES`, referring to the semantics of evaluating predicates and measures over partial matches as the pattern progresses.[5]

The Microsoft research paper reports benchmark results for applying a join‑based rewrite of `MATCH_RECOGNIZE` queries in Trino, indicating that Trino’s native implementation was used as a baseline and that their approach achieved median speedups of 5.4× on Trino with ORC files on Hive.[2] This confirms that Trino’s `MATCH_RECOGNIZE` implementation adheres sufficiently to the standard semantics that it can be targeted by formal rewrites and used in performance experiments. Together, these sources verify that Trino supports `MATCH_RECOGNIZE` in production for row pattern recognition over tables, with semantics largely matching SQL:2016 feature R010.[13][5][2]

### 3.4 Flink SQL and Streaming CEP with MATCH_RECOGNIZE

## 4. Alternatives to MATCH_RECOGNIZE for Sequence and Kill-Chain Detection

### 4.1 Self-Joins and Equality-Based Row Linking

In engines that lack native `MATCH_RECOGNIZE`, sequence detection is commonly implemented using self‑joins over ordered data. Materialize’s “Lead over” idiomatic SQL documentation provides a concrete example of this style: it suggests using a self join with an equality condition on the order field to access the next row’s field value when rows are ordered by a field that increases in regular intervals.[19] For instance, one might join a table `t1` to `t2` with a condition like `t1.order_field = t2.order_field - 1` to retrieve the “next” row, or `t1.order_field = t2.order_field * 2` to model specific interval relationships.[19] In the case of a left join, the query can include the last row, returning `NULL` as the lead value where no successor exists.[19]

This technique generalizes to sequence detection by chaining multiple self‑joins: to detect patterns like “A then B then C”, one can join three copies of the table on conditions linking their order fields, such as `tA.order_field < tB.order_field < tC.order_field`, and applying predicates to each copy to test whether row `tA` satisfies condition A, `tB` satisfies B, and `tC` satisfies C.[19] More complex patterns may require additional joins, and overlapping matches can be handled by carefully defining join conditions to allow multiple matches per source row. However, as patterns become more intricate—introducing repetition, optional segments, or variable lengths—the number and complexity of joins increase rapidly, making queries harder to write, read, and maintain.

From a correctness standpoint, self‑join-based sequence detection must be carefully designed to avoid logical errors such as inadvertently skipping rows, misordering events, or miscounting overlapping patterns. For example, if the ordering column is not unique, joins based on equality or inequality may match multiple rows for each event, creating spurious patterns unless additional constraints are added.[19] Similarly, if the join conditions do not enforce strict ordering or uniqueness, sequences may be misidentified. `MATCH_RECOGNIZE` avoids many of these pitfalls by providing built‑in semantics for partitioning, ordering, and pattern matching, but self‑joins remain the only option in engines without RPR.

Performance-wise, self‑joins can be expensive, especially for long patterns. Each joined copy of the table effectively multiplies the input size in the intermediate result, leading to large join graphs and potential blow‑ups in intermediate cardinality. Even with indexes or ordered data, these joins may involve substantial compute and memory overhead. While query optimizers can sometimes recognize specific patterns and optimize them, they rarely have the global pattern awareness that an NFA-based `MATCH_RECOGNIZE` implementation would provide. The Microsoft research paper’s motivation for rewriting `MATCH_RECOGNIZE` to join-based queries acknowledges that pure join-based implementations can be optimized, but also demonstrates the need for careful design to avoid performance degradation.[2] In general, self‑joins are flexible but error‑prone, and their performance depends heavily on data characteristics and optimizer sophistication.

### 4.2 Window Functions: LAG, LEAD, and Beyond

Window functions such as `LAG` and `LEAD` provide another mechanism for pattern recognition across rows, especially for simple adjacency-based patterns. SQL window functions support partitioning and ordering similar to `MATCH_RECOGNIZE`, and by using `LAG`, one can compare a row’s attributes to those of preceding rows, while `LEAD` enables comparisons to subsequent rows.[11][19] For instance, to detect a simple pattern where a value increases from one row to the next, one might compute `LEAD(value)` over an ordered partition and filter for rows where `LEAD(value) > value`. Materialize’s documentation explicitly suggests this pattern for accessing the lead value when the order field increases regularly, and points out that window functions exclude the last row since it lacks a successor.[19]

Window functions can be combined to simulate more complex patterns: for example, one can compute multiple lags and leads to access a small window around each row and use Boolean logic in the `WHERE` clause to test for patterns like “A followed by B then C”. However, as patterns become longer and more complex, the number of window functions required grows, and the resulting expressions become unwieldy. Unlike `MATCH_RECOGNIZE`, window functions do not inherently support variable-length patterns or quantifiers such as `*`, `+`, or `{m,n}`; they are best suited for fixed-length patterns involving a small number of adjacent rows.[11]

Correctness is a challenge when using window functions for kill‑chain detection. Ensuring that comparisons are made in the correct partitions and order, avoiding off‑by‑one errors, and handling edge cases such as missing rows or duplicates require careful attention. Moreover, overlapping patterns may be difficult to express: window functions are typically row‑centric, focusing on relationships around a single row, whereas CEP often requires reasoning about sequences that span many rows and may overlap in various ways. `MATCH_RECOGNIZE` handles overlapping matches via options like `AFTER MATCH SKIP TO NEXT ROW` or `AFTER MATCH SKIP PAST LAST ROW`, whereas window-function-based approaches must emulate overlap semantics manually, often with complex logic.[2][17]

Performance-wise, window functions can be efficient when properly implemented, especially for simple patterns. Many engines optimize window functions using partitioned and ordered scans, minimizing overhead. However, repeated window functions with large frames or many partition keys can become expensive. Additionally, when window functions are used to approximate complex patterns not well suited to their semantics, the resulting queries may perform poorly, and optimizers might struggle to recognize opportunities for simplification. Compared to a native NFA‑based `MATCH_RECOGNIZE` operator, window functions typically lack the specialized optimizations tailored to pattern detection.

### 4.3 Recursive Common Table Expressions

Recursive common table expressions (CTEs) provide a way to traverse sequences step by step, constructing paths through events that satisfy certain conditions. In pattern detection, one might use a recursive CTE to start from an initial event satisfying condition A, then recursively join to subsequent events satisfying condition B, then C, and so on, building up sequences until some termination condition is met. This approach can, in principle, implement arbitrary patterns, including variable-length paths, loops, and conditional transitions.

However, recursive CTEs are more akin to graph traversal than to regular expression matching. They require users to explicitly write recursion logic, manage base and recursive cases, and maintain state in the CTE rows, such as cumulative conditions or path length. This manual state management is error‑prone: a mis-specified recursion step can lead to infinite loops, duplicate paths, or missed sequences. Moreover, expressing overlapping patterns and controlling match resumption semantics analogous to `AFTER MATCH SKIP` becomes complicated in recursive form.

Performance is also a concern. Recursive CTEs typically execute in iterative fashion, materializing intermediate results at each recursion level. For large data sets or complex patterns, this can result in substantial computational overhead. Many SQL engines impose limits on recursion depth to avoid runaway queries, which may interfere with pattern detection if sequences are long. While advanced optimizers can sometimes transform recursive CTEs into more efficient plans, general recursion is harder to optimize than specialized pattern operators like `MATCH_RECOGNIZE` that have well-understood automata semantics.

Consequently, while recursive CTEs provide expressive power for sequence detection, they are considered more of a workaround than a canonical mechanism, especially compared to standardized row pattern recognition.

### 4.4 Gap-and-Island Patterns and Conditional Aggregation

Gap-and-island techniques are widely used to detect contiguous ranges or segments in ordered data, such as consecutive days of events or uninterrupted sequences of values. They typically involve computing grouping keys based on differences between row indices and values, then aggregating over groups to identify “islands” of consecutive rows. Conditional aggregation further allows summarizing patterns, for example counting how many events of type A occur before a type B event within a partition.

For CEP and kill‑chain detection, gap-and-island methods can identify contiguous runs of events that satisfy certain conditions, but they are less suited to expressing complex patterns with multiple event types and sequence constraints. For instance, detecting a pattern like A then B then C may be simulated by computing groupings where events A and C appear at boundaries, but expressing intermediate event B’s role and timing requires more elaborate logic. Conditional aggregation can count occurrences and enforce threshold conditions, but it typically operates per group rather than per sequence, making overlapping patterns hard to model.

Performance of gap-and-island queries can be reasonable, as they often involve single passes over ordered data combined with grouping and aggregation. Nonetheless, they lack the direct semantics of regular-expression-like pattern matching provided by `MATCH_RECOGNIZE`. Correctness is heavily dependent on the specific grouping logic chosen, and subtle variations in event timing or ordering can drastically alter results.

### 4.5 Correctness and Performance Limitations vs Native Row Pattern Recognition

Comparing these alternatives to native row pattern recognition, several limitations emerge. First, correctness is harder to guarantee when patterns are encoded via self‑joins, window functions, recursion, or ad hoc grouping. Each technique requires careful handling of partitioning, ordering, overlapping matches, and edge cases. `MATCH_RECOGNIZE`, by contrast, provides a unified framework where pattern variables, regular-expression syntax, and built‑in semantics for overlapping matches and match resumption (`AFTER MATCH SKIP`) reduce the likelihood of subtle bugs.[2][17][1]

Second, performance is less predictable and often inferior. The Microsoft research paper demonstrates that join-based rewrites of `MATCH_RECOGNIZE` semantics can be made efficient on certain engines, but it also emphasizes the complexity of devising such rewrites and the need for specialized optimization rules.[2] In the absence of such rules, self‑joins and recursive CTEs may generate large intermediate results and require multiple passes over data. Window functions and gap-and-island patterns may be efficient for simple cases but struggle with more complex patterns. Native RPR implementations, using NFA or DFA automata, operate by scanning partitioned and ordered data once and applying automaton transitions, achieving linear or near‑linear complexity in many cases.[2][1]

Third, maintainability and expressiveness favor `MATCH_RECOGNIZE`. Analysts can write patterns using intuitive constructs like `PATTERN (A B+ C*)` and `DEFINE A AS condition_A, B AS condition_B, C AS condition_C`, whereas equivalent self‑join or window-function queries may require dozens of lines of SQL with nested conditions and multiple aliases.[4][13][6] Vendor documentation for Oracle, Snowflake, and Trino highlights this readability as a key advantage, noting that `MATCH_RECOGNIZE` statements are easier to read and maintain than complex join-based queries.[17][4][13]

Finally, some semantics, such as overlapping match control (via `ALL MATCHES` or `AFTER MATCH SKIP`) and non‑event detection (via `DURATION` or time-window predicates), are not naturally expressed in traditional SQL constructs without substantial effort.[9][2] Native RPR offers these semantics as first‑class features. Therefore, while alternatives exist and are widely used in engines lacking `MATCH_RECOGNIZE`, they are best understood as workarounds rather than substitutes, with clear correctness and performance limitations compared to native row pattern recognition.

## 5. Implementing MATCH_RECOGNIZE on a Query Engine Like DataFusion

### 5.1 SQL:2016 Grammar and Subset Implementability

The SQL:2016 grammar for row pattern recognition, as reflected in Oracle’s syntax and Trino’s documentation, is reasonably well specified.[11][17][13] It defines the `MATCH_RECOGNIZE` clause as a table operator in the `FROM` clause with a sequence of subclauses, including:

- Optional `PARTITION BY` and `ORDER BY` to define logical partitions and row ordering.
- A `PATTERN (row_pattern)` clause to specify regular-expression-like patterns over pattern variables.
- A `DEFINE` clause to associate Boolean predicates with pattern variables.
- A `MEASURES` clause to define expressions available in the outer `SELECT`.
- Options for rows per match (`ONE ROW PER MATCH` vs `ALL ROWS PER MATCH`).
- An `AFTER MATCH SKIP` clause to control where pattern matching resumes after a match.
- Optional constructs such as `SUBSET` definitions and overlapping match controls like `ALL MATCHES` in vendor dialects.[17][9][13]

Modern-sql.com and SQLPerformance’s article further clarify the semantics, describing how patterns are interpreted as regular expressions and how aggregates and measures interact with matched subsequences.[1][11] This makes it feasible to implement a subset of `MATCH_RECOGNIZE` reliably by focusing on core constructs such as `PARTITION BY`, `ORDER BY`, `PATTERN`, `DEFINE`, `MEASURES`, and a limited set of `AFTER MATCH SKIP` options. Vendor documentation suggests that many practical use cases rely primarily on these core elements, with advanced features like `SUBSET` and non‑event detection being used less frequently.[17][3][9]

Given that `datafusion-sqlparser-rs` already parses `MATCH_RECOGNIZE`, the grammar for the clause is available in Rust code.[7][15] Implementing a subset in DataFusion would involve mapping parsed syntax trees into a logical plan operator representing row pattern recognition, with fields capturing partitioning columns, ordering columns, pattern definitions, variable conditions (DEFINE), measures, and post‑match skip semantics. The planner would then need to infer the necessary input ordering and partitioning, design a physical execution strategy, and integrate the operator into DataFusion’s optimizer.[16][7]

### 5.2 NFA Construction from PATTERN and Matching Semantics

The core challenge in implementing `MATCH_RECOGNIZE` lies in constructing and executing non‑deterministic finite automata (NFAs) derived from the `PATTERN` clause.[2][1] The `PATTERN` expression is a regular expression over pattern variables, each of which represents a row that satisfies a predicate defined in `DEFINE`.[11][13] For example, a pattern `PATTERN (A B+ C*)` indicates a sequence where one A event is followed by one or more B events and zero or more C events, all in order; the semantics treat each variable as a token type, and the pattern defines allowable sequences of tokens.[1][17] To execute such patterns, engines typically build NFAs where states represent positions in the pattern, transitions correspond to consuming events of particular variable types, and epsilon transitions handle constructs like optional segments and repetitions.[2]

The Microsoft research paper notes that since SQL:2016’s introduction of `MATCH_RECOGNIZE`, several leading relational systems have implemented row pattern recognition using NFAs.[2] These NFAs must handle regular-expression features such as concatenation, alternation, Kleene star (`*`), plus (`+`), optional segments (`?`), and bounded repetitions (`{m,n}`), all over pattern variables that correspond to rows satisfying `DEFINE` predicates.[2][1] They must also support greedy vs reluctant quantifiers, ensuring that patterns consume as many or as few rows as semantics dictate. For instance, a greedy `B*` will attempt to consume as many B events as possible, backtracking only when necessary to satisfy subsequent pattern elements, whereas a reluctant `B*?` (if supported) would consume as few as needed.[2] Implementing such behavior requires careful design of NFA or augmented automata, with backtracking or advanced control mechanisms.

Constructing NFAs from `PATTERN` grammars is a well-understood problem in theory but must be adapted to SQL semantics. The engine must consider pattern variables as classes of rows, not individual tokens, and must integrate `DEFINE` predicates into the automaton’s matching logic. This means that each potential transition in the NFA must be guarded by evaluating the predicate associated with the target pattern variable on the current row; if the predicate fails, the transition is invalid.[3][6][17] Efficiently evaluating these predicates while scanning large data sets is non-trivial, especially when predicates involve aggregates or navigation functions.

### 5.3 Backtracking, Greedy/Reluctant Quantifiers, and Overlapping Matches

Backtracking arises naturally in regular-expression matching when multiple possible paths through the automaton exist and initial choices must be revised to satisfy the overall pattern. SQL row pattern recognition inherits this behavior: patterns with alternation (using `|`) or with quantifiers that can match varying numbers of events require the engine to explore multiple matching possibilities. To manage complexity, many engines rely on NFAs that allow multiple active states, representing all possible ways the pattern could match the sequence at each step, thereby avoiding explicit backtracking; this is standard in NFA-based regex engines.[2][1] However, implementing this in a row-wise context with additional semantics like `AFTER MATCH SKIP` and measures still requires careful management of state and match boundaries.

Greedy and reluctant quantifiers add complexity. While the SQL standard’s exact semantics for greediness may vary by implementation, vendor documentation often indicates default greedy behavior for quantifiers, meaning that patterns like `B*` are interpreted as matching as many B events as possible before letting the pattern proceed.[17][3][6] Reluctant quantifiers, if supported, require the engine to prefer the minimal number of events, forcing more complex automaton behavior. Overlapping matches further complicate matters: if `AFTER MATCH SKIP TO NEXT ROW` is used, the engine must allow multiple matches that share rows, while `AFTER MATCH SKIP PAST LAST ROW` enforces non-overlapping matches.[2][17][9] Oracle CQL’s `ALL MATCHES` clause explicitly configures whether overlapping patterns are detected, adding another dimension to match management.[9]

Implementing these semantics in DataFusion would require designing automaton execution that can handle multiple active matches, controlling how matches are finalized and how matching resumes per partition. The engine must track partial matches, manage multiple starting points as new pattern matches begin, and ensure that matches are emitted according to rows-per-match settings and measures. For overlapping matches, the automaton must allow new matches to start before previous ones are fully consumed, whereas for non-overlapping matches, it must suppress overlapping starts. These behaviors must be integrated with DataFusion’s stream or batch execution, partitioning, and ordering semantics.[16][7]

### 5.4 DEFINE Predicate Evaluation and Running vs Final Semantics

The `DEFINE` clause associates conditions with pattern variables, specifying the predicates that determine whether a row can be labeled with a particular variable.[3][17][13] For example, one might define `A` as rows where `event_type = 'login'`, `B` as rows where `event_type = 'purchase'`, and `C` as rows where `event_type = 'logout'`. More complex predicates may involve comparisons to previous rows, aggregates over the current match, or navigation functions like FIRST and LAST. These predicates must be evaluated as the automaton progresses through the row sequence.

Trino’s documentation mentions “running semantics” for `DEFINE` and `MEASURES`, indicating that predicate evaluation can occur over partial matches as the pattern progresses.[5][13] Running semantics imply that certain measures or predicates are evaluated for every row as it participates in potential matches, not just at match completion. For example, a predicate might require that a value is monotonic over the sequence, necessitating evaluation at each step. Implementing running semantics demands that the automaton maintain state about partial matches, including the values of measures and the results of previous predicate evaluations.

DataFusion would need to integrate predicate evaluation into its expression evaluation engine, ensuring that `DEFINE` conditions can reference row fields, pattern variables, and possibly navigational functions. This integration is complicated by the need to evaluate predicates in the context of multiple active partial matches: each potential match may have different accumulator values or navigation references, and the engine must correctly maintain these contexts. In addition, aggregates used in `DEFINE` or `MEASURES` must respect feature R030’s restrictions, such as whether `DISTINCT` aggregates and filter clauses are permitted.[1][11]

### 5.5 AFTER MATCH SKIP Semantics and Time-Window WITHIN/DURATION

The `AFTER MATCH SKIP` clause specifies how pattern matching resumes after a successful match. Options like `SKIP PAST LAST ROW`, `SKIP TO NEXT ROW`, or `SKIP TO FIRST` can be supported, each with distinct semantics.[2][17][6] For example, `SKIP PAST LAST ROW` means that after a match ending at row `i`, the next search begins at row `i+1`, ensuring non-overlapping matches; `SKIP TO NEXT ROW` allows overlap by starting at the row immediately following the first row of the previous match.[2] Implementing these semantics requires the engine to track match boundaries and the starting points for subsequent searches per partition, adjusting the automaton’s initialization accordingly.

Time-window semantics like “within X minutes” or non-event detection (e.g., alert when an expected event does not occur within a time limit) often appear in CEP scenarios.[9][6][18] While SQL:2016 does not define a dedicated `WITHIN` clause for row pattern recognition, vendor implementations such as Oracle CQL’s `DURATION` clause provide explicit time-window controls.[9] The `DURATION` clause ensures that a match is reported only when the pattern is matched completely and no other event arrives until the specified duration expires, effectively implementing non-event detection.[9] Flink SQL and Azure Stream Analytics handle time windows by combining `MATCH_RECOGNIZE` with stream windowing and event-time semantics; time constraints are expressed in `DEFINE` predicates or in surrounding window functions.[6][18]

In DataFusion, implementing similar behavior would require integration with timestamp columns and possibly with time-window constructs in SQL. For batch data, time windows can be expressed using filters and `DEFINE` predicates that compare timestamp differences. For streaming contexts (if DataFusion is extended to streaming), more complex logic may be needed, including window management and non-event detection. Implementing non-event detection is particularly challenging, as it involves reasoning about the absence of events rather than their presence, and coordinating this with pattern matching across partitions.

### 5.6 Integration into DataFusion’s Optimizer and Execution Engine

Beyond semantics, implementing `MATCH_RECOGNIZE` in DataFusion requires integration with its optimizer and execution engine. DataFusion’s optimizer currently focuses on traditional relational operators, such as scans, projections, filters, joins, aggregations, and window functions.[16] A new logical operator for row pattern recognition would need to be introduced, with rules for pushing down filters, reordering computations, and combining pattern matching with other operators. For example, filters that restrict partitions or event types should be pushed below `MATCH_RECOGNIZE` to reduce input size, while measures computed inside `MATCH_RECOGNIZE` must be integrated with outer aggregations in an efficient manner.[16][7]

The physical execution engine would need a specialized operator that performs pattern matching per partition. This operator would likely read input data partitioned and ordered by the specified keys, maintain per-partition automaton states, and emit matches according to rows-per-match and skip semantics. It must be parallelizable across partitions to leverage DataFusion’s parallel execution model, and it must manage memory carefully to handle large partitions and numerous partial matches.[16] Integrating such an operator would require careful design to avoid disrupting existing performance characteristics and to ensure consistent behavior across data types and sources.

Given the complexity of these tasks, the DataFusion issue’s comment that `MATCH_RECOGNIZE` is “most probably too complex to integrate in the core DataFusion” appears accurate.[7] Implementing even a subset of SQL:2016 row pattern recognition would be a significant project, requiring new components in parsing, planning, optimization, and execution. While the standard’s grammar is sufficiently well-specified to define a subset, the hardest parts—NFA construction, overlapping match semantics, running predicate evaluation, and time-window logic—demand specialized engineering efforts and deep understanding of CEP semantics.[2][1][17][6]

## 7. Conclusion and Forward-Looking Assessment

Row pattern recognition in SQL, encapsulated in the `MATCH_RECOGNIZE` clause introduced by SQL:2016, constitutes a major advance in declarative pattern detection across ordered rows.[11][1] It allows users to express patterns using regular-expression-like syntax over pattern variables, partition and order data for pattern matching, define predicates that map rows to variables, compute measures over matched sequences, and control match resumption via `AFTER MATCH SKIP` and related options.[17][13][2] This standardized mechanism is widely regarded as the canonical way to implement complex event processing and sequence detection in SQL, particularly for kill‑chain patterns such as “A then B then C within a time window”, although time-window semantics themselves are often expressed via predicates or vendor-specific clauses like Oracle CQL’s `DURATION`.[9][6][18]

Vendor adoption confirms the practical significance of `MATCH_RECOGNIZE`. Oracle Database and Oracle CQL provide robust implementations for both static and streaming data; Snowflake integrates `MATCH_RECOGNIZE` into its cloud warehouse; Trino supports RPR in distributed query processing; Flink SQL uses it for streaming CEP; and Azure Stream Analytics and DeltaStream offer similar functionality.[17][3][9][4][13][5][6][18][12][2] At the same time, engines like SQL Server, Spark SQL, Materialize, and RisingWave—based on the evidence available here—do not have verified native `MATCH_RECOGNIZE` clauses, relying instead on join-based rewrites, window functions, self‑joins, and other idioms.[2][11][14][19][10] Apache DataFusion, despite having parser support via `datafusion-sqlparser-rs`, lacks execution semantics for `MATCH_RECOGNIZE` and is described by a contributor as finding the feature “most probably too complex to integrate in the core” engine, indicating that full RPR support is currently absent.[7][15][16]

In engines without native row pattern recognition, sequence and kill‑chain detection are performed using self‑joins, window functions, recursive CTEs, gap-and-island patterns, and conditional aggregation. These techniques can express many patterns but suffer from correctness and performance limitations compared to `MATCH_RECOGNIZE`: they require verbose and intricate SQL, are prone to subtle bugs in ordering and overlap semantics, and often perform less efficiently due to large intermediate results and complex execution plans.[11][19][2] Native RPR, by contrast, leverages NFA-based pattern matching with well-defined semantics, enabling efficient scanning of ordered partitions and clear control over overlapping matches and non-event detection when combined with vendor extensions.[2][1][9]

Implementing `MATCH_RECOGNIZE` on a query engine like DataFusion is technically challenging but conceptually feasible. The SQL:2016 grammar is sufficiently well specified to define a subset focusing on core constructs, and `datafusion-sqlparser-rs` already parses the clause.[11][17][13][7][15] The hardest parts lie in automata construction from `PATTERN`, integrating `DEFINE` predicate evaluation with running semantics, handling greedy and reluctant quantifiers, managing overlapping matches and `AFTER MATCH SKIP` semantics, and supporting time-window and non-event detection in CEP scenarios.[2][1][3][6][9] Integrating such an operator into DataFusion would require significant extensions to its optimizer and execution engine, as well as careful design to maintain performance and correctness.[16][7]

The Rust ecosystem offers potential building blocks for such implementation, including SQL parsing via `datafusion-sqlparser-rs`, expression evaluation in DataFusion, and general regex and automata libraries. However, there is no verified dedicated Rust crate implementing SQL:2016 `MATCH_RECOGNIZE` semantics; any such effort would need to be custom-built or heavily adapted from existing components.[15][16] As of the information available here, Apache DataFusion users must rely on traditional SQL idioms for pattern detection or integrate custom CEP logic in Rust, while engines like Oracle, Snowflake, Trino, Flink SQL, Azure Stream Analytics, and DeltaStream provide native RPR capabilities.

Looking toward 2025–2026, it is reasonable to expect continued growth in the adoption of row pattern recognition across SQL engines and streaming systems, driven by CEP use cases in domains like finance, security, and user analytics.[2][6][18] Whether Apache DataFusion will incorporate `MATCH_RECOGNIZE` or similar features into its core remains an open question; the existing parser support and community interest suggest potential, but the acknowledged complexity may push such functionality into external libraries or higher-level frameworks built on DataFusion.[7][15][16] In any case, the standardized semantics of SQL:2016 provide a solid foundation for future implementations, and the vendor experiences documented here offer valuable guidance for designing efficient, correct, and expressive row pattern recognition systems in Rust and beyond.
