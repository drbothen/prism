# Query Languages in Federated Search and Federated Query Engines: Architecture, Normalization, Execution, and Safety

Federated query and search systems enable a single logical query to span multiple, heterogeneous data sources while presenting a unified interface and schema to users. At their core, these systems rely on a global query language, a mediated schema, and a query planner that decomposes incoming operations into source-specific subqueries, pushing computation as close to the data as possible and recombining the results. Systems such as Apache Calcite, Trino/Presto, Starburst, Apache DataFusion, AWS Athena, Steampipe, GraphQL federation via Apollo, and Elasticsearch/OpenSearch cross-cluster search exemplify variant designs of this architecture, addressing the challenges of differing source capabilities, schema heterogeneity, and unpredictable performance across backends.[1][5][6][7][8][9][10][12][14][15][17][18] This report analyzes in depth how unified query languages are translated and pushed down to heterogeneous backends, how mediated schemas and normalization frameworks such as OCSF reconcile divergent data models, how federated query planners execute and optimize cross-source queries, and how engines balance expressiveness with safety through cost-bounding and operational controls. The goal is to distill general architectural patterns, independent of any specific vendor, while referencing concrete mechanisms and interfaces employed by existing systems.

## Foundations of Federated Query and Search

### Federated data access versus warehousing

Federated query systems occupy a conceptual space between direct per-source querying and data warehousing. In traditional data warehouses, data from multiple sources is extracted, transformed, and loaded into a centralized, homogeneous database, after which queries run solely against that warehouse, decoupling query execution from the original systems.[16] Federation, in contrast, keeps data in place at the original sources and provides a unified query interface that transparently accesses and combines data from those sources at query time.[2][6] This distinction has profound architectural implications: federated engines must understand and negotiate the capabilities and performance characteristics of each source for every query, whereas warehouses can rely on uniform storage and query semantics.

The PMC article on federated query engines highlights that early architectures often faced a choice between ETL into a central repository and on-the-fly mediation over distributed databases, emphasizing that federation trades off up-front integration work for increased query-time complexity and network sensitivity.[16] Modern systems increasingly adopt hybrid approaches, combining data virtualization and federation for some sources with materialized views or data lakes for others, but the core challenge remains supporting optimized queries across heterogeneous data sources via a single high-level interface.[2][12] Apache Calcite was explicitly developed to address this challenge by serving as a foundational framework for SQL parsing, optimization, and data virtualization, allowing relational queries to target diverse underlying systems through a common optimizer and adapter model.[6][12]

In federated search, the same principles apply to search-oriented engines such as Elasticsearch or OpenSearch, where cross-cluster search permits a single search operation to span indices hosted in multiple clusters, coordinated by a “local” cluster that distributes the query and merges the results.[10][18] Cross-cluster search behaves much like database federation, but the underlying query language is a search DSL, and the sources are remote index clusters instead of relational databases. Whether the interface is SQL, GraphQL, or a search DSL, federation hinges on the ability to express a logical query independently of any one backend and to decompose that query into executable fragments per source.

### The basic architecture: global interface, mediator, adapters

A generic federated query architecture can be understood as three logical layers. At the top resides the global query interface and schema, which expose to users a unified set of tables, views, or types, and accept queries in a single language such as SQL, GraphQL, or a domain-specific DSL.[2][6][9] Beneath, the mediation or federation engine parses these queries into internal representations, performs semantic analysis, generates and optimizes a logical plan, and ultimately constructs a physical execution plan that describes which parts of the plan run in which sources and which operators run centrally.[6][12][17] At the bottom layer are connectors, adapters, or wrappers: source-specific modules that present each backend’s data as tables or objects, advertise capabilities, translate pieces of the logical plan into the source’s native query language, and stream results back to the engine.[5][6][7][8][15][17]

Apache Calcite’s adapter model provides a canonical example of such an architecture. Calcite allows developers to register schema adapters that expose external data stores as schemas and tables within Calcite, with the adapter responsible for reading data and supplying metadata such as supported operations, collation, and distribution.[6] Calcite then uses its optimizer to rewrite and push operations like joins and filters as far as possible into these adapters, turning the unified logical query into one or more source-specific subqueries plus local operations.[6][12] Similarly, Trino and Presto use connectors that implement a service provider interface (SPI) to interact with data sources, exposing tables and columns and optionally supporting predicate, projection, aggregation, join, and limit pushdown.[5][14][15] In Rust-based Apache DataFusion, custom table providers play the adapter role, with methods such as `supports_filters_pushdown` informing the optimizer about what can be executed by the source.[7]

Steampipe demonstrates how this architecture can extend beyond databases to APIs. It provides Postgres foreign data wrappers (FDWs) that translate SQL queries against “foreign tables” into API calls; each FDW acts as an adapter that maps SQL filters, projections, and limits into HTTP parameters and pagination schemes.[8] GraphQL federation via Apollo Gateway adopts a similar layered architecture, where a gateway plays the role of the mediation engine and subgraphs (services) act as sources; the gateway parses a global GraphQL operation, generates a query plan, and issues sub-queries to each subgraph in order, reconciling results into the overall response.[9] Elasticsearch and OpenSearch cross-cluster search adopt coordinating nodes and remote clusters in analogous roles, with the coordinating cluster parsing and distributing the search request and merging results.[10][18]

Viewed through this lens, federated query engines are special cases of data virtualization: they virtualize a single schema and query language over heterogeneous storage and query environments. Their distinguishing feature is that query execution crosses source boundaries dynamically, so they must carefully manage data movement and pushdown to maintain performance and correctness.

### Unified query languages and mediated schemas

The global query interface must be backed by a global or mediated schema. Federated engines typically present a logical schema comprising tables, views, or types that abstract over the disparate schemas of underlying sources. This mediated schema may be expressed as relational tables, as in SQL-based engines, or as object types and fields, as in GraphQL schemas or OCSF event classes.[3][4][6][9] Its purpose is to give users a consistent vocabulary for expressing queries, while connectors and adapters handle the mapping between this vocabulary and source-specific field names, types, and semantics.

Mediation theory distinguishes Global-as-View (GAV) and Local-as-View (LAV) approaches to schema integration, each with implications for query rewriting and evolution.[3] In GAV, the global schema is defined as a set of views over source schemas; each global table or relation is expressed in terms of one or more source relations, and queries over the global schema are rewritten by the mediator using these view definitions to generate source-specific queries.[3][2] In LAV, the global schema is expressed independently, and each source is described as a view over the global schema; the mediator then must reason about which combinations of source views can answer a given global query, a more complex query rewriting problem but one that allows easier addition and removal of sources.[3][2] These approaches are central to understanding how federated engines perform schema normalization and query rewriting.

OCSF, the Open Cybersecurity Schema Framework, is an example of a mediated schema in the security domain. It defines an extensible, vendor-agnostic core schema for cybersecurity events, intended to be agnostic to storage format, data collection, and ETL processes, while enabling security teams to work with a common language for threat detection and investigation.[4] Vendors and data producers can adopt and extend OCSF for their domains, and data engineers can map differing schemas to OCSF to simplify data ingestion and normalization; a security-focused federated search interface can then expose OCSF event categories as its global schema and use connectors to map queries to each vendor’s native schema.[4]

In subsequent sections, we will examine in detail how unified query languages can be designed to function over such mediated schemas, how mappings are maintained and applied at query time, and how query planners and optimizers exploit source capabilities to push computation down and control data movement.

## Unified Query Language Design for Federation

### Logical query representations and dialect independence

A federated query engine must accept queries in a single logical language while ultimately executing subqueries in the native languages of its sources. This necessitates a clear separation between the user-facing query syntax and the internal logical representation on which optimization and decomposition operate. Most relational federated engines parse SQL into an abstract syntax tree and then convert it into a logical plan expressed in relational algebra or an equivalent operator tree, comprising operators such as Scan, Filter, Project, Join, Aggregate, Sort, and Limit.[6][12] From the perspective of the optimizer, this logical plan is dialect-independent: it models the semantics of the query without committing to any specific database syntax.

Apache Calcite embodies this pattern by providing a generic SQL parser that produces a representation which is then transformed into relational algebra and optimized using a rule-based and cost-based system.[6][12] Calcite’s optimizer operates on abstract relational expressions (RelNodes) with traits describing physical properties, and adapters supply relational expressions that model access to external sources, allowing Calcite to treat diverse sources uniformly during optimization.[6][12] Similarly, Trino and Presto parse SQL into logical plans that are then optimized by applying transformations such as predicate pushdown, join reordering, and aggregation pushdown, before translating portions of the plan into connector-specific operations.[5][14][15] Rust-based DataFusion follows a comparable pattern: it parses SQL into a logical plan, performs logical optimizations, and then builds a physical plan made of operators like Scan, Filter, and Join, which are implemented as execution plans and may delegate work to custom table providers.[7][17]

When sources do not speak SQL, the engine still uses a logical representation akin to relational algebra. Steampipe, although exposing SQL to users, must translate relational operations into API calls and JSON processing. Its FDWs accept the logical description of a scan with filter and projection and turn that into HTTP requests with query parameters and body payloads, mapping back the returned JSON into rows.[8] The same is true for search federation: the federated engine parses the search DSL into a logical representation of the query, then constructs source-specific search requests expressed in Lucene-like query syntax, mapping back hits into logical rows or documents. Elastic’s cross-cluster search architecture treats search requests as logical operations and distributes them to remote clusters where they are executed locally, returning results that correspond to the logical expectations of the initial query.[10][18]

GraphQL federation uses a different logical representation, but the principle is the same. The Apollo Gateway parses a GraphQL operation and generates a query plan, represented as a hierarchy of nodes describing which fields are fetched from which subgraph and in what order.[9] These nodes do not directly encode SQL or REST operations; instead, they model the logical resolution of fields across subgraphs, and each subgraph’s GraphQL server then translates its portion into native data access via its resolvers. The gateway’s query language is GraphQL, and the internal representation is a query plan tree; dialect-specific operations are hidden inside each service.

In all these systems, the unified query language design hinges on a canonical logical representation that abstracts away source-specific syntax. This representation enables the optimizer to reason about equivalences, pushdown opportunities, and data movement without tightly coupling to backend dialects.

### Connectors, adapters, and capability descriptors

Once the query is expressed in a logical form, the federation engine must decide which parts of the plan can be executed by each source. This decision depends on the capabilities of the sources, which are advertised by connectors or adapters via capability descriptors. A capability descriptor is a structured description of which operations can be performed remotely, such as which filter predicates, aggregations, joins, sorts, limits, or subqueries are supported, and under what constraints.[5][7][14][17]

Trino’s connector framework illustrates this concept clearly. A connector in Trino presents a catalog and schema, exposing tables and columns, but it can also implement interfaces that support predicate pushdown, projection pushdown, aggregation pushdown, join pushdown, and limit pushdown.[5][14] For example, connectors can implement methods like `applyFilter` to accept a filter expression and determine which parts of it can be executed by the underlying source. The connector returns a modified constraint that indicates what predicates have been successfully pushed down and what remains to be applied by Trino.[5] Starburst’s documentation explains that Trino can push down processing of query parts into the connected data source, including predicates, aggregation functions, and join operations, when the connector declares support and the query structure allows it.[14] It notes that join pushdown is possible only if all predicates in the join are pushdown-capable and the tables in the join come from the same catalog.[14]

Apache DataFusion uses a similar capability signaling mechanism in its TableProvider abstraction. During logical optimization, DataFusion determines which filters and projections could be pushed down to the source and passes those hints to the table provider when `scan()` is called during physical planning.[7] The table provider implements methods like `supports_filters_pushdown` to indicate which filters can be handled by the source. DataFusion then uses this metadata to decide whether to push filters or to execute them in memory, noting that filter pushdown should only be implemented when the data source can do strictly better, such as by avoiding I/O through skipping files or partitions based on metadata.[7] DataFusion Federation extends this model, allowing certain parts of a query plan to be executed by a remote DataFusion engine, with the goal of resolving queries across remote databases while pushing down as much compute as possible to the remote side.[17]

AWS Athena’s federated query capability uses data source connectors implemented as Lambda functions, which are invoked to determine how to read requested tables and identify filter predicates in the WHERE clause that can be pushed down to the source.[1] The connector examines the query’s filter conditions and determines which are applicable for pushdown, resulting in the source omitting unnecessary rows early and improving overall query execution time.[1] This is a practical instance of connectors acting as capability-aware translators between Athena’s unified SQL language and the native filter mechanisms of remote sources such as relational databases, NoSQL stores, or object storage.

Steampipe’s FDWs act as connectors that translate SQL to API requests, and they must advertise which predicate pushdowns they support (for example, equality filters and simple ranges) based on the API’s parameters. The PostgreSQL planner then uses this information to generate foreign scans that push filters into FDW operations where possible, leaving non-pushable predicates for local evaluation.[8] Similarly, JDBC-based connectors may advertise support for various SQL constructs based on the underlying database dialect.

Capability descriptors are also implicit in GraphQL federation. Each subgraph defines a GraphQL schema indicating which types and fields it can resolve. The Apollo Gateway uses this schema, along with federation metadata such as keys and field ownership, to decide which parts of a query are delegated to which subgraph.[9] While GraphQL does not offer explicit filter capability descriptors in the same way that SQL connectors do, the gateway’s query planner must still reason about whether a given selection or sub-selection can be resolved entirely by a single subgraph or whether it requires follow-up queries and joins across subgraphs.

In federated search, Elastic’s cross-cluster search configuration defines which remote clusters are connected and how indices are referenced, implicitly indicating that the remote clusters support the same search DSL as the local cluster.[10][18] Since OpenSearch domains are required to run compatible versions, and cross-cluster search does not allow custom dictionaries or SQL, the capabilities are constrained to the search API. This simplifies capability reasoning but introduces version and configuration constraints, such as requirements for fine-grained access control and node-to-node encryption.[18]

These capability descriptors form the foundation upon which predicate and query pushdown decisions are made. They allow the optimizer to know in advance which parts of the logical plan can be executed at the sources and which must be executed centrally, thereby shaping the federated execution strategy.

### Predicate pushdown: filtering at the source

Predicate pushdown is the practice of moving filter operations (predicates) as close to the data source as possible, so that fewer rows flow through the rest of the plan. It is one of the most important optimization techniques in federated environments, because filtering at the source reduces network traffic, lowers memory usage, and can exploit indexes or partitions in the source system.[1][5][7][14][15]

In relational engines, a predicate corresponds to a condition in the WHERE clause or in join conditions; examples include equality filters, range filters, LIKE patterns, and compound Boolean predicates. When a federated query is submitted, the optimizer analyzes the logical plan to identify filters that can be pushed down to each source. If a connector advertises support for predicate pushdown, the optimizer passes filters to it, and the connector determines which predicates can be translated into the source’s native query language and executed there. The remaining predicates are applied centrally.

Athena’s documentation explicitly describes this process. When a query is submitted against a data source, Athena invokes the data source connector to determine how to read the table and identify filter predicates in the WHERE clause that can be pushed down.[1] Applicable filters are automatically pushed down and result in the source omitting unnecessary rows early, improving query execution time.[1] This might involve pushing down filters to relational databases using SQL WHERE clauses, to object stores using partition filters, or to APIs using query parameters.

Starburst’s pushdown documentation notes that predicate pushdown allows Trino to pass specific predicates to the data source, which then reads and returns only rows that satisfy those predicates.[14] For example, a connector for a columnar data store might use partition metadata to skip entire files or segments that do not match the predicate, eliminating I/O. The documentation also observes that predicate pushdown reduces network traffic and the load on remote sources, potentially resulting in significant cost reduction.[14]

DataFusion’s guide on custom table providers explains that DataFusion already pushes filters as close to the data source as possible in the logical plan, typically placing them directly above the scan.[7] However, it cautions that filter pushdown should only be implemented when the data source can eliminate I/O, such as by skipping files or partitions based on metadata. When a table provider opens a scan, DataFusion passes hints about which filters and projections could be pushed down; the provider then decides whether to apply these filters in the source or rely on DataFusion’s in-memory execution, which is already efficient.[7]

In federated environments, predicate pushdown can be partial. Connectors may support certain kinds of predicates (such as simple equality filters) but not others (such as complex expressions or non-deterministic functions). Trino’s issue tracker, for example, includes discussions about whether expressions involving functions (such as `func(a)`) can be pushed down to connectors, highlighting the need to determine whether the source can evaluate such expressions and whether the performance benefit outweighs any cost.[11] Complex predicates may be decomposed into pushdown-capable parts and residual parts, with the residual applied centrally.

In API-based federation, predicate pushdown corresponds to mapping SQL or GraphQL filters to API query parameters or body fields. Steampipe’s FDWs translate conditions on columns into API parameters, allowing the API to return only matching data.[8] However, many APIs only support equality filters or simple search strings, limiting the range of predicates that can be pushed down. The FDW must therefore compute residual predicates in Postgres after retrieving data.

Predicate pushdown is equally important in search federation. Elastic and OpenSearch cross-cluster search send the entire search request to remote clusters, including filters, query DSL, and aggregations.[10][18] The remote clusters execute the query locally, applying filters on indices and shards before returning hits or aggregations. Since cross-cluster search is symmetric to local search, predicate pushdown is effectively full: all filters are executed at the remote clusters, although partial execution may incur network cost when results must be merged.

### Query pushdown: delegating subplans to sources

While predicate pushdown focuses on filters, query pushdown refers to the delegation of larger portions of the query plan—possibly entire subqueries—to sources that can execute them. When a source supports joins, aggregations, group-by operations, and sorting, it may be more efficient to execute these operations at the source and only transfer the final results to the federated engine.[5][14][17] Query pushdown can be partial or complete: an engine may push down a subplan that scans and joins multiple tables in the same source, or it may push down an aggregate with grouping and filtering, leaving only final merging or joining across sources to the central engine.

Starburst’s documentation describes several forms of pushdown beyond predicates, including projection pushdown (which limits columns read and returned), aggregation pushdown, join pushdown, and limit pushdown.[14] Projection pushdown uses the columns specified in the SELECT clause and other parts of the query to restrict access to necessary columns, pushing this logic down so the data source reads and returns only the required columns.[14] Aggregation pushdown occurs when the connector supports the specific aggregate functions and the query structure allows pushing them down; in such cases, the explain plan omits an Aggregate operator for that part of the query, indicating that aggregation is performed by the source.[14] Join pushdown allows the connector to delegate table join operations to the underlying data source, provided that the connector supports join pushdown and the tables in the join belong to the same catalog.[14] Limit pushdown permits connectors to push LIMIT operations, so the source executes queries with limits and returns fewer rows.

Presto and Trino both benefit from such pushdown, as their connectors can offload heavy operations to remote databases when supported, reducing data movement and central processing.[5][15] Presto, for example, executes federated queries across multiple data sources by having worker nodes query source systems in parallel and move data into Presto’s memory for processing, retrieving only necessary columns and rows using pushdown optimizations where possible.[15] When a connector can push down entire queries that include filters, joins, and aggregations, Presto’s workers may receive only aggregated results rather than full detail, which is more efficient.

DataFusion Federation exemplifies query pushdown across engines. It allows DataFusion to execute part of a query plan on a remote execution engine with the goal of resolving queries across remote databases while pushing down as much compute as possible to the remote side.[17] This means that a subplan comprising multiple operators may be sent to a remote DataFusion instance, which executes it and returns results for further processing centrally.[17] Query pushdown thus extends beyond individual predicates and operations to entire relational subgraphs.

GraphQL federation, though not using relational algebra, implements a variant of query pushdown by delegating portions of a GraphQL operation to subgraphs. The Apollo Gateway generates a query plan, which is a hierarchy of nodes specifying operations that each subgraph can resolve.[9] Some operations depend on the results of others, so the query plan defines an ordering for execution.[9] Each node encapsulates a selection of fields and associated arguments; when the node targets a particular subgraph, the gateway sends a GraphQL sub-operation to that subgraph, which then executes its own internal query logic—often SQL or other data access—amounting to a form of query pushdown to that service.

In search federation, cross-cluster search effectively pushes down entire search queries to remote clusters. The coordinating node forwards the search request to relevant remote clusters, each of which executes the query on its local indices and returns results.[10][18] Aggregations, filters, and scoring are performed by the remote clusters. The coordinating node then merges results, possibly performing final aggregation steps or sorting across clusters. Since cross-cluster search operates in terms of search requests at the DSL level, the entire query is pushed down.

The extent of query pushdown depends on the expressiveness of the source. Sources that only support simple scans and filters may see only predicate pushdown, while those with full SQL, search aggregation, or GraphQL capabilities can support composite operations. The capability descriptors discussed earlier provide the optimizer with the information needed to determine which subplans can be delegated.

### Capability-based planning under heterogeneous expressiveness

In federated environments, sources differ dramatically in their expressiveness. Some sources are full-featured relational databases that support complex joins, nested subqueries, window functions, and arbitrary aggregations. Others are search engines with rich text search and aggregations but limited join capabilities. Still others are REST APIs offering only basic filter parameters and pagination, or logs in object storage with no server-side computation. Federated engines must plan queries based on these heterogeneous capabilities, deciding what can be executed where and how to compensate for missing functionality centrally.

Capability-based planning involves associating each source with a profile of supported logical operations and using those profiles during optimization. Calcite’s framework models sources as schemas with adjoint relational expressions, and adapters can contribute rules indicating how to push down operations and what is supported.[6][12] For example, an adapter for a relational database may support pushing down filters, projections, joins, and aggregates, while an adapter for a CSV file might support only scanning with predicate pushdown based on file partitioning. Calcite’s optimizer then rewrites the logical plan so that operations compatible with the adapter’s capabilities are executed in the source, while incompatible operations are performed by Calcite’s runtime.

Trino’s connector SPI provides explicit methods to determine pushdown support; connectors can declare which functions are supported for aggregation pushdown, whether join pushdown is available, and whether limit pushdown is possible.[5][14] The optimizer uses this information to apply transformations that move operations into connector-access nodes. If a connector does not support join pushdown, the engine must fetch rows from each table separately and perform the join centrally. If aggregation pushdown is not supported for a specific function, such as a custom aggregate, the engine executes the aggregation after retrieving rows.

DataFusion’s TableProvider capabilities similarly drive planning. During logical optimization, DataFusion tries to push filters and projections down; however, when scanning, the provider declares what it supports, and the engine respects this decision.[7] DataFusion Federation extends this idea by introducing remote execution capabilities: some sources may be full DataFusion instances that can execute arbitrary subplans, while others may only allow limited pushdown.[17]

In GraphQL federation, capability-based planning manifests through schema and federation metadata. Each subgraph owns certain types and fields and may expose specific resolvable keys. The Apollo Gateway uses this information to determine which fields are fetched from which subgraph and how to link them using keys.[9] For example, a user type may be merged from multiple subgraphs, one providing identity fields and another providing profile information. The gateway’s query planner ensures that it first fetches key fields from one subgraph and then uses them as input to queries in another subgraph, effectively performing a join across sources using application-level capabilities rather than SQL joins.

REST APIs accessed via FDWs or custom connectors often support only equality filters and coarse search parameters. The federation engine’s planner must recognize that such sources cannot perform joins or group-by operations and plan accordingly. It may perform queries to retrieve datasets from each API and then join or aggregate them centrally. In such cases, the unified query language may expose joins, but the engine ensures that join execution occurs in its own runtime rather than being delegated.

Search federation is constrained by the capabilities of search engines. Elasticsearch and OpenSearch clusters can perform full-text search, filters, aggregations such as terms, histograms, and metrics, but they cannot perform arbitrary relational joins. Cross-cluster search therefore supports search queries that do not require cross-document joins, focusing instead on aggregations and scoring.[10][18] Any notion of join across clusters is effectively implicit, as documents sharing fields can be aggregated or filtered, but relational joins are not supported.

Capability-based planning in federated settings thus requires the optimizer to reason not only about the cost of operations but also about whether they can be executed by the sources. The planner must handle sources with limited expressiveness by executing more logic centrally, while exploiting the capabilities of rich sources to reduce data movement through pushdown. This heterogeneity leads to hybrid plans where some parts of the query run at the sources and others run in the central engine.

## Schema Normalization and Unified Logical Schemas

### Schema-on-read and schema-on-write in federated contexts

One fundamental design choice in federated systems concerns when schema is applied to data: schema-on-write, where data is transformed into a unified schema when ingested, or schema-on-read, where heterogeneous schemas are reconciled at query time. Data warehousing typically uses schema-on-write, loading data into a warehouse schema; federation favors schema-on-read, using mediated schemas and mappings applied dynamically.[2][16]

Schema-on-read is particularly important when data sources are numerous, diverse, and fast-changing, as is common in modern enterprises. Rather than performing expensive ETL into a common warehouse, federated engines define a global schema that is flexible enough to accommodate variations and rely on connectors to interpret source data on demand. Apache Calcite and DataFusion support this mode by treating external sources as schemas whose tables are discovered and mapped into logical tables at query time.[6][7][12] In such engines, the adapter or TableProvider translates raw source representations into rows conforming to the mediated schema only for the portion of data needed by the query, leveraging predicate and projection pushdown to minimize the translation cost.[7][14]

Schema-on-read raises challenges around data type differences, null semantics, and missing fields. Connectors must coerce types where necessary and handle absent fields gracefully, often mapping them to nulls. For example, an API returning JSON fields with string representations of timestamps must be mapped to a timestamp type in the mediated schema, and queries must be aware of conversion semantics. A federated engine may provide runtime type coercion operators or rely on connectors to handle conversions.

Schema-on-write still plays a role when certain sensitive or performance-critical sources are replicated into central stores. For instance, a security analytics platform may ingest logs into a data lake normalized to OCSF while treating other sources via federation, blending schema-on-write and schema-on-read approaches.[4] However, the essence of query federation is that the global schema is virtual, and connectors map onto it at query time.

### Mediated schemas and virtual tables

The mediated schema in a federated engine is typically organized as a set of virtual tables, views, or object types that abstract over underlying physical representations. Users query these virtual objects using the unified language, unaware of the actual source structure. The mediation layer must define how virtual tables map to source tables or resources and how their columns map to source fields.

In SQL-based federation, mediated schemas are often defined by catalog and schema definitions that list tables and columns for each connector. For example, Trino exposes schemas and tables for each catalog registered by connectors, and users can select from and join these tables as if they were local.[5][14] When a user queries a table representing an external source, the connector maps the table name and column names to the source’s schema. The virtual table may correspond directly to a physical table in a relational database, or it may represent a view over multiple source tables, a file partition, or an API endpoint.

Calcite and DataFusion provide abstractions for virtual tables through their schema and table provider models. In Calcite, a schema adapter defines tables that correspond to external data, and can expose views implemented by the adapter that combine multiple source tables or apply filters.[6] DataFusion’s TableProvider supplies schema information describing columns and types, forming a virtual table that DataFusion scans using the provider’s `scan()` implementation.[7] These virtual tables may be mapped to different kinds of data sources, including Parquet files, relational databases, or remote APIs.

GraphQL uses schemas defined in SDL (schema definition language) to describe types and fields accessible via queries.[9] In federation, each subgraph defines its own schema segment, and the gateway composes them into a unified schema. The fields in the global schema may be resolved by different subgraphs, but the user sees a single, logical schema comprising types such as `User`, `Order`, or `Event`. Federation metadata indicates how these types are composed from subgraph definitions.

Virtual tables also appear in search federation, where indices and index patterns represent logical groupings of documents. Cross-cluster search allows queries such as `cluster_us_east:logs-*` or `cluster_eu_west:logs-*` to target remote indices, effectively treating them as virtual tables addressed by `cluster:index` notation.[10] The indices themselves are physical resources, but the cross-cluster notation presents them as unified logical targets in the federated query.

Mediated schemas may be defined via explicit mappings. For example, a federated engine might have a virtual table `Events` with columns like `timestamp`, `source`, `severity`, and `message`, mapped to different fields in various logs. One connector might map `timestamp` to a field `ts` in a JSON log, another to `time` in a relational table, and yet another to `@timestamp` in Elasticsearch indices. The mediated schema thus defines the global vocabulary, and connectors implement the mappings.

### Global-as-View (GAV) mediation

Global-as-View (GAV) is a mediation approach in which the global schema is expressed entirely in terms of source schemas. In GAV, each global relation or table is defined as a view over one or more source relations, with mappings that specify how source fields correspond to global fields, and possibly selection or transformation logic.[3][2] Queries over the global schema are rewritten by the mediator using these view definitions.

The GeeksforGeeks article on GAV describes it as one of the mediator types of view-based data integration, where the global schema acts as a view over source schemas.[3] Given a query over the global schema, the mediator follows rules and templates to convert the query into source-specific queries, sending them to wrappers for execution.[3] Wrappers search for all possible expressions and combinations to answer the given query, and results are merged and returned to the user.[3] This process is called mediation and involves mapping queries at query time, using wrappers responsible for mapping queries based on templates representing many queries.[3]

The article’s example of integrating catalogs for a company purchasing chips illustrates GAV. The global schema defines relations `DIP(manufacturer, model, protocol)` and `PGA(manufacturer, model, protocol)`, while local schemas for each manufacturer have relations `(model, protocol)`.[3] When the user queries the mediator for chips with matching protocols, the mediator maps the query to queries against each manufacturer, adding the manufacturer attribute and then combining results.[3] The global relations are thus views over local relations, and queries are answered by rewriting them using these views.

GAV’s primary advantage is simplicity of design and implementation, because the global schema is directly tied to sources.[3] Query answering is procedural, and many industrial systems adopt this approach.[3] However, GAV has significant drawbacks in dynamic environments. Since the global database is defined in terms of multiple sources, the global schema cannot represent information absent from any source schemas.[3] Adding new sources requires updating mappings and often affects existing mappings, making GAV inflexible. Removing sources may also require substantial work, and independent sources are rarely added because the global schema is tightly coupled.[3] These limitations make GAV less suitable when sources evolve frequently or when new sources must be added at runtime.

In federated query engines, GAV appears when connectors define global tables as views over source tables or when the mediated schema is built directly from source schemas. For example, a Trino connector for a relational database may expose each source table as a global table, essentially adopting GAV for that source.[5][14] Similarly, a DataFusion TableProvider may map columns directly to source fields. When engines define global views that combine multiple sources, they may still rely on GAV patterns, but the complexity of global view management rises.

### Local-as-View (LAV) mediation

Local-as-View (LAV) is the complementary approach, where the global schema is defined independently, and each source is described as a view over the global schema. In LAV, the global schema can include conceptual relations that are not exactly present in any single source, and local sources may only cover parts of the global schema. Query rewriting is more complex, because the mediator must determine which combination of local views can answer a given query over the global schema.[3][2]

The GeeksforGeeks article notes that in LAV, mappings take place at query time, and when a user queries, it is mapped to multiple other queries sent to sources, with results merged together.[3] Wrappers use templates representing many queries, and if the mediator query matches a template, results are returned; otherwise, they may not.[3] LAV therefore requires more sophisticated rewriting algorithms, often using logical inference or query containment reasoning, to determine how to decompose global queries into local queries.

LAV’s main advantage is flexibility: the global schema can evolve independently, and sources can be added or removed without re-designing the global schema. The mediator can also express richer conceptual relationships, capturing semantics that only emerge when combining source data. However, implementing LAV requires more complex planning and potentially more metadata about which sources contain which portions of the global schema.

Many modern federated engines implicitly use hybrid models. They may define a global schema for key domains (such as security events) and map sources onto it using LAV-style mappings, while still exposing direct source tables in GAV style for other use cases. Calcite-based engines can support both patterns, as adapters can declare tables representing source relations while global schemas may define views and mappings onto them.[6][12]

### Schema mapping, semantic alignment, and type coercion

Irrespective of mediation style, federated engines must perform schema mapping, aligning field names, types, and semantics across sources. Schema mapping involves constructing mapping rules for each connector that indicate how source fields correspond to global fields. For example, an OCSF-based security schema might define fields like `event_time`, `threat_category`, and `actor_ip`, and connectors must map these to source-specific fields such as `timestamp`, `category`, and `src_ip`.[4] The mapping process may involve renaming, type coercion, splitting or combining fields, and semantic translation.

Semantic heterogeneity is common, where different sources use different attribute names for similar data, or different enumerations for categories. Federated engines may introduce normalization layers that translate source enumerations into global ones. For instance, one log might use severity levels `INFO`, `WARN`, `ERROR`, while another uses numeric codes; the mediator must map these to a common severity scale to support unified queries. OCSF’s design as an open standard for cybersecurity events aims explicitly to address such heterogeneity by providing a common language and extensible framework for security schemas.[4]

Type heterogeneity also arises, as sources may store timestamps as strings, integers representing epoch times, or native timestamp types. Connectors must coerce source types into the global type system. A federated engine may have a type system with primitive types such as integer, float, string, boolean, timestamp, and complex types such as arrays or structs. Schema mapping rules must specify conversions, and the engine must implement functions for converting values at runtime. Some conversions can be pushed down to sources if they support equivalent functions; others are computed centrally.

Schema mapping is particularly complex when sources have nested structures, such as JSON or document-oriented storage. Mediated schemas may flatten nested fields or represent them as nested types. The mapping from nested JSON to relational rows involves selecting specific fields and possibly generating multiple rows per nested element. Connectors for document databases must implement such mapping logic.

In GraphQL federation, schemas are explicitly merged, and fields can be extended across subgraphs. The Apollo Gateway uses federation directives such as `@key`, `@extends`, and `@external` to understand how types are composed across subgraphs.[9] Semantic alignment is handled at the schema design level, where teams agree on common type definitions and fields, and connectors (subgraphs) implement resolvers to supply those fields.

Schema mapping also influences pushdown opportunities. If a source uses different field names than the global schema, connectors must translate filter predicates on global fields into source-specific fields. For example, a filter `WHERE actor_ip = '1.2.3.4'` must be translated to `src_ip` or equivalent in the source schema. Connectors must interpret such mappings when performing predicate pushdown.

### OCSF as a normalization target in security federated search

The Open Cybersecurity Schema Framework (OCSF) provides an illustrative example of how a domain-specific mediated schema can serve as a normalization target for federated search in security analytics. OCSF is an open-source project delivering an extensible framework for developing schemas, along with a vendor-agnostic core security schema.[4] It is designed to be agnostic to storage format, data collection, and ETL processes, and it aims to provide an open standard adopted in any environment, application, or solution, complementing existing security standards and processes.[4]

OCSF defines a core schema for cybersecurity events, organizing them into categories such as network activity, authentication events, alerts, and configurations, with standardized fields for timestamps, actor information, target resources, outcomes, and context.[4] Vendors and data producers can adopt and extend this schema for their specific domains, mapping their native event formats into OCSF classes and attributes. Data engineers can use OCSF as a normalization target, mapping differing schemas to help security teams simplify data ingestion and normalization; this allows data scientists and analysts to work with a common language for threat detection and investigation.[4]

In a federated search environment, a security platform might expose OCSF-defined tables or types as its global schema. For example, it could present virtual tables such as `ocsf_authentication_events`, `ocsf_network_activity`, and `ocsf_alerts`, each with standardized columns. Connectors for SIEMs, endpoint protection platforms, cloud logs, and other security data sources would then map their native schemas to OCSF fields. Queries written once against OCSF tables would be translated into source-specific queries using these mappings, allowing cross-source search and analytics without requiring analysts to understand each system’s field naming conventions.

Predicate pushdown in such a platform would involve translating filters on OCSF fields into source-specific fields. If a query filters on `event_time` and `actor_ip`, connectors must translate these into appropriate fields such as `@timestamp` and `source.ip` in Elasticsearch, or `log_time` and `source_ip` in a relational table. OCSF thus serves as a semantic anchor for mapping.

OCSF also facilitates schema evolution. Because it is extensible, vendors can add fields and categories as needed, and connectors can incorporate these extensions. Federated engines can treat OCSF as a base schema and allow connectors to extend tables with vendor-specific columns, using GraphQL-like mechanisms or schema introspection to expose extended fields to advanced users.

By providing a normalization target and a common language, OCSF helps mitigate the semantic heterogeneity that complicates federated search across security data sources. It exemplifies how domain standards can be integrated into federation architectures to simplify schema mapping and query expression.[4]

## Federated Query Planning and Execution

### The lifecycle of a federated query

Federated query execution follows a multi-stage lifecycle that closely resembles that of single-source query engines but includes additional stages for source selection and remote execution. The lifecycle can be summarized as parsing, validation, logical planning, optimization, physical planning, source-specific translation, execution coordination, and result merging.[6][12][5][7][17]

In the parsing stage, the engine reads the user’s query in the unified language (SQL, GraphQL, search DSL) and constructs an internal representation, such as an abstract syntax tree. Validation ensures that the query adheres to the schema, checking that tables, fields, and functions exist and that types are consistent. Logical planning converts the syntax into a logical plan with operators representing relational operations or field resolutions.

Optimization is then performed at the logical level, using rule-based rewrites and cost-based decisions to produce an equivalent plan that is more efficient. In federated settings, optimization includes identification of predicate and query pushdown opportunities, join reordering, aggregation pushdown, and potential decomposition into source-specific subplans. Apache Calcite’s optimizer, for instance, employs transformations that push filters below joins, convert joins into semi-joins when beneficial, and push operations into adapter-provided expressions.[6][12] DataFusion similarly performs logical optimizations such as predicate pushdown, projection pruning, and expression simplification.[7]

Physical planning assigns physical operators and execution strategies to the logical plan. In federated engines, physical planning must decide where each operator will execute: at which source or in the central engine. This results in a physical plan that includes remote scan nodes, remote subquery operators, and local operators. The physical plan also determines join algorithms (nested loop, hash join, sort-merge), memory allocation, and parallelism.

Source-specific translation involves turning portions of the physical plan into native queries or operations for each source. Connectors and adapters perform this translation, generating SQL dialect queries, REST API calls, search DSL requests, or GraphQL sub-operations. Execution coordination then orchestrates the execution of these subqueries, often in parallel, managing data streams and applying local operations such as joins and aggregations. Result merging combines outputs from multiple sources into a single result set, applying sorting, deduplication, and final aggregation as needed.

This lifecycle is evident in various systems. Trino’s planner transforms the logical plan into a distributed plan with tasks assigned to worker nodes, each responsible for part of the query, and connectors handle source-specific scanning and pushdown.[5][14][15] DataFusion’s execution engine constructs an `ExecutionPlan` from the physical plan, and DataFusion Federation allows delegation of portions of the plan to remote engines, which execute and return results to the local engine.[7][17] Apollo Gateway’s query planner builds a query plan tree, and the gateway executes nodes in order, sending GraphQL sub-operations to subgraphs and combining responses.[9] Elastic’s cross-cluster search uses a coordinating node to distribute search requests to remote clusters, which execute locally and return results for merging.[10][18]

### Cost-based optimization with incomplete and heterogeneous statistics

In federated settings, cost-based optimization is complicated by the lack or heterogeneity of statistics across sources. A traditional optimizer relies on statistics such as row counts, value distributions, and correlation metrics to estimate the cost of operators and choose optimal plans. In federation, each source may have its own statistics, accessible via its optimizer or information schema, and these statistics may not be available or comparable.

Apache Calcite’s design acknowledges the need to support optimized queries across heterogeneous data sources and includes mechanisms for integrating source-specific metadata into cost models.[12] Adapters can supply statistics for tables and columns, and Calcite’s cost-based optimizer can use this information to estimate row counts and selectivities. However, when statistics are absent or unreliable, Calcite may fall back to heuristic rules, such as pushing filters down whenever possible and ordering joins based on simple heuristics.[6][12]

Trino and Presto use statistics from connectors where available, but for external sources, statistics may be limited. Some connectors implement methods to retrieve table statistics from the source, such as row counts and column histograms, but others cannot. In such cases, the optimizer must approximate costs or rely on generic rules, such as preferring smaller tables as build sides of hash joins and pushing filters down as aggressively as possible.[5][14][15] Cost-based decisions about whether to push aggregation to the source may depend on whether the source can compute aggregates faster or more cheaply than the central engine, which in turn depends on storage and indexing.

DataFusion’s optimizer currently has limited cost-based capabilities and relies more on rule-based optimizations.[7] It pushes filters and projections down based on capabilities but does not always compute detailed cost models. DataFusion Federation introduces additional complexity, as remote engines may have independent cost profiles; the local optimizer must decide whether to delegate execution based on approximate costs or policy rules.[17] For example, remote engines with larger clusters or specialized hardware may be better suited for heavy aggregations, while local execution may be preferable when network latency is high.

In search federation, cross-cluster search relies largely on uniform search cost models. Elasticsearch and OpenSearch treat all clusters as similar, though hardware differences may exist.[10][18] The coordinating node does not typically re-optimize search queries; it delegates the same query to all clusters and merges results. Cost-based decisions are limited to load balancing and concurrency; the main concern is avoiding overload by controlling fan-out.

GraphQL federation has its own cost considerations. Subgraphs may have varying performance characteristics, and queries that trigger heavy operations in certain services can be problematic. While Apollo Gateway’s query planner focuses on correctness and field resolution, platform operators may implement cost control policies, such as limiting expensive resolver operations or using caching. However, the federation engine itself does not often perform detailed cost-based optimization across subgraphs.

The lack of uniform and detailed statistics motivates alternative approaches to optimization, such as dynamic feedback and runtime adaptivity. Federated engines can monitor query performance and adjust future plans accordingly, or allow connectors to annotate queries with cost estimates. However, these techniques remain challenging, especially when sources are black boxes.

### Distributed join strategies across sources

Joining data across sources that cannot perform joins themselves is one of the most complex aspects of federated query execution. When two tables reside in different sources or when a source lacks join capabilities, the federated engine must execute the join centrally, fetching results from each source and combining them. This introduces significant data movement and potential performance bottlenecks.

Distributed join strategies commonly include broadcast joins, repartitioned hash joins, and semi-joins. In a broadcast join, the engine fetches the entire small table from one source and broadcasts it to workers that join it with a large table from another source. In a repartitioned join, the engine fetches both tables, partitions them by join key, and distributes partitions to workers that perform local joins. Semi-joins can reduce data movement by filtering one table based on join keys from the other before fetching full rows.

In a federated context, the central engine typically implements these strategies within its execution environment. For example, Trino’s distributed execution model uses worker nodes and supports broadcast and partitioned joins. When joining tables from different catalogs, Trino must fetch rows from each connector and perform the join centrally, using its in-memory execution engine.[5][14][15] Connectors may help by pushing down filters that reduce the size of fetched tables, but the join itself happens in Trino.

DataFusion’s execution engine similarly supports different join implementations, and when DataFusion Federation is used, some joins may be delegated to remote engines if they can handle them.[7][17] However, joins across sources usually remain a central responsibility. If a remote DataFusion instance hosts both tables, the local engine may push down a join; if not, the local instance must fetch and join.

GraphQL federation addresses joins at the application level rather than the relational level. The Apollo Gateway uses keys and references to link data across subgraphs.[9] For example, a `User` type may be resolved from one subgraph and extended with fields from another subgraph based on a key such as `userId`. The gateway’s query plan may first fetch users from `Accounts` subgraph, then use their IDs to fetch additional fields from `Profile` subgraph, effectively performing a join via two sequential GraphQL operations.[9] This is akin to a nested loop join executed by the gateway.

Search federation typically avoids explicit joins. Cross-cluster search operates on indices that share schemas and may store related documents, but relational joins across indices or clusters are not supported.[10][18] Instead, search queries use filters and aggregations to correlate documents and fields. Any multi-source joining is performed at the application level, by combining search results from multiple queries.

REST API federation via FDWs often uses joins executed in the database hosting the FDWs. For example, Steampipe runs SQL queries in Postgres, where foreign tables representing APIs can be joined with local tables or other foreign tables.[8] Postgres performs the join using data retrieved from the APIs by FDWs, essentially centralizing join execution. FDWs may push down filters but not joins.

Distributed join strategies must consider data volumes and network costs. Broadcasting a small table is feasible when its size is manageable; larger tables require partitioning strategies. Federated engines may restrict joins that would require fetching unbounded amounts of data from sources, enforcing limits or requiring that queries include selective filters.

### Result merging, sorting, and aggregation pushdown

Result merging is the process of combining outputs from multiple sources into a single result set while preserving query semantics. It may involve concatenating rows from multiple shards, deduplicating overlapping results, merging aggregations, and applying final sorting.

Elasticsearch and OpenSearch cross-cluster search illustrate result merging in search contexts. The coordinating node forwards the search request to remote clusters, each executing the query on local indices and returning hits and aggregations.[10][18] The coordinating node then merges hits based on scores, combining them into a global result set, and merges aggregations by summing counts, consolidating buckets, or merging metric values, depending on aggregation type.[10] Sorting across clusters requires combining sorted results from each cluster and selecting top hits, which can be done using priority queues.

In relational federation, result merging occurs at the central engine after fetching results from connectors. If aggregation pushdown is used, connectors may return aggregated results for their portion of the data, and the engine merges these partial aggregates.[14][5] For example, a sum pushed down to a source returns a single value per group, and the engine sums these values across sources to produce final results. Aggregation pushdown thus requires associativity and commutativity of aggregates, and connectors must adhere to semantics.

Starburst’s documentation explains that when aggregate functions are pushed down and the explain plan omits an Aggregate operator, the central engine relies on the connector’s results.[14] The engine may still apply additional aggregations across sources if necessary. Similarly, limit pushdown allows connectors to return limited sets of rows per source, which the engine then combines and applies final LIMIT across the merged result.

Sorting pushdown is possible when sources support ordering. Connectors can push ORDER BY operations to sources, returning sorted results. However, when results from multiple sources must be merged and sorted, the engine must perform a final sort. It may receive sorted runs from sources and merge them using external sort algorithms.

DataFusion’s execution engine includes operators for sort and aggregate and can push down aggregations when TableProviders support them.[7] DataFusion Federation may delegate aggregations to remote engines, which compute partial aggregates and return results for further aggregation centrally.[17] Projection pushdown likewise reduces the number of columns read, with connectors returning only necessary fields.

GraphQL federation uses result merging at the JSON level. Apollo Gateway executes query plan nodes and merges field values from subgraphs into the final response document.[9] Sorting and aggregation are often handled within subgraphs’ resolvers, and the gateway simply merges JSON fields according to GraphQL semantics.

Result merging also interacts with partial results. Cross-cluster search includes a setting `skip_unavailable` that ensures cross-cluster queries return partial results despite failures on one or more remote clusters.[18] When some layers fail or remote clusters are inaccessible, the coordinating node merges results from successful clusters and returns them, marking partial results. Federated relational engines may adopt similar semantics, returning partial results when some sources time out, though this can complicate correctness.

### Partial results, fan-out, and timeouts

Federated queries often involve fan-out to multiple sources, each of which may respond at different times or may fail. Engines must handle timeouts and partial results gracefully. In search federation via OpenSearch, before setting up cross-cluster search, operators must satisfy requirements such as fine-grained access control, node-to-node encryption, and potentially VPC peering, but once configured, cross-cluster search allows queries across domains.[18] The `skip_unavailable` setting ensures that queries return partial results despite failures on one or more remote clusters, skipping unavailable clusters.[18] The source domain passes requests to destination domains, which evaluate access policies, and failures in remote domains do not necessarily cause the entire query to fail if partial results are acceptable.[18]

In relational federation, partial results semantics are more complex. Some engines may not support partial results by default, failing queries when any source is unreachable. Others may support partial modes, where results from available sources are returned along with warnings or metadata indicating missing sources. Parallel fan-out execution must be controlled to avoid overwhelming sources, and timeouts may enforce limits on how long queries wait for responses.

GraphQL federation includes error propagation semantics. When a subgraph fails, the gateway may include errors in the response while still returning partial data for other fields.[9] This is akin to partial results, where some parts of the query are answered and others fail.

Fan-out with timeouts also introduces scheduling considerations. Coordinating nodes may limit the number of concurrent remote queries or throttle requests to avoid overload. They may implement backoff strategies or fallback heuristics, such as sampling fewer sources when timeouts occur.

DataFusion Federation’s remote execution environment must likewise manage how many remote engines it engages and how long it waits for results.[17] Design patterns for safe fan-out include limiting the number of sources per query, imposing per-source timeouts, and requiring selective filters to reduce data volumes.

In summary, federated query execution involves careful coordination of parsing, planning, pushdown, remote execution, result merging, and partial results handling. Systems like Calcite, Trino, DataFusion, GraphQL federation, and cross-cluster search provide concrete instances of these patterns, each with its own nuance.

## Patterns for Balancing Expressiveness and Safety

### The tension between rich query languages and unpredictable backend performance

Federated engines promise rich expressiveness: users can issue complex queries involving joins, aggregations, and nested filters across many sources. However, underlying sources may have unpredictable performance and resource constraints, and the network between the engine and sources may be congested. Rich queries can easily lead to runaway resource usage, timeouts, and degraded performance. Federation engines must therefore balance query expressiveness with safety, enforcing bounds on query cost and controlling resource consumption.

This tension is particularly acute when users have access to a unified query language that hides backend complexities. A user may write a query joining a large table from a relational database with a wide index from a search cluster, applying complex filters, without realizing that this will require fetching millions of rows across the network and performing a massive join centrally. The engine must enforce controls that prevent such queries from overwhelming the system.

Safety mechanisms can be categorized into query language constraints, execution policies, and resource controls. Query language constraints limit what queries can express, such as requiring time predicates or disallowing unbounded joins. Execution policies shape how queries are planned and executed, such as limiting fan-out or using sampling. Resource controls enforce CPU, memory, and network limits, such as killing queries that exceed budgets.

### Bounding query cost with time predicates, pagination, and limits

One common pattern for bounding query cost is enforcing mandatory time predicates, especially in log and event analytics. Queries that lack time constraints may implicitly consider all historical data, leading to huge scans. Engines may require that queries include filters on time fields, such as `event_time` or `timestamp`, and may enforce default time windows when filters are absent. For example, a security analytics platform might require that queries include `WHERE event_time BETWEEN now() - interval '7 days' AND now()`, limiting scans to recent data.

Pagination and row limits also play a crucial role. Engines often impose default LIMIT clauses on queries that return rows, capping the number of rows returned and the amount of data transferred. Users may override limits within bounds, but engines may enforce maximum row counts per query. In APIs, pagination is standard, with queries returning pages of results and requiring clients to issue multiple requests to fetch more data. Steampipe’s FDWs translate SQL LIMIT and OFFSET clauses into API pagination parameters, and engines can enforce maximum limits per query to protect APIs.[8]

Limit pushdown leverages source capabilities to enforce row limits. Starburst’s pushdown documentation notes that limit pushdown enables connectors to push processing of queries with limits to the data source, allowing sources to return fewer rows and reduce network traffic.[14] When limit pushdown is not available, engines must fetch larger sets and truncate results centrally, which may still incur high costs.

Federated search systems also use pagination and size limits. Elastic’s search APIs use parameters like `size` and `from` to limit results, and cross-cluster search queries include these settings.[10][18] Coordinating nodes enforce these limits when merging results, ensuring that global results stay within bounds.

By bounding time and row count, engines reduce the worst-case cost of queries and encourage users to write more focused queries. These controls also aid connectors that access APIs with rate limits, as fewer remote calls are needed per query.

### Preventing runaway cross-source joins

Cross-source joins are particularly risky, because they often require fetching large volumes of data from both sources and joining in the federated engine. To prevent runaway cross-source joins, engines may restrict joins in several ways. They can disallow joins between certain sources entirely, allow only joins involving small dimension tables, or require join predicates to be selective and index-based.

In Trino and Presto, join pushdown is only possible when tables belong to the same catalog and connectors support join pushdown.[14][5] Joins across catalogs must be executed centrally, and connectors may not support join pushdown. Engines may apply heuristics, such as requiring that one side of the join has a small row count (estimated or known) to permit the join, otherwise rejecting the query or requiring additional filters. Some deployments restrict user access to cross-catalog joins altogether.

GraphQL federation avoids relational joins, using key-based field resolution. Nevertheless, the gateway may limit operations that lead to high fan-out, such as querying lists of entities and then performing nested queries per entity, which can effectively implement a join. Practices such as connection types and pagination in GraphQL encourage more controlled queries.

REST API federation via FDWs may also restrict joins. Steampipe, for example, operates over foreign tables that map to APIs; Postgres can technically join any tables, but Steampipe may impose limits or recommend joining only on keys where remote lookups are efficient.[8] Queries joining large API tables may be discouraged or flagged.

Federated engines can implement join guards that inspect queries at planning time and exclude those that are likely to be expensive. They can rely on statistics and heuristics to estimate row counts and join cardinalities and reject queries that exceed thresholds. Join guards can also enforce that joins between sources must include equality predicates on key fields and disallow cross products or non-key joins.

### Handling fan-out, timeouts, and partial results safely

Fan-out, timeouts, and partial results must be managed carefully to preserve both performance and user expectations. As discussed, cross-cluster search in OpenSearch includes the `skip_unavailable` option, which allows queries to return partial results when remote clusters are unavailable.[18] This option is a safety mechanism, preventing the entire query from failing due to one cluster’s failure, but it also implicitly bounds the scope of queries. Operators must consider whether partial results are acceptable and configure skip behavior accordingly.

Federated relational engines may implement similar mechanisms. DataFusion Federation, for instance, could allow some remote engines to fail without causing the entire query to fail, returning partial results with annotations.[17] Such behavior must be clearly documented and optionally enabled, because partial results can mislead users.

Timeouts are another critical safety mechanism. Federated engines should impose per-source timeouts, canceling remote queries that exceed allocated time and preventing hung calls. Sources may be slow or heavily loaded, and waiting indefinitely for responses could tie up resources in the central engine. Timeouts also protect connectors from misbehaving sources.

Fan-out controls limit how many sources a query can involve. Engines may restrict queries to specific sets of sources or impose caps on the number of remote endpoints. This prevents queries from scanning dozens of sources simultaneously. Combined with timeouts, fan-out controls ensure that worst-case query runtimes and resource usage are bounded.

In search federation, queries that target entire clusters or many indices may be restricted by index naming patterns and access controls. Cross-cluster search configurations limit the number of incoming connections and require fine-grained access control, ensuring that users cannot arbitrarily scan all indices across clusters.[18] Node-to-node encryption and VPC configurations further enforce boundaries and security.

### Access control, permissions, and safety in federation

Access control plays a crucial role in safety. Federated engines must respect source-level permissions and apply global policies. For example, OpenSearch cross-cluster search requires fine-grained access control and node-to-node encryption, and users must have the `indices:admin/shards/search_shards` permission in addition to standard `read` or `search` permissions for relevant indices on the source domain.[18] The destination domain must include the `es:ESCrossClusterGet` permission in its access policy to allow cross-cluster operations.[18] These permissions ensure that users cannot issue searches against remote indices they are not authorized to access.

In relational federation, connectors must enforce database-level permissions. Users may have limited rights on certain schemas or tables, and connectors must verify credentials or use service accounts with restricted privileges. Federated engines may implement role-based access control (RBAC) that restricts which connectors and schemas users can access, preventing them from querying sensitive sources.

GraphQL federation uses schema-level authorization, where resolvers enforce permissions based on user roles. The gateway may implement global policies, but each subgraph can also enforce its own rules. Authorization can thus be distributed across federation.

Safety patterns also include query whitelisting or templating, where only certain query patterns are allowed, and others are rejected. For example, in some security analytics platforms, queries must conform to pre-defined templates that ensure safe filters and groupings, avoiding arbitrary cross-source joins.

### Rich expressiveness via carefully designed query languages

Despite the need for safety, federated engines strive to offer rich query languages. They achieve this by carefully designing language constructs that map well to safe operations and by exposing capabilities that reflect backend strengths. For example, search DSLs emphasize filters, full-text search, and aggregations, which are efficiently executed by search engines, and avoid joins that engines cannot support. GraphQL emphasizes field selection and nested objects, which map well to service resolvers and caching.

SQL-based federation engines often support the full SQL language, but they may restrict features when used with certain connectors. For example, connectors to APIs may not support complex expressions in WHERE clauses or certain aggregate functions. Engines may dynamically adjust language capabilities per source, such as disabling subqueries in connectors that cannot handle them.

Query languages can include hints that guide optimization and safety. Users may specify resource usage hints, such as priority or time budget, and engines may rely on them to schedule queries. However, hints are only effective if engines enforce them.

Overall, the pattern for balancing expressiveness and safety involves defining a rich language, constraining it through schema and capability mappings, and enforcing resource and policy controls at execution.

## Emerging Directions and Architectural Lessons

### Standardized federation frameworks and adapters

Systems like Apache Calcite illustrate a trend toward standardized federation frameworks that can be embedded in many products.[6][12] Calcite serves as a foundational framework for optimized queries across heterogeneous data sources and is used in projects and products for SQL parsing, query optimization, data virtualization, and materialized view rewrite.[6][12] Its adapter model allows developers to create schema adapters that read particular kinds of data and present them as tables, using Calcite’s optimizer to push down operations.[6] This standardization reduces the need for each product to implement its own federation logic.

Apache DataFusion similarly provides a reusable engine, with TableProviders and Federation enabling multi-engine execution.[7][17] As DataFusion evolves, more systems may adopt its federation features to integrate heterogeneous sources within Rust-based pipelines.

Trino and Starburst demonstrate how a connector SPI can be used to support a broad range of data sources, from relational databases to object stores and search engines.[5][14] Enterprise products such as Starburst build on Trino’s architecture to add advanced pushdown and security features.[14] The connector model is becoming a common pattern, defining how sources advertise capabilities and expose schemas.

Steampipe’s Postgres FDWs over APIs show how FDW mechanisms can be used for federation beyond databases, allowing SQL queries to be expressed over REST APIs.[8] PostgreSQL’s FDW architecture, combined with connectors like postgres_fdw, file_fdw, and custom FDWs, allows federation from Postgres into many sources.

These frameworks suggest that future federation systems may rely heavily on standardized adapters and engines, rather than bespoke integration, improving portability and consistency.

### Domain schemas and normalization standards

OCSF is an example of domain-specific standardization, providing a core schema for cybersecurity events.[4] As more domains adopt schemas like OCSF, OpenTelemetry, or FHIR (in healthcare), federated engines will be able to leverage them as normalization targets. Domain schemas simplify schema mapping and semantic alignment, reducing the complexity of cross-source queries.

Federated engines can embed these schemas directly into their mediated layer, exposing tables or types corresponding to domain events and using connectors to map sources. This approach encourages vendors to align with standards and simplifies user query expression.

### Multi-model and polyglot federation

Federation increasingly spans multiple models—relational, document, search, graph, and stream. Engines must support multi-model queries that target different data models concurrently. Calcite’s relational algebra and virtualization capabilities already support some non-relational sources.[6][12] Trino supports connectors for Kafka, Elasticsearch, and other non-relational stores.[5][14] GraphQL federation naturally spans services, each of which may use different storage backends.

Multi-model federation challenges query language design. Unified languages may require extensions to express search-specific operations, graph traversals, or JSON path expressions. Some engines adopt specialized languages for each model and perform federated queries by combining them, while others extend SQL to represent multi-model queries.

Polyglot federation also includes using multiple query languages concurrently. For instance, a GraphQL gateway may access sources via SQL, REST, search DSL, or other languages, translating GraphQL operations accordingly. Federated engines increasingly support such polyglot integration.

### Improved cost models and adaptive optimization

Future federated engines may adopt more sophisticated cost models that incorporate network latency, source workload, and data location. They may gather runtime statistics across sources and use them to improve planning. Adaptive optimization, where plans are adjusted at runtime based on observed performance, can help mitigate uncertainties in federated environments.

As engines like Calcite and DataFusion evolve, they may allow connectors to supply dynamic cost estimates for operations, enabling the optimizer to choose between pushdown and local execution more effectively. For example, connectors could indicate that performing a group-by at the source is more expensive than fetching rows and aggregating centrally, influencing decisions.

Adaptive federation may also include dynamic source selection, where engines choose among multiple equivalent sources based on current load or cost. This requires metadata about source performance and capacity.

### Security, governance, and compliance in federation

Federation raises security and governance concerns, as queries may cross administrative boundaries. Engines must enforce policies that govern which sources can be queried together, what data can be joined, and how results are logged and audited. Cross-cluster search exemplifies security constraints, requiring fine-grained access control, node-to-node encryption, and VPC connectivity.[18] Relational federation must likewise enforce security.

Governance frameworks may define policies that restrict cross-source queries involving sensitive data, requiring approvals or maskings. Engines may implement data lineage tracking, recording how results were derived from sources.

Compliance regimes, such as GDPR or HIPAA, may limit federation across jurisdictions. Engines must respect data residency requirements when planning queries, possibly blocking queries that would move data across borders.

### Developer and operator tooling for federation

Finally, developer and operator tooling is crucial. Tools that visualize query plans and explain pushdown decisions help users understand how queries are executed. Starburst’s documentation encourages checking explain plans to see whether pushdown was performed, noting that absence of operators like Aggregate or Join indicates pushdown.[14] Similar tooling exists in Calcite-based engines and Trino.

Operators need dashboards that show remote source usage, query latencies, and errors. Federation engines must provide configuration interfaces for connectors, cross-cluster connections, and security policies. For example, OpenSearch’s console allows operators to configure outbound connections and skip-unavailable settings.[18] Good tooling makes federation manageable at scale.

## Conclusion

Federated search and federated query engines provide powerful capabilities for querying data across heterogeneous sources through a single unified query language and schema. Their architectures revolve around a mediated layer that parses and optimizes queries, connectors or adapters that expose sources and capabilities, and execution engines that orchestrate pushdown and result merging. Systems like Apache Calcite, Trino/Presto, Starburst, Apache DataFusion, AWS Athena, Steampipe, GraphQL federation via Apollo, and Elasticsearch/OpenSearch cross-cluster search embody these patterns in different domains, illustrating how unified query languages can span relational databases, APIs, search engines, and microservices.[1][5][6][7][8][9][10][12][14][15][17][18]

Unified query language design in federation depends on a dialect-independent logical representation, such as relational algebra or query plan trees, and on capability descriptors supplied by connectors that indicate which operations can be pushed down. Predicate pushdown filters data at the source, reducing data movement and leveraging indexes, while query pushdown delegates broader operations such as joins, aggregations, and limits to sources when they support them.[1][5][7][14][17] Capability-based planning ensures that sources with different expressiveness are used appropriately: rich sources handle complex operations, while limited sources contribute filtered or raw data that is processed centrally.

Schema normalization and mediated schemas provide the semantic backbone for federation. Global-as-View (GAV) and Local-as-View (LAV) approaches offer different trade-offs between simplicity and flexibility, with GAV tying global schemas closely to sources and LAV allowing independent global design but requiring more complex query rewriting.[3][2] Frameworks like OCSF illustrate how domain standards can serve as normalization targets, allowing security federated search to operate over a vendor-agnostic core schema and enabling consistent analytics.[4]

Federated query execution involves parsing, optimization, physical planning, pushdown decisions, remote execution, and result merging. Cost-based optimization in federated settings is challenged by heterogeneous or incomplete statistics, motivating heuristic and adaptive approaches.[6][12] Distributed join strategies, aggregation and limit pushdown, and partial results semantics must be carefully handled to maintain performance and correctness.[14][5][7][17][10][18] Systems like Cross-Cluster Search demonstrate how coordination and partial results can be implemented in search, while DataFusion Federation and GraphQL federation show alternative strategies for delegation and orchestration.[9][17][10][18]

Finally, balancing expressiveness and safety is central to federation. Engines must bound query cost through mandatory time predicates, default limits, and pagination; prevent runaway cross-source joins through constraints and join guards; handle fan-out and timeouts safely; and enforce access control and security policies.[18][10][8][15][17] Rich query languages are enabled but constrained by capability mappings and resource controls.

The architectural lessons from these systems suggest a future in which standardized federation frameworks, robust domain schemas, multi-model and polyglot federation, improved cost models, and strong governance and tooling become the norm. Federation will continue to be a key pattern for organizations that want to query data where it lives, without sacrificing performance or safety, and the design of unified query languages, mediated schemas, and optimizers will remain central to achieving that goal.
