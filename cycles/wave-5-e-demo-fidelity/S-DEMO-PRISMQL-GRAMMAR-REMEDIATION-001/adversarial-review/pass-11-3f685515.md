## Findings

### HIGH-1: FORBID-BOTH bypass via `| tail N` (ADR-043 D4 / INV-FORBID-BOTH-PERMANENT / TD-VSDD-060)

**Severity:** HIGH
**Classification:** ADR-043 D4 invariant breach; TD-VSDD-060 sibling-sweep miss

**Description:**

The FORBID-BOTH guard (E-QUERY-040) was triggered correctly for `| limit N` following a SQL `head LIMIT N`, but `| tail N` was not covered. The function `plan_sqlpipe_query` matched only `PipeStage::Limit` in its row-capping check; `PipeStage::Tail` was omitted from the sibling sweep.

**Impact:** A query of the form `SELECT * FROM t LIMIT 5 | tail 3` silently sent TWO row-cap constraints to DataFusion — the SQL `LIMIT 5` head cap and the `tail 3` cap — bypassing the INV-FORBID-BOTH-PERMANENT invariant declared in ADR-043 §D4. The result was undefined DataFusion row-limit behavior rather than the structured E-QUERY-040 error with actionable guidance.

**AC coverage gap:** AC-002 exercised `| limit N` after head LIMIT N. The `| tail N` variant was not tested, leaving the bypass latent.

**Adjudication:** Fix in scope. Full sibling sweep of all PipeStage variants that lower to LIMIT is required.

**Status:** CLOSED by implementer (code `3f685515 → 9fcb8a42 → 71b196ad`)

**Fix description:**
- `plan_sqlpipe_query` now triggers `RedundantRowLimit` (E-QUERY-040) for BOTH `PipeStage::Limit` AND `PipeStage::Tail` when `head.limit.is_some()`.
- Full sibling sweep completed: `PipeStage::Join` errors on conflicting conditions (structural error, not row-cap); `PipeStage::Where`, `Sort`, `Stats`, `Fields`, `Dedup`, `Enrich` do not lower to LIMIT — positive-control verified.
- 3 load-bearing tests added:
  - `test_bc_2_11_tail_after_limit_rejected` — `SELECT * FROM t LIMIT 5 | tail 3` returns E-QUERY-040 with actionable message
  - `test_bc_2_11_limit_after_limit_regression` — existing `| limit N` after head LIMIT N still returns E-QUERY-040 (regression guard)
  - `test_bc_2_11_non_capping_stage_positive_control` — `SELECT * FROM t LIMIT 5 | sort ts DESC` is NOT rejected (non-row-capping stage passes through)

### LOW-1: Filter-mode execute arm missing unfolded-temporal guard (F-P1-MED-001 sibling miss)

**Severity:** LOW
**Classification:** TD-VSDD-060 sibling-sweep miss on the Filter execute arm

**Description:**

The `predicate_has_unfolded_temporal` guard was added to the parse path (catching `Expr::Interval` at parse time), but the filter-mode `execute` arm lacked an equivalent guard. A bare `Expr::Interval` comparison RHS (e.g. `timestamp > INTERVAL '24h'`) that bypassed the parse path — such as one constructed programmatically or injected via a different code route — would silently emit empty SQL to DataFusion, producing a redacted generic failure rather than the structured `QueryExecutionFailed` with actionable message.

**Adjudication:** Fix in scope. The guard must be present at both parse and execute boundaries.

**Status:** CLOSED by implementer (code → `71b196ad`)

**Fix description:**
- Added `predicate_has_unfolded_temporal_pub` guard to the `Ast::Filter` execute arm.
- Returns structured `QueryExecutionFailed` with actionable message when bare `Expr::Interval` detected at execute time.
- 2 load-bearing tests added:
  - `test_bc_2_11_filter_execute_unfolded_interval_rejected` — bare `Expr::Interval` on filter execute arm returns structured error (not empty SQL)
  - `test_bc_2_11_filter_execute_folded_timestamp_passes` — folded `Expr::Value(Timestamp)` is NOT caught by guard (positive control)
