# S-5.12 — prism-mcp: `add_sensor_spec` MCP Notification Dispatch

## Narrative

As a Claude Code AI agent connected to a running Prism instance, I want to receive
`notifications/resources/list_changed` and `notifications/tools/list_changed` after
successfully invoking the `add_sensor_spec` tool, so that I automatically discover
the new sensor's tables without needing to call `tools/list` manually.

## Problem Statement

S-5.03 wires `notifications/resources/list_changed` + `notifications/tools/list_changed`
into the `reload_config` **tool handler** path: when `reload_config` is called via MCP
and the table-name set changes, the `Peer<RoleServer>` from `RequestContext` is used to
dispatch both notifications.

The `add_sensor_spec` tool (BC-2.16.008) internally calls `reload_config`, but it is a
**different MCP tool handler** with its own `RequestContext`. To dispatch notifications
from `add_sensor_spec`, the handler needs its own `Peer<RoleServer>` access — which
requires adding `peer: Peer<RoleServer>` (or equivalent) to the `add_sensor_spec` handler
signature.

This asymmetry between `reload_config` (notifies) and `add_sensor_spec` (currently does
not notify) was noted during S-5.03 spec authorship and deferred to this story as the
named anchor (Canonical Principle Rule 3).

## Authority

BC-2.16.007 and BC-2.16.008 are the authoritative behavioral contracts for this story.

`.factory/specs/behavioral-contracts/BC-2.16.007-sensor-spec-hot-reload.md` defines the `Peer<RoleServer>` notification dispatch pattern established by S-5.03 in the `reload_config` handler path — the table-set-delta gate and the `notifications/resources/list_changed` + `notifications/tools/list_changed` dispatch semantics. S-5.12 applies the identical pattern to the `add_sensor_spec` handler, which currently lacks notification dispatch.

`.factory/specs/behavioral-contracts/BC-2.16.008-add-sensor-spec-tool.md` defines the `add_sensor_spec` tool behavior — including the confirmation-token update path, dry-run mode semantics, and the internal `reload_config` call. The notification postcondition for the `add_sensor_spec` tool path is the BC prerequisite that must be authored by the product-owner before this story can reach `status: ready`.

`architecture/module-decomposition.md §Cargo Workspace Structure` establishes SS-10 (MCP Server) ownership in `prism-mcp` and SS-16 (Sensor Spec Engine) ownership in `prism-spec-engine`.

No formal ADRs govern this story.

## Acceptance Criteria (Sketch — PO to elaborate before status: ready)

**AC-001 (traces to BC-2.16.007 v1.7 / BC-2.16.008 — add_sensor_spec notification):**
Given an `add_sensor_spec` invocation that successfully adds a new sensor spec with one
or more new tables, When the spec is validated, written, and hot-loaded, Then
`notifications/resources/list_changed` AND `notifications/tools/list_changed` are
dispatched to the MCP client that called `add_sensor_spec`.

**AC-002 (traces to BC-2.16.007 v1.7 invariant "File-hash-based change detection"):**
Given an `add_sensor_spec` invocation in dry-run mode (`dry_run: true`), When invoked,
Then no MCP notifications are dispatched (dry-run does not persist or reload).

**AC-003 (traces to BC-2.16.008 — confirmation token / update path):**
Given an `add_sensor_spec` invocation that updates an existing sensor spec (confirmation
token required), When the spec is successfully updated, Then both notifications are
dispatched if the table-name set changed; no notification if the update changed only
column definitions or non-schema attributes (table-set-delta gate from S-5.03 applies).

## Dependency Notes

- **Depends on S-5.03:** S-5.03 establishes the `Peer<RoleServer>` notification pattern.
  S-5.12 adds the same wiring to the `add_sensor_spec` handler — it does NOT modify the
  `reload_config` path established by S-5.03.
- **Handler signature change:** The `add_sensor_spec` handler in `server.rs` (currently
  created by S-5.01 stub + BC-2.16.008 scope) must accept `Peer<RoleServer>` from its
  `RequestContext` to dispatch notifications. This is an rmcp 1.7 `RequestContext.peer`
  access, identical to the pattern used in the `reload_config` handler.
- **BC prerequisite:** Before this story can move to `status: ready`, either BC-2.16.008
  must be amended by PO to add a notification postcondition for the `add_sensor_spec`
  tool path, or BC-2.16.007 must be extended to cover this case.

## Tasks (Sketch)

1. In `crates/prism-mcp/src/server.rs`, update the `add_sensor_spec` handler to extract
   `context.peer` (type `Peer<RoleServer>`) from its `RequestContext`.
2. After a successful non-dry-run `add_sensor_spec` + internal `reload_config` call,
   apply the same table-set-delta gate as S-5.03: compare table-name sets before and
   after reload; dispatch both notifications if the set changed.
3. Do NOT dispatch notifications on dry-run invocations.
4. Write Red Gate tests for AC-001, AC-002, AC-003.

## Architecture Compliance Rules

- Notification dispatch uses `RequestContext.peer` (rmcp 1.7) — same pattern as S-5.03.
  Do NOT introduce a shared `Arc<Peer<RoleServer>>` field on `PrismServer` as a shortcut;
  use the per-request context peer.
- The table-set-delta gate from S-5.03 MUST be applied here too — `add_sensor_spec` must
  not send notifications on column-only or non-schema-attribute changes.
- Dry-run mode (`dry_run: true`) MUST NOT dispatch any notifications (no persistent change
  was made).
