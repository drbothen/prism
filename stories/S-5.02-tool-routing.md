# S-5.02 — prism-mcp: Tool Routing, Errors, and Client Scoping

## Narrative

As an MSSP analyst using Prism, I want every tool call to be scoped to a specific client
(or set of clients) and to receive structured, actionable error responses when something
goes wrong, so that I can reason about failures and route queries correctly in a
multi-tenant environment.

## Objective

Fix and extend the already-merged `validate_client_ids` free function, upgrade
`error_mapping.rs` to produce the ratified nested BC-2.10.007 structured content shape,
and replace the merged `list_capabilities` simple bool map with the ratified tri-state +
resolution-chain model (BC-2.10.011). This story bridges the gap between what shipped in
S-5.01-FOLLOWUP-MCP-BOOT and the locked PO contracts.

## Tasks

### R1 — Fix `validate_client_ids` message prefix (BC-2.10.004 v2.8)

**File:** `crates/prism-mcp/src/server.rs` (lines 1215–1231 — delta, do not rewrite the function)

The merged `validate_client_ids` emits an `rmcp::ErrorData` with message
`"Invalid client_id '{id}': must match [a-zA-Z0-9_-]{1,64} (BC-2.10.004)"` — it is
missing the `E-MCP-001: ` prefix required by BC-2.10.004 v2.8 Implementer Note §1.
Change the message format to:

```
"E-MCP-001: invalid client_id format: '{id}'"
```

Additionally, the `ErrorData` returned by `validate_client_ids` must be upgraded from the
flat `rmcp::model::ErrorData::new(...)` to produce the nested `structuredContent.error`
shape required by BC-2.10.007. Because `validate_client_ids` currently returns raw
`rmcp::model::ErrorData`, the MCP error response it produces has no `structuredContent`
key — only a `code` and `message`. To emit the full nested shape, `validate_client_ids`
must construct a `CallToolResult` with `isError: true` and the BC-2.10.007
`structuredContent.error` object (9 fields + `_meta.trust_level`). See R3 for the
shared error response builder.

Three cases per BC-2.10.004 v2.8 Error Cases table — all three MUST flow through
the structured shape:
- **(a) Missing/empty:** `client_id` absent or `""` → `E-MCP-001`, `original_params_valid: false`
- **(b) Malformed/invalid characters:** fails `[a-zA-Z0-9_-]{1,64}` → `E-MCP-001`, `original_params_valid: false`
- **(c) Well-formed but not registered:** passes format; unknown at runtime → `E-CFG-100` via `PrismError::ClientNotFound` → `error_mapping.rs` → existing `-32602` arm, `original_params_valid: true`

**CRITICAL — do NOT route (a)/(b) through `PrismError::InvalidClientId`.**
`PrismError::InvalidClientId` displays as `"E-AUTH-003: ..."` — a namespace collision
with the sensor-layer bearer-token rejection code. The `validate_client_ids` path must
stay on the `E-MCP-001` path, constructing the message string directly.

### R2 — Add `SensorRateLimited` explicit arm in `map_prism_error` (BC-2.10.007 v1.5)

**File:** `crates/prism-mcp/src/error_mapping.rs` (delta to the `PrismError::SensorRateLimited` match arm)

The existing arm in `map_prism_error` collapses `SensorRateLimited` into the generic
`SensorHttpError | SensorTimeout | SensorResponseParse | SensorRateLimited` group with
`(-32000, "Internal error; see audit log")`. This loses the `retry_after_ms` field.

Replace the multi-arm sensor group by splitting `SensorRateLimited` out:

```rust
// E-SENSOR-004: Sensor rate limited → -32000 Internal, retry_after_ms threaded out
PrismError::SensorRateLimited { retry_after_ms, .. } => (
    codes::INTERNAL_ERROR,
    format!("Internal error; see audit log"),  // redacted per AD-017
    // NOTE: retry_after_ms threaded to structured error builder; see to_error_data_with_retry
),
```

Because `map_prism_error` returns `(i32, String)`, the `retry_after_ms` value cannot be
carried through to `to_error_data` without changing the signature. The implementer MUST
add a companion function:

```rust
/// Like `to_error_data` but threads `retry_after_ms` through to the structured
/// BC-2.10.007 envelope when the error is `SensorRateLimited`.
pub fn to_error_data_with_retry(err: PrismError) -> (ErrorData, Option<u64>)
```

This function extracts `retry_after_ms` from `SensorRateLimited` before delegating to
`map_prism_error`, and returns the millisecond value alongside the `ErrorData` so the
caller (the structured error response builder) can convert it to seconds
(`retry_after_ms / 1000`) for `retry_after_seconds`.

### R3 — Upgrade error response shape to nested BC-2.10.007 envelope

**File:** `crates/prism-mcp/src/error_mapping.rs` (new function `build_structured_error_response`)

The BC-2.10.007 v1.5 wire shape is NESTED — not the flat 7-field object referenced in
the v1.5 story spec. The old story spec framing is superseded. The ratified shape is:

```json
{
  "isError": true,
  "content": [{"type": "text", "text": "ERROR: [{category}] - {message}. {suggestion}"}],
  "structuredContent": {
    "error": {
      "code":                  "E-MCP-001",
      "message":               "...",
      "category":              "validation",
      "retryable":             false,
      "retry_after_seconds":   null,
      "suggestion":            "...",
      "source":                "prism_mcp",
      "original_params_valid": false,
      "upstream_message":      null
    },
    "_meta": {"trust_level": "internal"}
  }
}
```

Add `build_structured_error_response(...)` to `error_mapping.rs` that constructs this
shape given the 9 `structuredContent.error` fields + the `content[].text` string.
All callers of `to_error_data` that produce user-visible MCP tool error responses MUST
route through this builder so the `_meta.trust_level: "internal"` field is always present.

`retry_after_seconds` MUST be `null` in JSON (not absent) when `retry_after_ms` is
`None`. Type: `u64 | null`.

`upstream_message` MUST be `null` when the error originates in Prism (not a sensor).
For `SensorRateLimited`, the sensor error detail goes into `upstream_message` only —
never into `message` or `content[].text` per DI-006.

### R4 — Replace `list_capabilities` bool map with tri-state + resolution-chain (BC-2.10.011 v1.5)

**File:** `crates/prism-mcp/src/server.rs` (lines 3108–3197 — substantial delta to the `list_capabilities` handler body)

The merged handler produces `{client_id, client_registered, capabilities: Map<String, bool>, not_implemented, note}`. BC-2.10.011 v1.5 supersedes this with the tri-state + hierarchical capability-path model.

Required changes (per BC-2.10.011 v1.5 Implementer Gap §1–6):

1. **Tri-state per-capability:** Replace `capabilities: Map<String, serde_json::Value::Bool(live)>` with `capabilities: Map<String, CapabilityEntry>` where `CapabilityEntry` is a new struct with:
   - `status: CapabilityStatus` (enum: `"enabled"` | `"runtime_disabled"` | `"compile_time_disabled"`)
   - `resolution_chain: Vec<ResolutionStep>` (each step: `level: "compile_tier"|"runtime_tier"`, `result: "permit"|"allow"|"deny"`, `source: String`)

2. **Resolution logic:** For each capability path, call the SAME capability resolver used by the write pipeline (BC-2.04.004). If the capability resolver is not yet accessible from `PrismServer`, expose it from `WriteExecutor` or `FeatureFlagEvaluator`. A separate implementation is forbidden.

3. **Rename `not_implemented` → `not_registered_tools`:** Same constant (`NOT_YET_AVAILABLE_TOOLS`), renamed field.

4. **Cross-client summary mode** (`client_id: null`): Return per-client summary shape instead of the `"<all>"` placeholder string:
   ```json
   {"client_id": null, "clients": {"acme": {"client_registered": true, "enabled_count": 3, "runtime_disabled_count": 1, "compile_time_disabled_count": 2}}, "not_registered_tools": [...]}
   ```

5. **Remove `note` field:** The response is now self-documenting via `resolution_chain`.

6. **`client_registered`:** Keep — already correctly driven by `FeatureFlagEvaluator::client_exists()`.

**`ListCapabilitiesParams.client_id`** is already `Option<String>` in the merged code. No change needed to the params struct.

## Acceptance Criteria

**AC-001:** Given a `validate_client_ids` call with an empty string `""`, When the function
is invoked, Then it returns an error whose message starts with `"E-MCP-001: invalid client_id format:"`.
(traces to BC-2.10.004 v2.8 postcondition case (a))

**AC-002:** Given a `validate_client_ids` call with a client_id containing `/` or `..`
(e.g., `"acme/../../etc"`), When invoked, Then it returns `E-MCP-001` with
`original_params_valid: false` in the structured error envelope.
(traces to BC-2.10.004 v2.8 postcondition case (b))

**AC-003:** Given a tool call where `client_id` passes format validation but is not present
in the runtime capability registry, When `PrismError::ClientNotFound` is mapped via
`error_mapping.rs`, Then the response carries code `E-CFG-100`, `category: "configuration"`,
`retryable: false`, `original_params_valid: true`.
(traces to BC-2.10.004 v2.8 postcondition case (c))

**AC-004:** Given any MCP tool error response generated by the structured error builder,
When the response JSON is inspected, Then `structuredContent.error` contains exactly these
9 fields — `code`, `message`, `category`, `retryable`, `retry_after_seconds`, `suggestion`,
`source`, `original_params_valid`, `upstream_message` — and `structuredContent._meta.trust_level`
equals `"internal"`.
(traces to BC-2.10.007 v1.5 postcondition — wire shape)

**AC-005:** Given a `PrismError::SensorRateLimited { retry_after_ms: 30_000, .. }`, When
mapped through `to_error_data_with_retry`, Then the structured error response has
`retryable: true` and `retry_after_seconds: 30` (ms / 1000).
(traces to BC-2.10.007 v1.5 postcondition — 429 wiring)

**AC-006:** Given a `PrismError::SensorRateLimited { retry_after_ms: None, .. }` (no
Retry-After header), When mapped, Then `retry_after_seconds` is present in the JSON as
`null` (not absent).
(traces to BC-2.10.007 v1.5 postcondition — null-not-absent invariant)

**AC-007:** Given a sensor error whose raw message contains a prompt-injection payload,
When the structured error response is constructed, Then the payload appears only in
`upstream_message` and is absent from `message` and `content[].text`.
(traces to BC-2.10.007 v1.5 invariant DI-006)

**AC-008:** Given `list_capabilities(client_id: "acme")` where a capability path has a
`[[write_endpoints]]` entry (compile tier permits) and the runtime prism.toml grants it,
When called, Then `capabilities["sensor.crowdstrike.containment"].status` is `"enabled"`
and `resolution_chain` has two steps (`compile_tier` → `permit` and `runtime_tier` → `allow`).
(traces to BC-2.10.011 v1.5 postcondition — single-client mode)

**AC-009:** Given `list_capabilities(client_id: "acme")` where a capability has no
`[[write_endpoints]]` entry in the sensor TOML (compile tier denies), When called, Then
`status` is `"compile_time_disabled"` and `resolution_chain` has one step
(`compile_tier` → `deny`).
(traces to BC-2.10.011 v1.5 postcondition — compile_time_disabled status)

**AC-010:** Given `list_capabilities(client_id: null)` (cross-client summary), When called,
Then the response shape is `{client_id: null, clients: {<id>: {client_registered, enabled_count, runtime_disabled_count, compile_time_disabled_count}}, not_registered_tools: [...]}`.
(traces to BC-2.10.011 v1.5 postcondition — cross-client summary mode)

**AC-011:** Given a `list_capabilities` response, When inspected, Then the field is named
`not_registered_tools` (not `not_implemented`), and it contains exactly the
`NOT_YET_AVAILABLE_TOOLS` constant's entries.
(traces to BC-2.10.011 v1.5 postcondition — field rename)

## Architecture Compliance Rules

1. **`validate_client_ids` must stay on the `E-MCP-001` path.** NEVER route cases (a)/(b)
   through `PrismError::InvalidClientId` — it displays as `E-AUTH-003`, a namespace
   collision with the sensor-layer bearer-token error.
2. **Nested structured error shape required (BC-2.10.007 v1.5).** The old flat 7-field
   story-spec framing is superseded. Every error response builder invocation must produce
   the 9-field `structuredContent.error` object + `_meta.trust_level: "internal"`.
3. **`retry_after_seconds` must be `null` (not absent) when not applicable.** Consistent
   client-side handling requires the field to always be present in the JSON.
4. **`list_capabilities` capability resolver must be the SAME instance used by the write
   pipeline (BC-2.04.004).** A separate implementation is a P1 finding under
   architecture compliance.
5. **`upstream_message` isolation.** Raw sensor error text must appear ONLY in
   `structuredContent.error.upstream_message`. It must never be interpolated into
   `message` or `content[].text` per DI-006.
6. **`#[non_exhaustive]` compliance.** Any new public struct (`CapabilityEntry`,
   `ResolutionStep`, `CapabilityStatus`) must carry `#[non_exhaustive]` per CLAUDE.md
   `#[non_exhaustive]` discipline.
7. **No `PrismError::InvalidClientId` in the MCP validate-path.** The symbol-keyed
   `new_unchecked_audit.rs` allowlist applies only to `OrgSlug::new_unchecked`.

### Forbidden Dependencies

`prism-mcp` must NOT gain a dependency on `prism-spec-engine` for capability resolution.
The capability resolver must be accessed via `prism-core`'s `FeatureFlagEvaluator` or
`WriteExecutor`. If that indirection requires an API addition to `prism-core`, add it
there — do not bypass the module boundary.

## Dev Notes

- The `resolution_chain` in `list_capabilities` serves the same diagnostic function as
  the old `resolution_trace` concept in v1 story specs — one entry per resolution tier,
  showing what determined the outcome. Keep each step concise: `level + result + source`.
- Prompt injection defense (S-1.10 / DI-006) applies to sensor error messages in the
  `upstream_message` field. The `build_structured_error_response` builder must ensure
  the sensor text never leaks into `message` or `content[].text`.
- For the capability resolver integration: `FeatureFlagEvaluator` is already accessible
  from `PrismServer` via `self.write_executor` (see merged code line 3135
  `let ff = we.feature_flags()`). The tri-state evaluation must use `ff` for runtime-tier
  checks and `WriteEndpointRegistry` (or equivalent) for compile-tier checks.
- The test file follows the project convention: `tests/<bc-slug>_test.rs` for bc-specific
  suites, or additions to the existing `tests/tool_dispatch_tests.rs`. The 13 new Red
  Gate tests belong in `tool_dispatch_tests.rs` to keep BC-2.10.* tests colocated.
