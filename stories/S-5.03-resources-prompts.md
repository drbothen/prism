# S-5.03 — prism-mcp: Resources and Prompts

## Narrative

As a Claude Code AI agent orchestrating MSSP workflows, I want to access structured
resources (client list, sensor inventory, OCSF schema, health status) and pre-built
prompt templates for common security operations workflows, so that I can quickly orient
to the environment and guide analysts through repeatable investigation patterns.

## Objective

Implement MCP resources for client and sensor inventory, MCP prompts for common security
workflows, the `check_sensor_health` tool, and the `prism://sensors/health` resource. These give AI
agents a structured way to explore the Prism environment before issuing queries.

## Tasks

1. Implement MCP resource handlers in `crates/prism-mcp/src/resources.rs`:
   - `prism://config/clients`: return JSON array of all configured clients, each element a
     `ClientInventoryEntry` with fields `{ client_id, display_name (String|null), sensor_count,
     enabled_sensors: [String] }` (BC-2.10.008 v1.12 postcondition 1). `display_name` is the
     human-readable org name sourced from `[[orgs]].name` in `prism.toml` (the `OrgEntry.name:
     Option<String>` field); serializes to JSON `null` when the `name` field is absent from the
     `OrgEntry`. Read directly from the config snapshot in `render_client_list_resource`. Note:
     `capabilities_summary` is NOT part of this shape — the canonical capabilities surface is
     BC-2.10.011 (`list_capabilities` meta-tool); do NOT add `capabilities_summary` to
     `ClientInventoryEntry`.
   - `prism://config/clients/{client_id}/sensors`: validate `client_id` via `TenantId::new()`, then
     return JSON array of sensor configs for that client, each entry a `SensorConfigEntry` with
     fields `{ sensor_type, status, credential_ref, sources: [String], api_base_url }` (BC-2.10.008
     v1.12 postcondition 2). `status` is ALWAYS `"active"` — a constant, not a variable. Sensors
     appear in this resource ONLY because they are present in `resolved_spec_map`; presence IS
     definitional activity. The overlay model has no "disabled but present" state — a disabled
     sensor is simply absent from the overlay and therefore absent here. EC-10-015 ("all disabled →
     enabled: false") is retired in BC-2.10.008 v1.12 as structurally impossible under this model;
     do NOT add an `enabled` boolean field. `api_base_url` MUST contain only scheme+host+port
     (e.g., `"https://api.crowdstrike.com"`); strip full paths, query strings, and credentials.
     **Stale field names `sensor_id`, `enabled` (boolean), `configured_sources` are NOT part of
     this shape** — use `sensor_type`, `status`, `credential_ref`, `sources`, `api_base_url`.
   - `prism://schema/{sensor_id}/{table_name}`: return the OCSF schema definition for a given
     sensor + source combination, sourced from the spec engine (BC-2.10.008)
   - Implement resource serving by overriding `list_resources`, `list_resource_templates`,
     and `read_resource` methods on `ServerHandler` for `PrismServer` in `server.rs`
     (rmcp 1.7 has no `#[resource_handler]` macro; resources are served via direct
     `ServerHandler` method overrides — confirmed against rmcp 1.7 source)

2. Implement MCP prompts in `crates/prism-mcp/src/prompts.rs`:
   - `triage_alerts`: "Triage open alerts for a client" — guides the agent through
     checking all sensors for open high/critical alerts; argument: `client_id`
   - `investigate_host`: "Investigate a specific host across all sensors" — guides
     cross-sensor correlation by hostname or IP; arguments: `client_id`, `hostname`
   - `client_overview`: "Security posture overview for a client" — guides pulling alert
     counts, health status, and recent activity; argument: `client_id`
   - `cross_client_status`: "Cross-client security status" — guides checking all clients
     for critical alerts; argument: `time_range` (optional)
   - Each prompt includes `name`, `description`, and parameterized `arguments`
   - Each prompt message includes a security reminder about untrusted sensor data (DI-006)
   - Prompts are static (defined at build-time, not dynamically generated) (BC-2.10.009)
   - Wire via `PromptRouter<PrismServer>` held on `PrismServer`, using the
     `#[prompt_handler(router = self.prompt_router)]` macro on `impl ServerHandler for PrismServer`
     (rmcp 1.7 pattern — confirmed against `rmcp-1.7.0/tests/test_prompt_handler.rs`)

## Acceptance Criteria

**AC-1:** Given a Prism instance configured with two clients ("acme" with `name = "Acme Corp"` in
`[[orgs]]`, "globex" with no `name` field), When `prism://config/clients` is read, Then the response
is a JSON array containing both clients, each element a `ClientInventoryEntry` with `client_id`,
`display_name`, `sensor_count`, and `enabled_sensors` populated. `display_name` for "acme" MUST be
`"Acme Corp"` (sourced from `OrgEntry.name`); `display_name` for "globex" MUST be JSON `null`
(absent `OrgEntry.name`). Field `capabilities_summary` MUST NOT appear — it is not part of this
shape (canonical capabilities surface is BC-2.10.011).
(traces to BC-2.10.008 v1.12 postcondition 1)

**AC-2:** Given `prism://config/clients/acme/sensors` for a client "acme" with CrowdStrike and
Claroty sensors (and a second client "globex" with different sensors also configured), When read,
Then: (a) the response lists ONLY the two sensors belonging to "acme" — sensors from "globex" or
any other client MUST NOT appear (DI-008 per-client filter — the handler MUST filter by the
`client_id` URI segment before returning results; returning all sensors regardless of `client_id`
is a data separation defect); (b) each sensor entry includes an `api_base_url` field containing
ONLY the scheme+host+port component (e.g., `"https://api.crowdstrike.com"`) — full URL paths,
query strings, and credentials MUST NOT appear in this field; (c) each entry is a `SensorConfigEntry`
with the complete canonical field set: `sensor_type`, `status` (always `"active"` — a definitional
constant in the overlay model; EC-10-015 is retired in BC-2.10.008 v1.12 as structurally impossible),
`credential_ref`, `sources` (list of data source identifier strings), and `api_base_url`. **The stale
field names `sensor_id`, `enabled` (boolean), and `configured_sources` MUST NOT appear** — they were
removed in BC-2.10.008 v1.12 (RECONCILIATION-1B); any implementation emitting them is non-conformant.
(traces to BC-2.10.008 v1.12 postcondition 2; DI-008 invariant; VP-050)

## Architecture Mapping

| Component | Module | Pure/Effectful |
|-----------|--------|----------------|
| MCP resources and prompts handlers | `prism-mcp` (SS-10, SS-08) | Effectful |

`prism-mcp` implements the MCP resources surface (schema definitions, sensor specs as
resources, OCSF class catalog) and prompt templates (query-builder prompts, security
analyst prompts). Resource content generation is mostly pure; MCP transport I/O and
arc-swap config reads are effectful. Per `architecture/module-decomposition.md`, SS-10
(MCP Interface) and SS-08 (Sensor Health) are both owned by `prism-mcp`.

## Architecture Compliance Rules

- Resource URIs MUST follow the `prism://` scheme — do not use HTTP URLs or bare paths
- The `prism://schema/{sensor_id}/{table_name}` resource MUST source its data from the spec
  engine (S-1.11), not from hardcoded schema definitions in prism-mcp
- The `check_sensor_health` tool MUST perform actual API calls — it MUST NOT return cached
  data from `prism://sensors/health` (the resource caches the tool's output, not vice versa)
- Prompt templates MUST be stored as static strings in `prompts.rs`, not as files on
  disk — this avoids filesystem path dependencies in the MCP server
- `SensorHealthResult.error` MUST be sanitized (prompt injection defence) before
  inclusion in the response
- **rmcp 1.7 resource pattern:** Override `list_resources`, `list_resource_templates`, and
  `read_resource` on `impl ServerHandler for PrismServer` directly — there is NO
  `#[resource_handler]` macro in rmcp 1.7 (confirmed against rmcp source)
- **rmcp 1.7 prompt pattern:** Add a `PromptRouter<PrismServer>` field to `PrismServer` and
  decorate `impl ServerHandler for PrismServer` with
  `#[prompt_handler(router = self.prompt_router)]` — this is the rmcp 1.7 canonical pattern
  (confirmed against `rmcp-1.7.0/tests/test_prompt_handler.rs`)
- **Notification dispatch pattern:** `Peer<RoleServer>::notify_resource_list_changed()` and
  `notify_tool_list_changed()` are called on `context.peer` from within the `reload_config`
  tool handler — NOT from a background thread. The peer handle must be passed from the
  hot-reload code path back to the MCP handler layer
- **Prompt names are BC-authoritative:** The four mandated prompt names are
  `triage_alerts`, `investigate_host`, `client_overview`, `cross_client_status`
  per BC-2.10.009. Do NOT implement different names.

## Dev Notes

- Prompts are distinct from tools in MCP: they are retrieved via `prompts/get` and are
  intended as starting templates for user workflows, not executable operations. Keep
  prompt text concise (under 500 tokens each) to avoid overwhelming the AI context.
- The four mandated prompt names are `triage_alerts`, `investigate_host`, `client_overview`,
  `cross_client_status` per BC-2.10.009. Earlier story versions listed different names
  (`investigate_alert`, `triage_case`, etc.) — those were incorrect and have been corrected
  in v1.14 of this story.
- Health cache should have a TTL (suggest 5 minutes) to avoid staleness. After TTL
  expiry, `prism://sensors/health` should return the cached data with a `stale: true` flag
  rather than clearing it. BC-2.08.006 EC-08-012 confirms no automatic expiry is required.
- **EC-08-013 retired/subsumed (BC-2.08.006 v1.6):** EC-08-013 ("zero clients configured →
  `{\"clients\":{}}` ") is retired and subsumed into EC-08-011 per architect Ruling 4
  (2026-06-18). With zero clients, no `check_sensor_health` call is semantically meaningful
  → health cache remains empty → the EC-08-011 sentinel fires. EC-08-013 is un-retired
  when S-5.04 ships with cache write semantics and a zero-client integration test is needed.
  The ID EC-08-013 is reserved; do NOT reuse it.
- **Notification dispatch failure handling (BC-2.16.007 v1.7):** If `notify_resource_list_changed`
  or `notify_tool_list_changed` returns an error, the error MUST be logged (e.g., `tracing::warn!`)
  rather than silently discarded. Silent dispatch failure is a correctness defect — the hot-reload
  completes successfully, but the silent discard makes the notification unreliable. Use
  `if let Err(e) = context.peer.notify_resource_list_changed().await { tracing::warn!(...) }`.
- **Cross-client health is OUT of S-5.03 scope, deferred to S-5.04** (BC-2.08.005 v1.7
  RECONCILIATION-2, confirmed per OOD-001 adjudication v1.4). `client_id: String` is required
  and must never be null. `check_sensor_health` always operates within a single client scope in
  S-5.03. S-5.04 (`S-5.04-sensor-health.md`) owns the live-probe work and must explicitly extend
  this contract if a cross-client mode is desired. The `with_partial_failures` builder and
  `partial_failures` field serve only the removed cross-client path — they MUST NOT be added to
  S-5.03 implementation; if already added, they MUST be removed.
- **`add_sensor_spec` MCP notification dispatch is OUT of S-5.03 scope, deferred to S-5.12.**
  The `add_sensor_spec` tool (BC-2.16.008) internally triggers a `reload_config` call, which
  should dispatch `notifications/resources/list_changed` + `notifications/tools/list_changed`
  when it adds tables. However, wiring the `Peer<RoleServer>` into the `add_sensor_spec` handler
  requires adding a `peer: Peer<RoleServer>` parameter to that handler signature — a distinct
  handler modification outside S-5.03's `reload_config` notification path. S-5.12
  (`S-5.12-add-sensor-spec-mcp-notifications.md`) is the named anchor for this work.
