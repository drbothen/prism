# S-5.11 — prism-mcp: Column-Schema-Change MCP Notifications

## Narrative

As a Claude Code AI agent connected to a running Prism instance, I want to receive
`notifications/tools/list_changed` when a sensor spec is hot-reloaded and column
definitions change within an existing table (without any table name being added or
removed), so that I can refresh my knowledge of the available schema fields without
needing to poll.

## Problem Statement

S-5.03 (AC-9) implements the **table-set-delta gate**: MCP notifications fire only when
the set of registered table names changes. A column-only spec change — columns added,
removed, or renamed within an existing table, with no change to the table-name set —
does NOT fire a notification in S-5.03 scope.

BC-2.16.007 v1.7 explicitly defers column-delta notification to this story:

> **Deferred — column-delta notification (S-5.11):** Notifying MCP clients when column
> definitions change within an existing table (no table-name-set change) is explicitly
> deferred to S-5.11.

This story extends the S-5.03 notification gate to also fire when column definitions
change, even if the table-name set is unchanged.

## Authority

BC-2.16.007 (sensor spec hot-reload behavioral contract) is the authoritative specification for this story. The contract's deferral block explicitly names S-5.11 as the anchor for column-delta notification, making this story a named deferral from that contract:
`.factory/specs/behavioral-contracts/BC-2.16.007-sensor-spec-hot-reload.md`.

BC-2.16.007 defines the `notifications/tools/list_changed` and `notifications/resources/list_changed` dispatch semantics, the file-hash-based change detection invariant, and the table-set-delta gate established by S-5.03. S-5.11 extends that gate with a second trigger condition: column-definition-set changes within existing tables (even when the table-name set is unchanged before and after reload).

`architecture/module-decomposition.md §Cargo Workspace Structure` establishes SS-10 (MCP Server) ownership in `prism-mcp` and SS-16 (Sensor Spec Engine) ownership in `prism-spec-engine`.

No formal ADRs govern this story. This story cannot move to `status: ready` until BC-2.16.007 is amended by the product-owner to add the column-delta notification postcondition (or a new BC is authored), and the `behavioral_contracts:` frontmatter is updated accordingly.

## Acceptance Criteria (Sketch — PO to elaborate before status: ready)

**AC-001 (traces to BC-2.16.007 postcondition "Modified spec files" — column-delta extension):**
Given a hot-reload where a sensor spec gains a new column in an existing table (the
table-name set is unchanged before and after), When the reload completes, Then
`notifications/tools/list_changed` (and `notifications/resources/list_changed`) are
dispatched — signalling that the tool schema has changed because new fields are
queryable.

**AC-002 (traces to BC-2.16.007 postcondition "Modified spec files" — column-delta extension):**
Given a hot-reload where a sensor spec removes a column from an existing table (the
table-name set is unchanged), When the reload completes, Then both MCP notifications
are dispatched.

**AC-003 (traces to BC-2.16.007 invariant "File-hash-based change detection"):**
Given a hot-reload where only a non-schema spec attribute changes (rate limits, pagination
config — no column definitions, no table-name-set change), When the reload completes,
Then no MCP notification is dispatched (non-schema-attribute changes remain silent).

- **Depends on S-3.13:** S-3.13 delivers `TableRegistry::registered_tables()` and the

  BC-2.16.009 must be authored), and the `behavioral_contracts` array updated.

## Tasks (Sketch)

1. Extend `TableRegistry` (or add a column-hash accessor in `prism-query`) to expose
   column-definition sets for set-comparison on reload.
2. Extend the notification gate in `resources.rs` (S-5.03's `reload_config` path) to
   also compare column-definition sets before and after reload.
3. Fire `notifications/tools/list_changed` + `notifications/resources/list_changed` when
   the column-definition set changes (even with unchanged table-name set).
4. Do NOT fire notifications for non-schema attribute changes (rate limits, etc.).
5. Write Red Gate tests covering AC-001, AC-002, AC-003.

## Previous Story Intelligence

- **S-5.03:** Wires `Peer<RoleServer>` into `reload_config` and implements the
  table-set-delta gate. The column-delta gate in S-5.11 is an additive extension — do
  not replace the table-set gate.
- **S-3.13:** Delivers `TableRegistry` with `registered_tables() -> Vec<String>`. An
  additional API exposing column-definition sets (or column hashes) per table will be
  needed. Architect adjudication may be needed on whether this is an extension to
  `TableRegistry` or a new `ColumnRegistry`.

## Architecture Compliance Rules

- Notification dispatch pattern is identical to S-5.03: `Peer<RoleServer>` from
  `RequestContext` in the `reload_config` handler path.
- The table-set-delta gate from S-5.03 MUST remain active. S-5.11 only adds a second
  trigger condition; it does not replace the first.
