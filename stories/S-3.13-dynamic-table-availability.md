# S-3.13 v1.19 — prism-query: Dynamic Table Availability

## Narrative

As a Prism analyst, I want the query engine to only expose tables for sensors that
are currently configured and loaded so that my query workspace reflects reality —
unloaded sensors produce helpful errors with suggestions, not cryptic DataFusion
schema failures, and adding or removing a sensor spec file immediately changes
which tables are available.

## Objective

Implement dynamic DataFusion table registration driven by the live `ConfigSnapshot`.
When a sensor spec is loaded, its tables are registered in the DataFusion schema.
When a spec is unloaded or removed, its tables are deregistered. Queries against
unregistered tables return `E-QUERY-037` (`TableNotAvailable`) with a `did_you_mean`
suggestion listing configured sensors. Hot reload adds and removes tables atomically within the
config swap. Per osquery's dynamic table availability pattern.

## Tasks

1. Implement `TableRegistry` in `crates/prism-query/src/table_registry.rs`:
   ```rust
   pub struct TableRegistry {
       registered: Arc<RwLock<HashSet<String>>>,  // table names currently available
       schema_by_table: Arc<RwLock<HashMap<String, SchemaRef>>>,
   }
   impl TableRegistry {
       pub fn register_sensor(&self, spec: &SensorSpec) -> Result<()>;
       pub fn deregister_sensor(&self, sensor_id: &str) -> Result<()>;
       pub fn is_registered(&self, table_name: &str) -> bool;
       pub fn registered_tables(&self) -> Vec<String>;
       pub fn sensor_for_table(&self, table_name: &str) -> Option<String>;
   }
   ```
   - `register_sensor()`: for each `[[sensor.tables]]` entry in the spec, add
     `{sensor_id}_{table_name}` to `registered` and store its Arrow schema
   - `deregister_sensor()`: remove all tables whose names start with `{sensor_id}_`
   - Thread-safe: `Arc<RwLock>` on both collections; reads are non-blocking in normal
     operation

2. Initialize `TableRegistry` on `QueryEngine` construction:
   - Load initial set from the `ConfigSnapshot` at startup
   - For each sensor spec in the snapshot: call `register_sensor()`
   - Store `TableRegistry` as `Arc<TableRegistry>` in `QueryEngine`

3. Integrate `TableRegistry` with the hot-reload path (S-1.12):
   - After a successful config swap, compute the delta:
     - New sensors in `new_config` not in `old_config`: call `register_sensor()`
     - Sensors in `old_config` not in `new_config`: call `deregister_sensor()`
     - Sensors in both: check if spec changed; if so, deregister + re-register
   - **DEFERRED-TO-S-5.03:** Send MCP `notifications/tools/list_changed` if the registered table set changed. (The table-registration delta above is in scope for S-3.13; only the MCP notification dispatch defers to S-5.03.)
   - In-flight queries that started before deregistration: they hold an
     `Arc<ConfigSnapshot>` reference (CI-007); their `SensorAdapter` calls proceed
     against the old spec. Only new queries see the updated table set.

4. Validate table references against `TableRegistry` in a plan-time gate in
   `engine.rs` (in the validation pass BEFORE `materialize_query` is called;
   `planner.rs` does NOT exist — do not create it):
   - After parsing, for each `source_ref` in the `QueryPlan`: check
     `table_registry.is_registered(source_ref)` at the earliest point where
     `TableRegistry` is accessible. If `scoping.rs` performs source-ref inspection,
     the gate may live there; the invariant is: the check must fire BEFORE
     `materialize_query` so errors are reported without fan-out.
   - Add `PrismError::TableNotAvailable` variant to `prism-core/src/error.rs`:
     ```rust
     TableNotAvailable {
         table: String,
         sensor: String,
         available_sensors: String,   // pre-formatted, e.g. "[crowdstrike, claroty]"
         available_tables: String,    // pre-formatted, e.g. "[crowdstrike_alerts, ...]"
         did_you_mean: String,        // "" or " Did you mean: 'crowdstrike_alerts'?"
     }
     ```
     Caller pre-formats all `String` fields; `Display` impl on the variant assembles
     the final error message from pre-formatted strings. `did_you_mean` is `""` when
     no candidate within Levenshtein ≤ 3 exists.
   - If not registered: return `Err(PrismError::TableNotAvailable { table, sensor,
     available_sensors, available_tables, did_you_mean })` BEFORE the fan-out phase
     (fail fast). Error code: `E-QUERY-037`.
   - Error message format (assembled by `Display` impl):
     ```
     Table 'armis_alerts' is not available. Sensor 'armis' is not configured.
     Available sensors: [crowdstrike, claroty, cyberint]
     Available tables: [crowdstrike_alerts, crowdstrike_hosts, claroty_devices, ...]
      Did you mean: 'crowdstrike_alerts'?
     ```
   - Use `strsim::levenshtein(candidate, requested)` (NOT `edit-distance`) between
     the requested table name and all registered tables; suggest the top-1 match
     if minimum distance ≤ 3. `strsim = "0.11"` must be added as a direct dependency
     to `prism-query/Cargo.toml` (already in `Cargo.lock` transitively; zero new
     packages pulled in).
   - Add explicit `PrismError::TableNotAvailable { .. } =>
     (codes::INVALID_PARAMS /* -32602 */, format!("{err}"))` arm to
     `prism-mcp/src/error_mapping.rs` in the `map_prism_error` function. This arm
     MUST be explicit — do NOT rely on the `#[non_exhaustive]` catch-all fall-through,
     which would regress the MCP error code to `-32000 InternalError`.
   - Merge-coordination note: S-3.13 modifies `prism-query/engine.rs`
     (QueryEngine constructor + plan-time gate). PIVOT-001 also touches `engine.rs`
     (UDF registration). Land the constructor-signature change from PIVOT-001 first,
     then rebase S-3.13 on top. Orchestrator must sequence these branches accordingly.
   - `register_sensor` consumes `SensorSpec` / `Vec<TableSpec>` from
     `ConfigSnapshot.sensor_specs`; the constructor reads from the initial snapshot.

5. Update `explain_query` to list only registered tables:
   - `"available_tables"` in the explain response MUST reflect
     `table_registry.registered_tables()` — not a hardcoded list
   - Call `registered_tables()` at explain time (not cached in the plan)

6. **DEFERRED-TO-S-5.03.** Update `prism://config/clients` MCP resource to reflect only
   loaded sensors. The resource handler (`crates/prism-mcp/src/resources.rs`) reads
   `table_registry.registered_tables()` grouped by sensor_id. On hot-reload that changes
   the table set, dispatch `notifications/resources/list_changed` + `notifications/tools/list_changed`
   (with set-comparison gate so the notification only fires when the table set actually changes).
   This task belongs to S-5.03 (SS-10 MCP interface scope); S-3.13 delivers the
   `TableRegistry` API that S-5.03 consumes. S-5.03 implementer: see S-5.03 AC-8 and AC-9.
   Orchestrator adjudication: ACCEPT-MOVE (2026-06-14).

7. **DEFERRED-TO-S-5.03 (or a dedicated diagnostics story).** Update `prism://diagnostics/summary`
   to include unavailable sensor warnings. If a query was attempted against an unregistered
   table in the last hour: include a summary entry `"unregistered_table_queries": [{"table":
   "armis_alerts", "count": 3, "last_attempted": "10:05:00"}]`. This is MCP diagnostics
   resource scope (SS-10); route to S-5.03 or a dedicated `prism://diagnostics` story if
   S-5.03 scope is already at capacity. Orchestrator adjudication: ACCEPT-MOVE (2026-06-14).

## Acceptance Criteria

**AC-1:** Given `armis.sensor.toml` is loaded and `crowdstrike.sensor.toml` is NOT
loaded, When `table_registry.is_registered("crowdstrike_alerts")` is called, Then
it returns `false`. When `table_registry.is_registered("armis_alerts")` is called,
Then it returns `true`.

**AC-2:** Given a query `SELECT * FROM crowdstrike_alerts` when CrowdStrike is not
configured, When the query is planned, Then it returns `E-QUERY-037` (`TableNotAvailable`)
with the message "Sensor 'crowdstrike' is not configured. Available sensors: [armis,
claroty]" — before any fan-out occurs. (traces to BC-2.11.001 postcondition:
plan-time gate returns structured error with available-sensor context)

**AC-3:** Given a user types `SELECT * FROM crowdstrike_alert` (missing 's'), When
the error is returned as `E-QUERY-037`, Then the `PrismError::TableNotAvailable`
`did_you_mean` field contains `" Did you mean: 'crowdstrike_alerts'?"` (Levenshtein
distance 1 ≤ 3 threshold; computed via `strsim::levenshtein`). (traces to BC-2.11.001
postcondition: did_you_mean suggestion populated when closest registered table is
within distance ≤ 3)

**AC-4:** Given `armis.sensor.toml` is added via hot-reload (file drop or
`add_sensor_spec` MCP call), When the config swap completes, Then

behavior: hot-reload register/deregister updates the live TableRegistry).

## Architecture Compliance Rules

- Table availability check MUST happen at plan time (before fan-out), not at parse
  time. The parser produces a syntactically valid AST regardless of whether tables
  exist; `engine.rs` validates semantic correctness against the live registry in the
  validation pass BEFORE `materialize_query`. `planner.rs` does NOT exist — do not
  create it.
- `TableRegistry` reads during query planning use `RwLock::read()` (non-exclusive) —
  they MUST NOT block query execution. `RwLock::write()` is only held during
  registration/deregistration which happen on the config-reload path, not the
  query path.
- The fuzzy-match suggestion (Levenshtein ≤ 3) MUST be computed via
  `strsim::levenshtein(candidate, requested)` at error time from
  `table_registry.registered_tables()` — not a static list. This ensures
  suggestions are always accurate even as sensors are added/removed. Use `strsim`
  (NOT `edit-distance`); `strsim = "0.11"` is already transitively in `Cargo.lock`.
- In-flight query isolation (CI-007): a query that started before a deregistration
  holds a reference to the old `ConfigSnapshot` and the old `AdapterRegistry`. It
  MUST NOT be terminated mid-execution. Only new queries see the updated table set.
- **DEFERRED-TO-S-5.03:** `notifications/resources/list_changed` dispatch is an SS-10 MCP resource-framework
  deliverable. The set-comparison gate (only fire when the table set actually changes, not on every
  hot-reload) is S-5.03's responsibility; S-3.13 delivers the `TableRegistry` API that exposes
  the registered set for S-5.03 to compare. No notification dispatch in S-3.13's implementation.
- **Org-scoped enumeration (ADR-039, SEC-001/CWE-200):** In multi-tenant overlay deployments,
  `available_sensors` and `available_tables` in `E-QUERY-037` MUST be filtered to the requesting
  org(s) registered sensors/tables via `filter_to_org_visible`. The filter is applied only at
  error-construction time (the non-hot path); the `is_registered()` existence check on the query
  path is NOT org-scoped (the leak was exclusively in the ERROR ENUMERATION fields). See ADR-039
  §Design Specification for the exact `check_availability_gate` and `check_table_availability`
  signature changes, and the sibling-site sweep requirement (TD-VSDD-060: both `execute_inner` and
  `execute_scheduled_inner` call sites must be updated in the same commit).
- **Org-scoped explain_query (ADR-039, SEC-003/CWE-200):** ADR-039's `filter_to_org_visible_*`
  mechanism extends to the `explain_query` surface. `ExplainResult.available_tables` MUST be
  filtered via `filter_to_org_visible_tables(all_registered, &org_scope, &resolved_spec_map)`

  global (when `clients=None` or `resolved_spec_map=None`) preserves backward compatibility with
  single-tenant deployments. The fix lives in `crates/prism-query/src/explain.rs` — the same file
  as Task 5's live-registry wiring.

## Dev Notes

- The osquery pattern: osquery only registers tables for extensions that are currently
  running. If an extension crashes, its tables disappear from the schema. Prism's
  equivalent is sensor specs — if a spec is removed, its tables disappear from the
  DataFusion namespace.
- The error message with sensor suggestions is particularly important for AI-generated
  queries. When Claude generates a query against a sensor the analyst hasn't configured,
  the error message tells Claude exactly which sensors ARE available — enabling it to
  self-correct without human intervention.
- Fuzzy-match suggestions: compute Levenshtein distance via `strsim::levenshtein`
  between the requested name and all registered table names; return the top-1 match
  if minimum distance ≤ 3. Use `strsim = "0.11"` (already in `Cargo.lock`
  transitively; add as a direct dep to `prism-query/Cargo.toml`). Do NOT use
  `edit-distance` — architect decision D-1163 ratified `strsim`. Avoid bringing in
  a full fuzzy-search library for this simple use case.
- Hot-reload table delta: the simplest correct implementation is deregister-all-for-sensor
  then re-register. This handles schema changes within a spec (e.g., new table added
  to an existing sensor) without needing fine-grained diff logic.
- `HotReloadWatcher` is NOT used in this story (D-1163). S-3.13 integrates via the
  merged `ConfigManager` surface: `register_swap_listener`, `process_spec_changes`,
  and `add_sensor_spec`. Do not introduce a separate `HotReloadWatcher` dependency.
