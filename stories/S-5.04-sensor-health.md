# S-5.04 — prism-mcp: Sensor Health Subsystem

## Implementation Note — GAP-002-A Closure

**Dependency update (S-5.04-FIX-001, 2026-05-29):** S-2.07 removed from `depends_on`; replaced
with S-DEMO-001. Rationale: S-2.07's per-sensor auth pattern was superseded by ADR-023 /
PLUGIN-MIGRATION-001-H (merged 2026-05-27). Health check pings must use `SpecDrivenSensorAdapter`
via `AdapterRegistry::get(org_id, sensor_id)` — the registry populated by S-DEMO-001's boot
step 9A. The S-5.04 implementer should call the registered adapter's `fetch()` with a probe
query (e.g., `LIMIT 0`) to verify connectivity; not construct a raw HTTP client independently.
The GAP-002-A comment at boot.rs is removed once S-DEMO-001 merges. S-5.04 is NOT on the
critical path for the initial demo (S-DEMO-001 → S-DEMO-002 → S-DEMO-003 is the demo path);
S-5.04 is a downstream consumer of the adapter registry.

---

## Narrative

As an MSSP analyst managing multiple clients and sensors, I want accurate, detailed
health information for each sensor — connectivity status, authentication validity, rate
limit state, and last successful query time — so that I can quickly identify and remediate
data gaps before they affect detection coverage.

## Objective

Implement the detailed sensor health monitoring subsystem: per-sensor connectivity
checks, authentication validity detection, rate limit state derived from HTTP headers,
last successful query timestamp tracking, and partial health reporting when only some
sensors are available.

## Tasks

1. Create `crates/prism-mcp/src/health/` module directory with:
   - `mod.rs`: `SensorHealthChecker` struct, `HealthCheckResult` type
   - `connectivity.rs`: per-sensor connectivity probe logic
   - `auth.rs`: authentication validity detection
   - `rate_limit.rs`: rate limit state detection from HTTP headers
   - `timestamp.rs`: last successful query timestamp tracking

2. Implement connectivity check in `health/connectivity.rs`:
   - The health probe MUST route through `SpecDrivenSensorAdapter::fetch()` obtained via
     `AdapterRegistry::get(org_id, sensor_id)` (signature: `crates/prism-sensors/src/registry.rs:83`).
     Issue a minimal probe query (e.g., `LIMIT 0` / `LIMIT 1`) against the registered adapter.
     The adapter owns the endpoint path derived from the sensor TOML spec — do NOT hard-code
     endpoint paths in the health module (FIX-001/v1.6 is the authority; supersedes earlier
     raw-HTTP-client approach). For reference only (not for health module to hard-code): the
     CrowdStrike host-enumeration path used by the adapter is `GET /devices/queries/devices/v1`
     (per prism-dtu-crowdstrike routes/mod.rs; `/sensors/queries/devices/v1` is the WRONG,
     unrelated Sensor-Download surface).
   - Probe MUST exercise the actual API endpoint through the adapter — not a TCP ping or DNS check
   - Map probe results: 2xx equivalent → `up`, 5xx → `degraded`, connection error → `down`
   - Capture `latency_ms` using `tokio::time::Instant` around the adapter `fetch()` call
   (BC-2.08.001)

3. Implement auth validity check in `health/auth.rs`:
   - Issue the same adapter-based probe as the connectivity check (same `SpecDrivenSensorAdapter::fetch()` LIMIT-0 path)
   - HTTP 401 or 403 from the adapter → `auth_invalid` (distinct from `down`)
   - Connection error (no HTTP response) → `{ connectivity: down, auth: unknown }`
   - Never conflate "unreachable" with "auth invalid" — these require different
     remediation actions (BC-2.08.002)

4. Implement rate limit detection in `health/rate_limit.rs`:
   - Track HTTP 429 responses per sensor per client
   - Extract `Retry-After` header (seconds or HTTP-date format, parse both)
   - Expose `RateLimitState { is_rate_limited: bool, retry_after: Option<DateTime<Utc>>,
     observed_at: DateTime<Utc> }`
   - Rate limit state clears automatically after `retry_after` time passes
   (BC-2.08.003)

5. Implement last successful query timestamp in `health/timestamp.rs`:
   - Maintain `HashMap<(TenantId, SensorType), DateTime<Utc>>` in `PrismContext`
   - Update on every successful sensor data fetch (not just health checks)
   - Expose via `SensorHealthChecker::last_successful_query(client_id, sensor_type)`
   - Persist timestamps in RocksDB `StorageDomain::Default` under a known key prefix
     so they survive server restarts (BC-2.08.004)

6. Implement partial health aggregation in `health/mod.rs`:
   - `HealthCheckResult::aggregate(results: Vec<SensorHealthResult>) -> OverallStatus`
   - `OverallStatus`: `healthy` (all up), `partial` (some up, some down/degraded),
     `unhealthy` (all down)
   - `partial` is a SUCCESS state, not an error — do not return an error response for
     partial health (BC-2.08.007)

7. Write tests in `crates/prism-mcp/tests/bc_s_5_04_health_test.rs`:
   - Mock sensor returning 200 → `up` with latency
   - Mock sensor returning 401 → `auth_invalid`
   - Mock sensor returning 429 with `Retry-After: 60` → `is_rate_limited: true`,
     `retry_after` is 60s from now
   - Connection refused mock → `down`
   - 3 of 4 sensors up → `OverallStatus::Partial`
   - Last successful query timestamp persists across `SensorHealthChecker` restarts

## Acceptance Criteria

**AC-1:** Given a CrowdStrike sensor endpoint returning HTTP 200, When connectivity is
checked, Then `SensorHealthResult.status` is `up` and `latency_ms` is a non-zero value.
(traces to BC-2.08.001 postcondition 1)

**AC-2:** Given a sensor endpoint returning HTTP 401, When the health check runs, Then
`SensorHealthResult.status` is `auth_invalid` (not `down`), indicating that the sensor
is reachable but credentials are invalid.
(traces to BC-2.08.002 postcondition 1)

**AC-3:** Given a sensor returning HTTP 429 with header `Retry-After: 30`, When rate
limit state is checked, Then `is_rate_limited: true` and `retry_after` is approximately
30 seconds in the future.
(traces to BC-2.08.003 postcondition 1)

**AC-4:** Given a successful CrowdStrike query at 10:30 UTC, When
`last_successful_query("acme", CrowdStrike)` is called at 10:35, Then the returned
timestamp is 10:30 UTC.
(traces to BC-2.08.004 postcondition 1)

**AC-5:** Given a Prism restart, When `last_successful_query` is called after restart,
Then the persisted timestamp from before the restart is returned (not `None`).
(traces to BC-2.08.004 postcondition 2)

**AC-6:** Given a client with 3 sensors up and 1 sensor down, When
`HealthCheckResult::aggregate` is called, Then `OverallStatus` is `Partial` and the
tool response is a success (not an error).
(traces to BC-2.08.007 postcondition 1)

**AC-7:** Given `check_sensor_health(client_id: "acme")` in S-5.04 scope (live probe — actual
API probe is performed via `SpecDrivenSensorAdapter`), When called against a reachable and
authenticated CrowdStrike sensor, Then the response includes a `SensorHealthResult` with:
`probe_level: "live"` (not `"spec-only"`); `reachable: true` (boolean, populated from the
actual probe result — NOT null); `auth_valid: true` (boolean, populated from the actual probe
result — NOT null); `last_successful_query_at` populated with the probe timestamp. When called
against an unreachable sensor, Then `reachable: false` (boolean). When called against a sensor
with invalid credentials, Then `auth_valid: false` (boolean). The prose summary uses live-probe
phrasing (e.g., "2 of 3 sensors healthy for client 'acme' (live probe)") and MUST NOT contain
"spec-only".
(traces to BC-2.08.005 postcondition — live-probe anchor; two-phase probe contract S-5.04 half)

**AC-8:** Given a sensor TOML spec that declares `probe_table = "missing_table"` where no
`[[tables]]` block has `table_name = "missing_table"`, When the spec is loaded by `SpecLoader::parse()`,
Then spec loading is rejected with error code `E-SPEC-026` and the error message includes the
`sensor_id`, the invalid `probe_table` value (`"missing_table"`), and the sorted list of declared
table names. No probe is attempted for this sensor.
(traces to BC-2.16.009 Validation Rule 8 / E-SPEC-026; BC-2.08.001 Error Cases E-SPEC-026)

**AC-9:** Given a valid sensor spec with `probe_table = "detections"` (matching a declared
`[[tables]]` block), When `probe_connectivity()` in `health/connectivity.rs` runs for that sensor,
Then the LIMIT 0 fetch request is routed to the fully-qualified table `"{sensor_id}_detections"`.
If `probe_table` is absent from the spec but `spec.tables` is non-empty, the probe routes to the
first declared table (`spec.tables[0].table_name`, fully-qualified as `"{sensor_id}_{spec.tables[0].table_name}"`). If both `probe_table` is
absent and `spec.tables` is empty, the probe is a structural no-op (legacy fallback; `Up` status
does not imply HTTP contact was made).
(traces to BC-2.08.001 postcondition 5 — probe_table routing / fallback chain)

**AC-10:** Given a Prism instance with CrowdStrike, Cyberint, Claroty, and Armis canonical sensor
TOML specs loaded, When the specs are parsed, Then each spec declares `probe_table` at its top
level: `crowdstrike.sensor.toml` → `"detections"`, `cyberint.sensor.toml` → `"alerts"`,
`claroty.sensor.toml` → `"devices"`, `armis.sensor.toml` → `"devices"`. Each value matches a
declared `[[tables]]` block `table_name` in its respective spec (Rule 8 validation passes with no
`E-SPEC-026` error).
(traces to BC-2.08.001 precondition — sensor spec declares probe_table; BC-2.16.009 Rule 8 EC-009-026 happy path)

**AC-11:** Given all of a client's sensors return HTTP 429 (`is_rate_limited: true`) and none are
unreachable or auth-invalid, When `check_sensor_health` runs, Then `overall_status` is
`"rate_limited"` (not `"healthy"`, `"partial"`, or `"unhealthy"`), the prose summary is
`"0 of N sensors healthy for client 'X' — all rate-limited"` (where N is the sensor count and X
is the client identifier), and every per-sensor entry carries
`suggestion: "Rate limit in effect — wait before retrying."`.
(traces to BC-2.08.007 v1.4 §Postconditions — all-rate-limited aggregate / EC-08-015)

**AC-12:** Given any `check_sensor_health` live-probe call, When the call returns, Then
`structuredContent` includes: (a) `overall_status` — exactly one of `"healthy"`, `"partial"`,
`"rate_limited"`, or `"unhealthy"`; (b) a `summary_counts` object with integer fields
`healthy_count`, `unhealthy_count`, `total_count`, and `rate_limited_count`; (c) for each sensor
entry that is unhealthy, auth-invalid, or rate-limited, a non-empty `suggestion` field — auth-invalid
sensors carry `"Check credentials — sensor rejected authentication."`, unreachable sensors carry
`"Sensor unreachable — verify network and endpoint configuration."`, and rate-limited sensors carry
`"Rate limit in effect — wait before retrying."`. Sensors with `overall_status: "healthy"` need not
carry a `suggestion` field.
(traces to BC-2.08.007 §Postconditions — response shape; `structuredContent` fields `overall_status`, `summary_counts`, per-sensor `suggestion`)

## Architecture Mapping

| Component | Module | Pure/Effectful |
|-----------|--------|----------------|
| Sensor health probes | `prism-mcp` (SS-08) — `src/health/` module owns all probe logic | Effectful |
| Sensor TOML specs | `prism-sensors` (SS-01) — `probe_table` field only; no runtime code added | Data |

`prism-mcp` exposes the `check_sensor_health` MCP tool and owns all probe logic in
`src/health/` (connectivity, auth, rate-limit, timestamp modules). `prism-sensors`
contributes only the TOML spec additions (`probe_table` field on each canonical sensor
spec). Health probe dispatch and result aggregation are effectful (HTTP I/O). The health
module issues probes via `SpecDrivenSensorAdapter::fetch()` obtained through the
`AdapterRegistry` wired at boot. Per `architecture/module-decomposition.md`, SS-08
(Sensor Health) is owned primarily by `prism-mcp`.

## Architecture Compliance Rules

- Connectivity probes MUST route through `SpecDrivenSensorAdapter::fetch()` obtained via
  `AdapterRegistry::get(org_id, sensor_id)` — do NOT construct a `reqwest::Client` directly
  in the health module. The adapter is the correct, unified entrypoint for both data fetching
  and health probing (S-5.04-FIX-001 / v1.6 authority; S-2.07 raw-HTTP-client pattern
  is SUPERSEDED by ADR-023 / PLUGIN-MIGRATION-001-H merged 2026-05-27)
- `auth_invalid` and `down` MUST be distinct enum variants — tools that report
  remediation suggestions need to distinguish them
- Rate limit state MUST be derived from observed HTTP headers only — do not infer it
  from latency or other signals
- Timestamps MUST be stored in UTC — no local time
- The health aggregation MUST NOT return `PrismError` for partial health — partial is
  a valid operational state, not a failure

## Dev Notes

> **BLOCKING DEPENDENCY — S-1.11 (read-side tables) REQUIRED BEFORE MERGE**
>
> S-5.04's live probe works by calling `SpecDrivenSensorAdapter::fetch()` via
> `AdapterRegistry::get(org_id, sensor_id)`. This is correct by design (S-5.04-FIX-001,
> v1.6 authority). However, the shipped sensor TOML specs currently declare **no read-side
> tables**. Until S-1.11 ("Spec Loading and Pipeline Execution") delivers read-side table
> definitions, `SpecDrivenSensorAdapter::fetch()` returns `Ok([])` **without making any
> HTTP request** — the adapter has nothing to fetch.
>
> Consequence: with no S-1.11, the probe returns empty results with no HTTP traffic.
> Reporting this as a healthy sensor would be a **false-positive**. S-5.04 MUST NOT report
> `reachable: true` when the underlying fetch was hollow (no HTTP made).
>
> **Resolution (user directive 2026-06-19, F-S504-R2-001):** S-1.11 is added to
> `depends_on`. S-5.04 must not merge until S-1.11 merges. Wave scheduling must place
> S-1.11 before S-5.04.
>
> The implementer for S-5.04 should verify, as a pre-flight step, that the Cyberint and
> CrowdStrike sensor specs (post-S-1.11) declare at least one `[[tables]]` read block.
> If no read table is declared, the probe is still hollow and this story is not ready
> to deliver.

- The choice of "probe" endpoint per sensor is important: it should be a real data
  endpoint (not `/healthz` or `/ping`) so that the probe validates end-to-end auth,
  not just network reachability. A `limit=1` query on the device or vulnerability
  endpoint works well for CrowdStrike.
- Rate limit clearing is time-based, not event-based. When `retry_after` elapses,
  the next health check will see a cleared rate limit state automatically — no explicit
  "reset" needed.
- For sensors that return 429 without a `Retry-After` header, default to `retry_after:
  60 seconds` as a conservative fallback.
- **Retry-After parsing (CONFIRMED approach — uncertainty-pivot003-s504-2026-06-19.md §Item 3):**
  `reqwest` 0.12 does NOT parse `Retry-After` — it is exposed only as a raw `HeaderValue`.
  Parse the raw header value as follows (NO new crate needed; `chrono` 0.4.44 is sufficient):
  1. Trim whitespace; try `s.parse::<u64>()` → `Duration::from_secs(n)` (delta-seconds form).
  2. On failure, try `chrono::DateTime::parse_from_rfc2822(s)` → absolute HTTP-date form
     → compute `Duration` relative to `SystemTime::now()`, clamping past/negative to
     `Duration::ZERO` ("retry immediately").
  CRITICAL: Do NOT use `parse_from_str` with a `%Z` format string — chrono issue #1575 causes
  it to fail on `"GMT"` timezone tokens. Use `parse_from_rfc2822` ONLY for HTTP-date form.
  Use `u64` (not `u32`) for delta-seconds to avoid integer overflow on hostile values.
  Parse failure on the header value is advisory: log at debug level and fall back to the
  default 60-second backoff.
