# Prism Consumer Contract

This document defines the stable contract any external consumer of `prism` may rely on.
It is grounded in the actual code and scripts as of develop HEAD (e116a587). All behavioral
references cite their authoritative source in the codebase.

**Scope:** this contract covers the `prism` binary's external interface. It does NOT cover
internal crate APIs — those are `publish = false` library crates not intended for external
consumption.

---

## 1. MCP Stdio Launch Shape

### 1.1 Canonical invocation

```
prism --config-dir <config-dir> start
```

`prism` speaks the MCP stdio transport on stdin/stdout. An MCP host (e.g., Claude Code)
launches it as a subprocess and communicates over stdio JSON-RPC.

**Authority:** `crates/prism-bin/src/main.rs` dispatch → `PrismCommand::Start`; boot sequence
defined in `crates/prism-bin/src/boot.rs` (ADR-022 §A).

### 1.2 Claude Code MCP server config block

```json
{
  "mcpServers": {
    "prism": {
      "command": "/path/to/prism",
      "args": ["--config-dir", "/path/to/config-dir", "start"],
      "env": {
        "CROWDSTRIKE_BASE_URL": "<crowdstrike-api-base>",
        "ARMIS_INSTANCE_URL": "<armis-instance-url>",
        "CLAROTY_INSTANCE_URL": "<claroty-instance-url>",
        "CYBERINT_ENVIRONMENT": "<cyberint-env>"
      }
    }
  }
}
```

**Note:** `RUST_LOG` must NOT be set in the `env` block (or must be set to `off`). The tracing
subscriber writes structured JSON to stdout by default; MCP stdio transport also uses stdout
for JSON-RPC frames. Log output on stdout corrupts the JSON-RPC framing and causes the MCP
host to fail to parse responses. Authority: `e2e.yml` env block; `crates/prism-bin/tests/helpers/mod.rs`.

### 1.3 `--config-dir` resolution

Precedence (highest to lowest):
1. `--config-dir <path>` CLI flag
2. `PRISM_CONFIG_DIR` environment variable
3. Platform default: Linux `~/.config/prism/`, macOS `~/Library/Application Support/prism/`, Windows `%APPDATA%\prism\`

Authority: `crates/prism-bin/src/main.rs` lines 70–80 (`dirs::config_dir()`).

## 2. Mandatory Environment Variables

The four TYPE-spec variables are **mandatory at boot**. If any is absent or empty, boot
hard-aborts with exit code 2 (E-SPEC-024). They satisfy boot step 4a env-token resolution
before per-org overlay loading (step 4c) replaces `base_url` with actual sensor endpoints.

| Variable | Purpose | Required |
|----------|---------|---------|
| `CROWDSTRIKE_BASE_URL` | CrowdStrike TYPE spec base_url token | YES |
| `ARMIS_INSTANCE_URL` | Armis TYPE spec base_url token | YES |
| `CLAROTY_INSTANCE_URL` | Claroty TYPE spec base_url token | YES |
| `CYBERINT_ENVIRONMENT` | Cyberint base_url template: `https://${env.CYBERINT_ENVIRONMENT}.cyberint.io` | YES |

**For real deployments:** set to the actual sensor API base URLs for each sensor.

**For demo/DTU mode:** set to placeholder values that satisfy SEC-003 host validation;
per-org overlay files (generated by `demo-run.sh`) override `base_url` before any HTTP
request is made.

### Optional environment variables (enrichment)

| Variable | Purpose | Required |
|----------|---------|---------|
| `PRISM_THREATINTEL_BASE_URL` | ThreatIntel infusion plugin base URL | Optional; enrichment skipped if absent |
| `PRISM_THREATINTEL_API_KEY` | ThreatIntel API key | Optional; enrichment fails with auth error if absent when URL is set |
| `PRISM_NVD_BASE_URL` | NVD enrichment HTTP-lookup base URL | Optional (override); defaults to `https://services.nvd.nist.gov` in spec |
| `PRISM_NVD_API_KEY` | NVD API key | Optional; NVD enrichment returns None silently if absent |
| `PRISM_DTU_MODE` | Set `true` to permit SSRF guard to allow 127.0.0.1 endpoints | Optional; for DTU/demo use only |
| `RUST_LOG` | Tracing log filter; set `off` in MCP stdio context | Strongly recommended `off` in MCP context |

Authority: `scripts/demo-run.sh` §Print prism-bin start command; `crates/prism-bin/src/boot.rs`.

### E-SPEC-024 abort semantics

When any mandatory `${env.VAR}` token in a TYPE spec resolves to empty or absent:
- Boot exits with code 2
- Stderr emits: `E-SPEC-024: env var resolution failed for <VAR>`
- No MCP connection is established

Authority: `crates/prism-spec-engine/src/env_resolver.rs`; error taxonomy `.factory/specs/prd-supplements/error-taxonomy.md`.

## 3. Config-Dir Layout

The `--config-dir` must contain a valid `prism.toml` before `start` is invoked. The full
expected layout:

```
<config-dir>/
  prism.toml              # mandatory; defines [[orgs]] entries
  specs/                  # spec_dir (from prism.toml spec_dir field)
    <sensor_id>.sensor.toml         # TYPE spec; ships with prism release
    customers/
      <org_slug>/
        <sensor_id>.sensor.toml     # per-org overlay (BC-2.06.012)
  plugins/                          # plugin_dir (from prism.toml)
    crowdstrike-oauth2.prx
    crowdstrike-oauth2.manifest.toml
    threatintel-lookup.prx          # optional enrichment plugin
    threatintel-lookup.manifest.toml
  infusions/                        # optional; InfusionLoader reads *.infusion.toml here
    threatintel.infusion.toml
    nvd.infusion.toml
  state/                            # state_dir (from prism.toml); RocksDB
```

### 3.1 Shipped TYPE specs

The four built-in sensor TYPE specs ship with the prism release (inside the binary or
alongside it via demo bundle). For production deployments, they are sourced from the
prism release archive:

- `crowdstrike.sensor.toml`
- `armis.sensor.toml`
- `claroty.sensor.toml`
- `cyberint.sensor.toml`

These specs define the `auth_type`, `tables`, and column schemas. They are read-only;
consumers must not modify TYPE specs directly.

Authority: `crates/prism-sensors/specs/`; `scripts/demo-setup.sh` step 4.

### 3.2 Per-org overlay TOMLs (scalar-only hybrid instance overlay)

Per-org overlays live at `<spec_dir>/customers/<org_slug>/<sensor_id>.sensor.toml`.
Each overlay contains exactly three scalar fields — no table schema, no auth_type:

```toml
extends     = "<sensor_id>"         # which TYPE spec this extends
instance_id = "<sensor_id>@<org_slug>"  # unique adapter identity
base_url    = "<actual-api-base>"   # replaces TYPE spec base_url
```

Authority: BC-2.06.012 (overlay loading), BC-2.06.013 (scalar-only enforcement), BC-2.06.014 (per-org isolation).

### 3.3 `prism.toml` schema

```toml
spec_dir   = "<absolute-path-to-specs>"
state_dir  = "<absolute-path-to-state>"
plugin_dir = "<absolute-path-to-plugins>"

[[orgs]]
org_id   = "<uuid-v7>"
org_slug = "<slug>"

# ... additional [[orgs]] entries
```

`org_id` must be a valid UUID v7. `org_slug` must be a non-empty string.
Authority: BC-2.06.001; `crates/prism-bin/src/boot.rs` step 2 (config parse).

## 4. Credential Model

### 4.1 Resolution chain (four-tier; BC-2.06.003)

Credentials are resolved in this order at query time. First non-empty value wins:

| Tier | Source | Format |
|------|--------|--------|
| Tier 1 | Per-invocation env (test/CI only) | `PRISM_CLIENTS_{ORG_UPPER}_SENSORS_{SENSOR_UPPER}_{NAME_UPPER}` |
| Tier 2 | Process env (production fallback) | Same format as Tier 1 |
| Tier 3 | OS keyring (production primary) | Service `prism`, namespace `{org_id_uuid}/{sensor}/{name}` (ADR-034 §D3) |
| Tier 4 | No credential | Hard-error E-CRED-008; no fallback |

**Env var format (Tiers 1/2):** Org slug is uppercased with hyphens replaced by underscores.
Example: `org-a` → `ORG_A`, sensor `crowdstrike`, name `client_id` → `PRISM_CLIENTS_ORG_A_SENSORS_CROWDSTRIKE_CLIENT_ID`.

Authority: ADR-032; `crates/prism-credentials/src/resolution.rs`; BC-2.06.003.

### 4.2 Keyring write (AD-017 stdin-only)

Credentials are written via:
```
echo "<value>" | prism --config-dir <dir> credential set \
  --sensor <sensor_id> \
  --name <credential_name> \
  --org-slug <org_slug>
```

The value is piped via stdin (AD-017 compliance). It must never be passed as a CLI argument.
Authority: `crates/prism-bin/src/credential_cli.rs`; AD-017.

### 4.3 Keyring namespace

Credentials are stored under the OS keyring service `prism` with namespace key
`{org_id_uuid}/{sensor}/{name}` (ADR-034 §D3). The `org_id_uuid` is read from `prism.toml`
`[[orgs]]` entry matching the `--org-slug` argument.

**Important:** reading via `PRISM_CLIENTS_*` env vars (Tier 2) does NOT require the keyring
to be accessible. This is the recommended fallback for headless or containerized deployments.

## 5. Versioning

### 5.1 Tag scheme

Releases follow semantic versioning with a pre-release RC qualifier:
- `v1.0.0-rc.1` — first release candidate
- `v1.0.0` — general availability (after soak)
- `v1.1.0` — minor feature release (new sensors, new MCP tools)
- `v2.0.0` — breaking change to MCP tool surface or config schema

Tags are cut from `develop`. `main` is fast-forwarded at final GA release.

### 5.2 `prism --version` check contract

```
prism --version
prism 1.0.0-rc.1
```

**Canonical form:** `prism --version` (clap auto-flag). This is the pinned canonical form
for all programmatic consumers including secops-factory's `activate` skill version check.

Both `prism --version` (clap auto-flag) and `prism version` (subcommand) print the same
string: `prism <CARGO_PKG_VERSION>` to stdout, then exit 0. The `prism --version` form is
canonical because it follows the universal `--version` CLI convention and is consistent
with how most tooling (package managers, CI scripts, wrapper scripts) checks binary versions.

Consumers MUST use `prism --version`. Do not rely on `prism version` for automated version
checks — its subcommand parsing requires the binary to be fully initialized before dispatching.

Authority: `crates/prism-bin/src/main.rs` dispatch on `PrismCommand::Version`; `env!("CARGO_PKG_VERSION")`. Human decision OQ-4 (2026-07-19).

**Consumer version check pattern (secops-factory activate skill):**
```bash
PRISM_VERSION=$(prism --version 2>/dev/null | awk '{print $2}')
# Compare against minimum required version using semver ordering
```

### 5.3 Semver stability guarantees on the MCP tool surface

| Surface | Stability | Notes |
|---------|-----------|-------|
| `query` tool name | STABLE in 1.x | Breaking change only with major version bump |
| `query` tool parameter schema | STABLE in 1.x | `sql` (string), `org_id` (optional string) |
| `prism_describe` tool | STABLE in 1.x | Schema discovery; column names and types guaranteed stable |
| `sensor-health` tool | STABLE in 1.x | Returns sensor connectivity status |
| `prism --config-dir <dir> start` | STABLE in 1.x | CLI launch shape |
| Config-dir layout | STABLE in 1.x | `prism.toml`, `specs/`, `customers/`, `plugins/` |
| Credential env var format | STABLE in 1.x | `PRISM_CLIENTS_{ORG}_{SENSOR}_{NAME}` |
| Error codes (`E-SPEC-NNN`, `E-CRED-NNN`) | STABLE in 1.x | Taxonomy in error-taxonomy.md |
| Exit codes (0, 2, 4, 5) | STABLE in 1.x | ADR-022 §A table |

Breaking changes require a major version bump and a migration notice in RELEASING.md.

## 6. Verification Surface Available Post-Onboarding

After a consumer has configured `prism` and connected an MCP host, the following MCP tools
are available for health checks and schema discovery:

### 6.1 `prism_describe`

Returns the full schema of all tables available to the connected org(s):
```sql
-- Via MCP query tool:
prism_describe
```

Response: JSONL of `TableDescriptor` rows, each containing `table_name`, `columns[]`
(with `name`, `type`, `nullable`), `sensor_id`, `org_slug`. Authority: ADR-041; BC-2.11.xxx.

### 6.2 Sensor health

```sql
-- Check sensor connectivity for all orgs:
SELECT * FROM prism_sensor_health
```

Returns per-org × per-sensor health status. Authority: prism-mcp sensor-health tool.

### 6.3 Basic connectivity smoke query

```sql
SELECT 1
```

Returns a single-row result. Exit 0 on the MCP tool call = prism is reachable and a
query can be executed. No sensor credentials required.

## 7. Version Compatibility (secops-factory minimum version check)

The `activate` skill in secops-factory must:

1. Locate the `prism` binary (via configured path or `$PATH`)
2. Run `prism --version` and capture output
3. Parse the version string (format: `prism <semver>`)
4. Assert version >= minimum required (e.g., `1.0.0-rc.1`)
5. If version check fails: emit a human-readable error with the actual vs required version
   and a link to the download page

**Minimum required version for secops-factory v1:** `1.0.0-rc.1`

The version check must handle pre-release identifiers correctly (rc.1 < rc.2 < 1.0.0).
Authority for semver ordering: the Rust `semver` crate semantics (which Cargo uses).
