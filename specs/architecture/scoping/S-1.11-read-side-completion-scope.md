### The Actual Gap — "Partial-Merge" Residue

The `status: partial-merge` on S-1.11 was set in v1.6 (Bundle-A.2.2, 2026-05-08) based on the
plugin audit finding TD-PLUGIN-P0-001 ("PipelineExecutor::execute is stub"). TD-PLUGIN-P0-001
was subsequently closed by S-PLUGIN-PREREQ-B. TD-PLUGIN-P0-004 ("sensor TOMLs are write-only")
was closed by PLUGIN-MIGRATION-001-D.

**The original `partial-merge` flag is therefore stale — the PipelineExecutor and the TOML
read tables are both real and functional on develop.**

However, the S-5.04 adversary finding F-S504-R2-001 (D-1252) identified a narrower, real gap:

#### The Specific Gap: Cyberint Has No `devices` Table

S-5.04's health probe (`connectivity.rs:204`) constructs the probe source table as:

```rust
let probe_source_table = format!("{}_devices", adapter.sensor_type());
```

Then calls `adapter.fetch()` with `SensorSpec { source_table: probe_source_table, ... }`.

`SpecDrivenSensorAdapter::fetch()` strips the sensor_id prefix from `source_table` to derive
the raw table name (e.g., `"cyberint_devices"` → `"devices"`), then iterates
`self.sensor_spec.spec.tables` to find a matching `TableSpec`. If no match is found, the
for-loop body never executes and the method returns `Ok([])` **without any HTTP request.**

Current sensor TOML table inventory on develop@f6739764:

| Sensor | Tables Declared | Has `devices`? |
|--------|-----------------|----------------|
| crowdstrike | detections, devices, incidents | YES |
| armis | devices, alerts | YES |
| claroty | alerts, audit_logs, devices | YES |
| cyberint | alerts, incidents | **NO** |

**Cyberint is the ONLY sensor that lacks a `devices` table.** For CrowdStrike, Armis, and
Claroty the current probe is functional (the adapter will issue a real HTTP call). For
Cyberint, the probe is hollow.

#### Root Cause

The Cyberint API exposes alerts and incidents, not devices. A `devices` table for Cyberint
would be semantically wrong. The S-5.04 connectivity probe hard-codes `_devices` as the
probe table suffix. This is the architectural mismatch.

## 2. What S-5.04 Specifically Needs

S-5.04 requires that `SpecDrivenSensorAdapter::fetch()` makes an actual HTTP request when
called from the health probe, so that the probe reflects true sensor reachability and auth
validity rather than reporting a false-positive `reachable: true` on `Ok([])`.

The gap is **not a missing TOML table** for Cyberint — the API genuinely lacks a devices
endpoint. The gap is that the health probe's table selection strategy (`{sensor_id}_devices`)
is not sensor-generic.

### What Actually Unblocks S-5.04

One of the following approaches closes the gap for S-5.04. They differ in scope and BC
impact:

**Option A — Probe-first-available-table (minimal code change, no new BC/spec)**
Modify `connectivity.rs` in S-5.04 (already in the S-5.04 worktree) to attempt
`{sensor_id}_devices` first, and fall back to the FIRST declared table in the sensor
spec if `_devices` produces an empty result. For Cyberint this would be `cyberint_alerts`.
This is a purely mechanical change inside S-5.04's own code. No TOML schema change.
No new BC.

**Option B — Explicit probe table declaration in TOML (spec extension)**
Add a `probe_table` field to the TOML sensor spec (e.g., `probe_table = "alerts"` in
cyberint.sensor.toml) and plumb it through `SpecDrivenSensorAdapter` to `connectivity.rs`.
This requires:
- A new TOML field in `SensorSpec` (prism-spec-engine spec_parser.rs)
- Updated cyberint.sensor.toml (and optionally other specs for explicitness)
- BC-2.16.001 amendment (new optional field in spec schema)
- No changes to the PipelineExecutor or query engine

**Option C — Sensor-specific probe path in health module (bounded scope, no spec change)**
Define a lookup table in the health module mapping `sensor_id → canonical probe table`.
Example: `{ "cyberint" => "alerts", ... }`. Default is `devices` for all others.
This is purely in `prism-mcp/src/health/`, no TOML or spec changes.

#### Minimal-Unblock Recommendation for S-5.04

**Option A is the minimal-unblock scope.** It requires no new BCs, no TOML schema changes,
no `prism-spec-engine` crate changes, and no coordination with product-owner or spec changes.
The change is entirely within `crates/prism-mcp/src/health/connectivity.rs` — already in
S-5.04's crate scope. This is a fix to S-5.04's own code, not a new prerequisite.

Option B (explicit `probe_table` field) is the production-grade long-term approach but adds
BC/spec scope that would require product-owner authoring and an additional story cycle.
Recommendation: defer Option B to a follow-up story after S-5.04 merges — it is an
improvement to spec expressiveness, not a correctness prerequisite.

Option C is acceptable if the concern is "any table name might change" but introduces
a hidden coupling between health module and sensor API knowledge. Less preferable than A.

## 9. Risks and Open Questions

### Risk 1: Human May Want the Original S-1.11 Label Meaning

The user directive (D-1252) was "pull S-1.11 into scope before S-5.04 merges." If the
human intended this as "implement whatever remains in S-1.11's original scope" (rather
than "close the specific blocking gap"), then the scoping question is moot — but the
answer is still the same: the original S-1.11 scope IS complete.

**Open question for human:** Is the directive satisfied by confirming S-1.11's BCs are
all delivered and fixing the probe table logic in S-5.04 — or is there additional S-1.11
scope the human had in mind?

### Risk 2: Cyberint Probe Uses Wrong Table Semantically

If the health probe falls back to `cyberint_alerts` (Option A), it is testing alert-query
connectivity, not device connectivity. This is semantically different from the
CrowdStrike/Armis/Claroty probes. For health monitoring purposes (is the sensor reachable
and authenticated?), probing any real table is correct. But if the intent is specifically
to probe device data availability, a `devices` table for Cyberint would need to be
added (which the API may not support).

**Open question for product-owner:** Is the health probe's semantic requirement
"probe ANY real data endpoint" (Option A is fine) or "probe the devices endpoint
specifically" (would require Cyberint to expose a devices API that may not exist)?

### Risk 3: Other Sensors in Future Without `devices` Tables

Option C (lookup map) or Option B (explicit `probe_table` in TOML) are more robust
for future sensor onboarding where `devices` is not the canonical first table.
This is a spec hygiene concern, not a blocker.
