# BC-2.11.016: E-QUERY-038 Column-Not-Found Plan-Time Gate (L4)

## Description

When a PrismQL query references a column name that does not exist in the `TableRegistry` schema for the specified table and client, the plan-time column-availability gate rejects the query with `E-QUERY-038` before any sensor API call is made. The error payload includes `available_columns` (always present, org-scoped) and `did_you_mean` (present when a Levenshtein distance ≤ 3 match exists against the available column names). This enables an LLM agent to self-correct the column reference in a single retry without human intervention. The gate fires at the same plan-time validation point as the E-QUERY-037 table-availability gate and shares the same `TableRegistry` read.

## Preconditions

1. A PQL query has been parsed successfully by Chumsky (no E-QUERY-001 parse error).
2. The query references a column name in a position where column resolution is possible. The gate covers fourteen clause positions across all three AST modes — **this is an exhaustive closed list**:

   **SQL-mode positions (positions 1–6, `Ast::Sql` and `Ast::SqlPipe` head):**
   - Position 1: `SELECT <column>` projection
   - Position 2: `WHERE <column> = ...` predicate
   - Position 3: `GROUP BY <column>`
   - Position 4: `ORDER BY <column>`
   - Position 5: `JOIN ON <column>`
   - Position 6: `HAVING <column>` / `HAVING <agg>(<column>)` — base-column refs including refs nested inside aggregate function calls such as `count(col)`, validated on parity with WHERE and GROUP BY

   **HEAD-JOIN SUSPENSION RULE (positions 1–6, `Ast::Sql` and `Ast::SqlPipe` head forms):** When the head query's JOIN list is non-empty AND a bare unqualified column reference at positions 1–6 is absent from `schema_columns(table, OrgId)`, the E-QUERY-038 gate MUST NOT fire for that column reference (fail-open; skip the reject). Rationale: the absent column may validly exist in a JOIN-partner table at execution time; DataFusion resolves unqualified column references across all join sources. Columns PRESENT in the FROM table schema are still checked normally — only absent column refs with a non-empty JOIN list trigger the suspension. Qualified references at positions 1–6 retain existing behavior (FROM-qualifier checked; non-FROM qualifiers were already silently skipped per implicit fail-open). **PER-REFERENCE SCOPING:** The suspension applies per individual column reference, not per column name; a qualified reference (FROM-table- or FROM-alias-qualified) to a name that also appears bare elsewhere in positions 1–6 is NOT suspended — it retains full E-QUERY-038 checking. Joinless queries are UNCHANGED — the suspension applies ONLY when the head JOIN list is non-empty. Applies to both `Ast::Sql` and `Ast::SqlPipe` head SQL clauses (the `Ast::SqlPipe` head is the SQL block up to the first pipe operator; the rule applies identically across both head forms). False-negative trade-off: a genuinely nonexistent unqualified column in a query with JOINs is deferred to execution-time DataFusion error — this is accepted per FP-001 absolute-invariant precedent, the same trade-off as STAR-WITH-JOIN SUSPENSION RULE and STAGE-JOIN SUSPENSION RULE. **Future strengthening:** a precise multi-source schema union (seeding JOIN-partner schemas via the registry) is a permissible future implementation that restores E-QUERY-038 coverage for position-1–6 bare unqualified refs in join-containing queries without violating FP-001; the HEAD-JOIN SUSPENSION RULE is the contract's minimum obligation; any future strengthening MUST preserve FP-001.

   **Filter-mode position (position 7, `Ast::Filter`):**
   - Position 7: Filter-mode root predicate — all columns in the predicate tree, walking `Predicate::Logical`/`Predicate::Not` recursively

   **Pipe-mode stage positions (positions 8–12, `Ast::Pipe` and `Ast::SqlPipe` stages):**
   - Position 8: Pipe-mode `| where` stage predicates — every `PipeStage::Where` in the stages vec, walking the embedded `Predicate` tree recursively
   - Position 9: SqlPipe `| where` stage predicates — `Ast::SqlPipe` head SQL clauses covered by positions 1–6; `| where` stages walked identically to position 8
   - Position 10: Pipe `| sort` field key references — every field reference in `PipeStage::Sort` sort-key list
   - Position 11: Pipe `| stats ... by` grouping field references AND aggregate function argument field paths — every field reference in `PipeStage::Stats(StatsStage)` `by_fields` (`Vec<FieldPath>`) grouping list AND every `FieldPath` argument in `PipeStage::Stats` aggregate expressions (CountField/Sum/Avg/Min/Max/DistinctCount/Percentile); all checked against the `available` set BEFORE the Stats stage replaces the binding context
   - Position 12: Pipe `| fields` column references — every field reference in `PipeStage::Fields` inclusion/exclusion list
   - Position 13: Pipe `| enrich f(input_col)` input column — the column argument to the enrichment infusion in each `PipeStage::Enrich` stage; checked against the current binding set BEFORE the stage updates it
   - Position 14: Pipe `| dedup` field path references — every field reference in `PipeStage::Dedup` dedup-key list

   **DERIVED-COLUMN BINDING RULE (pipe-mode positions 8–14):**

   The gate maintains a running binding context `{ available: Set<String>, suspended: bool }` while walking pipe stages in order. Checking is performed against the binding context at the point each stage is reached — the context evolves as stages are processed:

   - **Initial state:**
     - For `Ast::Pipe` (pure pipe mode): `available = schema_columns(table, OrgId)` (full set registered in `TableRegistry` for this table/client; same source as positions 1–7); `suspended = false`.
     - For `Ast::SqlPipe` (SQL→Pipe composed mode — **SQLPIPE HEAD-PROJECTION BINDING RULE**): `available` is seeded from the HEAD SQL's projection output — not the raw schema — computed at plan time: (a) `SELECT *` head → `available = schema_columns(table, OrgId)` (full raw schema; same as `Ast::Pipe` initial state; current behavior preserved); (b) fully-explicit SELECT head (no `Star`/`TableStar` items) → `available = {explicit SELECT aliases (each `AS <alias>`)} ∪ {bare column names for un-aliased bare-`Field` SELECT items} ∪ {bare field names in the GROUP BY clause}`; any SELECT item that is a non-`Field` expression WITHOUT an explicit `AS <alias>` (e.g., `count(*)`, `sum(amount)`) is an anonymous computed/aggregate column whose output name is unpredictable at plan time → `suspended := true` for the stage walk (FP-001 fail-open; mirrors the Stats stage anonymous-aggregate rule). `suspended = false` unless triggered by the anonymous-item rule; (c) MIXED-STAR SELECT head (at least one `Star`/`TableStar` item AND at least one explicit non-star item) → `available = schema_columns(table, OrgId) ∪ {AS aliases from explicit items} ∪ {bare Field names of un-aliased explicit bare-`Field` items} ∪ {bare field names in the GROUP BY clause}`; if any explicit non-`Field` item lacks an `AS` alias (anonymous computed/aggregate column whose output name is unpredictable at plan time) → additionally `suspended := true` for the stage walk (FP-001 fail-open; same anonymous-item rule as branch (b)). Rationale: the Star/TableStar component brings the full raw schema into scope; explicit items may contribute additional aliased computed columns (e.g., `upper(severity) AS sev_up`); the union prevents false positives on correct queries referencing these aliases in downstream pipe stages. **Head SQL clause checking (positions 1–6) is unaffected** — position 1–6 checks run against `schema_columns(table, OrgId)` (raw schema) unchanged; the SQLPIPE HEAD-PROJECTION BINDING RULE applies only to the initial `available` set for the stage walk (positions 8–14). **STAR-WITH-JOIN SUSPENSION RULE (applies to branches (a) and (c); the contract's sanctioned fail-open for star-with-join heads):** In branches (a) and (c), when the SqlPipe head's JOIN list is non-empty AND at least one `Star`/`TableStar` item is present in the SELECT list, the initial binding context for the pipe-stage walk is **SUSPENDED** (`suspended := true`), overriding the partial `available` seeding from branches (a)/(c). Rationale: `SELECT * FROM t JOIN j ...` and `SELECT j.* FROM t JOIN j ...` — star expansion at execution spans ALL join-source schemas; only the FROM table's schema is statically seeded by branches (a)/(c) from the `TableRegistry`; checking downstream pipe-stage column refs against the FROM table schema alone fires false E-QUERY-038 and E-QUERY-002 on columns that validly exist only in the joined table (FP-001 violation class: star-with-join). Branch (b) (fully-explicit SELECT with JOINs) is UNCHANGED — the LAST-SEGMENT OUTPUT-NAME RULE (v1.17) already handles join-qualified explicit items with DERIVED provenance; no additional suspension is needed for explicit-only heads. Joinless heads are UNCHANGED across all branches — the suspension applies ONLY when the JOIN list is non-empty. **Future strengthening:** a precise multi-source union (seeding join-source schemas by resolving JOIN aliases via the registry) is a permissible future implementation that would restore E-QUERY-038/E-QUERY-002 coverage for star-with-join heads without violating FP-001; the STAR-WITH-JOIN SUSPENSION RULE is the contract's minimum obligation; any future strengthening MUST preserve FP-001.
   - **Enrich stage (`PipeStage::Enrich`):** Position 13 (input column) is checked against `available` BEFORE this stage updates the binding context. After the position-13 check: output columns are resolved via `InfusionRegistry::udf_descriptors()` → `enrich_descriptor(infusion_id)` → `EnrichStageDescriptor.output_columns`. When output columns are successfully resolved, those names are **unioned** into `available` (the infusion output columns become bindable for downstream stages). When output column resolution fails — because no `InfusionRegistry` is wired into the engine (registry-absent engine context: single-tenant, test, or no-infusions deployment) or due to a defensive lookup failure on an absent descriptor — `suspended := true` and all E-QUERY-038 checking for subsequent stages is suspended (fail-open). **Note (E-QUERY-039 downstream gate):** Unknown UDF names are caught by the downstream E-QUERY-039 gate, which fires AFTER the binding-context walk per BC-2.11.019 §Gate ordering (E-QUERY-001 → E-QUERY-037 → E-QUERY-038 → E-QUERY-039). When the binding-context walk reaches an enrich stage with an unknown UDF, the resolver returns `None`, suspension engages (fail-open), and E-QUERY-039 fires downstream with the pedagogical "unknown UDF" error. The suspend path is therefore live both in registry-absent engine contexts (no `InfusionRegistry` wired) and in registry-wired engines when the resolver returns `None` for the presented UDF name (unknown UDF or defensive lookup failure on an absent descriptor). Rationale: downstream references to infusion output columns (e.g., `cvss_base_score` from the canonical NVD pivot per BC-2.06.019 v1.13 §PC-4) are valid at execution time; a false positive on a correct query is forbidden by invariant FP-001.
   - **Stats stage (`PipeStage::Stats`):** The by-field refs (position 11) and aggregation expressions are checked against `available` BEFORE this stage updates the binding context. After those checks: `available` is **replaced** with `{explicit aggregate aliases} ∪ {bare column names from by_fields}`. Rationale: after a `| stats` stage, only aggregate outputs and GROUP BY keys remain in the result; continuing to check against the original schema would produce false negatives. Anonymous aggregations (no explicit `as alias`) do not contribute to the replacement set — their DataFusion-generated names are not predictable at plan time; fail-open for those references in subsequent stages. If any by-field expression is non-static (not a bare `Field` name): `suspended := true`.
   - **Fields stage (`PipeStage::Fields`) — FIELDS TRANSITION RULE:** `| fields a, b` (include-list, no leading `-`) → `available := {listed field names}` (REPLACE — downstream stages are checked against the include-list only, not the prior `available` set; analogous to the Stats stage REPLACE; provenance of surviving names is preserved from their prior binding provenance); `| fields - a, b` (exclude-list, leading `-`) → `available := available ∖ {listed excluded names}` (subtraction; provenance of surviving names is preserved). Suspension state carries forward unchanged — a Fields stage neither clears nor sets `suspended`. Rationale: the SQL emitter's `apply_fields` genuinely restricts the projection — an include `| fields` removes non-listed columns from the output; downstream `| where` references to removed columns fail at DataFusion. Modelling the Fields transition exactly prevents the gate from passing a query that DataFusion will reject (false-negative class).
   - **Join stage (`PipeStage::Join`) — STAGE-JOIN SUSPENSION RULE:** When the stage walk encounters a `PipeStage::Join` stage, set `suspended := true` for the remainder of the walk. Rationale: join-source schemas are not statically seeded into the binding context (only the FROM table's schema is populated in `available`); downstream column references that resolve through the join source would falsely fire E-QUERY-038 if checked against the FROM-only `available` set (FP-001 violation class: stage-join). Symmetry with STAR-WITH-JOIN SUSPENSION RULE (head-level): both rules share the principle that when a join source is in scope but its schema is not statically seeded, the gate fails open for the remainder of the stage sequence. **Future strengthening:** a precise multi-source union (seeding join-source schemas by resolving JOIN aliases via the registry) is a permissible future implementation that restores E-QUERY-038/E-QUERY-002 coverage for join-containing pipes without violating FP-001; the STAGE-JOIN SUSPENSION RULE is the contract's minimum obligation; any future strengthening MUST preserve FP-001.
   - **All other stages** (Where, Sort, Dedup): `available` and `suspended` are unchanged.
   - **LAST-SEGMENT OUTPUT-NAME RULE (SqlPipe SELECT-head seeding, branches (b) and (c)):** In branches (b) and (c) of the SqlPipe initial `available` seeding, un-aliased bare-`Field` SELECT items are seeded by evaluating their qualifier: if the qualifier is absent or matches the FROM table name or the declared FROM alias, the bare column name is extracted and seeded with **RAW** provenance (type known from the FROM table's schema). If the qualifier matches **neither** the FROM table name **nor** the declared FROM alias — e.g., `j.col` in `SELECT j.col FROM crowdstrike_alerts JOIN some_other_table j ON ...` where `j` is a JOIN alias that is not the FROM source — the **last path segment** (`col`) is seeded as the output column name with **DERIVED** provenance. Rationale: SQL output-naming semantics dictate that `SELECT j.col` produces output column `col`; the column's type is not statically known from the FROM table's schema. Fail-open rationale: if the qualifier is genuinely invalid (no matching JOIN target), the SQL engine rejects the query at execution regardless — the gate's obligation under FP-001 is to not raise a false E-QUERY-038 on a query that succeeds at execution. Both the E-QUERY-038 existence gate and the E-QUERY-002 type-compat gate MUST fail open for names seeded with DERIVED provenance under this rule (SIBLING-GATE CONSISTENCY applies).
   - **FROM-ALIAS RESOLUTION (SqlPipe pipe-stage positions 9–14):** For `Ast::SqlPipe`, when the head SQL declares a `FROM <table> [AS <alias>]` alias (e.g., `FROM crowdstrike_alerts t` or `FROM crowdstrike_alerts AS t`), FieldPath column references in pipe-stage positions that include the alias qualifier (e.g., `t.severity`) MUST be resolved by stripping the alias qualifier and checking the bare column name (`severity`) against the binding context. `extract_column_name_from_field_path` MUST receive the declared FROM-alias (not `None`) so that `t.col` resolves to `"col"` and is checked against `available`. When the qualifier matches neither the table name nor the declared FROM-alias (unknown qualifier, e.g., `other.col`), fail-open behavior is preserved (extraction returns `None`; the gate skips that reference). Without this threading, all alias-qualified references silently bypass the gate — typos like `t.sevrity` reach DataFusion as opaque errors.
   - **SIBLING-GATE CONSISTENCY (E-QUERY-002 operator-type-compat gate):** The E-QUERY-002 type-compat gate (`check_operator_type_compatibility`) runs as a sibling gate inside the same `check_pipe_stage_columns` binding-context walk as E-QUERY-038. Names in `available` carry per-name provenance: **RAW** (bound to the original `TableRegistry` schema type for this name) vs **DERIVED** (bound as a stats output alias, enrich output column, SqlPipe head alias, or any name that shadows a raw-schema column under a derived context). The E-QUERY-002 gate MUST honor this provenance: (a) names with **RAW** provenance → full operator-type-compat checking applies; (b) names with **DERIVED** provenance → E-QUERY-002 gate MUST skip them (fail-open per FP-001); the type for a DERIVED name is not statically known at plan time. Example false-E-QUERY-002: `SELECT count(*) AS severity FROM crowdstrike_alerts | where severity > 5` — alias `severity` is DERIVED (Int64 at execution); raw `severity` column is String; applying String's operator restrictions to the alias fires a false E-QUERY-002 (FP-001 violation). Similarly, `FROM crowdstrike_alerts | stats count() as severity by timestamp | where severity > 5` — stats output alias `severity` is DERIVED; gate must skip E-QUERY-002 for it. This clause binds both SqlPipe head aliases and Stats output aliases that shadow raw-schema column names.
   - **Suspension propagation:** once `suspended = true`, ALL subsequent stages in the pipe sequence skip E-QUERY-038 entirely. Not reversible within a single query.

3. The table referenced in the query has been validated to exist in the `TableRegistry` (E-QUERY-037 passed — no point checking column availability for a non-existent table).
4. The `TableRegistry` has been initialized with the per-client schema for the requesting org.

## Postconditions

### Gate firing conditions

The E-QUERY-038 gate fires when a query passes the E-QUERY-037 table-availability check (the table exists) but references a column name that is NOT in the `TableRegistry` schema for that table under the requesting client's `OrgId`.

The gate fires at plan time (after parse, before fan-out), consistent with E-QUERY-037. No sensor API call is made for a rejected query.

### E-QUERY-038 error payload shape

```
E-QUERY-038: column '{column}' not found in table '{table}' for client '{client_id}';
  available_columns: [...],
  did_you_mean: Option<String>
```

**Payload fields:**

- `column`: the exact column name as written by the model in the query (e.g., `"sevrity"`)
- `table`: the table name in which the column was not found (e.g., `"crowdstrike_alerts"`)
- `client_id`: the requesting client's org slug (identifies which per-client schema was checked)
- `available_columns`: an array of all column names available for `(table, OrgId)` at error-construction time. This list is ALWAYS present (never null, never omitted). If the table has zero columns (or the binding context holds no columns), the array is empty `[]`. **Positions 1–7 (SQL mode + filter mode):** `available_columns` is sourced from `TableRegistry` columns for `(table, OrgId)` — the raw schema registered for this client's sensor overlay for this table; raw-`TableRegistry` wording applies here. **Positions 8–14 (pipe mode, `check_column_against_available_set` called from `check_pipe_stage_columns`):** `available_columns` reflects the binding-context `available` set at the failing stage — the more pedagogical view of what the LLM analyst could validly reference at that pipeline position: post-stats REPLACE = `{explicit aggregate aliases} ∪ {by_fields}`; post-enrich union includes the infusion `output_columns`. This means the listed columns may differ from the raw `TableRegistry` schema when a `| stats` or `| enrich` stage precedes the failing stage. **Org-scoped:** same `filter_to_org_visible` principle as E-QUERY-037 — `available_columns` reflects ONLY the columns for this client's registered schema (or derived binding set) for this table; not columns from a different client's sensor overlay for the same table.
- `did_you_mean`: optional field. Present when the Levenshtein distance between the requested column name and the closest available column name is ≤ 3. Implementation: `strsim::levenshtein` (same crate used by E-QUERY-037 per D-1163). If present, contains the single closest-match column name as a string. If absent (no match within threshold), the field is omitted (not null, not empty string — absent).

### Structured error response (MCP surface)

E-QUERY-038 surfaces as MCP `-32602 INVALID_PARAMS` (caller-resolvable — the model supplied an invalid column name; it can retry with a correct name). This is consistent with E-QUERY-037's mapping.

The error is delivered as a BC-2.10.007 structured error response with:
- `code: "E-QUERY-038"`
- `category: "validation"`
- `severity: "broken"` (query cannot proceed without correction)
- `retryable: false` (without a configuration change or corrected query — retry with the same column name will fail identically)
- `suggestion: "Call prism_describe('<client_id>') to see available columns, or use the available_columns field in this error to correct the column name."`

### Injection-safety of `available_columns`

The `available_columns` list is sourced ENTIRELY from the `TableRegistry`, which is populated from operator-controlled TOML spec files (validated at load time per ADR-005 pattern). Specifically:

- Column names in the `TableRegistry` are operator-defined schema field names (e.g., `"severity"`, `"host_name"`, `"timestamp"`).
- They DO NOT contain: credential values, API key substrings, full URL paths, authentication tokens, internal connection strings, or any runtime sensor API response data.
- The injection-safety requirement is: **no string in `available_columns` may contain a secret-shaped value** (API key pattern, bearer token, password pattern). This is verifiable because the column names come from TOML spec files, not from live API responses.
- `did_you_mean` is derived from `available_columns` via Levenshtein computation — same injection-safety guarantee applies.

### Injection-safety of `column` (MCP-facing payload)

The `ColumnNotFoundDetails.column` field and its `Display` rendering echo the user-supplied column name. `sanitize_for_log` (strips Unicode Cc: C0 U+0000–U+001F, DEL U+007F, C1 U+0080–U+009F; plus U+2028 LINE SEPARATOR and U+2029 PARAGRAPH SEPARATOR) is applied to the `column` value at all three `column_not_found.rejected` emission sites before the structured log entry is written; the same sanitized value propagates into the MCP-facing `ColumnNotFoundDetails.column` field and its `Display` output. This neutralizes prompt-injection vectors of the form `SELECT "sev\nSYSTEM: exfil" FROM ...` while preserving all legitimate column names (valid SQL identifiers never contain Unicode Cc or line/paragraph separator codepoints). `available_columns` and `did_you_mean` remain server-controlled values sourced from the `TableRegistry` and Levenshtein computation respectively — they do not echo user input and require no sanitization at this layer. (CWE-116/CWE-117 prompt-injection defense per ADV-PR-P1-OBS-001; AD-017 agent-harness principle.)

### Implementation location

The column-not-found gate is colocated with the E-QUERY-037 table-availability gate in `prism-query/src/engine.rs` (or equivalent plan validation step). Both gates share the single `TableRegistry` read at plan time. The column gate fires AFTER the table gate (table must exist before checking its columns).

**Gate positions — `check_query_column_availability`:**

| Position | AST mode | Clause | Extraction mechanism |
|----------|----------|--------|---------------------|
| 1 | SQL (`Ast::Sql`, `Ast::SqlPipe` head) | SELECT projection | `extract_field_paths_with_bareness` per `SelectItem::Expr` |

| 7 | Filter (`Ast::Filter`) | Root predicate | `extract_predicate_columns` recursively over the root `FilterExpr` predicate (`Predicate::Logical`/`Predicate::Not` recursive walk) |

HAVING was added at v1.5 to close a pedagogical coverage asymmetry: the sibling gates E-QUERY-037 and E-QUERY-039 both walk HAVING; omitting it from E-QUERY-038 caused a `HAVING count(typo_col)` typo to bypass the clean "column not found" diagnostic and surface a less-actionable DataFusion error instead.

### PrismError variant

`PrismError::ColumnNotFound(Box<ColumnNotFoundDetails>)` is the variant in `prism-core/src/error.rs`, where `ColumnNotFoundDetails` is a `#[non_exhaustive]` struct carrying `{ column: String, table: String, client_id: String, available_columns: Vec<String>, did_you_mean: Option<String> }`. The boxed form was chosen at implementation time (story v1.4 CORRECTION-2, gate=83) because the `Vec<String>` field for `available_columns` pushes the inline variant over the `clippy::result_large_err` threshold — the same justification as `TableNotAvailableDetails` for E-QUERY-037. The `#[non_exhaustive]` attribute on `ColumnNotFoundDetails` is required per CLAUDE.md `#[non_exhaustive]` discipline (the struct is a public type in `prism-core`; external match arms must include a wildcard). The Display output and MCP surface are unchanged from the original design.

`#[non_exhaustive]` is NOT applicable to `PrismError` enum variants themselves (it is the enum-level attribute). The `PrismError` enum already carries `#[non_exhaustive]` on the type (CLAUDE.md conventions). The new variant is added to the existing non-exhaustive enum.

`map_prism_error` in `prism-mcp/src/error_mapping.rs` MUST add an explicit `-32602 INVALID_PARAMS` arm for `PrismError::ColumnNotFound` — it MUST NOT fall through to the `#[non_exhaustive]` catch-all `-32000`.

### Interaction with DataFusion column resolution

DataFusion itself would produce a column resolution error if the query reached execution. The E-QUERY-038 gate is a plan-time pre-check that fires BEFORE DataFusion receives the query. This means the model gets a structured, pedagogical error with `available_columns` rather than a DataFusion internal error string (which would be redacted into E-QUERY-034).

## Design Constraints

E-QUERY-038 is exclusively a plan-time gate (`engine.rs` `execute_inner`, three emission sites). A DataFusion runtime `SchemaError::FieldNotFound` reaching `materialization.rs` is an INTERNAL anomaly — it means the plan-time gate was bypassed or the schema changed between plan time and execution time. Such an error MUST surface as `QueryExecutionFailed` (emitting the `sql.sql_planning_error` structured event), never as `E-QUERY-038`. Routing a runtime schema error through the E-QUERY-038 code path would produce a misleading pedagogical response (`available_columns`, `did_you_mean`) against an error that has no user-actionable column fix. Adjudication record: `research/defect-csdevices-empty-pipeline-rootcause-2026-07-10.md` §F-CSD-P20-003.

**Internal table coverage (D-1670, 2026-07-10):** The E-QUERY-038 gate covers internal (`prism_*`) tables in addition to sensor tables. When a query references a column not present in an internal table's static schema (`InternalTableDescriptor::full_schema()` from `INTERNAL_TABLE_SPECS`), the gate fires E-QUERY-038 with `available_columns` listing the actual columns of that internal table and `did_you_mean` suggesting the closest match. A prior implementation had an unconditional early-return skip for all `prism_*` table names (`if table_name.starts_with("prism_") { return Ok(()); }`) on the basis that internal tables have their own capability gate (`check_internal_table_capabilities`). That skip is removed. The capability gate and the column gate are ORTHOGONAL checks that MUST both run — capability gate fires first (E-QUERY-039 or equivalent), column gate fires after. A user querying `SELECT nonexistent_col FROM prism_alerts` now receives a pedagogical E-QUERY-038 with the `prism_alerts` column set rather than an opaque DataFusion runtime failure. The internal-table column lookup MUST use `INTERNAL_TABLE_SPECS` (pure static data in `prism-core`; no async I/O, no DataFusion plan required — preserves the plan-time-only invariant above). Delivered by: S-DRIFT-INTERNAL-TABLE-COLUMN-GATE-001 (DRIFT-INTERNAL-TABLE-COLUMN-GATE-001, DEFECT-CSDEVICES-EMPTY-PIPELINE-001 LOCAL pass-21 F-CSD-P21-OBS-003; D-1670, 2026-07-10).

## Invariants

- DI-019: This gate fires at plan time, before fan-out, consistent with the security limits principle that problems are caught early.
- DI-004: The query rejection event is included in the `AuditEntry` for the `query` tool call (outcome: `"rejected"`, reason: `"column_not_found"`).
- DI-002: `available_columns` contains no credential values (operator TOML schema → `TableRegistry`; no sensor API data).
- DI-008: `available_columns` is org-scoped — columns for this client's schema only; not columns from another client's sensor overlay.
- **AST-completeness (OBS-002):** For every `Ast::*` variant carrying a `Predicate` sub-tree or schema-bound column references, the column-availability gate MUST walk all embedded column positions. New `Ast` variants introduced in future development require a corresponding gate arm in `check_query_column_availability`. The `_ => Ok(())` fallback is deliberate fail-open ONLY for variants that carry no schema-bound column references (e.g., a hypothetical non-schema-referencing utility node). Any `Ast::*` variant that introduces new schema-bound column positions MUST extend the gate enumeration — omission is a HIGH-severity finding in adversarial review.
- **False-positive prohibition (FP-001):** The plan-time gate MUST NEVER reject a query that would succeed at execution time. This prohibition applies to ALL plan-time gates run from the binding-context walk — both the E-QUERY-038 existence gate and the E-QUERY-002 operator-type-compat gate (see SIBLING-GATE CONSISTENCY clause in §Preconditions DERIVED-COLUMN BINDING RULE). When binding provenance is uncertain — the infusion output schema is not statically resolvable, an anonymous aggregate alias is not predictable at plan time, any non-Field by-expression produces an unpredictable column name, a name is bound with DERIVED provenance (stats alias, enrich output, SqlPipe head alias, or any shadow of a raw-schema column), or the SqlPipe head SELECT list contains at least one `Star`/`TableStar` item with a non-empty JOIN list (STAR-WITH-JOIN SUSPENSION RULE — star expansion spans join-source schemas not statically seeded by the gate), or a `PipeStage::Join` stage is encountered in the pipe-stage walk (STAGE-JOIN SUSPENSION RULE — join-source schema not statically seeded into the binding context; suspension propagates to all remaining stages in the walk), or a bare unqualified column reference at head SQL positions 1–6 is absent from `schema_columns(table, OrgId)` AND the head's JOIN list is non-empty (HEAD-JOIN SUSPENSION RULE — the absent column may validly exist in a JOIN-partner table at execution time; DataFusion resolves unqualified column references across all join sources; applies to both `Ast::Sql` and `Ast::SqlPipe` head SQL clauses) — the affected gate MUST fail open for that name. A false negative (a column typo in infusion output is not caught) is an acceptable cost; a false positive on a correct query (e.g., the canonical NVD pivot where `cvss_base_score` is a real infusion output, or `SELECT count(*) AS severity … | where severity > 5` where a head/stats alias shadows a raw String column) is a blocking defect.
