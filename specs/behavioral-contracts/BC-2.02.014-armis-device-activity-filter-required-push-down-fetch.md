# BC-2.02.014: Armis Device Activity Surface — Filter-Required Push-Down Fetch Contract

## Description

The `armis_device_activity` TOML table provides a single-device, filter-required query surface over the Armis DTU route `GET /api/v1/devices/{device_id}/activity`. Unlike the flat AQL-based `armis_devices` and `armis_alerts` tables, every query against this surface MUST include a `WHERE device_id = '...'` predicate. The `device_id` predicate is pushed down via `FetchContext.query_filters["device_id"]` (the `${query.filter.*}` namespace) into the step `path_template`. Fleet-wide activity queries (absent `device_id` filter) are explicitly out of scope for Wave-A — per-record fan-out over prior-step results is a confirmed capability gap (ADR-057 §D6). SAP-2 column parity: all five `ActivityRecord` fields (`activity_id`, `device_id`, `activity_type`, `timestamp`, `details`) are verified against the DTU wire-emission site `routes::devices §get_device_activity`; the single-path handler has no generated-records branch (the branch's absence is the defect addressed by MED-005, not its clearance). Data-reachability gap (MED-005, contracted AC-008/RG-008): `routes::devices §get_device_activity` filters `state.activity_fixture` only; `clone.rs §new_with_seed_anchored` and `clone.rs §new_with_scenario` both load `activity_fixture` from `fixtures/device-activity.json` via `prism_dtu_common::load_fixture_as(crate_dir, "device-activity")` and pass the result to `ArmisState::with_admin_token §ArmisState::with_admin_token`, which assigns the parameter directly to `activity_fixture` without referencing the file path itself; `new_with_seed §new_with_seed` is a 4-line `#[cfg(feature = "fixture-gen")]` delegation to `new_with_seed_anchored §new_with_seed_anchored`; all three construction paths reside in `clone.rs` (fixture device IDs: `d-001`, `d-002`, `d-005`, `d-013`, `d-015`, `d-020`, `d-023`, `d-024`); generated device IDs (`dev-{org_slug}-{seed}-{i}` format, per `generator.rs §build_asset`) are disjoint from fixture IDs — zero overlap; `generator.rs` has no activity-record builder; in `fixture_gen_seeded=true` mode every `armis_device_activity` query against generated devices returns HTTP 200 with `activities: [], total: 0` (surface inert in the primary demo and holdout mode). Required: generator MUST produce activity records keyed to generated device IDs (EC-014-006, AC-008/RG-008).

## Preconditions

- The `armis_device_activity` TOML table is declared in `crates/prism-sensors/specs/armis.sensor.toml` with `table_name = "device_activity"` and `ocsf_class = "network_activity"` (registered SQL surface: `register_sensor §register_sensor` in `prism-query::table_registry §table_registry` composes `format!("{}_{}", spec.sensor_id, table.table_name)` = `format!("{}_{}", "armis", "device_activity")` = `"armis_device_activity"`), a step using `path_template = "/api/v1/devices/${query.filter.device_id}/activity"` and `response_path = "$.data.activities"` (per ADR-057 §D5)
- The `device_id` column in the `armis_device_activity` table carries `options = ["REQUIRED"]`, declaring that the sensor API requires this parameter — queries cannot execute without it (BC-2.11.007 §Postconditions, REQUIRED taxonomy entry; annotation corrected from `INDEX` per ADR-057 §D5 / §D7); the current Wave-A routing is annotation-agnostic: `predicate_tree_to_filter_map §predicate_tree_to_filter_map` collects all case-sensitive `field = 'string'` equality predicates regardless of column annotation into the `FilterMap`, which materializes as `FetchContext.query_filters`; `execute_impl §execute_impl` then pre-seeds `step_vars["query.filter.device_id"]` from that map (ADR-057 §D4); Wave-A mandatory enforcement is the step-level `required_filters = ["device_id"]` gate (E-SPEC-029, ADR-057 §D7); plan-time E-QUERY-009 enforcement via `classify_predicates §classify_predicates` is an OPEN OBLIGATION (ADR-057 §D7); implementing story: `S-REQUIRED-COL-GATE-001`
- A `WHERE device_id = '...'` predicate is present in the PrismQL query against `armis_device_activity` with a non-empty value (a predicate with an empty value — `WHERE device_id = ''` — fails the required-filter gate per ADR-057 §D7 Rule 2 "contains it as an empty string" arm; see EC-014-007)

## Postconditions

- `PipelineExecutor.execute_impl` pre-seeds `step_vars["query.filter.device_id"]` from `FetchContext.query_filters["device_id"]` via the `${query.filter.*}` pre-seed loop (block comment `F-LP1-HIGH-004` in `pipeline.rs §execute_impl`: `for (k, v) in &context.query_filters { step_vars.insert(format!("query.filter.{k}"), ...) }`)
- The step URL is constructed as `<base_url>/api/v1/devices/<device_id_value>/activity` via interpolation of `${query.filter.device_id}` in the `path_template`
- The pipeline fetches from the DTU `routes::devices §get_device_activity` handler, extracts `$.data.activities` via `response_path`, and returns an array of activity records
- Each emitted record contains the five fields from `ActivityRecord` in `prism-dtu-armis/src/types.rs`, serialized via `axum::Json(body)` in the `(StatusCode::OK, Json(body)).into_response()` return of `routes::devices §get_device_activity`, where `body = ActivityResponse { data: ActivityData { activities, total } }` (wire-emission site authority per SAP-2 §Rule 6):
  - `activity_id: String` → TOML column `activity_id`, `column_type = "string"`, `ocsf_field = "raw_extensions.activity_id"` (Armis-specific activity record identifier; no OCSF standard field)
  - `device_id: String` → TOML column `device_id`, `column_type = "string"`, `ocsf_field = "device.uid"`, `options = ["REQUIRED"]` (device identifier matching the filter value; mandatory-filter annotation — sensor API requires this parameter; queries cannot execute without it per BC-2.11.007 §Postconditions; annotation corrected from `INDEX` per ADR-057 §D5 / §D7)
  - `activity_type: String` → TOML column `activity_type`, `column_type = "string"`, `ocsf_field = "activity_name"` (OCSF activity classification field)
  - `timestamp: String` → TOML column `timestamp`, `column_type = "string"`, `ocsf_field = "time"` (ISO-8601 activity timestamp; maps to OCSF `time` field)
  - `details: serde_json::Value` → TOML column `details`, `column_type = "json"`, `ocsf_field = "raw_extensions.details"` (JSON blob preserving Armis activity detail structure)
- Absent `device_id` filter, or `device_id` present as an empty string in `FetchContext.query_filters` (`WHERE device_id = ''`), → pipeline MUST return `SpecEngineError::HttpRequestFailed` (`status_code = 0`, E-SPEC-029, message `"required filter 'device_id' not provided; query requires WHERE device_id = '...' predicate"`) BEFORE issuing any HTTP request (ADR-057 §D7 Rule 2: gate fires when `FetchContext.query_filters` does NOT contain the key OR contains it as an empty string; POL-24 note: the canonical message template says "not provided" but the gate also fires for present-but-empty — F-WASE-P72B-OBS-002 tracks template wording separately); pre-fix behavior (absent case): `seed_missing_query_filter_vars §seed_missing_query_filter_vars` inserts empty-string seed → path `/api/v1/devices//activity` → `build_router §build_router` dispatches via `matchit §NodeType::Param` `split_at(0)` capturing `device_id = ""` (router-layer determination per ADR-057 §D4) → `get_device_activity §get_device_activity` filters fixture for `device_id == ""` → **HTTP 200 with `activities: []` and `total: 0`** (silent empty result, Standing Rule 3 §2 violation); pre-fix behavior (empty-string case): `predicate_tree_to_filter_map §predicate_tree_to_filter_map` pushes `device_id = ''` into `FetchContext.query_filters["device_id"] = ""` (key IS present, value is empty string); the pre-seed loop's `or_insert` path is NOT taken (key already present); interpolation still yields `/api/v1/devices//activity` → same silent empty result; anchor: absence arm — AC-004 / RG-004 (`test_armis_device_activity_absent_device_id_filter_returns_hard_error`); empty-value arm — `S-WAVE-A-ARMIS-ACTIVITY-001` AC-009 / RG-009 (`test_armis_device_activity_empty_device_id_filter_returns_hard_error`) [story-writer leg follows this burst — AC-009 / RG-009 to be added] per §TOML Contract required-filter note

## Invariants

- DI-005: OCSF schema validity — every record must produce a valid OCSF output with required fields populated

## TOML Contract

The `armis_device_activity` table MUST be declared in `crates/prism-sensors/specs/armis.sensor.toml` per ADR-057 §D5 (authoritative copy-source; anchor: `S-WAVE-A-ARMIS-ACTIVITY-001` AC-001 / RG-001 `test_armis_toml_armis_device_activity_table_declared_with_correct_step_block`). **Registered SQL surface:** `register_sensor §register_sensor` in `prism-query::table_registry §table_registry` composes `format!("{}_{}", spec.sensor_id, table.table_name)` = `format!("{}_{}", "armis", "device_activity")` = `"armis_device_activity"`. Declaring `table_name = "device_activity"` (not `"armis_device_activity"`) is required — the latter double-prefixes to `"armis_armis_device_activity"` and breaks all consumers that query `FROM armis_device_activity`. `TableSpec §TableSpec` requires both `pub table_name: String` and `pub ocsf_class: String` with no `#[serde(default)]`; both are mandatory at deserialization time. The keys `name` and `sensor_name` are not `TableSpec §TableSpec` fields and must not appear in the header. **`ocsf_class = "network_activity"`** (OCSF Class 4001): Armis device activity captures IoT/OT network behavior events; Class 4001 provides `device` (← `device_id` → `device.uid`), `activity_name` (← `activity_type`), and `time` (← `timestamp`), covering all five schema columns. `"detection_finding"` (OCSF Class 2001, used by `alerts`) is excluded — it covers evaluated security findings, not raw behavioral events. `"device"` is excluded — activity log is not inventory. This choice is decided (not implementer-determined) per ADR-057 §D5. **Authoritative copy-source for `S-WAVE-A-ARMIS-ACTIVITY-001` T-IMPL-01 (FB91 copy-target):** The complete block below (header + step + all columns) is copy-safe as a unit; reflects ADR-057 §D5 at its current state (`required_filters = ["device_id"]` field added to step block per ADR-057 §D7 in FB95; all other fields verbatim from ADR-057 §D5):
