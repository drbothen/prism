# BC-2.11.001: `query` MCP Tool Accepts Scoping + PrismQL Query String

## Description

The `query` MCP tool is the primary interface for analysts to interrogate sensor data. It accepts a PrismQL query string alongside optional scoping parameters (clients, sensors, sources, time range, limit, force_refresh), fans out concurrently to all resolved sensor API and internal RocksDB sources, materializes results as Arrow RecordBatch in a DataFusion SessionContext, and returns rows projected from OCSF-normalized event data (external) or native Prism records (internal). The SessionContext is ephemeral — it is torn down when the tool call returns, so there is no cross-call pagination; instead, the `limit` parameter (max 1000) truncates results and `is_truncated`/`total_available` fields in the response tell the analyst how to narrow further.

## Preconditions
- The `query` MCP tool is invoked with at minimum a `query` string parameter (required)
- Optional scoping parameters: `clients` (array of client IDs or null for all), `sensors` (array of sensor types or null for all — includes `"prism"` for internal tables), `sources` (array of data source names or null for all — includes `prism.*` names like `"prism.alerts"`, `"prism.cases"` for internal RocksDB-backed tables), `time_range` (relative or absolute), `limit` (max results, default 25, max 1000), `force_refresh` (boolean, default false -- bypass response cache; has no effect on internal tables which always read fresh from RocksDB)
  - **Interim implementation status (2026-06-10, MCP cascade P2-04 — implementer-verified):** `clients`, `limit`, and `force_refresh` are wired end-to-end in the shipped `query` tool. `sensors`, `sources`, and `time_range` are **declared; production wiring tracked by the query scope-params story per the 2026-06-10 review** (story-writer burst registering the anchor in parallel); **interim behavior: rejected with MCP `-32602` INVALID_PARAMS (`deny_unknown_fields`) — fail-closed, never silently ignored.** The declarations remain normative (POL-1 append-only spirit): the postconditions referencing `sensors`/`sources`/`time_range` resolution (scoping resolution, predicate intersection, `time_range_applied` in `query_context`) describe the target contract behavior the wiring story must deliver, not currently-shipped behavior.
- At least one client with at least one enabled sensor exists in configuration

## Postconditions
- The query string is parsed by the Chumsky parser (auto-detecting filter/SQL/pipe mode)
- Scoping parameters (`clients`, `sensors`) are resolved to concrete client/sensor combinations from config
- If the query contains `client_id`, `sensor`, or `source` predicates, they are intersected with tool parameters (narrowing, never widening)
- Fan-out to sensor APIs occurs for all resolved (client, sensor) combinations
- For external tables: Sensor responses are normalized to OCSF, materialized as Arrow RecordBatch, registered as DataFusion MemTable
- For internal tables (`prism.*` sources): Data is read directly from RocksDB, deserialized into Arrow RecordBatch, and registered as DataFusion tables. No API fan-out or OCSF normalization occurs. Virtual fields `sensor = "prism"` and `source = "{table_name}"` are injected.
- Both external and internal tables can be queried together in a single PrismQL statement (cross-source joins are supported)
- **Table availability is validated at plan time (before fan-out).** After AST parse and before any sensor API contact, the planner checks each `source_ref` in the `QueryPlan` against the live `TableRegistry`. If a referenced table is not registered, the query is rejected immediately with `E-QUERY-037` — a structured error carrying `table` (the requested table name), `sensor` (the sensor prefix), `available_sensors` (comma-separated list of currently-registered sensor IDs), `available_tables` (comma-separated list of currently-registered table names), and `did_you_mean` (the top-1 match from edit-distance ≤ 3 comparison against the org-visible registered table names, or absent if no close match exists). This check is mode-agnostic: it applies identically to SQL mode, filter mode, and pipe mode queries. No fan-out occurs for a rejected query. **Org-scoped enumeration (ADR-039, SEC-001/CWE-200):** The `available_sensors` and `available_tables` fields are computed via `filter_to_org_visible` at error-construction time using the following rules: (a) **Multi-tenant overlay deployment** — when `QueryOptions.clients` contains one or more `OrgSlug` values AND `resolved_spec_map` (the ADR-029 per-org overlay map, type `HashMap<ResolvedSpecKey, ResolvedSensorSpec>`) is populated on `QueryEngine`, `available_sensors` and `available_tables` are filtered to the union of sensors and tables registered for those requesting org(s). The `did_you_mean` suggestion is computed only over the org-visible table set via `TableRegistry::did_you_mean_for_tables(requested, &org_visible_tables)`. (b) **Single-tenant deployment or unrestricted multi-org query** — when `QueryOptions.clients` is `None` (no client restriction) OR `resolved_spec_map` is `None` (no overlay system configured), `available_sensors` and `available_tables` are read from the global `TableRegistry::registered_tables()` and `TableRegistry::registered_sensor_ids()` without filtering — identical to pre-ADR-039 behavior. (c) **Empty org scope** — when `QueryOptions.clients` is `Some([])` (empty slice), `available_sensors` and `available_tables` are both empty strings and `did_you_mean` is absent. When no sensors are configured globally, both fields are empty strings and `did_you_mean` is absent regardless of org scope.
- Query is executed via DataFusion; results returned as rows projected from OCSF-normalized event data (external) or native Prism records (internal)
- **No cross-call pagination for query results.** The ephemeral model means the SessionContext (and all materialized data) cannot be held across calls. Each `query` call re-materializes from scratch (the response cache mitigates re-fetch cost). The `limit` parameter truncates results. If more results exist than `limit`, the response includes `is_truncated: true` and `total_available` (count of all matching records before truncation). The user narrows their query or increases `limit` (up to 1000) to see more results. There is no cursor or offset-based pagination for query results.
- **Dual limit semantics (tool-level vs SQL-level).** Tool-level `limit` is applied after DataFusion execution (which may include SQL-level LIMIT). `total_available` reflects count after DataFusion execution but before tool-level truncation. SQL LIMIT reduces `total_available`; tool-level limit causes `is_truncated: true`.
- **Tool limit (max 1000) vs materialization limit (10K).** The tool-level `limit` (max 1000) is applied post-DataFusion. Materialization may fetch up to 10K records for sorting/aggregation before truncation. This is analogous to SQL LIMIT applied after ORDER BY. Future optimization: push limit hints to sensor adapters when no aggregation is needed.
- **Query limit vs materialization guidance:** If `total_available` significantly exceeds `limit`, the agent should narrow query scope (add filters, reduce client/sensor scope) rather than increasing `limit`. The max `limit` of 1000 means at most 1000 results per query call; records beyond that threshold require a narrower query, not a higher limit. The 10K materialization cap (DI-019) is a hard ceiling on sensor fan-out — increasing `limit` beyond 1000 is not possible, and even within the 1-1000 range, large result sets consume more memory and time.
- Response includes `query_context` with: `original_query`, `expanded_query` (after alias resolution), `clients_queried`, `sensors_queried`, `time_range_applied`, `total_available` (total matching records before limit), `returned_results` (actual count returned, <= limit), `is_truncated` (true if total_available > returned_results), `execution_time_ms`
- **Successful responses MAY include `normalized_pql`** (optional field): the Chumsky-normalized PQL string the planner accepted — the canonical form the server would replay to reproduce the identical query plan. The field is ABSENT on ALL error responses (including partial-failure-only errors). Zero-row successful results still carry `normalized_pql`. See BC-2.11.018 for the full contract (field shape, exclusions, round-trip guarantee, and injection-safety boundary).
- Response includes `sensor_errors` array for any sensors that failed (partial results are valid). **Per-target HTTP detail in `sensor_errors` (D-2151, human-approved 2026-08-14).** Each failing sensor target MUST contribute one entry to `sensor_errors` carrying the sanitized HTTP status and body snippet from the failed HTTP response. Per-target entry wire format: `"<table>: HTTP <status>: <body-snippet>"` when the response body is non-empty after sanitization; `"<table>: HTTP <status>"` when the response body is empty or absent. `<table>` is the sensor table identifier (e.g., `"xdome_devices"`); `<status>` is the integer HTTP status code (e.g., `403`); `<body-snippet>` is the first 256 UTF-8 bytes of the response body after `sanitize_body_snippet_bytes` sanitization (control bytes 0x00–0x08, 0x0B, 0x0C, 0x0E–0x1F, 0x7F–0x9F replaced with space; TAB/LF/CR preserved). Serialization invariants (wire-shape discipline, CLAUDE.md 2026-07-13): `sensor_errors` MUST be ABSENT from the response (MUST NOT be serialized as `null`, MUST NOT be `[]`) when no sensors failed; when present, MUST be a non-empty array; each array element MUST be a non-empty String (MUST NOT be element-null, MUST NOT be element-empty-string `""`); NULL vs absent vs empty MUST be asserted at the wire level in tests covering this contract. Injection safety: `sanitize_body_snippet_bytes` (256-byte cap + control-char replacement) is the sole sanitizer; upstream sensor body content MUST NOT be interpolated into any response field outside `sensor_errors` entries (DI-006). The aggregate `AllTargetsFailed` Display string (E-SENSOR-030) remains COUNT-ONLY — per-target HTTP detail MUST NOT appear in the aggregate Display string, only in `sensor_errors` entries (BC-2.10.007 Rule 1 unchanged; BC-2.01.010 §Postconditions AllTargetsFailed Per-Target Logging updated in same burst to dual-channel surfacing). **Live-path ratification and Ok-branch unreachability (F-P38-MED-002 re-adjudication, v1.25 supersedes v1.24 "Code-path coverage" text).** The per-target HTTP `sensor_errors` entries are delivered by the **AllTargetsFailed arm only** — this is the sole live code path for `sensor_errors` production in `materialize_single_external_target`. Mechanism: `materialize_single_external_target` calls `fan_out` with exactly one target per iteration to preserve per-client identity for per-client attribution (AC-6). The `fan_out` contract (`crates/prism-sensors/src/fanout.rs` §fan_out; BC-2.01.010) returns either `Ok(FanOutResult{successes:[...], errors:[]})` on success or `Err(SensorError::AllTargetsFailed{errors:[...]})` on failure for a single-target call — these are mutually exclusive outcomes for one target. Therefore `Ok` with non-empty `fan_result.errors` is **structurally unreachable** under the current single-target fanout design (POL-34 ratification). The v1.24 "Code-path coverage" paragraph incorrectly described the Ok-branch as a live requirement path; that framing is superseded. **Cross-client partial-failure** (e.g., client org-a returns HTTP 403, client org-b succeeds) is the correct real-world scenario — it is delivered via **two separate AllTargetsFailed arm iterations** (one per client's `fan_out` call), each producing a `sensor_errors` entry per EC-11-088/089/090. EC-11-091 describes this live scenario. **Dead-code disposition — option (i):** The `for fan_err in fan_result.errors` loop in the Ok-branch is retained with the same per-target HTTP format as the AllTargetsFailed arm, plus an unreachability comment citing the `fan_out` single-target contract; this is fail-safe behavior if the single-target fanout design changes in the future (no panic risk). Option (ii) (`debug_assert!(fan_result.errors.is_empty())`) is rejected: it panics in debug builds but silently loses error data in release builds. **T-QERR-4 prohibition:** Do NOT refactor `materialize_single_external_target` to call `fan_out` with multiple targets per iteration — that would regress per-client attribution (AC-6). MUSTs anchored to: DEFECT-ADAPTER-TLS-XDOME-LIVE-001 AC-QERR-001 + RG-016 (AllTargetsFailed arm; existing tests, expected GREEN); and AC-QERR-002 + RG-017 (live cross-client partial-failure regression guard; `clients=["org-a","org-b"]` scenario, expected GREEN; story-writer assigns canonical test name).
- Response includes `rows` array of OCSF-normalized results with `trust_level: "untrusted_external"`. **Key name rationale:** The response array is named `rows`, not `events`: query results are tabular projections over OCSF-normalized columns — aggregate buckets (GROUP BY), joined rows, enriched columns, and internal `prism.*` records are not OCSF event objects, and even raw-event results are flattened column projections rather than OCSF event entities. Key name shipped in S-5.01-FOLLOWUP-MCP-BOOT (PR #163); ratified per human adjudication 2026-07-13 (DEFECT-MCP-ROWSHAPE-NULLS-001 F-MCPNULL-P1-MED-001).
- **Row-shape null-not-absent — agent-harness schema stability (DEFECT-MCP-ROWSHAPE-NULLS-001).** Every column present in the DataFusion result schema — including projected columns, columns produced by `| enrich` stages, and joined columns from cross-source queries — MUST appear as an explicit key in every emitted row object within the `rows` array. For NULL-valued cells, the JSON value MUST be `null` (explicit null), never key-omission. The `arrow_json` `WriterBuilder` in `prism-mcp` MUST be configured with `.with_explicit_nulls(true)` at all RecordBatch-to-JSON serialization sites in the query tool response path. This invariant applies identically to all three query modes (SQL, filter, pipe) and to both OCSF-normalized external events and internal Prism records (`prism.*` sources). **Agent-harness rationale:** LLM agents consuming `query` tool results must be able to rely on consistent key presence across all rows in a result set; a row object missing a key is indistinguishable from a row with an intentionally absent field and causes silent reasoning errors in downstream agent logic (`project_agent_harness_design.md`). **Precedents:** ADR-051 §D2 (Coercion Semantics — NULL is the correct partial-failure signal for a single enrichment row, not a passthrough or empty string) establishes the NULL-when-unavailable rule for enrichment output; ADR-051 §D4 (Scalar-Input Consistency Rule) is a related rule establishing that JSON-list input to a typed-output UDF produces NULL + E-INFUSE-014. The key-presence component of this invariant — that a NULL output must be serialized as an explicit `null` JSON value rather than key-omission — is EC-11-079's own codification at this BC; ADR-051 specifies the NULL failure-signal at the enrichment layer, not the serialization-layer key-presence guarantee for the tool-response wire format. BC-2.10.007 v1.6 establishes the same null-not-absent pattern for `retry_after_seconds` in error responses (field present as `null`, never omitted). **Acceptance-criteria grade (T13 live-audit probes [C3]/[H20]):** (a) a query projecting a nullable column returns every row with that key present — JSON `null` for NULL cells, non-null value otherwise; (b) a pipe-mode `| enrich` query where the enrichment UDF returns NULL for some rows returns those rows with the enriched column key present as `null`; (c) no row object in `rows` may omit a key that is present in the projected result schema for that query.
- **Float64 non-finite serialization boundary (EC-11-081).** Float64 NaN and ±Infinity values in query results are coerced to JSON `null` at the MCP serialization boundary: the key is present in every row (EC-11-079 invariant holds), but the value is `null` — indistinguishable from Arrow-null. **Mechanism:** arrow-json v58 (`arrow-json = "58.2.0"`) hardcodes `is_infinite() || is_nan()` → literal `null` bytes in the float encoder; no `WriterBuilder` option overrides this behavior. **Current ingress reachability (all four paths are non-finite-proof):** (1) infusion UDF float coercion uses `serde_json::Number::from_f64`, which returns `None` for non-finite values and produces Arrow null rather than a non-finite Float64 array entry; (2) spec-driven adapters normalize through JSON (RFC 8259 §6 forbids non-finite numbers, so no non-finite value can survive deserialization); (3) PrismQL float literal grammar does not match `NaN` or `inf` tokens; (4) DataFusion division-by-zero propagates as a query error, not `Infinity`. **Caller invariant:** callers MUST NOT rely on distinguishing NaN/±Inf from Arrow null in query results — this is a documented serialization-boundary artifact, NOT silent data corruption. If a future direct-Rust adapter constructs `Float64Array` without JSON normalization, non-finite values will serialize silently as `null`; that adapter must add a pre-registration normalization step. **Option B (pre-serialization scan + new E-QUERY error) considered and declined:** the scan adds CPU cost for a currently-unreachable condition; no actionable behavior difference for current callers; revisit if a direct-Rust adapter path ships (F-MCPRS-PRL16-LOW-001 probe 2026-07-14).
