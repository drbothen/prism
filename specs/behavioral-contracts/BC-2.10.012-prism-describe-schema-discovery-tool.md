# BC-2.10.012: `prism_describe` Schema Discovery Tool (L2)

## Description

The `prism_describe` MCP tool is always registered and returns the per-client table/column/type schema catalog sourced from the spec layer: column schema is read from `query_engine.resolved_spec_map()` (multi-tenant: filter by `OrgSlug`, walk `ResolvedSensorSpec.spec.tables`, collect `TableSpec.columns`) or from `config_manager` (single-tenant/test fallback, same pattern as `render_schema_resource`). It emits an audit event on every call (schema enumeration is auditable in a multi-tenant MSSP security product), is annotated read-only and idempotent, and its response includes auto-generated per-table example queries grounded in the client's actual registered table names plus `pql_hints` about the client's specific sensor set. This is the primary schema-discovery surface for the 4-layer LLM onboarding mechanism (ADR-041 L2).

## Preconditions

1. The `prism_describe` tool is always registered — it is NOT gated by any feature flag or capability check. It is in the same always-registered tier as `list_capabilities` (BC-2.10.011).
2. The `TableRegistry` has been initialized at boot (may be empty — zero tables is a valid state).
3. The calling model has provided a valid `client_id` parameter (required; validated per BC-2.10.004).
4. Column schema is reachable via two existing `PrismServer` fields — no new injection required:
   - `self.query_engine.resolved_spec_map()` → `Arc<HashMap<(OrgSlug, SensorId), ResolvedSensorSpec>>` (multi-tenant, preferred path; `ResolvedSensorSpec.spec.tables: Vec<TableSpec>`, `TableSpec.columns: Vec<ColumnSpec>`)
   - `self.config_manager` → `Arc<ArcSwap<ConfigManager>>` (single-tenant/test fallback, same pattern as `render_schema_resource` in `resources.rs`)
   Note: `TableRegistry` is a concrete `#[non_exhaustive] struct` storing table-name strings only — it holds NO per-column schema. Column data lives exclusively in the spec layer above.

## Postconditions

### Tool registration and annotations

- `prism_describe` appears in `tools/list` on every session, regardless of client configuration or feature flags.
- MCP tool annotations (MCP 2025-06-18 spec): `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`.
- Tool description includes a clear statement of when to call it: "Call this tool before writing a PrismQL query to discover which tables and columns are available for the specified client."

### Response shape — `PrismDescribeResponse`

The successful response is a JSON object (carried in `structuredContent`) with the following shape:

```json
{
  "client_id": "<the requested client_id string>",
  "tables": [
    {
      "name": "<fully-qualified table name, e.g. 'cyberint_alerts'>",
      "sensor_type": "<sensor prefix, e.g. 'cyberint'>",
      "description": "<human-readable table description from TableSpec in resolved_spec_map>",
      "columns": [
        {
          "name": "<column_name>",
          "type": "<ColumnType string: String|Integer|Float|Boolean|Datetime|Json>",
          "description": "<optional human-readable column description, or 'unconfirmed — column declared in spec but not yet validated against live sensor data' for pending columns>",
          "nullable": true
        }
      ],
      "example_query": "<auto-generated PQL query using this client's real table name; always parseable — never contains `--` comment syntax>",
      "example_note": "<optional contextual note about the example_query, e.g. OCSF casing guidance; null for non-severity tables>"
    }
  ],
  "pql_hints": ["<1–3 hints; see §pql_hints content below. N≥1: always 3 elements (2 Category-1 + 1 Category-2). N=0: 1 element.>"]
}

**`example_note` invariant (F-MED-002 closure):** The `example_query` field MUST be valid, parseable PQL — it MUST NOT contain `--` SQL comment syntax (PrismQL has no line-comment support). Contextual prose notes (e.g., OCSF casing guidance, operator hints) are carried in `example_note: Option<String>`, a separate nullable field. An LLM agent MAY copy `example_query` verbatim into a `prism_query` call; it reads `example_note` as explanatory prose. `example_note` is `null` for all non-severity-IEQ templates.

**`example_note` gate note:** Adding `example_note: Option<String>` to the existing `#[non_exhaustive]` `TableDescriptor` struct is a non-breaking field addition — it does NOT change `EXPECTED=89` in `ci.yml`. The non-exhaustive compile-fail gate counts annotated *types*, not field additions within existing types. The `Deserialize` impl must default `example_note` to `None` when the field is absent (use `#[serde(default)]` or `Option` deserialize semantics).
```

**`name` postcondition — fully-qualified FROM-ready token (closes AUDIT-001, AUDIT-008):**

The `name` field MUST be the exact, fully-qualified table name that the `FROM` clause accepts — i.e., the underscore-qualified `<sensor_type>_<logical_name>` form (e.g., `"cyberint_alerts"`, `"crowdstrike_detections"`, `"armis_devices"`). It MUST NOT be the bare logical table name (e.g., `"alerts"`). The authoritative source is the `TableRegistry` registered-table key for this org, which uses the underscore-qualified form.

**Disambiguation guarantee (closes AUDIT-008):** When a client has multiple tables with the same logical suffix (e.g., both `claroty_alerts` and `cyberint_alerts`), the fully-qualified `name` field unambiguously identifies each table. An agent using `name` verbatim in a `FROM` clause MUST succeed without a plan-time error.

**`example_query` grounding (reinforced):** The `example_query` field MUST use the same fully-qualified table name as `name`. E.g., `"SELECT COUNT(*) FROM cyberint_alerts WHERE timestamp > NOW() - INTERVAL '1h'"` — never `"SELECT COUNT(*) FROM alerts ..."`.

**Column ordering guidance (closes AUDIT-003 UX component):**

Columns in the `columns` array MUST be ordered as follows:
1. Confirmed columns first — columns whose names and types have been validated against live sensor data (or are declared in a shipped sensor spec). These appear without any `"unconfirmed"` annotation in their `description`.
2. Unconfirmed/pending columns after confirmed columns — columns declared in the spec but not yet validated against the live sensor (e.g., IOC enrichment fields like `ioc_value_singleton`, `device_cves_first` that require an enrichment UDF to populate). These MUST include a `description` annotation: `"unconfirmed — column declared in spec but not yet validated against live sensor data"` (exact string, or prefixed to any other description text).

This ordering ensures that an agent reading the first few columns in the response sees the most reliable fields first, reducing the risk of selecting unresolvable columns in initial queries.

All public response types (`PrismDescribeResponse`, `TableDescriptor`, `ColumnDescriptor`) carry `#[non_exhaustive]` per CLAUDE.md conventions. Adding `example_note: Option<String>` to `TableDescriptor` is a field addition to an existing `#[non_exhaustive]` type — it does NOT increment `EXPECTED=89` (the gate counts annotated types, not field additions).

### Auto-generated example queries

The `example_query` field for each table is generated by `build_example_query` from the per-client schema catalog (sourced via `resolved_spec_map` or `config_manager` as described in §Preconditions) using canonical PQL query templates instantiated with the real table name and real column names. `example_query` is ALWAYS a valid, parseable PQL string — it MUST NOT contain `--` SQL comment syntax (PrismQL has no line-comment support; F-MED-002). Contextual prose about the query (e.g., OCSF casing guidance) is emitted in `example_note: Option<String>`, which is `null` for all non-severity-IEQ templates.

Template selection uses a **4-tier priority ladder** with a direct conditional structure (not a build-then-override approach). Tier 1 fires first; if it fires, Tiers 2/3/4 are skipped. The effective precedence (highest priority wins) is:

1. **Severity-IEQ template** (HIGHEST priority — F-MED-002 / AC-025 / ADR-047 §D.4) — used when: (a) a column named exactly `"severity"` (any `ColumnType`) is present, AND (b) the table's sensor prefix appears in the `SENSOR_SEVERITY_VOCABULARY` registry (controls which sensors have a meaningful severity column). This template fires **before** the aggregate check — severity-vocabulary tables with Integer/Float columns still emit IEQ form, not aggregate. This prevents the aggregate variant from silently suppressing the IEQ teaching example.
   - `example_query`: `FROM <table_name> | where severity IEQ 'high' | limit 50`
   - `example_note`: `"OCSF severity is Title-case post-normalization (e.g., 'High'). Use IEQ for case-insensitive matching."`
   - Rationale: BC-2.02.013 PRIMARY normalization (`build_column_array`) canonicalizes severity to OCSF Title-case before DataFusion materialization. The per-sensor `IN ('High', ...)` / `IN ('HIGH', ...)` / `IN ('high', ...)` literals from the previous `SENSOR_SEVERITY_VOCABULARY` casing approach are therefore redundant AND would silently return 0 rows against non-Title-case test data. `IEQ` matches regardless of casing — the canonical teaching example is always correct. The sensor vocabulary membership check remains for GUARD purposes (to avoid emitting an IEQ example for sensors with no meaningful severity column), but the casing lookup is no longer used for literal injection.
   - Registered vocabulary sensors (guard only — no longer casing source): `crowdstrike_*`, `armis_*`, `cyberint_*`. `claroty_*` — not registered (no `severity` column in claroty spec). Unknown sensor prefix with a `severity` column → severity-IEQ is suppressed; falls through to Tier 2/3/4.

2. **Aggregate template** — used when Tier 1 did NOT fire (no severity-vocabulary column) AND the table has at least one `Integer` or `Float` `ColumnType` column. The first such column in the schema array is used as `<field>`:
   - `example_query`: `SELECT <field>, COUNT(*) FROM <table_name> GROUP BY <field> ORDER BY COUNT(*) DESC LIMIT 10`
   - `example_note`: `null`

3. **Count-recent template** — used when Tiers 1 and 2 did NOT fire AND a `Datetime`-typed column exists. The datetime column name is **derived from the first `ColumnType::Datetime` column** in the schema array — it is NOT hardcoded as `"timestamp"`. Tables without any `Datetime`-typed column do not use this template.
   - `example_query`: `SELECT COUNT(*) FROM <table_name> WHERE <first_datetime_column> > NOW() - INTERVAL '1h'`
   - `example_note`: `null`

4. **Column-free fallback** (LOWEST priority) — used when Tiers 1/2/3 all did NOT fire (column set has no severity-vocabulary column, no `Integer`/`Float` column, AND no `Datetime`-typed column; e.g., a table with only `String` and `Boolean` columns, or an empty column list). Also used for tables with zero declared columns (EC-10-025).
   - `example_query`: `SELECT * FROM <table_name> LIMIT 25`
   - `example_note`: `null`

**Implementation notes for future implementers (TD-VSDD-091 — cite behavioral anchors, not line numbers):**

- The implementation uses a direct conditional: if severity-IEQ fires, skip aggregate. The previous build-then-override pattern (build base → maybe override with severity → maybe override with aggregate) is RETIRED — it caused aggregate to suppress the IEQ teaching example for severity-vocabulary tables that happened to have a numeric column.
- `SENSOR_SEVERITY_VOCABULARY` membership check is still used as a GUARD (does this sensor have a meaningful severity column?), but the per-sensor casing values are no longer used to inject literals. IEQ is always case-insensitive regardless of stored casing.
- Template selection is deterministic: the same table schema (same column names, types, and order) always produces the same `example_query` and `example_note`.

These examples are schema-grounded but not human-curated — they may be mechanical but they reference real column names and correct per-sensor literal casing for this client's actual tables.

### `pql_hints` content

The `pql_hints` array contains 1–3 client-specific informational strings. With all currently-specified categories emitted, the N ≥ 1 case always produces exactly 3 elements (2 Category-1 + 1 Category-2). Category-3 standing guidance is optional and not currently emitted by `build_pql_hints`. Two mandatory categories:

**Category 1 — Table availability summary (always present):**

When N ≥ 1 (the `tables[]` array is non-empty), exactly two hints are emitted:
1. `"Use 'SELECT * FROM <table> LIMIT 25' to query any of the N table(s) above."` — N is the count of entries in `tables[]`; the literal token `<table>` instructs the agent to substitute an actual table name from the `tables[]` array. This hint does NOT enumerate table names — the `tables[]` array is the authoritative source for names, sensor types, column details, and per-table `example_query` values.
2. `"Consult prismql://reference for full PQL grammar and operator reference."` — grammar/reference discovery pointer (serves the Category-3 standing-guidance purpose).

When N = 0 (the `tables[]` array is empty), exactly one hint is emitted, determined by `OrgRegistry` lookup:
- Registered-but-empty (org is in `OrgRegistry` but has zero sensor overlays configured): `"No sensor tables are available for client '<client_id>'. The client may not have any sensor overlays configured."`
- Not-registered (org is absent from `OrgRegistry` entirely): `"Client '<client_id>' is not registered. Check prism.toml [[orgs]] configuration."`
- Single-tenant fallback (no `OrgRegistry` available): same hint as registered-but-empty above.

These zero-table cases are also documented in §Non-existent client_id handling and §Canonical Test Vectors.

**Category 2 — Enrichment UDF discovery (mandatory when N ≥ 1; closes AUDIT-002):**

Category-2 hints are emitted ONLY when N ≥ 1 (the `tables[]` array is non-empty). When N = 0, Category-2 is suppressed entirely — the Category-1 zero-table hint is sufficient.

`InfusionRegistry` is a global registry (one per Prism instance, not per-org). Category-2 presence/absence reflects whether the Prism operator has configured enrichment UDFs, not the requesting `client_id`.

**`build_pql_hints` signature change (ADR-022 §C wiring — not redesign):**

Add parameter `infusion_registry: Option<&prism_spec_engine::InfusionRegistry>`. At the `handle_prism_describe` call site in `prism_describe.rs`, resolve with one new line:
```rust
let infusion_registry = query_engine.and_then(|qe| qe.infusion_registry());
// pass infusion_registry.as_deref() to build_pql_hints
```
This is the identical pattern already used for `org_registry` at the same call site — no new `PrismServer` fields required.

**`InfusionUdfDescriptor` augmentation (prerequisite):**

`InfusionUdfDescriptor` (in `prism-spec-engine/src/infusion/udf.rs`) must gain `pub input_field: String` — the column name fed to the enrichment lookup, sourced from `InfusionField.input_field`. Changes required:
1. Add `pub input_field: String` to the `InfusionUdfDescriptor` struct body.
2. Add `input_field: impl Into<String>` to the `new()` constructor signature and body.
3. In `udf_descriptors()` (in `infusion/mod.rs`), propagate `field.input_field.clone()` into each descriptor struct literal.
4. All callers of `InfusionUdfDescriptor::new()` in `prism-query` (~10 sites across `src/infusion_udf.rs`, `src/engine.rs`, and test files) must pass the `input_field` argument. Test fixtures may pass `""` (empty string) since `input_field` is only consumed by `build_pql_hints` — this is not a semantic gap, it is a fixture scope boundary.
The `#[non_exhaustive]` guard is already set; no external struct-literal breakage beyond `new()` callers.

**When `infusion_registry` is `Some(reg)` AND `reg.udf_descriptors()` returns a non-empty `Vec`:**

Exactly one hint is emitted. Build it as:
1. `let descriptors = reg.udf_descriptors();`
2. Sort by `d.name` using case-sensitive lexicographic order (`str::cmp` / natural `<`).
3. Build the list: each entry is `format!("{}({})", d.name, d.input_field)`, joined by `", "`.
4. Use the FIRST entry (after sorting) as the example call: `format!("{}({})", first.name, first.input_field)`.
5. Assemble the final hint string:
   `format!("Enrichment available via pipe syntax: | enrich {}. Available UDFs for this client: {}", first_entry, list)`

Byte-exact example — two UDFs: `nvd_cvss` (input_field: `device_cves_first`) and `threat_score` (input_field: `ioc_value_singleton`) — `nvd_cvss` sorts before `threat_score` (`n < t`):

`"Enrichment available via pipe syntax: | enrich nvd_cvss(device_cves_first). Available UDFs for this client: nvd_cvss(device_cves_first), threat_score(ioc_value_singleton)"`

Byte-exact example — three UDFs from a single infusion all sharing `iocs_value` input: `threat_is_known_malicious`, `threat_score`, `threat_sources` — sorted: `threat_is_known_malicious` first:

`"Enrichment available via pipe syntax: | enrich threat_is_known_malicious(iocs_value). Available UDFs for this client: threat_is_known_malicious(iocs_value), threat_score(iocs_value), threat_sources(iocs_value)"`

**When `infusion_registry` is `None` OR `reg.udf_descriptors()` returns an empty `Vec`:**

Exactly one hint is emitted (byte-exact):

`"No enrichment UDFs are registered for this client — enrichment is not available."`

This explicit negative signal prevents the agent from attempting `| enrich ...` syntax and receiving an opaque error.

**Ordering — combined `pql_hints` array for N ≥ 1:**

```
pql_hints = [
  "Use 'SELECT * FROM <table> LIMIT 25' to query any of the N table(s) above.",   // Category-1 index 0
  "Consult prismql://reference for full PQL grammar and operator reference.",       // Category-1 index 1
  "<Category-2 presence or absence hint>"                                           // Category-2 index 2
]
```

`pql_hints` for N ≥ 1 always has exactly **3 elements** once Category-2 is implemented.

**Category 3 — Standing guidance (optional, 0–1 hints):**
- `"For sensor API errors, retry the query or narrow the time range"` (standing operational hint, included at implementer discretion)

### Audit event emission

Every call to `prism_describe` emits an `AuditEntry` (DI-004) with:
- `tool_name: "prism_describe"`
- `client_id: <requested client_id>`
- `operation: "schema_enumeration"`
- `outcome: "success"` (or `"error"` on parameter validation failure)

**Implementer obligation:** The current `AuditWriter::write_tool_call` surface accepts `(tool_name, client_id, outcome)` — it has no `operation` slot. The implementer MUST extend `AuditWriter` (or add an overloaded variant) to accept the `operation` field so that `"schema_enumeration"` is written into the audit record. The `outcome` value MUST be a real success/error discriminant — NOT the literal string `"invoked"`. This requirement is non-negotiable: spec wins (VSDD standing rule), and the implementer brings the audit surface into conformance with this BC.

This satisfies ADR-041's security requirement: schema enumeration in a multi-tenant MSSP environment is an auditable action. Unlike host-side injection (which silently prepends schema to every prompt), model-initiated `prism_describe` calls produce an audit trace. This mirrors ADR-005's pattern for security-critical observability events.

### Non-existent client_id handling

If the `client_id` resolves via OrgRegistry lookup but has zero entries in `resolved_spec_map` (no sensors provisioned for this org), the response is returned with `tables: []` and `pql_hints: ["No sensor tables are available for client '<client_id>'. The client may not have any sensor overlays configured."]`. This is NOT an error — it is a valid empty-schema response (EC-10-025).

If the `client_id` fails format validation (`[a-zA-Z0-9_-]{1,64}`), the tool returns `E-MCP-001` (same as all other tools per BC-2.10.007, BC-2.10.004). This is consistent with the validator middleware used across the entire tool router.

If the `client_id` passes format validation but is not registered in `OrgRegistry`, the response returns `tables: []` and `pql_hints: ["Client '<client_id>' is not registered. Check prism.toml [[orgs]] configuration."]`. This matches the non-error posture of `list_capabilities` for unknown-but-well-formed clients (BC-2.10.011).

### Response envelope

The response uses `SafetyEnvelopeBuilder` (consistent with all Prism MCP tools) with `trust_level: "internal"` in `_meta`. The schema catalog is server-authored (sourced from operator TOML specs via `resolved_spec_map` or `config_manager`), not sensor data — `trust_level: "internal"` is correct.

### Single source of truth with `prismql://schema/{client_id}`

Both `prism_describe` and the `prismql://schema/{client_id}` resource template (BC-2.10.013) are computed from the same spec-layer column data: `query_engine.resolved_spec_map()` (multi-tenant) or `config_manager` (single-tenant fallback). There is exactly one authoritative per-client schema source — the operator TOML specs surfaced through these two existing `PrismServer` access paths. Neither caches independently from the other; short-TTL caching is acceptable for the resource path per BC-2.10.013, using the same `TableRegistry` change-notification signal as the invalidation trigger (the `TableRegistry` change event is the hot-reload signal, even though column data itself comes from `resolved_spec_map`).

## Invariants

- DI-004: Audit completeness — every `prism_describe` call emits an `AuditEntry`. Audit fail-closed does NOT apply here (this is a read tool, not a write tool): if audit emission fails, the call proceeds with `_meta.audit_warning` in the response (consistent with BC-2.11.001 and DI-004 split behavior).
- DI-002: Credential isolation — `prism_describe` response MUST NOT include any credential values, auth token snippets, or API key strings. Column names sourced from `resolved_spec_map → TableSpec.columns → ColumnSpec.name` are operator-defined schema identifiers — they do not contain credentials. `api_base_url` values are not part of the response.
- DI-006: The response is server-authored (operator TOML specs → `resolved_spec_map` / `config_manager` → response). It does not contain sensor API response bodies or user-controlled input. No prompt injection scan is required for the discovery response itself, but the `pql_hints` strings are server-authored constants, not interpolated sensor data.
- DI-008: The `client_id` scoping is enforced — the `resolved_spec_map` lookup is filtered to entries whose `OrgSlug` matches the requesting client's `client_id`. A call for `client_id = "acme"` MUST NOT return tables or columns belonging to "globex".

## Error Cases

| Error | Condition | Behavior |
|-------|-----------|----------|
| `E-MCP-001` | `client_id` fails `[a-zA-Z0-9_-]{1,64}` format validation | BC-2.10.007 structured error; `original_params_valid: false` |

**Non-error cases:**
- Unknown-but-well-formed `client_id` → success with `tables: []` and a hint
- Empty schema (no tables provisioned) → success with `tables: []` and a hint
- `TableRegistry` has tables for this client → success with full catalog
