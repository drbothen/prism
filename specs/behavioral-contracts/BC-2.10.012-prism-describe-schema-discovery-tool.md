# BC-2.10.012: `prism_describe` Schema Discovery Tool (L2)

## Description

The `prism_describe` MCP tool is always registered and returns the per-client table/column/type schema catalog sourced from the spec layer: column schema is read from `query_engine.resolved_spec_map()` (multi-tenant: filter by `OrgSlug`, walk `ResolvedSensorSpec.spec.tables`, collect `TableSpec.columns`) or from `config_manager` (single-tenant/test fallback, same pattern as `render_schema_resource`). It emits an audit event on every call (schema enumeration is auditable in a multi-tenant MSSP security product), is annotated read-only and idempotent, and its response includes auto-generated per-table example queries grounded in the client's actual registered table names plus `pql_hints` about the client's specific sensor set. This is the primary schema-discovery surface for the 4-layer LLM onboarding mechanism (ADR-041 L2).

## Preconditions

1. The `prism_describe` tool is always registered — it is NOT gated by any feature flag or capability check. It is in the same always-registered tier as `list_capabilities` (BC-2.10.011).
2. The `TableRegistry` has been initialized at boot (may be empty — zero tables is a valid state).
3. The calling model has provided a valid `client_id` parameter (required; validated per BC-2.10.004).
4. Column schema is reachable via two existing `PrismServer` fields — no new injection required:
   - `self.query_engine.resolved_spec_map()` → `Arc<HashMap<(OrgSlug, SensorId), ResolvedSensorSpec>>` (multi-tenant, preferred path; `ResolvedSensorSpec.spec.tables: Vec<TableSpec>`, `TableSpec.columns: Vec<ColumnSpec>`)
   - `self.config_manager` → `Arc<ArcSwap<ConfigManager>>` (single-tenant/test fallback, same pattern as `render_schema_resource` in `resources.rs`)
   Note: `TableRegistry` is a concrete `#[non_exhaustive] struct` storing table-name strings only — it holds NO per-column schema. Column data lives exclusively in the spec layer above.

## Postconditions

### Tool registration and annotations

- `prism_describe` appears in `tools/list` on every session, regardless of client configuration or feature flags.
- MCP tool annotations (MCP 2025-06-18 spec): `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`.
- Tool description includes a clear statement of when to call it: "Call this tool before writing a PrismQL query to discover which tables and columns are available for the specified client."

### Response shape — `PrismDescribeResponse`

The successful response is a JSON object (carried in `structuredContent`) with the following shape:

```json
{
  "client_id": "<the requested client_id string>",
  "tables": [
    {
      "name": "<fully-qualified table name, e.g. 'cyberint_alerts'>",
      "sensor_type": "<sensor prefix, e.g. 'cyberint'>",
      "description": "<human-readable table description from TableSpec in resolved_spec_map>",
      "columns": [
        {
          "name": "<column_name>",
          "type": "<ColumnType string: String|Integer|Float|Boolean|Datetime|Json>",
          "description": "<optional human-readable column description, or 'unconfirmed — column declared in spec but not yet validated against live sensor data' for pending columns>",
          "nullable": true
        }
      ],
      "example_query": "<auto-generated PQL query using this client's real table name>"
    }
  ],
  "pql_hints": ["<1-5 client-specific tips, see §pql_hints content below>"]
}
```

**`name` postcondition — fully-qualified FROM-ready token (closes AUDIT-001, AUDIT-008):**

The `name` field MUST be the exact, fully-qualified table name that the `FROM` clause accepts — i.e., the underscore-qualified `<sensor_type>_<logical_name>` form (e.g., `"cyberint_alerts"`, `"crowdstrike_detections"`, `"armis_devices"`). It MUST NOT be the bare logical table name (e.g., `"alerts"`). The authoritative source is the `TableRegistry` registered-table key for this org, which uses the underscore-qualified form.

**Disambiguation guarantee (closes AUDIT-008):** When a client has multiple tables with the same logical suffix (e.g., both `claroty_alerts` and `cyberint_alerts`), the fully-qualified `name` field unambiguously identifies each table. An agent using `name` verbatim in a `FROM` clause MUST succeed without a plan-time error.

**`example_query` grounding (reinforced):** The `example_query` field MUST use the same fully-qualified table name as `name`. E.g., `"SELECT COUNT(*) FROM cyberint_alerts WHERE timestamp > NOW() - INTERVAL '1h'"` — never `"SELECT COUNT(*) FROM alerts ..."`.

**Column ordering guidance (closes AUDIT-003 UX component):**

Columns in the `columns` array MUST be ordered as follows:
1. Confirmed columns first — columns whose names and types have been validated against live sensor data (or are declared in a shipped sensor spec). These appear without any `"unconfirmed"` annotation in their `description`.
2. Unconfirmed/pending columns after confirmed columns — columns declared in the spec but not yet validated against the live sensor (e.g., IOC enrichment fields like `ioc_value_singleton`, `device_cves_first` that require an enrichment UDF to populate). These MUST include a `description` annotation: `"unconfirmed — column declared in spec but not yet validated against live sensor data"` (exact string, or prefixed to any other description text).

This ordering ensures that an agent reading the first few columns in the response sees the most reliable fields first, reducing the risk of selecting unresolvable columns in initial queries.

All public response types (`PrismDescribeResponse`, `TableDescriptor`, `ColumnDescriptor`) carry `#[non_exhaustive]` per CLAUDE.md conventions. The `ci.yml EXPECTED` non-exhaustive gate count is incremented accordingly.

### Auto-generated example queries

The `example_query` field for each table is generated by `build_example_query` from the per-client schema catalog (sourced via `resolved_spec_map` or `config_manager` as described in §Preconditions) using canonical PQL query templates instantiated with the real table name and real column names. Template selection uses a **4-tier priority ladder**: the implementation builds a base query first, then successively overrides it with higher-priority variants when the column set qualifies — last override wins. The effective precedence (highest priority wins) is:

1. **Aggregate template** (highest priority) — used when the table has at least one `Integer` or `Float` `ColumnType` column. The first such column in the schema array is used as `<field>`:
   `SELECT <field>, COUNT(*) FROM <table_name> GROUP BY <field> ORDER BY COUNT(*) DESC LIMIT 10`

2. **Severity-filter template** — used when: (a) a column named exactly `"severity"` (any `ColumnType`) is present, AND (b) the table's sensor prefix appears in the `SENSOR_SEVERITY_VOCABULARY` registry. The severity literals are **per-sensor** from the vocabulary — they are NOT hardcoded lowercase. Current registered entries and their DTU-emitted casing:
   - `crowdstrike_*` → `WHERE severity IN ('High', 'Critical') LIMIT 50` (Title-case; source: `prism-dtu-crowdstrike` generator)
   - `armis_*` → `WHERE severity IN ('HIGH', 'CRITICAL') LIMIT 50` (UPPER-case; source: `prism-dtu-armis` generator)
   - `cyberint_*` → `WHERE severity IN ('high', 'critical') LIMIT 50` (lowercase; source: `prism-dtu-cyberint` generator)
   - `claroty_*` → **not registered** (no `severity` column declared in the claroty spec; this branch never fires for claroty tables)
   - Unknown sensor prefix with a `severity` column → severity-filter is suppressed; falls through to count-recent or column-free to avoid silently returning 0 rows against unrecognized DTU casing.
   Result shape: `SELECT * FROM <table_name> WHERE severity IN ('<high_literal>', '<critical_literal>') LIMIT 50`

3. **Count-recent template** — used when a `Datetime`-typed column exists and neither aggregate nor severity-filter applies. The datetime column name is **derived from the first `ColumnType::Datetime` column** in the schema array — it is NOT hardcoded as `"timestamp"`. Tables without any `Datetime`-typed column do not use this template.
   `SELECT COUNT(*) FROM <table_name> WHERE <first_datetime_column> > NOW() - INTERVAL '1h'`

4. **Column-free fallback** (lowest priority) — used when the column set has no `Integer`/`Float` column, no qualifying `severity` column, AND no `Datetime`-typed column (e.g., a table with only `String` and `Boolean` columns, or an empty column list). Also used for tables with zero declared columns (EC-10-025).
   `SELECT * FROM <table_name> LIMIT 25`

**Implementation notes for future implementers (TD-VSDD-091 — cite behavioral anchors, not line numbers):**

- The implementation builds the base query from the datetime-or-column-free determination first, then conditionally overrides with severity, then conditionally overrides with aggregate. The aggregate check is the final step and therefore takes precedence over both severity and count-recent when an Integer/Float column is present.
- `SENSOR_SEVERITY_VOCABULARY` is the authoritative severity-literal registry. Adding a new sensor requires verifying the EXACT casing emitted by the corresponding DTU clone generator before adding an entry — wrong casing causes the example to silently return 0 rows.
- Template selection is deterministic: the same table schema (same column names, types, and order) always produces the same `example_query`.

These examples are schema-grounded but not human-curated — they may be mechanical but they reference real column names and correct per-sensor literal casing for this client's actual tables.

### `pql_hints` content

The `pql_hints` array contains 1–5 client-specific informational strings covering two mandatory categories:

**Category 1 — Table availability summary (always present):**
- `"This client has N tables: <comma-separated fully-qualified table names>"` (when N ≥ 1)
- `"No sensor tables are available for this client"` (when N = 0, explicit negative to prevent hallucination)

**Category 2 — Enrichment UDF discovery (mandatory when UDFs are registered; closes AUDIT-002):**

When one or more enrichment UDFs are registered for the requesting client:

- A hint MUST be included listing all available UDF signatures and the pipe syntax to invoke them. Format:
  `"Enrichment available via pipe syntax: | enrich <udf_name>(<input_field>). Available UDFs for this client: <udf1>(<input_col1>), <udf2>(<input_col2>)[, ...]"`

  Example: `"Enrichment available via pipe syntax: | enrich threat_score(ioc_value). Available UDFs for this client: threat_score(ioc_value_singleton), nvd_cvss(device_cves_first)"`

  The `<input_field>` is the primary input column expected by each UDF (sourced from the UDF registration metadata). This gives the agent both the syntax and the required column name in a single discoverable string.

When NO enrichment UDFs are registered for the requesting client:

- A hint MUST explicitly state the absence: `"No enrichment UDFs are registered for this client — enrichment is not available."`

  This explicit negative signal prevents the agent from attempting `| enrich ...` syntax and receiving an opaque error.

**Category 3 — Standing guidance (optional, 0–1 hints):**
- `"For sensor API errors, retry the query or narrow the time range"` (standing operational hint, included at implementer discretion)

### Audit event emission

Every call to `prism_describe` emits an `AuditEntry` (DI-004) with:
- `tool_name: "prism_describe"`
- `client_id: <requested client_id>`
- `operation: "schema_enumeration"`
- `outcome: "success"` (or `"error"` on parameter validation failure)

**Implementer obligation:** The current `AuditWriter::write_tool_call` surface accepts `(tool_name, client_id, outcome)` — it has no `operation` slot. The implementer MUST extend `AuditWriter` (or add an overloaded variant) to accept the `operation` field so that `"schema_enumeration"` is written into the audit record. The `outcome` value MUST be a real success/error discriminant — NOT the literal string `"invoked"`. This requirement is non-negotiable: spec wins (VSDD standing rule), and the implementer brings the audit surface into conformance with this BC.

This satisfies ADR-041's security requirement: schema enumeration in a multi-tenant MSSP environment is an auditable action. Unlike host-side injection (which silently prepends schema to every prompt), model-initiated `prism_describe` calls produce an audit trace. This mirrors ADR-005's pattern for security-critical observability events.

### Non-existent client_id handling

If the `client_id` resolves via OrgRegistry lookup but has zero entries in `resolved_spec_map` (no sensors provisioned for this org), the response is returned with `tables: []` and `pql_hints: ["No sensor tables are available for client '<client_id>'. The client may not have any sensor overlays configured."]`. This is NOT an error — it is a valid empty-schema response (EC-10-025).

If the `client_id` fails format validation (`[a-zA-Z0-9_-]{1,64}`), the tool returns `E-MCP-001` (same as all other tools per BC-2.10.007, BC-2.10.004). This is consistent with the validator middleware used across the entire tool router.

If the `client_id` passes format validation but is not registered in `OrgRegistry`, the response returns `tables: []` and `pql_hints: ["Client '<client_id>' is not registered. Check prism.toml [[orgs]] configuration."]`. This matches the non-error posture of `list_capabilities` for unknown-but-well-formed clients (BC-2.10.011).

### Response envelope

The response uses `SafetyEnvelopeBuilder` (consistent with all Prism MCP tools) with `trust_level: "internal"` in `_meta`. The schema catalog is server-authored (sourced from operator TOML specs via `resolved_spec_map` or `config_manager`), not sensor data — `trust_level: "internal"` is correct.

### Single source of truth with `prismql://schema/{client_id}`

Both `prism_describe` and the `prismql://schema/{client_id}` resource template (BC-2.10.013) are computed from the same spec-layer column data: `query_engine.resolved_spec_map()` (multi-tenant) or `config_manager` (single-tenant fallback). There is exactly one authoritative per-client schema source — the operator TOML specs surfaced through these two existing `PrismServer` access paths. Neither caches independently from the other; short-TTL caching is acceptable for the resource path per BC-2.10.013, using the same `TableRegistry` change-notification signal as the invalidation trigger (the `TableRegistry` change event is the hot-reload signal, even though column data itself comes from `resolved_spec_map`).

## Invariants

- DI-004: Audit completeness — every `prism_describe` call emits an `AuditEntry`. Audit fail-closed does NOT apply here (this is a read tool, not a write tool): if audit emission fails, the call proceeds with `_meta.audit_warning` in the response (consistent with BC-2.11.001 and DI-004 split behavior).
- DI-002: Credential isolation — `prism_describe` response MUST NOT include any credential values, auth token snippets, or API key strings. Column names sourced from `resolved_spec_map → TableSpec.columns → ColumnSpec.name` are operator-defined schema identifiers — they do not contain credentials. `api_base_url` values are not part of the response.
- DI-006: The response is server-authored (operator TOML specs → `resolved_spec_map` / `config_manager` → response). It does not contain sensor API response bodies or user-controlled input. No prompt injection scan is required for the discovery response itself, but the `pql_hints` strings are server-authored constants, not interpolated sensor data.
- DI-008: The `client_id` scoping is enforced — the `resolved_spec_map` lookup is filtered to entries whose `OrgSlug` matches the requesting client's `client_id`. A call for `client_id = "acme"` MUST NOT return tables or columns belonging to "globex".
