# BC-2.11.019: E-QUERY-039 Enrich-UDF-Not-Found Plan-Time Gate

## Description

When a PrismQL query — in pipe mode (`| enrich <infusion>(<column>)`) or in SQL mode (`SELECT <infusion>(<column>) FROM ...`) — invokes an enrichment infusion name that is not registered in the process-global `InfusionRegistry`, the query engine rejects the query at plan time (before any sensor fan-out or DataFusion execution) with `E-QUERY-039`. The error payload carries `infusion` (the unrecognized infusion name as written), `available_infusions` (`Vec<String>` of all `InfusionField.name` values in the global `InfusionRegistry`, rendered in the message as a bracket-wrapped comma-joined list), and `did_you_mean` (Levenshtein ≤ 3 match against the global set, if any). This prevents an opaque runtime `E-INT-001` crash (AUDIT-005 root cause) and enables the LLM agent to self-correct the enrichment call in a single retry without human intervention. The gate fires at the same plan-time validation point as E-QUERY-037 (table) and E-QUERY-038 (column).

## Preconditions

1. A PQL query has been submitted containing either:
   - (a) **Pipe mode:** a `| enrich <infusion>(<column>)` stage (parsed successfully with no E-QUERY-001 error), where `EnrichStage.infusion` holds the enrichment function name token; OR
   - (b) **SQL mode:** a `SELECT` projection or `WHERE` clause containing `FuncCall::Scalar { func: ScalarFunc::Unknown(name), args }` — a function call whose name was not resolved to a built-in `ScalarFunc` variant by the PQL parser AND whose name is NOT a DataFusion built-in function (scalar, aggregate, or window) registered in the default `SessionContext` (e.g., scalar: `lower`, `upper`, `coalesce`, `date_trunc`, `concat`, `length`; aggregate: `stddev`, `median`, `variance`, `array_agg`; window: `row_number`, `rank`). DataFusion built-in functions (scalar, aggregate, and window) are excluded from the E-QUERY-039 gate (see §Gate Scope Boundaries — DataFusion Built-Ins Exclusion).
2. For pipe mode: the parser has successfully identified an `EnrichStage` node with an `infusion` token.
3. For SQL mode: the Chumsky parser has produced a `FuncCall::Scalar { func: ScalarFunc::Unknown(name) }` node — the `Unknown` escape hatch for function names not mapped to PQL built-in variants. The gate is triggered ONLY when `name` is also not resolvable as a DataFusion built-in function (scalar, aggregate, or window). A `ScalarFunc::Unknown(name)` for a DataFusion built-in (e.g., scalar: `lower`, `upper`, `coalesce`; aggregate: `stddev`, `median`, `array_agg`; window: `row_number`, `rank`) DOES NOT trigger E-QUERY-039; it passes through to DataFusion for execution. Note: PrismQL's parser recognizes only 7 aggregate keywords (COUNT/SUM/AVG/MIN/MAX/PERCENTILE/DISTINCT_COUNT); all other DataFusion built-in aggregate and window functions (e.g., `stddev`, `variance`, `corr`, `string_agg`, `approx_distinct`, `approx_percentile_cont`, `bool_and`, `bool_or`, `regr_*`, and window functions like `row_number`, `rank`, `dense_rank`, `lag`, `lead`) parse as `ScalarFunc::Unknown` and MUST pass through the gate without firing E-QUERY-039.
4. The `InfusionRegistry` (`prism_spec_engine::infusion`) has been initialized at boot from `{config_dir}/infusions/*.infusion.toml` — its `InfusionRegistryInner.udf_to_infusion` map (keyed by `InfusionField.name`) is available at plan time.
5. This gate is a no-op for queries that contain neither `EnrichStage` nodes nor qualifying `ScalarFunc::Unknown` nodes (i.e., nodes whose name resolves as a DataFusion built-in scalar, aggregate, or window function are NOT qualifying).

## Postconditions

### Gate firing condition

E-QUERY-039 fires when EITHER of the following is true at plan time:
- A pipe-mode query contains an `EnrichStage` node whose `infusion` token is NOT a key in `InfusionRegistry.udf_to_infusion`; OR
- A SQL-mode query contains a `FuncCall::Scalar { func: ScalarFunc::Unknown(name) }` node (in `SELECT` projection or `WHERE`) where ALL THREE of the following hold:
  (a) `name` is NOT a PQL typed/known scalar function (i.e., the parser produced `ScalarFunc::Unknown` rather than a named variant); AND
  (b) `name` is NOT a DataFusion built-in function (scalar, aggregate, or window) registered in the default `SessionContext` — covers: scalar functions (via `ctx.state().scalar_functions()`), aggregate functions (via `ctx.state().aggregate_functions()`), and window functions (via `ctx.state().window_functions()`); AND
  (c) `name` is NOT a key in `InfusionRegistry.udf_to_infusion`.

  A `ScalarFunc::Unknown(name)` where `name` IS a DataFusion built-in MUST pass the gate without error. DataFusion resolves such names during plan/execution — the gate must not intercept them. This preserves pre-story behavior where `SELECT lower(hostname) FROM crowdstrike_detections` executed correctly; with the infusion registry wired, over-broad interception would regress this to `E-QUERY-039: enrichment infusion 'lower' is not registered` (F-PJL1-HIGH-001).

- **Post-DEFECT-PQL-FNCALL-LHS-001 predicate fn-call positions:** A `FuncCall::Scalar { func: ScalarFunc::Unknown(name), args }` node appearing as the LHS of a `Predicate::Compare` in any of the following positions (all share `build_predicate_parser`): (i) pipe `| where` stage predicate (`PipeStage::Where(Predicate)` — `Predicate::Compare { lhs: Expr::FuncCall(FuncCall::Scalar), ... }`), (ii) filter-mode root predicate (`| lower(col) = 'val'` style), (iii) SqlPipe pipe-stage `| where` predicate (`Ast::SqlPipe` tail-stage `| where`), (iv) SQL DML WHERE (`dml.filter` of DELETE/UPDATE — post-grammar-extension via `build_delete_parser`/`build_update_parser` binding `build_predicate_parser`; walked by the explicit `Ast::Sql(SqlStatement::Dml(dml))` arm; load-bearing test `test_f_pqlfn_p7_low_002_delete_where_unknown_udf_fires_e_query_039`), or (v) INSERT source_select WHERE (`dml.source_select.where_` of INSERT INTO ... SELECT; ADR-048 v1.13 §D.7.6 OD-7) — where ALL THREE of conditions (a/b/c) above hold. **Pre-grammar-extension:** fn-call LHS in these positions was grammar-rejected (E-QUERY-001), so the walk was never reached. **Post-extension (DEFECT-PQL-FNCALL-LHS-001 Option A):** the grammar accepts them; the gate MUST walk fn-call LHS nodes in these predicate positions for `ScalarFunc::Unknown(name)`. **Enumeration note — two distinct walker scopes (F-PQLFN-P5-MED-001 correction; v1.9 mis-anchor corrected):** The following two enumerations are DISTINCT and must not be conflated: (a) **This BC's E-QUERY-039 gate scope** uses `collect_unknown_scalars_from_sql_query` for SQL mode (positions a–f: SELECT, WHERE, JOIN ON, GROUP BY, ORDER BY, HAVING) — SQL HAVING IS in the E-QUERY-039 gate's scope via position (f); an unregistered non-DataFusion-builtin name in HAVING fires E-QUERY-039 (DataFusion built-in aggregate and scalar names in HAVING are excluded by `DATAFUSION_BUILTIN_FUNCTION_NAMES` before the infusion check; **EXCEPTION — `percentile` in HAVING fires E-QUERY-001 not E-QUERY-039 (BC-2.11.004 v1.48 EC-11-086, F-PQLFN-PR3-LOW-001):** `percentile` is NOT in `DATAFUSION_BUILTIN_FUNCTION_NAMES` (not a DataFusion registry built-in) but IS in `DATAFUSION_BUILTIN_AGGREGATE_NAMES` (PrismQL-specific aggregate name set, manually inserted in engine.rs); `check_enrich_udf_availability` intercepts `name` ∈ `DATAFUSION_BUILTIN_AGGREGATE_NAMES` ∧ `name` ∉ `DATAFUSION_BUILTIN_FUNCTION_NAMES` in HAVING position BEFORE the infusion-registry lookup and fires E-QUERY-001 with HAVING-specific guidance: `"E-QUERY-001: query parse error at offset {offset}: 'percentile' is a PrismQL aggregate function; PERCENTILE is not directly supported in HAVING predicates — alias it in SELECT: SELECT PERCENTILE(field, p) AS alias ... HAVING alias > threshold (ADR-048 D.3 OD-2)"`. DataFusion-native aggregate names that are members of BOTH `DATAFUSION_BUILTIN_AGGREGATE_NAMES` AND `DATAFUSION_BUILTIN_FUNCTION_NAMES` (e.g., `stddev`, `avg`, `var_samp`) are excluded by the `∉ DATAFUSION_BUILTIN_FUNCTION_NAMES` guard and remain valid in HAVING — they pass through to DataFusion execution without E-QUERY-001 interception (TM-12 green lock: `stddev` in HAVING). `distinct_count` in HAVING is NOT affected — it parses as `FuncCall::Aggregate` via `build_agg_call_parser` (not `ScalarFunc::Unknown`) and never reaches this gate as an unknown name). For pipe mode, `check_enrich_udf_availability` processes `PipeStage::Enrich` directly; `collect_unknown_scalar_offsets_from_predicate` (cross-ref ADR-048 v1.17 §D.7.1 footnote) handles pipe `\| where`, filter-mode, and SqlPipe pipe-stage `\| where` predicate positions. Positions (i)–(v) above are where the walk MECHANISM is new — fn-call LHS inputs were grammar-rejected at parse time before DEFECT-PQL-FNCALL-LHS-001 Option A; now reachable via `fn_call_comparison`. SQL WHERE and SqlPipe-head WHERE are pre-existing E-QUERY-039 walk targets (via `collect_unknown_scalars_from_sql_query` positions b and head-query respectively) that now additionally receive fn-call LHS inputs post-extension (no new walk code required — the mechanism already existed; only the inputs are new). (b) **ADR-048 §D.7.1 aggregate-gate walker scope (`predicate_fncall_names`)** is a DIFFERENT, SEPARATE enumeration of exactly **seven** positions: (1) pipe `\| where`, (2) filter root, (3) SqlPipe `\| where`, (4) SQL WHERE (NEW in ADR-048 v1.2), (5) SqlPipe-head WHERE (NEW in ADR-048 v1.2), (6) SQL DML WHERE (NEW in ADR-048 v1.6 §D.7.5, OD-6 — `check_enrich_udf_availability` walks `dml.filter` via an explicit `Ast::Sql(SqlStatement::Dml(dml))` arm; load-bearing test `test_f_pqlfn_p7_low_002_delete_where_unknown_udf_fires_e_query_039`), (7) INSERT source_select WHERE (NEW in ADR-048 v1.13 §D.7.6, OD-7 — `check_enrich_udf_availability` walks `dml.source_select.where_` via the same explicit `Ast::Sql(SqlStatement::Dml(dml))` arm; load-bearing test `test_f_pqlfn_p32_obs_001_insert_source_select_where_aggregate_fires_e_query_001`). **HAVING is EXPLICITLY EXEMPT from the aggregate gate** (ADR-048 v1.4 §D.7.1 permit ruling — HAVING may legitimately reference aggregate functions; HAVING predicates are NOT walked into `predicate_fncall_names`; aggregate fn-calls in HAVING do NOT trigger E-QUERY-001). The v1.9 text incorrectly listed "(v) SQL HAVING" as one of ADR-048 §D.7.1's five aggregate-gate positions; the correct fifth position is SqlPipe-head WHERE. **Implementation note:** the `collect_unknown_scalar_offsets_from_predicate` (cross-ref ADR-048 v1.17 §D.7.1 footnote) walk function must descend into `Predicate::Compare { lhs: Expr::FuncCall(FuncCall::Scalar { func: ScalarFunc::Unknown(name), .. }), .. }` in ALL SEVEN predicate positions per ADR-048 §D.7.1 (the walker is context-agnostic; each gate arm passes it the position's predicate). This walk coverage was added incrementally: positions 1–3 by the original DEFECT-PQL-FNCALL-LHS-001 grammar-extension fix (ADR-048 pre-v1.2), positions 4–5 by OD-5 (v1.2), position 6 by OD-6 (§D.7.5), position 7 by OD-7 (§D.7.6); prior to the original fix, none of these inputs reached the walker.

AND:
- The query has already passed the E-QUERY-037 table-availability check (if the table itself is missing, E-QUERY-037 fires first).

The gate fires at plan time, after AST parse and before fan-out and before DataFusion execution. No sensor API call is made for a rejected query.

**Implementation note (F-PJL1-HIGH-001, expanded by F1):** The check for DataFusion built-ins MUST cover all three function namespaces — scalar, aggregate, and window — using the same `SessionContext` (or its underlying `FunctionRegistry`) that will be used for execution. Hard-coding an allowlist of built-in names is insufficient; new DataFusion versions may add functions across all three namespaces. The canonical check MUST attempt lookup in all three registries: `ctx.state().scalar_functions().get(name)`, `ctx.state().aggregate_functions().get(name)`, and `ctx.state().window_functions().get(name)` (or an equivalent mechanism such as `SessionStateDefaults::default_scalar_functions()`, `SessionStateDefaults::default_aggregate_functions()`, and `SessionStateDefaults::default_window_functions()`). If the name resolves in ANY of the three registries, it is a DataFusion built-in — pass the gate without E-QUERY-039. **Rationale for aggregate+window:** PrismQL's parser recognizes only 7 aggregate keywords; all other DataFusion aggregate and window function names (e.g., `stddev`, `variance`, `corr`, `array_agg`, `row_number`, `rank`) are emitted as `ScalarFunc::Unknown` at the parser level. Without aggregate+window exclusion, these valid built-in calls falsely trigger E-QUERY-039 ("enrichment infusion 'stddev' is not registered") — a regression from pre-gate behavior where they executed correctly.

### E-QUERY-039 error payload shape

```
E-QUERY-039: enrichment infusion '{infusion}' is not registered; available: [{available_infusions}]{did_you_mean}
```

**Payload fields:**

- `infusion`: the exact enrichment function name token as written in the query (e.g., `"threat_score"`, `"cvss"`)
- `available_infusions`: a `Vec<String>` of ALL `InfusionField.name` values in the process-global `InfusionRegistry` at plan time. When no infusions are registered, this is an empty `Vec` (renders as `[]` in the Display output). This field is ALWAYS present. The Display impl comma-joins the Vec (sorted lexicographically) and wraps it in square brackets — e.g., `[nvd_cvss, threat_score]`; an empty Vec renders as `[]`. **Global scope:** `available_infusions` reflects ALL `InfusionField.name` values across the entire `InfusionRegistryInner.udf_to_infusion` map — there is no per-org keying in the current implementation (infusions are shared across all orgs). See §Follow-Up Story Anchor for the per-org scoping deferral.
- `did_you_mean`: `Option<String>`. Present when the Levenshtein distance between `infusion` and the closest `InfusionField.name` in the global registry is ≤ 3 (implementation: `strsim::levenshtein`, same crate used by E-QUERY-037 and E-QUERY-038). When present, contains the single closest-match infusion name from the global set, rendered as `" Did you mean: '{best_match}'?"` (leading space, one candidate — consistent with E-QUERY-037/038 convention). When absent (no match within threshold), the field is `None` (omitted from the Display output — not rendered as empty string). **Org-scoping note:** computed against the global registry; per-org candidate filtering deferred to the §Follow-Up Story Anchor.

### MCP surface

E-QUERY-039 surfaces as MCP `-32602 INVALID_PARAMS` (caller-resolvable — the model supplied an unrecognized enrichment function name; it can retry with a registered name). This is consistent with E-QUERY-037 and E-QUERY-038 mapping.

The error is delivered as a BC-2.10.007 structured error response with:
- `code: "E-QUERY-039"`
- `category: "validation"`
- `severity: "broken"` (query cannot proceed without correction)
- `retryable: false` (without a configuration change or corrected infusion name)
- `suggestion`: when `available_infusions` is non-empty: `"Use one of the registered enrichment functions: {available_infusions}. Call prism_describe('<client_id>') to see pql_hints including available enrichment functions."` When `available_infusions` is empty: `"No enrichment functions are registered. Enrichment is not available in this deployment."`

### Injection-safety of `available_infusions`

The `available_infusions` list is sourced ENTIRELY from `InfusionRegistry`, which is populated from operator-controlled `*.infusion.toml` spec files (validated at load time). Specifically:

- Infusion names in `InfusionRegistry` are operator-defined `InfusionField.name` identifiers from `{config_dir}/infusions/*.infusion.toml` spec files.
- They DO NOT contain: credential values, API key substrings, full URL paths, authentication tokens, internal connection strings, or any runtime sensor API response data.
- The injection-safety requirement is: **no string in `available_infusions` may contain a secret-shaped value** (API key pattern, bearer token, password pattern). This is verifiable because the infusion names come from operator TOML spec files, not from live API responses.
- `did_you_mean` is derived from `available_infusions` via Levenshtein computation — same injection-safety guarantee applies.

### Injection-safety of `infusion` (MCP-facing payload)

The `EnrichUdfNotFoundDetails.infusion` field and its `Display` rendering echo the user-supplied enrichment function name. `sanitize_for_log` (strips Unicode Cc: C0 U+0000–U+001F, DEL U+007F, C1 U+0080–U+009F; plus U+2028 LINE SEPARATOR and U+2029 PARAGRAPH SEPARATOR) is applied to the `infusion` value at `EnrichUdfNotFoundDetails::new` construction; the sanitized value propagates into the MCP-facing `EnrichUdfNotFoundDetails.infusion` field and its `Display` output. This neutralizes prompt-injection vectors of the form `| enrich fn_name_with_control_char(col)` while preserving all legitimate infusion names (valid identifier names never contain Unicode Cc or line/paragraph separator codepoints). `available_infusions` and `did_you_mean` remain server-controlled values sourced from the `InfusionRegistry` and Levenshtein computation respectively — they do not echo user input and require no sanitization at this layer. (CWE-116/CWE-117 prompt-injection defense; SEC-001; AD-017 agent-harness principle. Load-bearing test: `test_f_pqlfn_p7_low_001_enrich_udf_infusion_cc_stripped_at_construction`.)

### PrismError variant

`PrismError::EnrichUdfNotFound(Box<EnrichUdfNotFoundDetails>)` in `prism-core/src/error.rs`, where `EnrichUdfNotFoundDetails` is a `#[non_exhaustive]` struct carrying:

```rust
pub struct EnrichUdfNotFoundDetails {
    pub infusion: String,
    pub available_infusions: Vec<String>,   // all registered InfusionField.name values; empty Vec when none
    pub did_you_mean: Option<String>,
}
```

**`available_infusions` rendering:** the `Display` implementation MUST comma-join the `Vec<String>` (sorted lexicographically) and wrap it in square brackets, e.g., `[nvd_cvss, threat_score]`. When the Vec is empty the rendered form MUST be `[]`. This bracket convention is consistent with `ColumnNotFoundDetails.available_columns` (E-QUERY-038 sibling). The canonical message format the Display MUST produce byte-for-byte is: `"E-QUERY-039: enrichment infusion '{infusion}' is not registered; available: [{available_infusions}]{did_you_mean}"` where `{available_infusions}` is replaced by the comma-joined Vec content (no additional brackets added — the brackets are part of the format string literal).

The `#[non_exhaustive]` attribute on `EnrichUdfNotFoundDetails` is required per CLAUDE.md `#[non_exhaustive]` discipline (public type in `prism-core`). This adds +1 to the `ci.yml EXPECTED` non-exhaustive gate count (currently 87; increment to 88). External match arms must include a wildcard `_ => {}` arm.

`map_prism_error` in `prism-mcp/src/error_mapping.rs` MUST add an explicit `-32602 INVALID_PARAMS` arm for `PrismError::EnrichUdfNotFound` — it MUST NOT fall through to the `#[non_exhaustive]` catch-all `-32000`.

### Gate ordering

The full plan-time gate sequence is:
1. E-QUERY-001 — parse error (Chumsky cannot parse the query at all)
2. E-QUERY-037 — table not in `TableRegistry` (fires before column/enrichment checks)
3. E-QUERY-038 — column not found in table schema
4. **E-QUERY-039** — enrichment infusion name not registered in `InfusionRegistry` (fires LAST among the plan-time validation gates — after both E-QUERY-037 table check and E-QUERY-038 column check have passed; applies to both pipe-mode `EnrichStage.infusion` and SQL-mode `ScalarFunc::Unknown(name)`)
5. E-QUERY-034 — fallback for DataFusion execution failures

**Implementer note (addresses HIGH-001 from S-DEMO-FIDELITY-REMEDIATION-001 adversary pass):** The code currently fires E-QUERY-039 BEFORE E-QUERY-037 and E-QUERY-038. This is wrong. The implementation MUST perform the checks in the order listed above: table check → column check → enrichment check. The spec ordering is the canonical ordering; the code must be corrected to match it.

### Closes AUDIT-005

AUDIT-005 reported that `cvss(device_cves_first)` — a scalar function-call projection in a SQL `SELECT` statement (`FuncCall::Scalar { func: ScalarFunc::Unknown("cvss"), args: [device_cves_first] }`) — triggered `E-INT-001 "Internal error; see audit log"`, an opaque, unactionable error for MCP clients who cannot see the audit log. The root cause was an unregistered function name reaching DataFusion execution without a plan-time gate.

E-QUERY-039 gates BOTH AST paths at plan time:
1. **Pipe-mode `EnrichStage.infusion`** — `| enrich cvss(device_cves_first)` is caught when `EnrichStage.infusion == "cvss"` is not in `InfusionRegistry.udf_to_infusion`.
2. **SQL-mode `ScalarFunc::Unknown(name)`** — the actual AUDIT-005 reproducer: `SELECT cvss(device_cves_first) FROM armis_devices` produces `FuncCall::Scalar { func: ScalarFunc::Unknown("cvss") }`, which is caught when `"cvss"` is not in `InfusionRegistry.udf_to_infusion`. This prevents E-INT-001 from surfacing for any unregistered enrichment function name in a SELECT projection or WHERE clause.

## Invariants

- DI-019: This gate fires at plan time, before fan-out, consistent with the security limits principle that problems are caught early.
- DI-004: The query rejection event is included in the `AuditEntry` for the `query` tool call (outcome: `"rejected"`, reason: `"enrich_udf_not_found"`).
- DI-002: `available_infusions` contains no credential values — infusion names are operator-defined `InfusionField.name` identifiers from `*.infusion.toml` spec files; no sensor API response data.

## Gate Scope Boundaries

These boundaries were adjudicated in S-DEMO-FIDELITY-REMEDIATION-001 LOCAL pass findings F-L1-OBS-001 through F-L1-OBS-003. They are recorded here so that future adversarial passes do not re-open the same surface area as unresolved gaps.

### OBS-001 — `Expr::InSubquery` / `Predicate::InSubquery` in enrich gate walk (SCOPED OUT)

The `collect_unknown_scalar_from_expr` and `collect_unknown_scalar_offsets_from_predicate` (cross-ref ADR-048 v1.17 §D.7.1 footnote) functions do NOT descend into the `subquery` member of `Expr::InSubquery` or `Predicate::InSubquery`. This means an `ScalarFunc::Unknown` node that appears inside an `IN (SELECT ...)` subquery projection escapes the E-QUERY-039 gate (fail-open).

**Rationale for scoping out:**

1. **Not a reachable demo query path.** The demo read-path is `SELECT projection` / `WHERE predicate` / `| enrich stage`. PrismQL's grammar does not produce a `ScalarFunc::Unknown` inside an `IN (subquery)` position from any real query text — `build_sql_expr_parser` only produces `ScalarFunc::Unknown` in projection contexts.

2. **Explicit fail-open is the correct semantic for subquery bodies.** The column gate (`extract_field_paths_from_expr`) documents: `Expr::InSubquery { field, .. } — collect the field directly; subquery is fail-open.` The enrich gate mirrors this fail-open policy for the same structural reason: the subquery body can self-govern. An opaque `E-INT-001` error would NOT result from a subquery-nested unregistered UDF in the current DataFusion path because DataFusion would produce a function-not-found error rather than an `E-INT-001` internal panic.

3. **Table gate parity is NOT a mandate for enrich gate.** The table gate (`collect_expr_sources_into_gate`) descends into subquery sources to detect missing FROM-source tables. That behavior is justified because table availability is a structural fact about the query plan. Enrichment UDF availability is a scoped fact about projection and explicit `| enrich` stages; a UDF embedded in an `IN (subquery)` body is architecturally unusual and not part of the demo shape.

4. **`TimestampArithmetic.base` is similarly scoped out.** The base expression in `Expr::TimestampArithmetic` is a date/time field reference, not a scalar function projection. A `ScalarFunc::Unknown` cannot appear as the `base` expression of a timestamp arithmetic node in valid PrismQL AST.

**Future gate parity:** If PrismQL grammar is extended to produce `ScalarFunc::Unknown` nodes inside `IN (subquery)` projections, this BC should be updated to mandate enrich gate descent into subquery bodies. Until then, fail-open at subquery depth is the correct and documented behavior.

**No implementer action required** from this finding. The fail-open `_ => {}` catch-all arm already correctly handles these AST variants per `#[non_exhaustive]` discipline.

### OBS-002 — E-QUERY-039 rejection emits no structured tracing audit event (DOCUMENTED — D-765 pattern)

The E-QUERY-039 enrich-gate rejection does NOT emit a dedicated `event_type = "enrich_udf_not_found.rejected"` tracing event. By contrast, the sibling E-QUERY-038 column gate emits `event_type = "column_not_found.rejected"`.

**Adjudication:** DOCUMENT — no new `event_type` required. Rationale:

1. **`?`-propagation provides an audit trail.** Per D-765 precedent, when a gate returns `Err(PrismError::EnrichUdfNotFound(...))` and the caller propagates via `?`, the error is recorded in the `AuditEntry` for the `query` tool call (DI-004 invariant: outcome `"rejected"`, reason `"enrich_udf_not_found"`). This provides an audit trail without a dedicated tracing emission.

2. **Adding a new `event_type` would require a BC-2.16.002 catalog row** (SAP-1). The cost of maintaining a new catalog entry for a gate that already has structured error audit coverage is not justified at this time.

3. **The column gate's `column_not_found.rejected` emission is retained** — it predates the D-765 precedent and is not removed. The enrich gate is a newer addition that opts into the cleaner D-765 pattern from the start.

**If per-org InfusionRegistry scoping is added** (§Follow-Up Story Anchor), a structured tracing event for E-QUERY-039 rejections should be reconsidered at that time, as the audit value increases when infusion visibility is org-scoped.

### F-PJL1-HIGH-001 — DataFusion Built-In Functions (Scalar, Aggregate, and Window) Are EXCLUDED from E-QUERY-039 (ADJUDICATED — regression fix; scope expanded to aggregate+window by F1 PR-LEVEL finding)

**Finding (original — v1.5):** With the infusion registry wired, the original "intentionally broad — ANY unknown scalar function in a SQL SELECT is treated as a potential enrichment UDF when the infusion registry is active" firing condition caused a functional regression. A legitimate query such as `SELECT lower(hostname) FROM crowdstrike_detections` fails at plan time with `E-QUERY-039: enrichment infusion 'lower' is not registered`, whereas before the infusion registry was wired, it executed correctly. The regression arises because `lower` is a `ScalarFunc::Unknown` at the PQL parser level (PQL does not map it to a named `ScalarFunc` variant), but `lower` IS a DataFusion built-in that the `SessionContext` can resolve — it never needed to be an enrichment infusion.

**Finding (expanded — v1.6, F1 PR-LEVEL):** The v1.5 fix excluded DataFusion built-in **scalar** functions only, but PrismQL's parser recognizes only 7 aggregate keywords (COUNT/SUM/AVG/MIN/MAX/PERCENTILE/DISTINCT_COUNT). Every OTHER DataFusion built-in aggregate or window function — `stddev`, `median`, `variance`, `approx_distinct`, `approx_percentile_cont`, `array_agg`, `string_agg`, `corr`, `covar_pop`, `bool_and`, `bool_or`, `regr_*`, and window functions like `row_number`, `rank`, `dense_rank`, `lag`, `lead` — parses as `ScalarFunc::Unknown`. Since the v1.5 exclusion checked only `ctx.state().scalar_functions()`, these valid built-in aggregates and window functions falsely trigger E-QUERY-039 ("enrichment infusion 'stddev' is not registered"). This is a regression (they executed correctly pre-gate) and produces a misleading diagnostic.

**Root cause:** The gate's SQL-mode firing condition checked only `InfusionRegistry.udf_to_infusion` containment (original) and then `ctx.state().scalar_functions()` (v1.5), without also excluding names that DataFusion's aggregate or window function registries can resolve.

**Adjudication (v1.6):** The firing condition is further refined. DataFusion built-in functions across ALL three namespaces (scalar, aggregate, and window) MUST be excluded from E-QUERY-039. The PQL engine emits built-in scalar names (e.g., `lower`, `upper`, `coalesce`, `date_trunc`, `concat`, `length`) in generated SQL (`pipe_sql_emitter.rs`), and analysts write valid DataFusion aggregate/window functions directly in SQL-mode queries — all of these must continue to execute without plan-time rejection.

**Refined firing condition (SQL mode):** E-QUERY-039 fires for `ScalarFunc::Unknown(name)` ONLY when `name` is NEITHER a DataFusion built-in (in any of the three registries) NOR a registered infusion. A name that DataFusion can resolve in any built-in registry MUST pass the gate. See §Postconditions §Gate firing condition for the full three-part condition.

**Implementation note:** The exclusion check MUST query all three DataFusion function registries: `ctx.state().scalar_functions().get(name)`, `ctx.state().aggregate_functions().get(name)`, and `ctx.state().window_functions().get(name)` (or equivalent mechanisms such as `SessionStateDefaults::default_scalar_functions()`, `SessionStateDefaults::default_aggregate_functions()`, `SessionStateDefaults::default_window_functions()`). Hard-coding a list of built-in names is an anti-pattern — a future DataFusion upgrade may add functions to any of the three namespaces, re-introducing the regression.

**Scope of change:** SQL-mode `ScalarFunc::Unknown` gate logic only. Pipe-mode `EnrichStage.infusion` gate is unaffected (pipe-mode `| enrich` is an explicit enrichment directive — the analyst typed the name intending it to be an infusion; there is no DataFusion built-in overlap by construction). This SQL-vs-pipe distinction MUST be preserved: `| enrich stddev(col)` in pipe mode MUST still fire E-QUERY-039 for an unregistered `stddev` infusion name (the analyst explicitly invoked an enrichment directive).

**No regression to AUDIT-005:** The AUDIT-005 reproducer (`SELECT cvss(device_cves_first) FROM armis_devices` where `cvss` is not registered) is still caught: `cvss` is not a DataFusion built-in in any of the three registries, so condition (b) in the refined firing condition evaluates to true and E-QUERY-039 fires normally. Only names that DataFusion's built-in registries can resolve are excluded.

### OBS-004 — HAVING-Position `DATAFUSION_BUILTIN_AGGREGATE_NAMES` Names Fire E-QUERY-001, Not E-QUERY-039 (F-PQLFN-PR3-LOW-001 adjudication, BC-2.11.004 v1.48 EC-11-086)

**Finding (F-PQLFN-PR3-LOW-001, pass-3):** `percentile` is in `DATAFUSION_BUILTIN_AGGREGATE_NAMES` (PrismQL-specific aggregate set, manually inserted in engine.rs alongside `distinct_count`) but NOT in `DATAFUSION_BUILTIN_FUNCTION_NAMES` (the DataFusion-registry-derived built-in exclusion set). Pre-fix, when a registry is active, `HAVING percentile(x, 50) > 90` walks through `check_enrich_udf_availability` HAVING position (f), passes the `DATAFUSION_BUILTIN_FUNCTION_NAMES` exclusion filter (not a DataFusion registry built-in), and fires E-QUERY-039 (`"enrichment infusion 'percentile' is not registered"`) — a false enrichment-registration suggestion that misleads LLM agents.

**Root cause:** `DATAFUSION_BUILTIN_AGGREGATE_NAMES` is a PrismQL-specific set for the aggregate-gate (`check_enrich_udf_availability` WHERE/predicate positions) that includes `percentile` and `distinct_count` as manually-inserted names because they ARE PrismQL's recognized aggregate keywords (ADR-048 §D.2 BNF). These names are absent from DataFusion's own registries (DataFusion uses `approx_percentile_cont` and `approx_distinct` internally). The HAVING E-QUERY-039 exclusion uses `DATAFUSION_BUILTIN_FUNCTION_NAMES` (DataFusion-registry-derived) not `DATAFUSION_BUILTIN_AGGREGATE_NAMES`, creating a gap for PrismQL-specific names in HAVING context.

**Adjudication (F-PQLFN-PR3-LOW-001, product-owner, 2026-07-15):** E-QUERY-001 class rejection is the correct outcome for `HAVING percentile(x, p)`. `percentile` is a PrismQL aggregate function explicitly excluded from `build_agg_call_parser`'s HAVING six-name list per ADR-048 §D.2 OD-2 (grammar ambiguity); analysts should alias it in SELECT. The correct message provides actionable guidance, not a misleading enrichment-registration suggestion.

**Resolution:** `check_enrich_udf_availability` must intercept `name` ∈ `DATAFUSION_BUILTIN_AGGREGATE_NAMES` ∧ `name` ∉ `DATAFUSION_BUILTIN_FUNCTION_NAMES` in HAVING position BEFORE the infusion-registry lookup and fire E-QUERY-001 with HAVING-specific guidance (byte-verbatim per POL-24): `"E-QUERY-001: query parse error at offset {offset}: 'percentile' is a PrismQL aggregate function; PERCENTILE is not directly supported in HAVING predicates — alias it in SELECT: SELECT PERCENTILE(field, p) AS alias ... HAVING alias > threshold (ADR-048 D.3 OD-2)"`. DataFusion-native aggregate names that belong to BOTH `DATAFUSION_BUILTIN_AGGREGATE_NAMES` AND `DATAFUSION_BUILTIN_FUNCTION_NAMES` (e.g., `stddev`, `avg`, `var_samp`) are excluded by the `∉ DATAFUSION_BUILTIN_FUNCTION_NAMES` guard and remain valid in HAVING — they pass through to DataFusion execution and MUST NOT be intercepted by this arm (TM-12 green lock: `stddev` in HAVING).

**DML scope cross-note (F-PQLFN-PR5-OBS-002):** The HAVING interception described in the Resolution above covers SELECT and SqlPipe-head HAVING positions; the DML `source_select.having` position rides the S-3.09 DML-surface deferral (cross-ref §OBS-003 / D-PQLFN-P47-OBS-001 anchor) and is intentionally un-gated by this interception — eliminating the apparent contradiction between §OBS-004's HAVING-interception claim and §OBS-003's `source_select.having` exemption.

**Sibling `distinct_count` in HAVING:** NOT affected. `distinct_count` IS in `build_agg_call_parser`'s six-name list (ADR-048 §D.2 BNF: `'DISTINCT_COUNT'`); `HAVING distinct_count(x)` parses as `FuncCall::Aggregate(Distinct("x"))` — not `ScalarFunc::Unknown` — and never reaches the E-QUERY-039 gate. No fix required for `distinct_count` in HAVING (BC-2.11.004 v1.48 EC-11-087).

**ADR-048 amendment required:** ADR-048 §D.2 currently documents E-QUERY-039 as the accepted behavior for `HAVING percentile(x, p)` on registry-active installations. Architect must amend ADR-048 §D.2 to reflect E-QUERY-001 as the new outcome per this adjudication. This is a product-owner adjudication that supersedes the prior ADR-048 §D.2 documentation — see BC-2.11.004 v1.48 EC-11-086 for the full specification.

**Convention note (F-PQLFN-PR4-OBS-002 — input-verbatim placeholder):** The `'{name}'` placeholder in the HAVING-interception canonical message is INPUT-VERBATIM: the analyst's original casing is echoed. For example, `HAVING PERCENTILE(x, 50) > 90` (uppercase input) produces `'PERCENTILE'`; `HAVING percentile(x, 50) > 90` (lowercase input) produces `'percentile'`. The lowercase `'percentile'` in the canonical example in §Resolution above reflects the canonical test-vector input, NOT a normalization requirement. The `{name_upper}` occurrences in the guidance template body — e.g., `SELECT PERCENTILE(field, p) AS alias ... HAVING alias > threshold` — are always rendered in uppercase regardless of input casing; these reference the PrismQL keyword form in guidance text, not the analyst's original input. This matches the pre-existing aggregate-in-WHERE gate convention documented in ADR-048 §D.7.2 `'{name}'` placeholder semantics (input-verbatim expansion for the error prefix; uppercase template body via `{name_upper}`).

**Invariant note (F-PQLFN-PR4-OBS-001 — template specificity; debug-assertion clause superseded-by-v1.23, F-PQLFN-PR5-LOW-001):** The triggering set `DATAFUSION_BUILTIN_AGGREGATE_NAMES ∖ DATAFUSION_BUILTIN_FUNCTION_NAMES` reachable as `ScalarFunc::Unknown` in HAVING position is exactly {`percentile`} today: `distinct_count` is also in `DATAFUSION_BUILTIN_AGGREGATE_NAMES` but is handled by `build_agg_call_parser` as `FuncCall::Aggregate(Distinct("x"))` — it parses as `FuncCall::Aggregate`, not `ScalarFunc::Unknown`, and never reaches this HAVING-interception arm. **Two-branch detail-builder (replaces the v1.22 `debug_assert_eq!` enforcement, F-PQLFN-PR5-LOW-001):** The `debug_assert_eq!` guard compiles out in release; a future AGGREGATE-only name reaching the arm would emit the percentile-specific two-arg template — wrong signature guidance for that name (fail-safe rejection, but misleading LLM-agent help text). REMOVED. The interception detail-builder now has TWO branches: (a) `name_lower == "percentile"` → the existing byte-verbatim canonical template UNCHANGED: `"E-QUERY-001: query parse error at offset {offset}: ‘{name}’ is a PrismQL aggregate function; {NAME_UPPER} is not directly supported in HAVING predicates — alias it in SELECT: SELECT {NAME_UPPER}(field, p) AS alias ... HAVING alias > threshold (ADR-048 D.3 OD-2)"`; (b) any other name → the signature-neutral generic template (byte-exact per POL-24): `"E-QUERY-001: query parse error at offset {offset}: ‘{name}’ is a PrismQL aggregate function; {NAME_UPPER} is not directly supported in HAVING predicates — alias it in SELECT: SELECT {NAME_UPPER}(...) AS alias ... HAVING alias > threshold (ADR-048 D.3 OD-2)"`. Branch (b) is unreachable today (triggering set = {`percentile`}) but is unit-tested directly via the extracted detail-builder function (implementer must factor out the detail-builder for testability — branch (b) is not reachable through the gate arm itself in production). Any future addition to `DATAFUSION_BUILTIN_AGGREGATE_NAMES` that satisfies BOTH (a) NOT in `DATAFUSION_BUILTIN_FUNCTION_NAMES` AND (b) NOT handled by `build_agg_call_parser` as `FuncCall::Aggregate` still REQUIRES a template review (new EC row in BC-2.11.004 documenting the HAVING behavior for that name) — branch (b)’s generic `(...)` signature provides correct fail-safe guidance for any such future name without the two-argument signature misapplication risk; the template review determines whether a more-precise dedicated branch is warranted.

### OBS-005 — `prism_query::error::ParseError` lacks `#[non_exhaustive]` (F-PQLFN-PR11-OBS-002 — RATIFY, gate 91→92)
