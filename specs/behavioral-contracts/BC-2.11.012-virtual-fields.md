# BC-2.11.012: Virtual Fields in Queries — `_sensor`, `_client`, `_source_table`, `_source_type`

## Description

Four virtual fields — `_sensor`, `_client`, `_source_table`, and `_source_type` — are injected into external sensor RecordBatches, making sensor provenance and data-delivery path queryable in all PrismQL modes. The underscore prefix distinguishes them from OCSF data fields. Virtual field predicates participate in scope intersection (same semantics as tool-level `sensors`/`clients` parameters). Virtual fields are string-typed; numeric comparisons are type errors. Their names are verified at build time to not collide with OCSF field names.

**Internal-table exclusion for `_source_type` (F-CSD-P21-OBS-003):** Internal RocksDB-backed tables (`prism_alerts`, `prism_cases`, `prism_audit`, `prism_schedules`, `prism_diff_results`, `prism_aliases`) receive three provenance virtual fields (`_sensor = "prism"`, `_client = "<system>"`, `_source_table = <table_name>`) plus the `_meta_scan_truncated` Boolean flag. `_source_type` is a sensor data-delivery concept — it encodes the routing decision between EventStream RocksDB buffer and live API fetch (S-2.08 AC-9/AC-10). Internal tables are first-party writes from Prism's own subsystems; neither "buffered" (which means EventStream RocksDB buffer) nor "live" (which means live API fetch) describes them accurately. A PrismQL query referencing `_source_type` against any `prism_*` internal table produces `PrismError::QueryExecutionFailed` (DataFusion field-not-found), NOT plan-time E-QUERY-038. Two mechanisms independently prevent the E-QUERY-038 gate from running: (1) `_source_type` is promoted to `Expr::VirtualField(SourceType)` at parse time, and `extract_field_paths_from_expr` unconditionally skips all `VirtualField` variants as always-valid sentinels — no column name is ever extracted for E-QUERY-038 to check; (2) `check_query_column_availability` has an explicit `if table_name.starts_with("prism_") { return Ok(()); }` fail-open per BC-2.11.016 §Design Constraints (code comment: "internal tables have a separate capability gate"). BC-2.11.016 §Design Constraints explicitly classifies `QueryExecutionFailed` as the correct surface when the plan-time gate is intentionally bypassed. **UX gap (DRIFT-INTERNAL-TABLE-COLUMN-GATE-001):** this user error — referencing a sensor-only field on an internal table — surfaces as an opaque `QueryExecutionFailed` rather than a pedagogical E-QUERY-038 with `available_columns`. See EC-11-035.

**Closed set — exclusion note:** The virtual query field set is exactly four. `_safety_flags` is NOT a virtual query field; it is a response-envelope aggregate field (`_meta.safety_flags` per BC-2.09.004) populated by the injection scanner at the MCP response layer, after query execution completes. A PrismQL query referencing `_safety_flags` as a column name will receive an E-QUERY-038 error (no such field), which is correct actionable behavior.

## Preconditions
- A PrismQL query references `_sensor`, `_client`, `_source_table`, or `_source_type` as field names in filter expressions, WHERE clauses, or pipe stages

## Postconditions
- Four virtual fields are available in all PrismQL query modes for **sensor (external) tables**:
  - **`_sensor`**: The sensor type that produced the event (values: `"crowdstrike"`, `"cyberint"`, `"claroty"`, `"armis"` for external tables; `"prism"` for internal RocksDB-backed tables). Underscore prefix distinguishes virtual fields from OCSF data fields (per BC-2.15.009).
  - **`_client`**: The client ID (OrgSlug value; formerly TenantId, renamed per ADR-006) that owns the sensor instance or the Prism record.
  - **`_source_table`**: The data source table name within the sensor (e.g., `"alerts"`, `"devices"`, `"vulnerabilities"` for external tables; `"alerts"`, `"cases"`, `"rules"`, `"schedules"`, `"diff_results"`, `"audit"`, `"aliases"` for internal tables). Injected during OCSF normalization (external) or during internal table materialization (internal).
  - **`_source_type`**: The data-delivery path for EventStream sensor tables. Value is `"buffered"` when the row was served from the RocksDB event buffer; `"live"` when served via live API fetch (PointInTime table or EventStream cold-start fallback). For all non-EventStream sensor tables, the value is always `"live"`. Semantics are defined by S-2.08 AC-9/AC-10 and the `inject_source_type` pure-data function in `prism-query/src/materialization.rs`. **This field applies to sensor tables only.** For internal tables (`prism_alerts`, `prism_cases`, `prism_audit`, `prism_schedules`, `prism_diff_results`, `prism_aliases`), `_source_type` is absent from the schema; querying it produces `PrismError::QueryExecutionFailed` (DataFusion field-not-found; plan-time E-QUERY-038 does NOT fire — see §Description for the two-mechanism explanation: VirtualField skip + `prism_*` fail-open; UX gap tracked as DRIFT-INTERNAL-TABLE-COLUMN-GATE-001; see EC-11-035). Internal tables are first-party RocksDB writes that have no sensor data-delivery path concept; "live" would falsely imply an API fetch. **[EventStream buffer path not yet wired (TD-S302-005):** As of the current implementation, all production sensor rows carry `"live"` — `inject_source_type` has zero production callers (`inject_virtual_fields` unconditionally injects `"live"`). The `"buffered"` value becomes reachable only when a future story wires `inject_source_type` into the EventStream buffer-serving path per S-2.08 Architecture Compliance Rule 5. No story exists yet for this delivery path; the orchestrator must queue story creation to close TD-S302-005.]
- Virtual fields are usable in all positions where regular OCSF fields are usable:
  - Filter mode: `_sensor = "crowdstrike" AND severity >= "high"`
  - SQL mode: `SELECT _sensor, _source_type, count(*) FROM events GROUP BY _sensor, _source_type`
  - Pipe mode: `| where _source_type = "buffered" | stats count by _client`
- Virtual fields are implemented as additional Arrow columns in the materialized RecordBatch
- Virtual field predicates participate in scope intersection:
  - `_sensor = "crowdstrike"` in the query intersects with `sensors` tool parameter
  - `_client = "acme"` in the query intersects with `clients` tool parameter
- Virtual field values are strings; comparison operators (`=`, `!=`, `in`) are supported; numeric comparisons (`>`, `<`) on virtual fields are type errors
- **`_safety_flags` is NOT a virtual query field** (see §Description exclusion note): a query filtering or selecting `_safety_flags` receives an E-QUERY-038 error; the injection-scanner result is a response-envelope concern only (BC-2.09.004)

## Invariants
- Virtual fields are not part of the OCSF schema; they are Prism-specific metadata fields
- Virtual field names cannot collide with OCSF field names (verified at build time against the OCSF proto schema)
- **Sensor-table virtual field set (exactly four):** `_sensor`, `_client`, `_source_table`, `_source_type`. `_safety_flags` is NOT a member of this set.
- **Internal-table virtual field set (three + Boolean):** `_sensor`, `_client`, `_source_table` (all three injected by `inject_internal_virtual_fields` in `prism-query/src/internal_tables.rs`) plus `_meta_scan_truncated` (Boolean, BC-2.15.011). `_source_type` is absent from internal-table schemas — querying it on any `prism_*` internal table produces `PrismError::QueryExecutionFailed` (DataFusion field-not-found; plan-time E-QUERY-038 does NOT fire; see §Description for the two-mechanism explanation and EC-11-035 + DRIFT-INTERNAL-TABLE-COLUMN-GATE-001). The `prism_core::VirtualField` enum (3 variants: `Sensor`, `Client`, `SourceTable`) correctly represents the internal-table set; the 4-field set for sensor tables is defined in `prism_query::virtual_fields`.
- **Empty MemTable schema parity (F-CSD-P14-001 / F-CSD-P16-001):** Every registered sensor-table schema — whether produced by the populated RecordBatch path (`inject_virtual_fields`, nullable=false) or the empty-table pre-registration path (`virtual_fields::append_virtual_fields_to_schema` called from `pre_register_empty_tables`, nullable=true) — MUST include all four virtual-field columns (`_sensor` Utf8, `_client` Utf8, `_source_table` Utf8, `_source_type` Utf8). The nullable=true divergence on the empty path is intentional and required: when the empty table occupies the right side of a LEFT JOIN, DataFusion propagates NULL for those columns rather than producing a schema mismatch error. For `_source_type`, NULL on the empty path is correct — no rows means no delivery context. The spoofed-column dedup guard (`remove_spoofed_virtual_columns` on the populated path; strip-and-append logic inside `append_virtual_fields_to_schema` on the empty path) applies on both paths, preventing duplicate virtual columns if a sensor response already includes a field of the same name. Cross-reference: BC-2.11.005 §Postconditions DEC-022 bullet and §Edge Cases DEC-022 row. This parity invariant applies to sensor (external) tables only; internal tables are registered via `InternalTableDescriptor::full_schema()`, which does not include `_source_type`.
